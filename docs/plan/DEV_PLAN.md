## 1. 목적과 가설

### 1.1 TradeSentry가 하는 일

TradeSentry는 관세청 수출입통계 공개 API(공공데이터포털 data.go.kr의 15100475 국가별, 15101609 품목별 API `[사실: 실측 메모 §1]`)로 수집해 동결한 수입통계에서 두 가지 급변을 경보로 잡는 에이전트 시스템이다.

- **두 신호**(경보를 일으키는 조건): 하나는 kg당 단가(단위가치. 금액 USD ÷ 순중량 kg)이고, 다른 하나는 상대국 점유율(해당국 금액 ÷ 전체국가 금액)이다. 둘 다 전년 같은 달과 비교한다.
- **반증 조사**: 경보가 뜨면 Nemotron(NVIDIA의 오픈 대형 언어 모델 계열) 조사자와 별도 문맥의 검수자 Critic(조사자의 초안에서 누락·반대 설명·비교 조건을 지적하는 역할)이 제한된 조회 도구로 반증을 시도한다. 조사자와 Critic은 같은 모델을 서로 다른 대화 문맥으로 쓴다.
- **결과**: 담당자의 다음 업무를 검토 유지(`MAINTAIN`) / 모니터링(`MONITOR`) / 자료 보류(`HOLD`) 중 하나로 제시한다.
- **하지 않는 것**: 부정·위법·원산지 조작을 판정하지 않는다. 실제 기관 승인이나 통관 조치도 아니다.
- **누구를 위해**: 2026 NVIDIA Korea Agentic AI Hackathon(패스트캠퍼스 × NVIDIA) 예선 제출물이다. 마감은 2026-09-28(월) 23:59 KST다 `[사실: 대회 조사 문서 §0]`. 가상의 수혜자는 무역통계·관세 분석 담당자(공공)다.
- **규모**: 혼자 로컬에서 실행하고, 추론은 NVIDIA 클라우드의 NIM API(모델을 OpenAI 호환 HTTP API로 제공하는 NVIDIA 추론 서비스)를 쓰는 데모다. 여러 사용자, 계정·권한, 실시간 수집, 운영 배포는 없다.

### 1.2 증명할 한 문장 가설

> "Nemotron이 숫자를 직접 쓴 조사 보고서보다, 검증된 값만 틀에 채우고 검증기로 막는 TradeSentry 보고서가 실제 관세청 자료 경보에서 사실 주장 오류율이 낮다."

- 이 가설이 **대표 지표**(제출서에서 내세우는 한 개의 숫자)인 실자료 사실 주장 오류율을 정한다(§9.3).
- 채점 대상은 봉인된 실자료 묶음 `real_sealed`의 경보다. 대표 숫자는 `real_sealed`에서만 나온다(§9.4).
- 합성 자료를 대표로 쓰지 않는 이유: 규범의 숫자 등급에서 대표 지표는 A 또는 B 등급 숫자여야 하는데, 합성 자료는 생성과 판정을 분리해도 최대 C다(우리가 만들고 우리가 채점하면 D) `[DESIGN]`. holdout40이 C인 것도 이 때문이다(§9.6).

### 1.3 기준선

- 규범 G1(정량 증명 가능성 게이트)은 "기준선이 무엇인지 지금 한 문장으로 말할 수 있는가"를 묻는다 `[DESIGN]`. 우리의 한 문장은 다음과 같다: **같은 자료·도구·예산으로 Nemotron이 사실 주장의 값을 직접 쓰는 보고서(`freeform` 모드)**.
- `freeform`은 전체 TradeSentry인 `full`과 **처리만 다르고 나머지는 같다**(§9.2). 그래서 두 모드의 차이에는 "검증된 값만 채우고 검증기로 막는 처리"의 효과만 남는다.

### 1.4 NVIDIA 결합의 목표

- 대회는 교육 미션 "Securing Agents with NemoClaw and OpenShell"을 먼저 확인하고 build.nvidia.com의 "Skill API"를 활용한 데모를 내라고 한다 `[사실: 대회 조사 문서 §3-1]`.
- 규범 G2(교육 미션 정합성 게이트)는 NemoClaw(모델·에이전트 하네스·보안 런타임을 묶은 NVIDIA 참조 스택) 또는 OpenShell(에이전트를 격리 실행하는 NVIDIA 샌드박스 런타임)이 아키텍처에 실질적으로 들어가기를 요구한다 `[DESIGN]`.
- 그래서 이 플랜은 NemoClaw·OpenShell·Agent Skills(에이전트용 작업 지침 묶음)·NIM·NAT(NVIDIA NeMo Agent Toolkit. 워크플로 실행·추적·평가 라이브러리)를 "로고만 붙이는" 수준이 아니라 최소한으로, 그러나 실제로 결합한다(§3~§5). 빼도 나빠지는 지표가 없는 구성요소는 넣지 않는다(§3.4).

## 2. 범위와 동결 자료

### 2.1 스냅샷 `kcs_202201_202412_v2`

스냅샷(한 시점에 수집해 동결한 원자료 묶음. raw 응답, manifest(수집 요청 목록과 조건을 적은 기록 파일), SQLite로 이뤄진다)은 `kcs_202201_202412_v2`를 **그대로 동결**한다. 추가 수집을 하지 않는다.

| 항목 | 값 |
|---|---|
| HS4 | `8504` |
| HS6 4개 | `850450`(기타 인덕터), `850431`(변압기 1kVA 이하), `850432`(변압기 1kVA 초과 16kVA 이하), `850490`(부분품) |
| 상대국 16개 | `CN, JP, DE, VN, US, PH, TW, FR, FI, SE, KH, NL, ID, IN, MX, MY` |
| 전체국가 분모 | `ALL`(관세청 품목별 API의 전체국가 합계. HS10 월 행을 (HS10 코드, 월) 기준으로 중복 제거해 합한다, §6.1) |
| 기간 | 2022-01~2024-12(36개월) |
| 전년동월 판정이 가능한 달 | 2023-01~2024-12(24개월) |
| 수집 설정 | `configs/collection_plan.json`(기존 파일, 위치 유지) |

- HS 코드는 국제 통일 상품 분류 코드다. HS2 → HS4 → HS6 → HS10 순으로 세분된다. 6자리까지는 국제 공통이고 7~10자리는 한국 세분(HSK)이다. BACI(§8.2)는 HS6까지만 있다.
- **탐지·분석 대상은 HS6 4개 × 16개국(+ `ALL`)이다.** v2에는 선정용 HS4 스캔(8504·8544·8536)이 함께 들어 있다 `[사실: 실측 메모 §2]`. 이 중 8544·8536 스캔과 8504의 다른 HS6 행은 범위 밖이다. 8504 스캔에 든 대상 HS6 4개의 행은 부모 행으로 쓴다(§6.1).
- 구 개발계획 §4.1의 "2022~2023 24개월, 판정 가능 2023년 12개월"은 폐기한다.
- 수집·검증 결과 `[사실: 실측 메모 §1~§2]`
  - 357요청이 모두 첫 시도에 성공했다. 357은 선정용 HS4 스캔까지 포함한 v2 전체 요청 수다.
  - 국가별 부모-하위 대조 2,096건이 일치하고 한쪽만 있는 조합은 0이다. 전체국가 분모 대조 612건이 일치한다. 품목별 API의 HS4 요청과 HS6 요청이 같은 HS10 월 행 612개를 값까지 같게 담고 있다는 뜻이며, 그래서 분모를 합할 때 중복을 뺀다(§6.1). raw 해시 불일치는 0이다.
  - 결합 해시와 계산 명령은 `data/snapshots/kcs_202201_202412_v2/snapshot_hash.json`에 있다.
- 단위와 반올림 `[사실: 실측 메모 §1]`
  - 금액 `impDlr`는 USD 정수, 중량 `impWgt`는 kg 정수다.
  - 금액은 하위 행의 합이 총계(API가 `hsCd='-'`로 주는 요청 구간 합계 행)와 정확히 일치한다. 중량은 행마다 정수 kg로 반올림돼 있어 허용오차 출발값을 0.5kg×(행수+1)로 둔다.
  - 무거래 응답은 `resultCode 00` + 빈 items다. 수집기는 그 달을 `UNRESOLVED_ZERO`로 기록하고 0으로 바꾸지 않는다. 12개월 구간 응답 안에서 행이 빠진 달도 `UNRESOLVED_ZERO`로 기록된다 `[사실: src/tradesentry/ingest.py]`.

### 2.3 경보 규모와 탐지 임계값

- 품목(HS6)×상대국 시계열 64개 중 전년동월 비교가 가능한 조합(양쪽 달 모두 금액>0, 중량>0)은 약 1,267개다 `[사실: 2026-09-23(수) v2 조회]`. 그중 |단가 변화율|≥30%는 771개다(최소 금액·중량 기준 적용 전). 두 값은 부모 HS6 행(§6.1) 기준이다. HS10 합 기준이면 1,265개와 767개다 `[사실: 2026-09-24(목) 무역통계 검토 v2 조회]`.
- 따라서 탐지 임계값(경보를 발동시키는 기준. 예: |r_U|≥30%)은 개발 자료로 조정될 가능성이 크다. 조정은 `real_dev` 묶음(실자료 시계열 중 개발용으로 나눈 묶음)만으로 한다(§6.2, §9.1).
- 자료 품질 관찰 `[사실: 실측 메모 §3]`
  - 금액>0인데 중량 0인 행이 677개다(v2 전체 기준. 대상 HS6 4개와 그 HS10만 세면 449행 `[사실: 2026-09-24(목) 무역통계 검토 v2 조회]`). 단가를 계산할 수 없다. `min_amount`·`min_weight`와 정밀도 분기의 실자료 근거다.
  - 수입 0이 명시된 달이 68개월이다. 결측이 아니라 API가 명시한 0이므로 `OBSERVED`(값 0)다.
  - 무응답 월(`UNRESOLVED_ZERO`)이 208개다. `CONFIRMED_NO_TRADE` 승격 규칙은 아직 없다.

### 2.4 스냅샷 취급 규칙

- 모든 조회의 유일한 원천은 동결된 스냅샷이다. 조사 중에 새로 수집하지 않고, 도구가 없는 값을 만들어 채우지 않는다.
- 동결 뒤에는 수정하지 않는다. 설정이 바뀌면 새 `snapshot_id`로 새 스냅샷을 만든다.
- v1·v2 스냅샷에 수집기의 `plan`·`collect`를 다시 돌리지 않는다. manifest가 덮어써진다 `[사실: 인계 문서 §6]`.
- `verify`의 기본 출력은 덮어써지므로 비교할 때는 `--out`을 쓴다: `python3 src/tradesentry/ingest.py verify --snapshot kcs_202201_202412_v2 --out <파일>`.
- 관측 상태는 `OBSERVED | NOT_COLLECTED | REQUEST_FAILED | UNRESOLVED_ZERO | CONFIRMED_NO_TRADE` 5종이다. 실패와 미수집을 구분하고, 빈 응답을 0으로 바꾸지 않는다. `CONFIRMED_NO_TRADE`로의 승격은 승인된 규칙이 있을 때만 한다. 수입 0이 명시된 달은 `OBSERVED`(값 0)다.

### 3.2 채점 대상 실행 경로와 시연 경로

| 경로 | 사슬 | 쓰는 곳 | 보여 주는 것 |
|---|---|---|---|
| 채점 대상 실행 경로 | OpenShell 샌드박스 안에서 같은 CLI를 직접 실행한다. NemoClaw 에이전트를 거치지 않는다 | dev20(공개 개발용 합성 자료 20건)·holdout40의 비교군 3개(`checklist`·`agent`·`full`), 대표 지표의 `freeform`·`full` | 정확도 지표(대표·보조) |
| NemoClaw 시연 경로 | NemoClaw(OpenClaw) → `tradesentry` 스킬 → OpenShell 안 CLI | A/B/C 합성 사례(구성변화·잔존변화·자료누락 세 갈래를 보여 주는 합성 시연 사례)와 `real_dev` 몇 건을 처음부터 끝까지 시연 | NemoClaw 결합이 실제로 동작함, 스킬 호출 성공률. 정확도 지표에는 영향을 주지 않는다 |

- "채점 대상 실행"은 샌드박스 안에서 돌리는 실행이고, "정답 대조 채점"은 샌드박스 밖에서 하는 비교다. 두 말을 섞어 쓰지 않는다.
- 두 경로는 서로 다른 샌드박스에서 돈다. 채점 대상 실행 경로는 채점 대상 실행 샌드박스, NemoClaw 시연 경로는 시연 샌드박스다(§4 머리말).
- 채점 대상 실행에서 NemoClaw를 빼는 이유: 하네스 에이전트가 한 겹 더 끼면 비교군 차이가 흐려지고 비용·실패가 는다(결정 기록 7번).

### 3.3 검증기와 NAT의 역할 구분

- 검증기(`validator/` 패키지)는 **실행 중에** 보고서를 검사해 막는다(§7.4).
- NAT는 조사 흐름을 감싸 실행·추적·프로파일·**사후** 평가를 맡는다. 프로파일러 산출물은 요청별 지연·토큰 표(`standardized_data_all.csv`), 평균·백분위 지표(`workflow_profiling_metrics.json`), 보고서(`workflow_profiling_report.txt`)다 `[사실: R3 문서 §8]`. 두 역할을 섞지 않는다.
- 정답이 필요한 계산(예: 예상 상태 일치)은 샌드박스 밖 독립 채점기만 한다. 정답표는 채점기만 읽는다. NAT 사후 평가는 정답 없이 계산할 수 있는 항목에 쓴다 `[추론]`. NAT를 조사 흐름에 붙이는 정확한 위치와 방식은 S0 외부 자문 질문으로 정한다 `[미확인]`.
- NAT 연동은 아직 시작하지 않았다 `[사실: 인계 문서 §3]`. MVP 기준(로드맵 체크리스트 7번)은 MVP 실행에 대한 NAT 실행 추적과 프로파일 결과가 남는 것이다.

### 3.4 넣지 않는 것과 이유

원칙은 최소 확장이다. 빼도 나빠지는 지표가 없는 구성요소를 넣으면 개수 채우기가 된다(규범 §7 "나쁜 신호" `[DESIGN]`).

| 넣지 않는 것 | 이유 |
|---|---|
| Nemotron Nano/Ultra 라우팅 | 조사자와 Critic이 같은 모델이라 라우팅할 대상이 없다. `inference.local`(샌드박스가 보는 추론 주소)은 게이트웨이(샌드박스의 요청을 받아 정책을 적용하고 전달하는 OpenShell 구성요소)당 모델 1개라 요청 단위 라우팅 용도도 아니다 `[사실: 03 문서 §2.1-1]` |
| NeMo Guardrails·NemoGuard | NemoGuard는 탈옥·유해성 탐지 NIM이고, NeMo Guardrails는 입력·출력 rail(가드레일 규칙 층) 프레임워크다 `[사실: R3 문서 §6, 대회 조사 문서 §8-8]`. 입력이 동결 통계와 코드가 만든 사례라 빼도 나빠지는 지표가 없다 `[추론]`. 도구가 돌려준 품목명·설명은 데이터로만 다룬다(§6.5) |
| NeMo Microservices | 2026-10-01(목) 일몰 예정이다 `[사실: 대회 조사 문서 §9]`. 핵심 기술로 적지 않는다 |

기능 범위 밖(이번 대회에서 하지 않는 것): 실시간 수집, 법적 판정, 다중 사용자, 제3 신호(비슷한 품목끼리 비교하는 품목 peer 기준선), 신설·소멸 HS10의 일반 귀속 모형.

### 3.5 환경

- Python 3.12 가상환경을 uv(파이썬 패키지·가상환경 관리 도구)로 관리하고, 패키지 버전 고정 파일(lock)을 둔다. NAT는 설치한 버전을 고정한다. NAT가 요구하는 파이썬 범위(`>=3.11,<3.14`)에 3.12가 들어간다 `[사실: 분담 D11]`.
- `src/tradesentry/ingest.py`는 표준 라이브러리만 쓰는 상태를 유지한다.
- 이 저장소의 시스템 `python3`는 3.9.6이고 pandas·openpyxl이 없다 `[사실: 실측 메모 §6]`. 기존 시험 17개는 네트워크 없이 돈다: `python3 -m unittest discover -s tests -v`.
- OpenShell 게이트웨이는 Linux 전용(glibc 2.28 이상)이라 macOS에서는 Docker 안에서 돌린다 `[사실: R3 문서 §7]`. NemoClaw는 알파 단계다.
- 키는 `.env`의 `NVIDIA_API_KEY`, `DATA_GO_KR_SERVICE_KEY`만 쓴다. 로그·trace·문서·PR에 쓰지 않는다. 샌드박스 안에는 키를 두지 않는다(§4.6).
- NIM 무료 키에서 HTTP 500이 간헐적으로 난다 `[사실: 실측 메모 §5]`. provider(모델 호출 클라이언트)의 자동 재시도는 끄고, 5xx는 코드가 명시적으로 재전송한다(요청당 최대 3회, 지수 대기, 조정값). 평가 동시성은 1로 시작한다.
- 기존 NIM 도구 호출 확인 스크립트: `python3 scripts/g4_nim_toolcall_probe.py`.

## 4. OpenShell 정책 요건

정책 파일은 구현 단계에서 `configs/openshell/policy.yaml`로 작성한다(M 소유, 보안 검토). 이 절은 그 파일이 지켜야 할 요건과 증명 방법이다. OpenShell 동작에 관한 서술은 저장소 근거 문서(03 문서, R3 문서, 대회 조사 문서)에 기댄다. 거기서 확인되지 않은 기능은 `[미확인]`으로 적고, 주장은 로컬 실측 결과로만 한다.

샌드박스는 쓰임에 따라 두 종류로 나누고, 정책과 증거를 종류마다 따로 적는다.

| 샌드박스 | 안에서 도는 것 | 쓰는 곳 | 봉인 입력 |
|---|---|---|---|
| 채점 대상 실행 샌드박스 | TradeSentry CLI만. NemoClaw가 없다 | dev20·`real_dev`의 채점 대상 실행. holdout40·`real_sealed`는 `RB-1` 동결 뒤 새로 만든 공식 채점 대상 실행 전용 샌드박스에서 돌린다(§9.8) | 공식 채점 대상 실행 전용 샌드박스에만 읽기 전용으로 넣는다 |
| 시연 샌드박스 | NemoClaw의 OpenClaw 하네스, `tradesentry` 스킬, CLI | NemoClaw 시연과 스킬 호출 성공률(§5.1) | 넣지 않는다 |

- 시연 샌드박스는 다르게 다뤄야 한다. NemoClaw는 OpenClaw를 OpenShell 샌드박스 안에서 돌린다 `[사실: R3 문서 §7]`. 03 문서 §1의 정책(DLI 코스가 2026-06-17(수) 런처블에서 읽은 "shields up" 정책)에는 `managed_inference`(경로 `/**` + `curl`·`python3`·`node` 허용)와 `clawhub`·`openclaw_docs`·`npm_registry` 블록이 있다 `[사실: 03 문서 §1]`. 우리가 설치한 NemoClaw의 기본 정책이 같은지는 라이브 정책 조회로 확인한다 `[미확인]`. 게다가 OpenClaw가 띄운 CLI·`curl`은 조상 프로세스 상속으로 OpenClaw의 허가를 물려받는다(§4.1 작성 원칙).
- 그래서 "허용 목적지 하나, 추론 요청 한 경로"(§4.6)는 **채점 대상 실행 샌드박스 기준**이다. 요건 (b) 자체는 두 샌드박스 모두 지킨다. 시연 샌드박스의 추가 통제는 §4.8에 적는다.
- 두 샌드박스의 정책을 `configs/openshell/policy.yaml` 한 파일로 쓸지 따로 둘지는 새 경로를 짓지 않고 X1 뒤 S0 자문에서 정하며, 그때 §10.1 경로 표를 함께 고친다 `[미확인]`.
- 채점 대상 실행 샌드박스에는 개발 평가용과, `RB-1` 동결 뒤 봉인 묶음만을 위해 새로 만드는 공식 채점 대상 실행 전용 샌드박스가 있다. 그래서 문서에 따라 샌드박스를 세 종류(채점 대상 실행용·공식 채점 대상 실행 전용·시연용)로 세기도 한다(`docs/plan/SCAFFOLD_BRIEF.md` §4.4.1).

### 4.1 요건

- **(a)** 봉인 폴더와 정답표는 샌드박스에 들이지 않는다. 저장소 안 평가 정답 경로의 읽기도 막는다.
  - 예외는 하나다: 공식 채점 대상 실행 전용 샌드박스에는 봉인 폴더 전체가 아니라 봉인 입력만 읽기 전용으로 넣는다(§9.8 절차 4). 정답표는 어떤 샌드박스에도 넣지 않는다.
- **(b)** 외부 전송은 NVIDIA 추론 엔드포인트만 허용한다. L7(HTTP 요청 수준) method·path를 명시하고, `rules` 생략이나 범용 바이너리 + `/**` 조합은 금지한다.
  - 두 샌드박스 모두 이 요건을 지킨다. 채점 대상 실행 샌드박스는 목적지 하나·추론 요청 한 경로로 지킨다(§4.6). 시연 샌드박스가 이 요건을 채우지 못하면 예외를 두지 않고 즉시 사용자 결정을 받는다. 대안의 예는 §5.4 대체 경로(NemoClaw 없이 OpenShell만)다(§4.8).
- **(c)** API 키를 샌드박스 안에 두지 않는다. 방식은 credential placeholder rewrite(샌드박스에는 자리표시 문자열만 두고 게이트웨이가 실제 키로 바꾸는 방식)와 `inference.local` 중 설치 확인 단계(X1, §5.3)에서 고르고 이유를 기록한다.
- **(d)** 허용·차단 감사 로그를 `openshell logs`로 수집한다.
  - 근거: 대회 조사 문서 §8-2는 허용·차단이 모두 감사 로그로 기록된다고 적는다. 계층별(네트워크·파일시스템 등)로 실제로 남는지는 X1 실측 전까지 `[미확인]`이다.
  - 이벤트 이름까지 확인한 것은 거부(`HTTP:* DENIED`)와 정책(`CONFIG:*`) 이벤트다 `[사실: R3 문서 §3]`. 허용 이벤트 행의 실제 형식은 X1 실측 전까지 `[미확인]`이다.
- **(e)** 의도적 위반 시험표를 만든다. 정답 경로 읽기 시도, 비허용 호스트 전송, 비허용 바이너리, 키 조회 각각에 대해 예측과 실측을 대조하고, 종료 코드와 로그 근거를 함께 남긴다.

작성 원칙 `[추론: 03 문서 §5]`:

- 라이브 정책(`openshell policy get <agent> --full`로 읽은 실제 적용 정책)에서 출발해 **빼는 방향으로만** 고친다. 새 허용은 위협 근거와 함께 PR로 올린다.
- `rules`를 생략하지 않는다. 생략하면 그 host:port 전체가 열린다 `[사실: 03 문서 §3.4]`.
- 같은 host:port를 여러 블록이 덮지 않게 한다. L7 검사는 이름 순으로 첫 번째 매칭 블록에만 적용된다 `[사실: 03 문서 §3.1]`.
- 바이너리 매칭은 실행 파일 경로와 **모든 조상 프로세스 경로**를 함께 본다 `[사실: 03 문서 §3.3]`. 그래서 허용 바이너리(예: OpenClaw)가 띄운 자식 프로세스(CLI, `curl`)는 그 블록의 허가를 물려받는다. 시연 샌드박스에서 CLI가 받는 허가에는 OpenClaw가 받은 블록 전체가 더해진다(§4.8).
- 채점 대상 실행 샌드박스에서 CLI가 쓰는 파이썬 실행 파일은 범용 바이너리다. 이 바이너리에 주는 네트워크 허용은 추론 요청 한 경로(`POST /v1/chat/completions`)로 좁힌다.
- github·메시징 프리셋은 켜지 않는다. 03 문서 §1 정책에서 일부러 빠져 있는 유출 표면이다 `[사실: 03 문서 §1]`.

### 4.2 정적 계층과 동적 계층

| 계층 | 섹션 | 바뀌는 시점 | 이 프로젝트에서의 뜻 |
|---|---|---|---|
| 정적 | `filesystem_policy`, `landlock`, `process` | 샌드박스를 만들 때 고정된다. 바꾸려면 샌드박스를 다시 만든다 | 봉인 입력은 공식 채점 대상 실행 전용 샌드박스를 **새로 만들어** 넣는다(§9.8). 실행 중에 파일 권한을 늘리거나 줄일 수 없다 |
| 동적 | `network_policies`, `network_middlewares` | 실행 중에 다시 불러올 수 있다(`openshell policy set`) | 목적지 제한과 키 주입 설정은 실행 중에도 조정할 수 있다 |
| 추론 라우팅 | 게이트웨이 설정 | 실행 중 변경, 전파 약 5초 | `inference.local` 뒤에는 provider 1개·모델 1개만 있다(§4.6) |

`[사실: 03 문서 §2.1-1(공식 문서 인용)]`

- Landlock(리눅스 커널의 파일시스템 접근 제한 기능) 설정 `landlock.compatibility: best_effort`는 커널이 지원하는 범위에서만 적용하는 모드이고 엄격 집행이 아니다 `[사실: 03 문서 §2.3]`. macOS의 Docker 안 리눅스 커널에서 실제로 집행되는지는 `[미확인]`이다. X1과 요건 (a)의 위반 시험으로 실측한다. 집행되지 않으면 정답 파일을 샌드박스에 아예 두지 않는 것으로 대신하고, 통제 ①(저장소 경로 차단, §4.5)이 기술적으로 성립하지 않았다고 적는다.
- `process`는 비특권 신원(`run_as_user: sandbox`)으로 실행한다. `setuid`·`mount`·`ptrace` 같은 권한 상승 차단은 이 정책 파일이 아니라 seccomp(리눅스 시스템 호출 필터) 층의 일이다 `[사실: 03 문서 §2.4]`.

### 4.3 파일시스템 정책은 허용 목록 방식이다

- 파일시스템 정책은 **허용 목록 방식**이다. 나열한 경로(와 작업 폴더)만 허용하고 나머지는 거부한다 `[사실: 03 문서 §3.6]`. 판정은 가장 긴 prefix(경로 앞부분 일치)가 이기고, 어디에도 맞지 않으면 작업 폴더(`include_workdir: true`일 때 `/sandbox` 아래)만 허용한다 `[사실: 03 문서 §3.6]`. 이 판정은 DLI 코스 평가 함수의 모형이다. 겹치는 경로의 실제 집행은 자료 계약 §10.3 "읽기 전용 입력"을 따른다.
- **따라서 요건 (a)는 정답 경로를 허용 목록이나 작업 폴더에 넣지 않을 때만 성립한다.**
- 설계 원칙 `[추론]`
  - 읽기 전용(`read_only`)으로 허용: 앱 코드, 설정, 읽기 전용 SQLite 스냅샷
  - 쓰기 허용: 샌드박스 안 작업 폴더(`/sandbox` 아래)의 실행 출력 경로만 쓴다. 호스트의 `outputs/`는 허용 목록에도 작업 폴더에도 넣지 않고, 실행이 끝나면 샌드박스 밖 실행기가 `openshell sandbox download`로 받아 `outputs/{실행명}/`(봉인 묶음이면 `outputs/sealed/{실행명}/`)에 둔다. 여러 사례 실행이 한 샌드박스를 쓰면 작업 폴더 안에서도 사례 실행별 하위 폴더를 나눈다 `[DESIGN: 오케스트레이터 권고, 자료 계약 §10.3의 방식 (나)]`. 이유: 정적 계층은 샌드박스를 만들 때 고정되고(§4.2) 사례 실행마다 시각이 든 새 실행명을 쓰므로, 호스트의 사례 실행 폴더를 허용 목록에 미리 넣을 수 없다. 그렇다고 `outputs/`를 통째로 열면, 허용 목록이 경로 앞부분 일치로 판정되므로 다른 실행의 출력과 `outputs/sealed/`의 봉인 실행 출력을 읽을 수 있다. 1차 근거는 공식 문서다. CLI는 샌드박스의 정식 작업 폴더를 찾아 그 안으로 풀리는 샌드박스 쪽 원본만 받고, 글자 그대로(예: `/sandbox/../etc/passwd`)나 심볼릭 링크로 그 밖으로 벗어나는 경로는 전송 전에 거부한다 `[사실: 공식 문서 manage-sandboxes "Transfer Files"]`. 원문은 자료 계약 §10.3에 있다. X1 임시 시험 기록(옛 이름, 자료 계약 §10.3)의 "저장소 파일·봉인 입력 반입 방식" 행과 "NAT 실행 추적 산출물 위치" 행은 OpenShell 0.0.116에서 같은 동작을 관찰한 보강 근거다. X1은 샌드박스 안 `/sandbox/x1-runs/<run_id>/`에 쓰고 download로 호스트에 받았다. 작업 폴더 `/sandbox`는 X1 이미지에서 관찰한 값이다 `[사실: X1 임시 시험 기록, X1 PR로 병합 예정]`. 대안 (가)는 샌드박스를 만들기 전에 묶음 단위 실행 폴더를 정해 그 폴더 하나만 여는 것이다. 호스트 폴더를 샌드박스에 마운트하는 수단은 `[미확인]`이다. 최종 확정은 로드맵 MT5(샌드박스 출력 방식과 봉인 입력 반입 방식의 확정·리허설)와 MT7(샌드박스 밖 실행기)에서 한다.
    - 내려받는 시점: 실행이 끝난 때는 CLI가 NAT 파일 내보내기의 남은 쓰기를 기다린 뒤 끝난 때다. X1에서 NAT 1.9.0의 `stop()`은 남은 쓰기를 기다리지 않아 끝 이벤트가 빠졌다 `[사실: X1 임시 시험 기록 "NAT 실행 추적 산출물 위치" 행]`.
    - 받기 전 확인: 받을 곳은 그 실행의 실행명을 확보할 때 만든 폴더(자료 계약 §10.3 N8)이고, 그 폴더가 비어 있어야 한다. 비어 있지 않으면 받지 않고 실패로 끝낸다. 공식 문서는 받는 곳에 같은 이름이 이미 있을 때 거부하는지 적지 않는다. 그래서 download가 덮어쓰기 금지(N8)를 보장한다고 볼 수 없다. 확보와 내려받기는 같은 샌드박스 밖 프로그램이 한다. download가 받는 곳의 기존 파일을 덮지 않는지는 로드맵 MT5에서 검증하고, 보장이 없으면 임시 위치에 받은 뒤 확보한 빈 폴더로 옮긴다.
    - 읽기 전용 입력: 읽기 전용 입력(앱 코드·설정·스냅샷·봉인 입력)은 작업 폴더와 `read_write` 경로 밖에 둔다(X1의 `/opt/x1`처럼). `include_workdir: true`이면 작업 폴더가 `read_write`에 더해지고, Landlock(리눅스 커널의 파일 접근 제한 기능)은 규칙 하나라도 허용하면 허용하므로 쓰기 가능한 부모 아래의 `read_only` 자식은 막히지 않을 수 있다 `[추론: 근거는 https://docs.nvidia.com/openshell/sandboxes/policies(include_workdir가 작업 폴더를 read_write에 더한다)와 https://docs.kernel.org/userspace-api/landlock.html(한 정책 층 안에서는 규칙 하나라도 허용하면 허용한다)]`. 로드맵 MT5 리허설에서 작업 폴더 아래 `read_only` 하위 경로에 탐침 파일(시험용으로 새로 만드는 빈 파일)을 써 본다. 검토 후보는 `include_workdir: false`에 `read_write: [<출력 폴더>]`만 두는 구성이다. 이때의 CLI 동작과 download 가능 여부는 `[미확인]`이다.
    - 반입 목록: 이미지 빌드나 upload로 들이는 파일은 명시한 포함 목록으로 고른다. `.env`, `outputs/`, `artifacts/eval/`, 정답표(`eval/dev/oracle_ABC.json`, dev20 정답표), `eval/scorer/`는 빼도록 명시한다. 저장소 루트나 `eval/dev/`를 통째로 올리지 않는다.
    - upload 주의: 근거는 공식 문서이고 `[사실: 공식 문서 manage-sandboxes "Transfer Files"]`, 우리 환경에서의 확정은 로드맵 MT5에서 한다 `[미확인]`. Git 저장소 안의 경로를 올리면 upload는 기본으로 `.gitignore`를 따른다. 추적 파일이 섞인 경로를 올리면 무시 대상(이 저장소에서는 스냅샷 SQLite와 `raw/` 등)은 빠진다. 모든 파일이 무시 대상인 경로(예: `snapshot.sqlite` 하나)는 경고와 함께 거르지 않고 올라간다. 그래서 `.gitignore`는 제외 장치가 아니고, 제외는 명시한 반입 목록이 맡는다. `--no-git-ignore`는 `.env`가 없는 경로에만 쓰고, 이 주의는 모든 파일이 무시 대상일 때 거르지 않고 올리는 자동 전환에도 똑같이 걸린다. 목적지를 빼면 샌드박스 작업 폴더에 올라간다. upload는 심볼릭 링크를 그대로 두고, 이미 있는 폴더에는 합쳐 덮어쓴다. 원문은 자료 계약 §10.3에 있다.
  - 넣지 않는 것: 평가 정답(`eval/dev/oracle_ABC.json`, `eval/dev/dev20/`의 정답표), 독립 채점기 `eval/scorer/`, 봉인 폴더(예외: 공식 채점 대상 실행 전용 샌드박스의 봉인 입력, §9.8), `.env`, 그리고 `outputs/` 전체와 `outputs/sealed/`, `artifacts/eval/`. 채점기 출력(정답표에서 온 값)은 샌드박스가 읽거나 쓸 수 있는 곳(허용 목록과 작업 폴더)에 두지 않는다. 커밋 사본 `artifacts/eval/score-{시각}/`(채점기 출력을 복사해 커밋한 폴더)도 같다. 위 방식에서는 어떤 샌드박스도 `outputs/`를 열지 않으므로 채점 실행 폴더 `outputs/score-{시각}/`가 이 조건을 채우고, 커밋 사본은 반입 목록에서 뺀다
  - 어떤 샌드박스도 허용 목록과 작업 폴더에 `outputs/` 전체나 `outputs/sealed/`를 넣지 않는다. 쓰기는 위 쓰기 허용 항목대로 샌드박스 안 작업 폴더에만 한다. 판정이 경로 앞부분 일치이고 작업 폴더 안은 허용 목록에 없어도 허용되므로(이 절 첫 항목), 작업 폴더를 `outputs/`나 그 위 폴더로 잡으면 다른 실행과 봉인 실행의 출력이 읽힌다. 정답 경로를 허용 목록과 작업 폴더에 넣지 않는 조건(`docs/rules/PARALLEL_DEV_RULES.md` §6.5 ①)과 같은 구조다
  - 넓은 prefix(작업 폴더 전체, 03 문서 §1 정책의 `/app` 같은 경로)가 정답 경로를 덮지 않는지 확인한다. 저장소 전체를 작업 폴더에 복사하면 정답 파일도 읽을 수 있게 된다.
  - `eval/dev/dev20/`에는 입력과 정답표가 함께 있다(§10.1). 샌드박스에는 입력만 들이고 정답표는 들이지 않는다.
  - 저장소 파일을 샌드박스의 어느 경로에 어떻게 들이는지는 로드맵 MT5에서 확정한다 `[미확인]`.
- 읽을 수 있는 것은 허용된 출력 채널로 나갈 수 있다 `[사실: 03 문서 §5·§7]`. 출력 채널은 채점 대상 실행 샌드박스에서는 추론 요청 한 경로이고, 시연 샌드박스에서는 요건 (b)에 맞게 좁힌 NVIDIA 추론 목적지다(§4.8). 그래서 정답과 키를 읽을 수 없게 하는 것이 외부 전송 제한만큼 중요하다.

### 4.4 요건별 대응표

요건마다 정책 위치(섹션, 계층), 위반 시험 입력, 기대 종료 코드와 감사 로그 행, 확인 검토자를 한 줄씩 적는다. 실측 결과는 위반 시험 실행 폴더의 결과 파일만 같은 이름의 OpenShell 증거 폴더 `artifacts/openshell/openshell_violation_tests-{시각}/`로 복사해 커밋한다(증거 복사, 자료 계약 §10.3). 결과 파일은 시험표 `openshell_violation_tests-{시각}.md`(예측·실측 대조표), 감사 로그 발췌(`.txt`), 라이브 정책 조회 본문(`.yaml`)이다. 시험을 다시 돌리면 시각이 다른 새 폴더가 생기고, 앞 폴더를 고쳐 쓰지 않는다. X1 임시 시험 기록은 옛 이름 위치에 있다(자료 계약 §10.3). 이 표는 채점 대상 실행 샌드박스 기준이다. 시험표에는 행마다 시험한 샌드박스(채점 대상 실행용·시연용)를 적는다. 채점 대상 실행용 샌드박스(개발 평가 포함) 행에는 샌드박스 이름과, 커밋한 라이브 정책 조회 본문(정책 YAML. 로컬 절대경로를 바꿔 적은 뒤의 본문)의 sha256도 적는다. 평가 묶음 채점 요약 `scorer_summary-{시각}.md`의 실행 조건에 대조한 시험표 실행 폴더 이름(`openshell_violation_tests-{시각}`)을 적고(적는 주체는 채점기다. 채점기가 실행 조건 입력 파일(채점기가 모르는 실행 조건을 채점기에 넘기는 파일)에서 옮긴다, 자료 계약 §8.2), 그 폴더 시험표의 같은 샌드박스 행과 값을 맞추기 위해서다(`docs/eval/RULEBOOK.md` B7, `skills/tradesentry-eval/SKILL.md`). 조회 출력의 정확한 형식과 바이트 안정성은 X1 실측 전까지 `[미확인]`이고, 해시할 바이트의 추출 규칙(코드 블록 경계, 줄 끝 문자, 마지막 줄바꿈)은 로드맵 MT5에서 정한다. 경로 치환은 평가 스킬 ②의 규칙을 따르고, 해시에 쓰는 치환 규칙은 로드맵 MT5에서 하나로 확정한다. 게이트웨이 추론 설정(provider·모델)은 정책 본문 밖이라 이 해시에 들지 않으므로 따로 조회해 적는다(§4.8). 이 해시는 시험 때 조회한 정책을 가리킬 뿐이다. 네트워크 계층은 실행 중에 다시 불러올 수 있으므로(§4.2) 실행 기간 내내 같은 정책이었다는 증거가 아니고, 샌드박스에 들인 파일은 덮지 않으므로 격리 증거로도 쓰지 않는다. 실행 중 재적용을 잡는 방법은 X1에서 `CONFIG:LOADED`가 재적용마다 남는지와 그 행 형식을 확인한 뒤 로드맵 MT5에서 정한다.

공식 채점 대상 실행 전용 샌드박스는 새 정적 정책으로 새로 만들므로 이전 시험 증거가 그대로 이어지지 않는다. 그래서 공식 실행 전에 그 샌드박스의 라이브 정책 조회 결과와 최소 시험 행을 "공식 채점용"으로 따로 남긴다. 최소 시험 행은 비허용 호스트 1건, 정답표 부재 확인, `outputs/`·채점기 출력 부재 확인, 요건 (c) 키 조회 1건, 봉인 입력 쓰기 거부다. 쓰기 거부 행에는 어느 장치가 거부했는지 적는다. 정책의 `read_only`이면 EACCES, 읽기 전용 마운트이면 EROFS가 나오며, EROFS는 03 문서 §6.4의 거부 문구 목록에 없다 `[사실: 03 문서 §2.2, §6.4, §6.6]`.

| (e) 의도적 위반 시험표 | (a)~(c)의 정책 전체 | 정답 경로(미끼 파일) 읽기, 비허용 호스트 전송, 비허용 바이너리, 키 조회 4종(+ L7 위반: 로드맵 MT5는 필수로 둔다)과 대조군 NIM 허용 호출 1건. 행마다 시험한 샌드박스를 적는다 | 행마다 정책 평가 규칙으로 계산한 예측(allow/deny)과 실측 종료 코드·분류를 나란히 적는다 | 행마다 로그 발췌 파일과 행 참조 | NVIDIA 스택·보안 |

- 로그 이벤트 이름(`HTTP:* DENIED`, `CONFIG:LOADED`)은 R3 문서 §3에서 확인한 것이다 `[사실]`. 실제 행의 형식은 X1과 위반 시험에서 실측으로 채운다.
- "정책 예측"에 적은 진단(endpoint-miss, binary-miss, L7 불일치)은 DLI 코스 평가 함수의 예측 출력이다 `[사실: 03 문서 §3.1·§6.2]`. 실제 감사 로그 행에 같은 진단 문구가 찍히는지는 `[미확인]`이다.
- 네트워크 시험((b) 행)의 시험 프로세스는 허용 바이너리의 자손이 아닌 곳에서 시작한다(03 문서 §6.3의 `openshell sandbox exec -n <agent> -- …` 형식). OpenClaw 같은 허용 바이너리가 띄운 프로세스는 그 허가를 물려받아(§4.1) 예측과 다른 결과가 난다. 키 조회 시험((c) 행)은 반대로, 시연 샌드박스에서 하네스가 띄운 프로세스에서도 돌려야 한다. 새 셸이 하네스가 넘기는 환경을 보지 못할 수 있기 때문이다 `[미확인]`. 같은 사용자 프로세스의 `/proc/<pid>/environ`을 읽을 수 있는지도 X1에서 확인한다(§5.3).
- HTTP 상태 코드를 함께 기록한다. `--fail` 없는 `curl`은 프록시가 403으로 거부해도 종료 코드 0으로 끝날 수 있으므로, 시험 스크립트는 403이면 0이 아닌 값으로 끝나게 만든다.
- 미끼 파일 시험을 하는 이유: 필요한 파일만 복사해 들이면 정답 파일을 읽으려 해도 ENOENT만 나와 통제 ①(§4.5)의 증거가 없다. 미끼 파일에는 실제 정답을 넣지 않는다. 배치 조건(이미지 빌드나 마운트로 넣기, 허용 경로 밖 위치)은 X1에서 확인한다(§5.3).
- 실측 분류는 03 문서 §6.4를 따른다: 종료 상태가 정수가 아니면 `incomplete`, 거부 문구(`permission denied`, `EACCES`, `EPERM`, 프록시 403·407 등)가 있으면 access-denial 증거, 종료 코드 0이면 `completed`, 그 밖은 `command failed`. 이 분류 이름은 시험표 전용이며 실행 상태(`COMPLETED` 등)와 다르다.
- 해석 규율 `[사실: 03 문서 §6.6]`: 일치는 시험한 그 행동에 대한 예측을 지지할 뿐 모든 규칙을 증명하지 않는다. 명령 실패만으로는 어느 장치가 거부했는지 알 수 없으므로 정책 조회와 감사 로그를 함께 둔다. HTTP 오류는 프록시에서 왔는지 대상 서비스에서 왔는지 먼저 가린다.
- 키 조회 시험은 어떤 경우에도 키 값을 출력하지 않는다. 결과 파일과 로그 발췌에도 값이 없어야 한다. 키 종류별 판정 방법:
  - NVIDIA API 키(`NVIDIA_API_KEY`): 변수 이름과 관계없이 환경변수 전체에서 실제 키 형식이 있는지 본다. 형식 판정은 비밀값·로컬 경로 검사(NVIDIA API 키 접두어, 공공데이터포털 서비스키 요청 파라미터, 로컬 절대경로를 찾는 검사. 실제 패턴 문자열은 검사 스크립트에만 두고 문서에는 적지 않는다)와 같은 방식이다.
  - 공공데이터포털 서비스키(`DATA_GO_KR_SERVICE_KEY`, 샌드박스에서 쓸 일이 없다): 고정 접두어가 없고 `[추론]`, 비밀값 검사가 찾는 것은 요청 파라미터 이름이라 환경변수 값에는 나타나지 않는다. 그래서 변수 이름으로 찾는다.
  - 값 대조가 필요하면 샌드박스 쪽은 변수별 해시만 내보내고, 실제 키의 해시와 대조하는 일은 샌드박스 밖에서 한다. 기록에는 일치 여부만 남긴다.
- MVP 기준(로드맵 체크리스트 4번): NIM 호출 허용 증거 1건과 위반 시도 3종 이상의 차단 증거(종료 코드 + 감사 로그 행). 파일시스템 거부가 로그에 남지 않더라도 네트워크 위반 3종(비허용 호스트·비허용 바이너리·L7)으로 이 기준을 채울 수 있다 `[추론]`. 그래도 (a) 시험은 로그가 남든 남지 않든 반드시 실행·기록한다. NIM 호출 허용 증거는 허용 이벤트 행이 없으면 그 실행의 trace·종료 코드 0·HTTP 상태 코드로 대신한다. 이때 위반 시험표와 제출서에 "허용 증거 출처: 앱 기록(`openshell logs` 행 없음)"을 적는다.

### 4.5 두 통제의 구분

- **① 저장소 경로 차단**: 샌드박스 파일시스템 정책(정적 계층)이 저장소 안의 평가 정답 경로 읽기를 막는다. §4.3의 허용 목록 조건이 지켜질 때만 성립한다. 도메인 출력 폴더도 같은 구조로 다룬다. 어떤 샌드박스도 허용 목록과 작업 폴더에 `outputs/` 전체나 봉인 실행 출력 `outputs/sealed/`를 넣지 않는다. 권고 방식은 샌드박스가 `outputs/`를 아예 열지 않고 샌드박스 안 작업 폴더에 쓴 출력을 밖에서 받아 오는 것이다(§4.3, 자료 계약 §10.3). 이 방식(자료 계약 §10.3의 방식 (나))에서는 `outputs/`를 반입하지 않는 것으로 막는다. 이것은 통제 ①(파일시스템 정책의 거부)의 증거가 아니므로, 제출서와 위반 시험표에서 OpenShell 차단으로 세지 않는다.
- **② 저장소 밖 봉인 격리**: 봉인 자료를 저장소 밖(`TRADESENTRY_SEALED_DIR`, 기본값 `~/.tradesentry/sealed/`)에 두어 격리한다. 공식 채점 대상 실행 때에만 봉인 **입력**을 그 실행 전용 샌드박스에 읽기 전용으로 넣고, 정답표는 샌드박스에 절대 넣지 않는다. 정답표는 밖의 채점기만 읽는다.
- **①이 ②를 보장한다고 쓰지 않는다.** ①은 샌드박스 안의 프로세스만 막는다. ②는 저장소를 보는 개발 에이전트와 봉인 자료를 떼어 놓는 장치다.
- ②의 정직한 한계: 봉인 폴더 위치는 문서에 적혀 있어 비밀이 아니다. 개발 에이전트가 같은 OS 사용자로 돌기 때문에 열람을 기술적으로 막지는 못하고, 지시와 기록으로 관리한다. 해시(`eval/sealed_manifest.json`)는 변조를 드러낼 뿐 열람을 막지 않는다. 기술적 차단은 런타임 샌드박스(OpenShell 정책)에만 해당한다.
  - 봉인 실행 출력(trace 포함, `outputs/sealed/{실행명}/`)에는 봉인 입력 내용이 담긴다. 이 출력과 봉인 묶음을 채점한 채점기 출력 폴더도 금지 해제 조건(정답 대조 채점이 끝나고, `real_sealed`이면 표본 추출 seed 공개 기록까지 있는 때. 자료 계약 §10.3 N10) 전에는 읽지 말라는 지시 대상에 넣는다(§9.8). 봉인 묶음 실행 출력은 샌드박스 작업 폴더에 있는 동안(내려받기 전, 지우기 전)에도 같은 열람·커밋 금지를 받고, 내려받기는 샌드박스 밖 실행기(프로그램)만 한다(자료 계약 §10.3 N10).
  - `real_sealed` 사례 목록은 기록된 값으로 다시 계산할 수 있어 기밀이 아니다. 봉인의 목적은 기밀이 아니라 개발 사용 금지와 무결성이다(§9.8).

### 4.6 키 주입 방식과 `inference.local`

요건 (c)의 두 후보:

| 방식 | 동작 | 근거 | 남은 확인 |
|---|---|---|---|
| credential placeholder rewrite | 샌드박스 안 프로세스는 자리표시 문자열(placeholder)만 갖고, 게이트웨이가 요청을 내보낼 때 실제 키로 바꾼다. 그래서 샌드박스는 실제 키 값을 보지 못한다. rewrite가 꺼진 목적지로 placeholder를 보내면 upstream(실제 목적지 서버)에 닿기 전에 거부된다 | `[사실: 03 문서 §2.1, R3 문서 §1]` | 근거 문서가 확인한 옵션(`request_body_credential_rewrite`)은 요청 **본문**의 placeholder 치환이다. NIM API는 키를 `Authorization: Bearer` 헤더로 받는다 `[사실: 대회 조사 문서 §7-2]`. 헤더에 키를 넣는 동작은 `[미확인]` |
| `inference.local` | 샌드박스는 `inference.local`만 보고, 게이트웨이가 설정된 provider(추론 백엔드)로 요청을 전달한다. 샌드박스에 키가 없다는 것은 추론이며, 요건 (c)의 키 조회 시험으로 실측한다 | 전달 방식 `[사실: 대회 조사 문서 §8-2, 03 문서 §2.1-1]`, 키 부재 `[추론]` | CLI의 요청 형식과 게이트웨이 전달이 맞물리는지 `[미확인]` |

- **채택 규칙**: X1 세로형 최소 통합 시험(§5.3)에서 **실제로 성공한 방식만** 채택하고, 고른 이유를 결정 기록(`docs/tracking/decisions/`)에 남긴다. 두 방식이 모두 실패하면 키를 샌드박스에 넣는 우회를 하지 않고 바로 사용자 결정을 받는다(§5.3·§5.4).
- **단일 백엔드**: `inference.local`은 게이트웨이당 provider 1개·모델 1개만 연결하는 단일 백엔드다 `[사실: 공식 문서, 03 문서 §2.1-1]`. 조사자와 Critic이 같은 모델이라 라우팅이 필요 없다.
- **하네스의 추론 경로**: 03 문서 §1 정책에는 OpenClaw가 쓸 수 있는 추론 목적지가 두 곳(`nvidia` 블록의 `integrate.api.nvidia.com`, `managed_inference` 블록의 `inference.local`) 있다 `[사실: 03 문서 §1]`. 하네스가 실제로 어느 경로로 모델을 부르는지는 `[미확인]`이며 X1에서 확인한다(§5.3).
- **채점 대상 실행 샌드박스 기준**으로, 요건 (b)의 허용 목적지는 채택한 방식에 따라 하나로 정해진다: rewrite면 `integrate.api.nvidia.com:443`, `inference.local`이면 `inference.local:443`. 어느 쪽이든 추론 요청 한 경로의 method·path만 연다. 시연 샌드박스는 목적지 하나 약속 대신 §4.8을 따르되 요건 (b)는 지킨다.

### 4.7 보안 관점 요약

- **핵심 통제**: 키와 모든 정답표(봉인 정답표 포함)는 어떤 샌드박스에서도 읽을 수 없다. 봉인 입력은 공식 채점 대상 실행 전용 샌드박스에서만 읽기 전용으로 읽는다.
- lethal trifecta(민감 데이터 읽기 + 외부 입력 수용 + 외부 전송 경로가 한 경로에 겹치는 위험) 관점에서, 공식 채점 대상 실행 전용 샌드박스는 세 요소가 실제로 겹치는 경로다. 봉인 입력(민감 데이터)을 읽고, 모델 응답(외부 입력)을 받고, 추론 요청(외부 전송)을 보낸다. 추론 요청에는 조사에 필요한 봉인 입력 내용이 실린다.
- 그 샌드박스에 남는 통제는 세 가지다: 요건 (b)의 추론 요청 한 경로 제한, 정답표 부재, 봉인 실행 출력 `outputs/sealed/{실행명}/`(trace 포함)의 취급(금지 해제 조건 전 열람 금지, 커밋하지 않음. §4.5·§9.8).
- 도구는 모델에게서 경로·SQL·URL·셸 명령을 받지 않는다(§6.5). 도구가 돌려준 품목명·설명은 데이터로만 다루고 지시문으로 실행하지 않는다.
- 목적지가 허용 목록에 있다는 사실만으로 안전하다고 쓰지 않는다. 정책은 목적지를 승인할 뿐 그 위로 오가는 바이트의 의미를 승인하지 않는다 `[사실: 03 문서 §4]`.

### 4.8 시연 샌드박스의 추가 통제

시연 샌드박스에는 03 문서 §1 정책(DLI 코스가 2026-06-17(수) 런처블에서 읽은 "shields up" 정책)과 같은 기본 블록이 딸려 올 수 있고 `[추론]`, CLI는 OpenClaw의 허가를 물려받는다(§4 머리말, §4.1). 그래서 채점 대상 실행 샌드박스와 따로 다룬다. 요건 (b)는 시연 샌드박스에도 예외 없이 적용한다.

- **(b)가 요구하는 것**: 목적지 하나를 요구하지는 않는다. 하네스가 `integrate.api.nvidia.com`과 `inference.local`을 좁힌 규칙으로 함께 쓰는 것은 (b)에 맞는다. (b)를 어기는 것은 `clawhub`·`openclaw_docs`·`npm_registry` 블록, `/**` + 범용 바이너리(03 문서 §1의 `curl`·`python3`·`node`) 허가, 그리고 `rules` 생략이다. `inference.local`이 NVIDIA 추론 엔드포인트인 것은 게이트웨이 provider가 NVIDIA NIM으로 설정됐을 때뿐이다(provider는 바꿀 수 있다, 대회 조사 문서 §8-2 `openshell provider create`, 03 문서 §2.1-1). 조상 프로세스 상속 때문에 하네스 블록에 `/**`가 남으면 하네스가 띄운 범용 바이너리도 그 허가를 물려받으므로, 하네스 블록도 좁힌 규칙이어야 한다.
- **방침** `[DESIGN]`: 기본 블록을 빼거나 좁힌다.
  - `clawhub`·`openclaw_docs`·`npm_registry`는 뺀다. 런타임에 패키지·문서를 받을 필요가 없다 `[추론: 03 문서 §5]`.
  - 설치한 NemoClaw의 라이브 정책에 03 문서 §5 하드닝 템플릿의 제거·축소를 적용하고, 템플릿에만 있는 허가는 더하지 않는다. 이 템플릿은 `managed_inference`의 바이너리를 `openclaw`만 남기고(`curl`·`python3`·`node` 제거) 경로를 `POST /v1/**`로 좁히며, `nvidia` 블록도 `POST /v1/chat/completions`·`POST /v1/embeddings`로 좁힌다 `[사실: 03 문서 §5]`.
  - CLI의 파이썬 실행 파일을 추론 블록의 바이너리에서 빼면(예: `inference.local`을 채택하고 `managed_inference`에서 `python3`를 뺀 경우), 시연 샌드박스에서 CLI의 NIM 호출은 조상 프로세스 상속에 기댄다 `[미확인]`.
- **확인할 것** `[미확인]`(X1 목록, §5.3):
  - 하네스 자체의 추론 경로
  - 조상 프로세스 상속이 실제 환경에서도 문서대로인지
  - 기본 블록을 빼거나 좁혀도 하네스가 도는지
- **증거**: 시연 샌드박스의 라이브 정책 조회(`openshell policy get <agent> --full`) 결과, 게이트웨이 provider 설정 조회 결과, 남은 블록 목록을 위반 시험표(OpenShell 증거 폴더 `artifacts/openshell/openshell_violation_tests-{시각}/`의 시험표)에 함께 적는다.
- **(b)를 채우지 못하면**: 예외를 두지 않고 즉시 사용자 결정을 받는다. 대안의 예는 §5.4 대체 경로(NemoClaw 없이 OpenShell만)다. 키 주입 방식이 모두 실패할 때(§4.6 채택 규칙)와 같은 처리다.
- 요건 (a)·(c)도 시연 샌드박스에 똑같이 적용한다. 정답표·봉인 자료·키를 들이지 않는다.

## 5. NemoClaw·스킬 경로와 대체 경로

### 5.1 NemoClaw 경로와 증명 방식

- 사슬: 운영자 요청 → NemoClaw의 OpenClaw 에이전트 → `tradesentry` 스킬 → OpenShell 안 TradeSentry CLI.
- 증명: A/B/C 합성 사례와 `real_dev` 개발 묶음 몇 건을 처음부터 끝까지 시연하고, **스킬 호출 성공률**을 잰다.
- 제출서에는 NemoClaw 경로가 "정확도 지표에는 영향을 주지 않는다"고 밝힌다. 정확도 지표는 NemoClaw를 거치지 않는 채점 대상 실행 경로(§3.2)에서만 나온다.
- MVP 기준(2026-09-25(금), 로드맵 체크리스트 1번): A/B/C 합성 사례와 `real_dev` 경보 1건 이상이 **NemoClaw 에이전트 → tradesentry 스킬 → OpenShell 안 CLI** 경로로 실제 Nemotron을 호출해 유효한 최종 보고서까지 간다. A/B/C는 각각 `MONITOR`/`MAINTAIN`/`HOLD`로 끝난다. 대체 경로(§5.4)가 발동했다면 그 경로와 사실 표기로 대신한다.
- 하네스 모델이 보고서를 다시 요약하면서 숫자를 고쳐 쓰면, 검증기가 막은 오류가 시연 경로에서 되살아날 수 있다 `[추론: 실측 메모 §5의 숫자 오독 관찰]`. 그래서 스킬은 CLI가 만든 보고서를 고쳐 쓰지 말고 그대로 전하도록 지시한다(§5.2).

### 5.2 런타임 `tradesentry` 스킬 인터페이스 계약

런타임 스킬의 SKILL.md는 구현 단계 산출물이다. 이번에는 인터페이스 계약만 정한다. 명령 배분은 팀 설계다 `[DESIGN]`.

| 항목 | 계약 |
|---|---|
| 위치·소유 | `skills/tradesentry/SKILL.md`, M 소유 |
| 형식 | Agent Skills 규격을 따른다. `name`은 디렉터리 이름과 같은 `tradesentry`다(소문자·숫자·하이픈만, 64자 이하). `description`은 무엇을 하는지와 언제 쓰는지를 담고 1024자 이하이며, 한국어 본문에 영어 한 문장을 덧붙인다(조정값) |
| 부르는 명령 | `tradesentry detect`(경보 목록), `tradesentry run-case`(사례 1건 조사). 공통 옵션 `--snapshot`, `--policy`, `--mode`(값은 `checklist`, `agent`, `full`, `freeform`). 사례를 지정하는 인자의 형식은 S0 뒤에 확정한다 |
| 부르지 않는 명령 | `snapshot-build`·`snapshot-verify`(자료 구축은 데이터 트랙의 일), `evaluate`(평가는 평가 스킬 ② `skills/tradesentry-eval/SKILL.md`가 샌드박스 밖 채점과 함께 다룬다) |
| 입력 | 운영자의 자연어 요청을 위 명령과 옵션으로 옮긴다. 스냅샷 ID·정책 버전·모드·사례만 넘기고, 파일 경로·SQL·URL·셸 조각은 넘기지 않는다. 이 경로에서는 하네스 모델이 CLI 명령을 조립하므로 CLI가 인자를 코드로 검증한다: 모드는 4개 값만, 스냅샷 ID와 사례 인자는 정해진 형식만 받는다. `--policy`는 파일 경로가 아니라 버전 이름(예: `policy_v1`)으로 받는다. 모델에게서 경로·SQL·URL·셸 명령을 받지 않는다는 원칙(§4.7, §6.5)과 같다 |
| 출력 | CLI 결과를 그대로 전한다: `case_id`, `review_status_final`, `signal_status`, `unresolved_evidence`, `execution_status`, 보고서 본문, 실행 폴더 위치(샌드박스 안 실행 폴더. 내려받은 뒤 `outputs/{실행명}/`). 숫자를 고쳐 쓰거나 다시 계산하지 않는다 |
| 금지 | 정답표·봉인 폴더·`.env` 읽기, 키 다루기, 봉인 자료 실행, 정답 대조 채점 |
| 기록 | 시연 요청마다 스킬이 CLI를 실제로 호출했는지와 그 실행의 `execution_status`를 남긴다. 스킬 호출 성공률의 정의는 로드맵(`docs/plan/ROADMAP.md`) §3 체크리스트 1번을 따른다 |
| 거버넌스 카드 | 공식 스킬 `skill-card-generator`로 우리 스킬의 카드를 만든다 |

### 5.3 X1 세로형 최소 통합 시험

- **무엇**: 구현을 시작하는 2026-09-24(목)에 OpenShell·NemoClaw 설치·기동 확인을 넘어, **한 줄로 이어진 최소 경로 전체를 한 번에** 통과시킨다.
- **경로**: NemoClaw 에이전트 → 스킬 → (샌드박스 안) CLI 최소 명령 → NIM 호출 1회 → NAT 실행 추적 1건 → 의도적 위반 1건의 차단 로그.
- **왜 세로형인가**: macOS + Docker + 알파 단계 NemoClaw 조합은 문서만으로 동작을 확정할 수 없다 `[미확인]`. 구성요소를 따로 확인하면 경계(호스트·컨테이너·키 경로)의 실패를 늦게 발견한다(결정 기록 17번).
- **코드**: 앱 뼈대가 아닌 임시 시험 코드(`spikes/x1/`, 조정값)로 확인한다. 임시 코드는 S0 스캐폴딩 결과에 섞지 않는다. 그래서 S0 외부 자문 대기와 병렬로 진행할 수 있다.
- **제한 시간**: 3시간(조정값). 넘기면 §5.4의 대체 경로로 간다.
- **남기는 것**: 채택한 키 주입 방식과 이유, 확인된 명령. 결정 기록과 `docs/plan/SCAFFOLD_BRIEF.md` 자문 회신 반영에 쓴다.
- **X1에서 함께 확인할 `[미확인]` 항목**
  - Docker 안에서 Landlock 파일시스템 제한이 실제로 집행되는지(요건 (a))
  - 키 주입 방식: 헤더에 키를 넣을 수 있는지, `inference.local` 전달이 되는지(요건 (c))
  - `openshell logs`의 거부·허용 이벤트 행 형식, 파일시스템 거부가 로그에 남는지(요건 (d))
  - 정책을 `openshell policy set`으로 다시 불러올 때마다 `openshell logs`에 `CONFIG:LOADED` 행이 남는지와 그 형식(§4.4, 실행 중 재적용 탐지의 입력)
  - 샌드박스 밖 프로그램이 `openshell sandbox exec -n <agent> -- <명령>` 형식으로 채점 대상 실행 샌드박스 안의 `run-case`를 돌릴 수 있는지(샌드박스 밖 실행기의 호출 경로, `docs/plan/SCAFFOLD_BRIEF.md` §4.4.2)
  - 저장소 파일과 봉인 입력을 샌드박스에 들이는 방식(요건 (a), §9.8)
  - NAT 실행 추적 산출물의 위치
  - 하네스 자체의 추론 경로: OpenClaw가 어느 목적지·블록으로 모델을 부르는지(§4.6, §4.8)
  - 조상 프로세스 상속: OpenClaw가 띄운 CLI·`curl`이 실제로 OpenClaw의 허가를 물려받는지(§4.1)
  - 기본 블록 제거·축소: 시연 샌드박스에서 `managed_inference`·`clawhub`·`openclaw_docs`·`npm_registry`를 빼거나 좁혀도 하네스가 도는지(§4.8)
  - OpenClaw가 SKILL.md를 불러 샌드박스 안 CLI를 실행하는 방식. S0 외부 자문 질문으로도 올린다
  - 시연 샌드박스에서 하네스가 띄운 프로세스로 키 조회 시험(요건 (c))을 돌리는 방법
  - 같은 사용자 프로세스의 `/proc/<pid>/environ`을 읽을 수 있는지(값은 출력하지 않는다). 03 문서 §1 정책은 `/proc`를 `read_only`로 허용하지만 Landlock이 막을 수도 있다. 읽힌다면 그 자체가 키 노출 경로이고, 하네스 환경을 확인하는 방법도 된다(요건 (c))
  - 미끼 파일 배치 조건: 샌드박스 사용자는 허용 목록 밖에 쓸 수 없으므로 미끼 파일은 이미지 빌드나 마운트로 넣는다. 경로는 모든 허용 경로의 앞부분(prefix) 밖이어야 하고, `include_workdir: true`이면 `/sandbox` 밖이어야 한다(03 문서 §3.6, 요건 (a))
- **두 키 주입 방식이 모두 실패하면**: 키를 샌드박스에 넣는 우회를 하지 않는다. 그 즉시 사용자 결정을 받는다. 대안의 예는 채점용 실행을 OpenShell 없이 돌리는 안이다. 이 안은 "채점 대상 실행"의 정의(§3.2)와 실행 규칙(§4, §9.7)을 바꾸므로 설계 명세(로컬 계획 폴더 `.dryforge/`의 명세, git 추적 제외, 부록 A) §2-8·§3.5·§3.6 변경이 필요한 사용자 승인 대상이다. 이 안을 고르면 채점 실행에 통제 ①과 요건 (b)의 증거가 없고 규범 G2가 약해진다는 점을 사용자 결정 자료에 함께 적는다(§5.4).

### 5.4 대체 경로

1. OpenShell과 NemoClaw는 로컬 Docker로 먼저 시도한다.
2. X1이 3시간(조정값)을 넘기면 원인과 무관하게(단, 아래 "키 주입 방식이 둘 다 실패한 경우"와 "시연 샌드박스가 요건 (b)를 채우지 못하는 경우"는 제외) Brev(드라이버·Docker 등이 미리 갖춰진 NVIDIA 원클릭 클라우드 개발 환경)로 옮긴다. 원인이 NemoClaw 밖이면 이때 사용자에게 알린다.
3. Brev 단계에도 3시간(조정값)을 둔다. 넘기면 원인을 판별해, NemoClaw 구간이 원인이면 OpenShell만 쓰고 제출서에 사실대로 적는다(사용자 결정). OpenShell 게이트웨이 자체·NAT 실행 추적·감사 로그가 원인이면 NemoClaw를 빼도 남으므로 우회하지 않고 즉시 사용자 결정을 받는다(로드맵 §7.1).

- 이 대체 경로는 MVP 합격 체크리스트 1번에 포함돼 있다.
- **대체 경로가 발동한 경우의 표기**: 모든 문서가 대체 경로(Brev → OpenShell만)와 제출서 표기 방식을 함께 적는다. 제출서에는 시도한 환경(로컬 Docker, Brev), 실패한 지점, 대신 쓴 경로를 사실대로 적고, NemoClaw 시연과 스킬 호출 성공률이 없다는 사실도 적는다. 자기채점의 NemoClaw 항목(규범 1c)은 실제 증거대로 매긴다 `[DESIGN]`.
- 채점 대상 실행은 NemoClaw를 거치지 않으므로, 대체 경로가 발동해도 정확도 지표의 실행 방식은 바뀌지 않는다.
- Brev로 옮기면 실행 환경이 로컬과 다르다는 사실을 결정 기록과 재현 안내에 적는다 `[추론]`.
- **키 주입 방식이 둘 다 실패한 경우**(§5.3): 위 대체 경로와 별개로 다룬다. 키를 샌드박스에 넣는 우회를 하지 않고 그 즉시 사용자 결정을 받는다. 대안의 예는 채점용 실행을 OpenShell 없이 돌리는 안이다. 설계 명세(로컬 계획 폴더 `.dryforge/`의 명세, git 추적 제외) §2-8·§3.5·§3.6 변경이 필요한 사용자 승인 대상이며, 이 안을 고르면 채점 실행에 통제 ①과 요건 (b)의 증거가 없고 규범 G2가 약해진다는 점을 사용자 결정 자료에 함께 적는다.
- **시연 샌드박스가 요건 (b)를 채우지 못하는 경우**(§4.8): 예외를 두지 않고 즉시 사용자 결정을 받는다. 대안의 예는 위 대체 경로 3번(NemoClaw 없이 OpenShell만)이다.

## 6. 조사·판정 규칙

이 절은 구 개발계획의 탐지·판정·조사 규칙 중 유지하는 부분이다. 바뀐 결정은 §11에 있다.

### 6.1 탐지 공식

탐지 공식은 그대로 옮긴다(공식 문자 그대로).

```text
U_t = V_t / Q_t                      # USD/kg, V=금액(USD 정수), Q=순중량(kg 정수)
r_U = U_t / U_(t-12) - 1             # 단가 전년동월 변화율
s_t = V_country,t / V_world,t         # 점유율, 분모 = 공식 전체국가(ALL) 합계
d_s = s_t - s_(t-12)                  # 퍼센트포인트(pp)로 표시

# HS10 구성효과 분해 (동일 HS10 집합, 양 시점 중량 유효, 부모 합계 일치일 때만)
u_i,t = V_i,t / Q_i,t
w_i,t = Q_i,t / Σ_i Q_i,t             # 금액 비중이 아닌 중량 비중
within_effect = Σ_i ((w_i,0 + w_i,1)/2) * (u_i,1 - u_i,0)
mix_effect    = Σ_i ((u_i,0 + u_i,1)/2) * (w_i,1 - w_i,0)
ΔU = within_effect + mix_effect      # 분해 잔차·개별 하위변화·상쇄를 함께 반환
```

- V는 금액(USD 정수), Q는 순중량(kg 정수)이다. 점유율 차이는 퍼센트포인트(pp. 두 비율의 차이를 나타내는 단위. 10%에서 6%로 바뀌면 −4pp)로 표시한다.
- **HS6 월 금액·중량의 원천 규칙** `[DESIGN]`. 자세한 규칙은 `docs/rules/DATA_CONTRACT_V1.md`에서 정한다.
  - 단가 U(와 점유율 분자)의 HS6 월 V·Q는 부모 HS6 행에서 가져온다. 부모 행은 국가별 API에 HS4 `8504`로 요청해 받은 HS6 행이다. 국가별 API는 HS4 요청에 HS6 행, HS6 요청에 HS10 행을 준다 `[사실: 실측 메모 §1]`. 금액은 부모 행과 HS10 합이 정확히 일치한다 `[사실: 실측 메모 §1·§2]`.
  - HS10 하위 행은 구성 분해와 부모 대조에만 쓴다. residual = ΔU(부모) − (`within_effect` + `mix_effect`)다.
  - 점유율 분모는 `ALL`의 HS10 월 행을 (HS10 코드, 월) 기준으로 중복 제거해 합한다. 품목별 API는 HS4·HS6 요청 모두 HS10 행만 주므로 `ALL`에는 월별 HS6 행이 없다 `[사실: 실측 메모 §1]`.
  - 중복 제거가 필요한 이유: v2에는 품목별 API의 HS4 `8504` 요청과 HS6 요청이 같은 행(612개 키, 값 동일)을 두 번 담는다 `[사실: data/snapshots/kcs_202201_202412_v2/data-readiness.json의 ALL 교차대조]`. 중복을 빼지 않으면 분모가 정확히 2배가 되고, 점유율 경보가 72건에서 17건으로 줄어든다(개발 제안 임계값 |d_s|≥10pp, 최소 금액·중량 기준 적용 전, 64개 시계열 대상) `[사실: 2026-09-24(목) 무역통계 검토 v2 조회]`.
  - 근거: 기존 `eval/dev/oracle_ABC.json`의 parent·residual 구조와 구 개발계획 §4.2·§5.1의 "부모 대조". §2.3의 1,267개·771개는 이 부모 HS6 행 기준 값이다.
- 전년동월 비교는 비교월 t와 12개월 전 t−12를 짝짓는다. 직전월은 보조 문맥일 뿐 별도 탐지 규칙을 두지 않는다(구 개발계획 §4.1).
- `within_effect`(하위품목 각각의 단가 변화로 생긴 부분)와 `mix_effect`(하위품목 중량 비중의 변화, 즉 구성효과로 생긴 부분)는 동일 HS10 집합, 양 시점 중량 유효, 부모 합계 일치일 때만 계산한다.
- 분해 잔차, 개별 하위품목 변화, 기여도 상쇄를 함께 반환한다. 합계 within 효과가 작아도 일부 하위품목의 큰 상승·하락이 상쇄됐다면 "구성변화만으로 설명"이라고 하지 않는다. `mix/ΔU` 비율 하나로 판정하지 않고, ΔU가 작으면 비율을 제시하지 않는다(구 개발계획 §4.2).
- 신설·소멸 HS10은 존재를 식별하되, 정의되지 않은 단위가치를 0으로 채워 분해하지 않는다. 이 경우 완전한 구성 설명은 미확인으로 남긴다.
- 지표는 값 또는 null + 사유를 반환하고, 입력 근거 ID와 공식 버전을 함께 기록한다.

### 6.2 탐지 임계값과 0·미상 기준

- 탐지 임계값의 개발 제안은 |r_U|≥30%, |d_s|≥10pp이다. 경제적 위험 경계가 아니라 조사 후보를 만드는 값이다.
- 아래 값은 데이터 트랙이 개발 묶음(`real_dev`)만으로 제안하고, 사용자가 승인하면 `configs/policy_v1.json`(정책 `policy_v1`)에 기록한다. 코드에 하드코딩하지 않는다.
  - `min_amount`, `min_weight`: 금액>0인데 중량 0인 677행이 근거다(v2 전체 기준. 대상 HS6과 그 HS10만 세면 449행, §2.3).
  - `CONFIRMED_NO_TRADE` 승격 규칙
  - 수입 0이 명시된 달(68개월)의 처리
  - 반올림 허용오차: 금액은 정확 일치, 중량은 0.5kg×(행수+1)을 출발값으로 한다. 임의의 1% 허용으로 덮지 않는다.
- 0·미상 기준
  - 기준월 값(t−12의 값)이 0이거나 미상이면 증가율을 계산하지 않는다(null + 사유).
  - 중량이 0이면 단가를 계산하지 않는다.
  - 빈 응답을 0으로 채우지 않는다.
  - 선택한 국가들의 합계를 전체국가 분모로 쓰지 않는다. 분모는 공식 전체국가(`ALL`) 합계이고, `ALL`의 HS10 월 행을 (HS10 코드, 월) 기준으로 중복 제거해 합한다(§6.1).
  - BACI(연간, 천USD·톤 단위의 국가 간 교역 자료, §8.2) 값을 관세청 월별 USD/kg 지표와 한 지표 안에서 섞지 않는다. 단위·주기만이 아니라 가격 기준도 다르다. 관세청 수입 금액은 CIF(운임·보험료 포함 가격)이고 BACI는 FOB(수출항 본선 인도 가격) 기준으로 조화한 값이다(분담 D4).
- 경보가 없는 것과 경보를 설명해 모니터링으로 낮춘 것을 구분한다. 자료 미달로 탐지할 수 없는 행은 숨기지 않고 데이터 품질 목록에 둔다.

### 6.3 신호별 판정표

구 개발계획 §5.1을 그대로 유지한다.

| 상황 | 처리 상태 | 반드시 남길 근거 |
|---|---|---|
| 필요한 월·단위·HS정의·분모·구성자료가 없어 검증이 불가능 | 자료 보류(`HOLD`) | 부족 항목, 실패/미수집 구분, 판단 가능한 범위, 필요한 다음 자료 |
| 완전한 하위자료에서 단가 신호 경보가 구성효과로 설명되고 개별 하위변동·잔차가 기준 안 | 모니터링(`MONITOR`) | 부모 대조, 분해 수치, 하위 안정성, 비교조건, 해당 신호의 모니터링 사유 |
| 자료 교정 뒤 동결 정책으로 경보가 해소 | 모니터링(`MONITOR`). "정상 확정" 문구는 쓰지 않는다 | 교정 전후 스냅샷, 재계산 값, 변경 사유 |
| 필수 비교를 마쳤는데 설명되지 않거나 설명이 충돌 | 검토 유지(`MAINTAIN`) | 남은 변화와 검사한 대안 설명, 반대 근거, 미확인 원인 |
| 다른 상대국도 비슷하게 변함 | 이 사실만으로는 등급을 낮추지 않는다 | 다른 확인을 계속하고, 최종 필수근거 충족 여부로 유지/보류 |
| 작은 기준월 값이나 반올림 때문에 방향이나 충족 여부가 불안정 | 자료 보류(`HOLD`) | 정밀도·유효범위·민감도. 작은 금액 자체를 정상 근거로 쓰지 않는다 |

- 필요한 자료가 부족한데 "설명되지 않는다"는 이유만으로 검토 유지하지 않는다. 반대로 비교 자료 하나가 없다고 해서, 이미 독립적으로 입증된 다른 신호의 검토 필요까지 지우지 않는다.
- 분모 축소로 점유율이 오른 것은 "산술 설명"일 뿐 하향 사유가 아니다. 유효한 점유율 급변이 남으면 검토 유지한다.
- 다른 상대국이 함께 하락했다는 결과는 공통 설명의 후보일 뿐, 정상 거래나 시장가격 하락의 증명이 아니다.

### 6.4 사례와 집계

- 사례(case)는 HS6 × 상대국 × 월(t) + 기준월(t−12) + 신호 2종의 발동 여부다. 동결 정책 `policy_v1`로 탐지될 때 **코드가** 만든다. 모델은 사례를 만들지 않는다.
- 판정 상태 코드와 한국어 표기:

| 코드 | 한국어 표기 | 쓰는 곳 |
|---|---|---|
| `MAINTAIN` | 검토 유지 | 신호별·사례별 |
| `MONITOR` | 모니터링 | 신호별·사례별 |
| `HOLD` | 자료 보류 | 신호별·사례별 |
| `NOT_TRIGGERED` | 미발동 | 신호별만 |

- 신호 코드는 `unit_value`, `share`다. 신호 발동 여부 `signal_trigger`는 `TRIGGERED | NOT_TRIGGERED`, 신호별 판정 `signal_status`는 `MAINTAIN | MONITOR | HOLD | NOT_TRIGGERED`다.
- **사례 집계 우선순위는 `MAINTAIN > HOLD > MONITOR`이다.**
  - `MAINTAIN`과 `HOLD`가 섞이면 결과는 `MAINTAIN`이고 `unresolved_evidence=true`를 붙인다.
  - 발동한 신호가 모두 `MONITOR`일 때만 사례 전체가 `MONITOR`가 된다.
  - 발동하지 않은 신호는 `NOT_TRIGGERED`로 둔다.
- 사례 상태는 조사의 완결성이 아니라 **담당자의 다음 업무**를 뜻한다.
- 사례의 처음 표시 상태 코드는 `PRE_INVESTIGATION`(표기 "조사 전 경보")이다. 판정 상태가 아니다.
- 기존 `eval/dev/oracle_ABC.json`은 한국어 표기("모니터링" 등)와 `TRIGGERED`를 쓴다. 이 파일은 고치지 않고 위 표로 코드와 대응시킨다.

### 6.5 도구 5개와 공통 봉투

| 도구 | 조회와 제한 |
|---|---|
| `check_comparability` | 기간·요청 완료·단위·HS 버전·분모·하위자료의 존재 상태. 존재 여부와 내용 조회를 구분하며 정답 상태를 돌려주지 않는다 |
| `get_history` | 대상 HS6·국가의 이력과 전년동월 비교. 정해진 작은 결과 구조와 원본 행 포인터를 돌려준다 |
| `compare_partners` | 사전에 허용된 비교국(§8)을 같은 HS·월·기준으로 조회한다. 분모 종류와 미포함 범위를 표시한다 |
| `decompose_hs` | 필요한 두 시점의 모든 HS10, 부모 대조, 중량 비중 분해, 개별 변화·상쇄·잔차·불가 사유 |
| `verify_evidence` | 이미 반환된 근거·지표를 읽기 전용 스냅샷 원본과 대조해 수치·단위·원본 행·출처·필수 근거·허용 상태·명시적 금지 문구를 검사한다. 다른 도구를 다시 부르거나 새 비교 근거를 만들지 않으며, 평가 정답 파일을 보지 않는다 |

- 공통 입력: `case_id`, `snapshot_id`, 허용된 scope(조회 범위).
- 공통 출력 봉투(도구 5개가 같은 형식으로 돌려주는 출력 구조)의 키: `query_id, tool, scope, snapshot_id, source_kind, evidence_ids, metrics, comparability, missingness, retryable_error, elapsed_ms`. 출처 종류 `source_kind`는 `real | controlled`다.
- 근거 ID 형식: `ev:<snapshot_id>:<table>:<rowid>`.
- 모델 인자로 DB 경로·SQL·외부 URL·셸 명령을 받지 않는다. 도구가 반환한 품목명·설명은 데이터로만 다루고 지시문으로 실행하지 않는다.
- 도구는 D가 만드는 자료 접근층 `dal/` 패키지(읽기 전용 SQLite 읽기 함수)를 M이 감싸서 만든다(분담 D7).
- 도구는 로컬 스냅샷만 조회한다. 외부 자료 HTTP 요청은 사전 수집 단계의 별도 기록(`collection_http_attempts`)에 있고, 도구 시도 횟수와 섞지 않는다.
- 공개 정책의 "이 주장을 하려면 이 근거가 필요하다"는 조건은 모든 모드가 쓸 수 있다. 숨기는 것은 사례별 예상 상태·생성 계열·평가 정답이다(구 개발계획 §5.2).

### 6.6 예산과 한도

| 항목 | 한도 | 셈 방식·규칙 |
|---|---|---|
| 도구 호출 시도 `tool_attempts` | 8회 이하 | 실패·같은 도구 재호출·캐시 적중·`verify_evidence`를 모두 센다. 기본 경로 5회 이하, 재조회 2회 이하, 최종 검증 1회 |
| 재조사(수정 단계) | 1회 | 그 안에서 조회는 최대 2회 |
| Critic | 도구 호출 없음 | 수정 뒤 다시 부르지 않는다 |
| 스키마 실패 | — | 최초 초안이 스키마 검사(보고서가 정해진 출력 형식을 따르는지 보는 검사)에서 실패하면 Critic을 생략하고 곧바로 수정 1회로 들어간다. 다시 실패하면 `INVALID`로 끝낸다 |
| 모델 요청 | 10회(재전송 포함, 조정값) | provider 자동 재시도는 끄고, 5xx 명시 재전송만 모델 요청 횟수에 센다 |
| 사례당 wall time(실제 경과 시간) | 300초(조정값) | 요청별 제한 시간은 min(60초, 전체 deadline까지 남은 시간 − 종료 기록 예약 시간). 남은 시간이 없으면 요청하지 않는다(구 개발계획 §5.3) |
| 누적 토큰 | 32,000(조정값) | 입력 + 출력 |

- 먼저 닿는 한도가 실행을 멈춘다. 비교군 사이에 같은 한도를 쓴다.
- 멈출 때는 실패 원인, 누적 시도, 마지막 정상 근거를 기록한다.
- 비교 불가가 확정되면 이력·하위 조회를 생략한다. 같은 스냅샷의 영구적 자료 부재를 같은 인자로 반복 조회하지 않는다.
- **조기 종료·호출 한도·같은 인자 재호출 차단은 프롬프트가 아니라 코드가 강제한다** `[사실: 구 개발계획 G4 관문 시험(NIM 도구 왕복) 관찰 — 모델이 "추가 조회 없이 보류" 지시를 어기고 호출함]`.
- 도구 8회에 모델 HTTP 요청을 섞지 않는다.
- MVP 기준(로드맵 체크리스트 2번): 9번째 도구 시도 차단, 두 번째 수정 단계 차단, 수정 단계의 세 번째 재조회 차단, 전체 deadline 우선 종료 시험이 통과한다.

### 6.7 조사 흐름

구 개발계획 §5.3의 흐름을 유지한다.

```text
코드: 후보·사례 생성(동결 policy_v1)
 → check_comparability            [도구 1회]
 → get_history                    [도구 1회, 비교 가능할 때]
 → 조사자: 다음 비교 선택          [기본 2회 이내]
 → 조사자: 근거 포함 초안(typed claim + 설명·가설)
 → Critic: 누락·반대 설명·비교조건 검수(도구 없음, 구조화된 지적과 재조회 요청 반환)
 → verify_evidence                [1회 예약]
 → 필요하면 수정 단계 1회          [재조회 최대 2회]
 → verify_evidence                [최종 1회 예약]
 → 검증기 판정(freeform은 기록만) → 보고서 확정 또는 INVALID → 실행 기록
```

- Critic은 조사자가 받은 근거와 초안만 본다. 재조회가 필요하면 조사자가 수정 단계에서 실행한다.
- 모델은 남은 횟수와 필수 근거를 받지만 예산을 늘릴 수 없다.
- 모드별 차이는 §9.2에 있다. `checklist`는 모델 없이 고정 순서로 조회하고, `agent`는 Critic 없이 같은 수정 기회를 갖는다.

## 7. 보고서와 검증기

### 7.1 typed claim

- 모든 사실 주장은 정해진 형식의 typed claim(사실 주장을 정해진 필드로 나눠 쓴 구조화 주장)으로 낸다.
- 필드: `claim_id, claim_type, hs6, partner, period, baseline_period, metric, value, unit, direction, evidence_ids, text`
- `claim_type`: `value | change | share | share_change | decomposition | comparison | data_status`
- `direction`: `UP | DOWN | FLAT | NA`

### 7.2 보고서 객체

- 키: `report_id, run_id, case_id, mode, claims, narrative, hypotheses, review_status, signal_status, unresolved_evidence, evidence_ids, validator_findings, report_hash, created_at, policy_version, snapshot_id, grouping_version`
  - `claims`: typed claim 목록
  - `narrative`: 설명 문장
  - `hypotheses`: 미확인 가설
  - `validator_findings`: 검증기가 막았거나(`full`), 막았을 것(`freeform` 기록 전용)의 목록. 모드별 차단 범위는 §7.3 표가 정한다
  - `report_hash`: `claims`·`narrative`·`hypotheses`·`evidence_ids`를 정규화한 sha256(내용을 256비트 값으로 요약하는 해시 함수)
- 보고서 언어는 한국어다. 처음 상태 표시는 "조사 전 경보"(`PRE_INVESTIGATION`)로 고정한다. 최종 판정이 바뀐 것처럼 이력을 꾸미지 않는다.
- 확정된 보고서는 `report_hash`로 고정된다. 내용이 바뀌면 새 보고서로 만든다.
- 보고서는 위법 여부나 원인을 단정하지 않는다. 검증기를 통과하지 못한 보고서는 공유·승인 대상이 아니다.

### 7.3 모드별 숫자 채우기

| 모드 | 숫자를 누가 쓰나 | 검증기 |
|---|---|---|
| `checklist`·`agent`·`full` | 검증된 metric에서 틀(템플릿)로 채운다 | 막는다 |
| `freeform` | typed claim의 값을 모델이 직접 쓴다 | 기록 전용. 막지 않고 "무엇을 막았을지"만 `validator_findings`에 남긴다 |

- 모델의 설명·가설 문장은 별도 필드(`narrative`, `hypotheses`)에 둔다.

### 7.4 검증기

- **무엇을 검사하나**: 보고서의 숫자·단위·원본 행·출처·스냅샷·허용 상태·금지 문구, 그리고 typed claim으로 뒷받침되지 않는 설명 문장 속 숫자·증감 표현(결정적 패턴 검사).
- **무엇을 못 하나**: 정답표를 읽지 않는다. 모델의 틀린 상태를 조용히 정답으로 고쳐 성공 처리하지 않는다. 자유 문장의 인과적 타당성을 보증하지 않는다.
- **어떻게 끝나나**: 보고서마다 통과 또는 차단 판정과 사유 목록(`validator_findings`)을 남긴다. 차단되면 예산 안의 수정 단계로 가고, 수정도 차단되면 실행은 `INVALID`로 끝난다.
- **왜 필요한가**: 구 개발계획 G4 관문 시험에서 점유율 감소(10→6)를 "6→10 증가"로 뒤집어 쓴 응답이 근거 ID를 언급했다는 이유로 통과로 셈해졌다 `[사실: 실측 메모 §5]`. 숫자는 검증된 값으로만 채우고 검증기로 막아야 한다.
- MVP 기준(로드맵 체크리스트 3번): 의도적으로 넣은 숫자·단위·근거 ID·스냅샷 변조와 뒷받침 없는 산문 숫자를 막는 시험이 통과한다.
- NAT 사후 평가와 역할이 다르다(§3.3).

### 7.5 실행 상태와 실행 기록

- `review_status`(업무 판정)와 `execution_status`(실행 결과)를 분리한다.
- 실행 상태: `COMPLETED | FAILED | TIMEOUT | INVALID | BUDGET_EXCEEDED`
- `execution_status ≠ COMPLETED`인 실행은 공유 승인할 수 없고 평가에서 성공으로 치지 않는다. 이때 `review_status_final`은 `null`이다.
- 코드가 모델의 틀린 상태를 조용히 정답으로 고치지 않는다.
- 실행 실패 때문에 화면에 보류로 보이는 것과 평가의 정답 보류를 같게 보지 않는다(구 개발계획 §5.3).
- 실행 결과 기록 키(run 1건): `run_id, case_id, dataset, mode, policy_version, rulebook_version, snapshot_id, grouping_version, code_version, review_status_final, signal_status, unresolved_evidence, execution_status, required_evidence_ok, numeric_ok, provenance_ok, tool_attempts, model_requests, tokens_in, tokens_out, wall_ms, critic_used, revision_used, errors`
- 실행 기록(trace JSONL, NAT 프로파일 결과)은 그 실행 폴더 `outputs/{실행명}/`에 두고 커밋하지 않는다. 봉인 묶음 실행은 `outputs/sealed/{실행명}/`이다. 실행 쪽 키는 평가 하네스(단위 `evaluation_batch_run`)가 `evaluation_batch_run-{시각}.jsonl`에 쓰고, 채점기가 세 키를 더한 평가 결과를 채점 실행 폴더에 새로 쓴다. 평가 결과는 채점 실행 폴더의 채점기 출력(`scorer_summary-{시각}.jsonl`, `scorer_claims-{시각}.jsonl`, `scorer_summary-{시각}.md`)만 같은 이름의 폴더 `artifacts/eval/score-{시각}/`로 복사해 커밋한다(증거 복사). trace와 NAT 프로파일 결과는 복사하지 않고, 봉인 묶음은 금지 해제 조건이 채워진 뒤에만 복사한다(자료 계약 §8.2·§10.3).
- 키 값은 로그·trace·결과 파일에 남지 않아야 한다.

### 7.6 승인(모의, 코드 검증만)

- 공유용 보고서 승인만 모의로 구현한다. 화면 없이 코드와 시험으로만 만든다(2026-09-26(토)~2026-09-27(일), 패키지 `approval/`).
- 승인 기록 필드: `reviewer_label`, `timestamp`, `report_hash`, `evidence_digest`, `snapshot_id`, `policy_version`, `code_version`
- 승인 유효 상태: `VALID | REVIEW_REQUIRED`
- 의존 자료·정책·수치·보고서가 바뀌면 기존 기록은 보존하고 유효 상태만 `REVIEW_REQUIRED`로 바꾼다. 승인 시점에 digest(의존 자료를 요약한 해시값)를 다시 계산해 대조한다.
- 구 개발계획 §8.3 완료 기준과 §10 주장은 "코드 수준 불변식 시험" 수준으로 맞춘다: 승인 뒤 의존 자료를 바꾸면 이전 승인이 보존되고 재검토 상태가 되며, 승인할 때 digest를 다시 확인한다.
- 실제 기관 승인이나 통관 조치로 표현하지 않는다. 계정·권한 시스템은 없다(단일 사용자 데모).
- 승인 불변식 시험은 일정이 밀릴 때 가장 먼저 줄이는 항목이다(§12.1).

### 7.7 화면

- Streamlit(파이썬으로 웹 화면을 만드는 라이브러리) 화면 3개를 2026-09-26(토)~2026-09-27(일)에 만든다. 일정이 밀리면 화면 3번째, 화면 2번째 순으로 줄인다.
- 화면은 사례별 조회 이유, 실제 실행한 도구, 반대 근거, 판정 전후, 원본 행 링크를 보여 준다(구 개발계획 §10).
- 화면 파일(`app.py`)의 위치는 §10.1 경로 표에 없으므로 S0에서 정한다.

### 7.8 한국어 품질

- Nemotron 3 Super 모델카드의 지원 언어 목록에 한국어가 없다 `[사실: R3 문서 §4]`.
- 자동 검사(한글 비율, 금지 표현, 필수 항목)와 검토 에이전트 표본 점검으로 측정하고 **참고 수치**로만 보고한다. 사람 검토는 필수가 아니다.

## 8. 비교 대상

비교 대상(peer group. 대상 상대국과 나란히 볼 다른 국가 집합)은 `compare_partners` 도구가 쓰는 비교집합이다.

### 8.1 `g0` — MVP 시험까지의 고정 목록

- 2026-09-25(금) MVP 시험까지는 고정 목록 `g0`를 쓴다.
- 정의 `[DESIGN]`: 품목(HS6)과 대상국마다, 대상국을 뺀 나머지 15개국에서 v2의 2023년 연간 수입금액 상위 5개국을 고른다(k=5, 조정값). 대상국을 먼저 빼므로 비교국은 항상 5개국이고, `g1`의 "상위 5개국(p 제외)"과 비교 조건이 같다. 이 해석은 사용자 확인 대기다(시한은 2026-09-25(금) MVP 시험 전, 자료 계약 §2.3.6·로드맵 §6.1).
- 경보 결과를 보고 바꾸지 않는다.

### 8.2 `g1` — 기본 비교 대상

- 유사도 그룹핑 `g1`이 기본 비교 대상이다. `g1`은 동결되는 즉시 MVP 이후 모든 채점 대상 실행의 기본값이 되고, `g0` 결과는 비교표로 남긴다.
- 그룹핑 작업은 2026-09-27(일)로 미루지 않고 2026-09-24(목)부터 병렬로 바로 진행한다. BACI(프랑스 연구소 CEPII가 만드는 국가 간 교역 조화 자료. 연간, 천USD·톤 단위) 원본 `.data/BACI_HS22_V202601.zip`(약 300MB)이 이미 로컬에 있다. `.data/`는 git 추적에서 빠져 있다.
- 방법은 분담 문서 §3 초안을 그대로 쓴다 `[DESIGN]`.

| 항목 | 내용 |
|---|---|
| 벡터 | 수출국 i의 2023년 BACI HS22 전세계 대상 HS85 내 HS6 수출 바구니(금액 비중) |
| 유사도 | 코사인(두 벡터가 얼마나 닮았는지 나타내는 값, 1에 가까울수록 비슷) |

| 대만 | BACI 490(S19, "Asia n.e.s.")에 대응한다. 주석 내용: BACI 490(Other Asia, nes)에는 대만 외 기타 아시아 미상분이 섞일 수 있다. 기록 위치는 분담 §3·D3의 국가 코드 대응표(country_map)이며, 그 파일 위치는 §10.1 표에 없어 S0에서 정한다 |

- 결과는 `data/reference/peer_group_g1.csv`(M 계산·D 검수)이고, 계산 패키지는 `src/tradesentry/grouping/`(M)다.
- 객체 필드는 분담 문서 §4의 `peer_group`을 그대로 쓴다(`schema_version=1`). 정본은 `docs/rules/DATA_CONTRACT_V1.md`다.

### 8.3 쓰는 곳과 쓰지 않는 곳

- 그룹핑은 **비교집합 선택과 문맥 표시에만** 쓰고 판정 신호로 쓰지 않는다. 신호는 2개로 유지한다.
- BACI 값(천USD/톤, 연간)을 관세청 월별 USD/kg 지표와 한 지표 안에서 섞지 않는다. 가격 기준도 다르다: 관세청 수입 금액은 CIF, BACI는 FOB 기준으로 조화한 값이다(분담 D4, §6.2).
- 미수집 국가를 "변화 없음"으로 보지 않는다. 비교국 수·유효월·제외 사유를 반환한다.
- 합성 평가 자료(dev20·holdout40)의 비교 대상은 자료 안의 합성 `peer_group`으로 정해지며 `g0`/`g1`과 무관하다.

### 8.4 `g1` 미동결 때

- 룰북 동결 시한(2026-09-26(토) 12:00)까지 `g1`이 동결되지 않으면 `g0`로 채점하고 제출서에 사실대로 적는다.
- `g1` 동결이 룰북 동결의 조건인 이유: 비교 대상이 `g0`에서 `g1`로 바뀌면 실자료 사례의 조사 경로와 보고서 숫자가 바뀐다.
- `g1`은 일정이 밀려도 끝까지 지키는 항목이다(§12.1).

## 9. 평가와의 연결

평가의 정본은 룰북(`docs/eval/RULEBOOK.md`)이다. Part A는 규범을 적용한 프로젝트 자기채점, Part B는 TradeSentry 성능 평가다. 이 절은 개발에 필요한 연결점만 요약한다. 룰북과 다르면 룰북을 따른다.

### 9.1 자료 묶음

| 이름 | 성격 | 만드는 쪽 | 쓰는 곳·보관 |
|---|---|---|---|
| `controlled_fixture_v0` | 합성 시험자료. A/B/C 포함 | D가 먼저 넘긴다 | M 개발용. `data/snapshots/controlled_fixture_v0/` |
| `dev20` | 공개 개발 자료 | D(독립 정답표 포함) | 모든 에이전트가 쓴다. `eval/dev/dev20/`(입력 + 정답표) |
| `holdout40` | 봉인 평가 자료 | D 트랙 작업. 모델 트랙과 격리된 Claude 보조 에이전트가 생성 | 봉인 폴더(저장소 밖). 해시만 커밋 |
| `real_dev` | 실자료 개발 묶음 | 실자료 분할 | 탐지 임계값·최소 기준 조정, 개발 확인 |
| `real_sealed` | 실자료 봉인 묶음 | 실자료 분할 | 대표 지표 채점 대상. 사례 목록과 채점 표본은 봉인 |

- `holdout40`
  - 구 개발계획 §8.1의 10개 시나리오 분류와 개발 20/평가 40 배분을 따른다.
  - 기초 시계열·하위품목 구조·결측 방식·부모 원본 계열 ID 단위로 dev20과 분리한다. 같은 계열의 규모·seed(난수 시작값) 변형은 한쪽에만 둔다.
  - 모델 트랙과 격리된 Claude 보조 에이전트가 시나리오 명세(`eval/scenarios/SCENARIO_SPEC.md`)만 보고 생성한다. Codex에게 생성을 맡기지 않는다(사용자 결정).
  - 정답표는 운영 코드를 복사하지 않은 독립 구현으로 만든다.
- `real_dev` / `real_sealed`
  - 탐지 임계값 조정 **전에** 품목×국가 시계열 64개를 고정 난수(같은 결과를 다시 만들 수 있게 시작값 seed를 고정한 난수)로 먼저 나눈다. 분할 비율 1:2와 seed는 조정값이며 기록한다.
  - 같은 시계열이 양쪽에 섞이지 않게 품목×국가 단위로 나눈다.
  - 탐지 임계값·최소 기준은 `real_dev` 묶음만으로 조정한다.
  - 동결된 `policy_v1`로 `real_sealed` 묶음에서 나온 경보가 대표 지표의 채점 대상이다. 표본 상한은 40건(조정값)이고, 넘으면 고정 난수로 표본을 뽑는다.
  - `real_dev`를 빌려 쓰지 않는다. 표본이 모자라거나 실행이 끝나지 않으면 §9.4를 따른다.

### 9.2 비교 방식(모드)

| 모드 | 동작 |
|---|---|
| `checklist` | 고정 체크리스트. 모델 없음 |
| `agent` | Critic 없는 Nemotron |
| `full` | 전체 TradeSentry |
| `freeform` | 대표 지표 기준선. `full`과 처리만 다르고 나머지는 같다 |

- `freeform`과 `full`에서 같은 것: 조사자·Critic·수정 1회·스키마 검사·도구·예산·한도·자료
- 다른 것 ①: typed claim의 **값을 모델이 직접 쓴다**(틀 채우기 없음).
- 다른 것 ②: 검증기는 **기록 전용**이다. 막지 않고 "무엇을 막았을지"만 기록한다.
- 그래서 두 모드의 차이에는 "검증된 값만 채우고 검증기로 막는 처리"의 효과만 남는다.
- 모든 모드에 같은 자료·도구·정책·한도·재시도 규칙을 적용한다. `checklist`는 모든 도구를 끝까지 부르는 약한 상대가 아니다. 결정적인 조기 종료와 같은 캐시 정책을 허용한다(구 개발계획 §8.2).

### 9.3 대표 지표 — 실자료 사실 주장 오류율

- 두 모드(`freeform` vs `full`. 참고용 `agent`는 평가 스킬 ②가 예정 실행 목록에 넣지 않는다, 룰북 B2)의 최종 보고서에서 **모든 사실 주장**을 채점한다. 설명 문장 속 주장까지 포함한다.
- 채점 범위
  - ① typed claim의 모든 필드(숫자·단위·증감 방향·기간·국가·품목·지표·근거 ID)
  - ② 설명 문장 속 숫자·증감 표현. **결정적 패턴 목록**으로 잡는다. 이 목록은 `RB-1`과 함께 동결하고, 누락 사례는 `real_dev`에서만 보강한다.
  - 숫자·증감이 없는 정성 서술(가설·해석)의 의미 정확성은 대표 지표 **범위 밖**이다. 룰북과 제출서에 그렇게 밝힌다.
- 채점 기준: 공식 통계 원본(스냅샷 raw 행)과 **결정적으로** 대조한다. 사람 판정자도 AI 채점자도 두지 않는다. 룰북은 필드별 채점 규칙과 산문 패턴 규칙을 따로 쓰고, 각각 예시와 경계 사례를 둔다.
- 주장 채점 결과: `CORRECT | WRONG_VALUE | WRONG_DIRECTION | WRONG_UNIT | WRONG_REFERENT | UNSUPPORTED | UNBACKED_PROSE`
  - 값 비교 허용오차는 표시 자릿수 반올림 기준이며 조정값이다.
  - `WRONG_REFERENT`: 기간·국가·품목·지표가 가리키는 대상이 없거나 다르다.
  - `UNSUPPORTED`: 근거 ID가 없거나, 풀리지 않거나, 주장을 뒷받침하지 않는다.
  - `UNBACKED_PROSE`: 설명 문장 속 뒷받침 없는 숫자·증감 표현.
- 오류율
  - 주장 단위 오류율 = `CORRECT`가 아닌 typed claim ÷ 전체 typed claim
  - 보고서 단위 오류율 = 오류 claim이나 `UNBACKED_PROSE`가 1개 이상인 보고서 ÷ 전체 보고서
  - `UNBACKED_PROSE`는 보고서당 건수로도 따로 보고한다.
  - 유효한 최종 보고서가 없는 실행은 보고서 단위 실패로 분모에 남긴다.
- 주장 채점 기록 키(claim 1건): `run_id, report_id, claim_id, source, outcome, expected_value, reported_value, unit_expected, unit_reported, tolerance, referent_resolved, evidence_ok, note`. `source`는 `claim | prose`(산문 패턴으로 잡힌 표현)이고, `outcome`은 위 채점 결과 값이다.
- 독립 채점기: `eval/scorer/`(D 소유). 런타임 모듈을 import하지 않는 **독립 구현**이며 런타임 `metrics/` 패키지를 재사용하지 않는다. import 금지에는 간접 import(런타임 패키지를 부르는 모듈을 거쳐 부르는 경우)도 들고, 평가 자료 도구 `eval/datagen/`도 import하지 않는다(자료 계약 §10.3). `eval/dev/oracle_ABC.json`과 손계산 예제로 먼저 검증하고, 샌드박스 밖에서 돈다. 실행: `python -m eval.scorer --run <run_dir>`. `<run_dir>`는 채점할 실행 폴더 `outputs/{실행명}/`(봉인 묶음은 `outputs/sealed/{실행명}/`)이고, 채점기는 자기 출력을 `outputs/score-{시각}/`에 쓴다. 봉인 묶음을 채점할 때 채점기는 시작 직후 자기가 확보한 실행 폴더 이름을 표준 출력 첫 줄로 알리고, 봉인 묶음을 채점한 채점기 출력은 금지 해제 조건(자료 계약 §10.3 N10) 전에는 에이전트가 열지 않고 커밋하지 않는다.
- MVP 기준(로드맵 체크리스트 6번): `real_dev`로 대표 지표 첫 값(`freeform` vs `full`)을 낸다. 이 값은 "개발 묶음 값, 대표 숫자 아님"으로 표기한다.

### 9.4 A등급 주장 조건

- 조건: `real_sealed`에서 **모드별(`freeform`, `full` 각각)** 유효 보고서(`execution_status=COMPLETED`)가 최소 20건(조정값)이고 봉인 실행이 끝났을 때만, 그 값을 A등급 대표 숫자로 내세운다. 두 모드는 같은 사례 집합에서 실행한다.
- 미달이거나 미완료면 A등급 대표 주장을 **보류**한다. 실제 건수·신뢰구간·미완료 사실과 함께 참고치로만 보고한다.
- 개발용 결과(`dev20`, `real_dev`)를 대표로 올리지 않는다.
- holdout40도 같다: 실행이 끝나지 않으면 끝난 부분만 실패 집계와 함께 보고하고, 미완료 부분에 대한 주장은 하지 않는다.
- 이유: 작은 표본이나 부분 결과로 A등급을 주장하면 규범이 요구하는 "외부인이 믿을 수 있는 숫자"가 되지 않는다(결정 기록 16번).

### 9.5 보조 지표 — holdout40

구 개발계획 §8.3을 유지한다. 비교군은 `checklist`·`agent`·`full` 3개이고, 40건 × 3 = 120회 실행한다.

- 근거 충족 처리정확도 = (예상 상태 일치 AND 필수근거 AND 수치/단위 AND 출처/버전 AND 정상 실행) ÷ 40
- 불필요 보류율, 잘못된 모니터링률, 상태별 혼동행렬, 실행 실패 수 ÷ 40
- 도구수·모델토큰·시간의 중앙값과 범위
- 모든 사례를 보류했을 때의 점수(기준 비교용)
- 95% 신뢰구간: Wilson(비율의 신뢰구간을 계산하는 방법)을 기본으로 한다(조정값). 40건이면 50% 부근에서 ±14.8pp라 작은 차이는 주장하지 않는다.
- 모델 원초안 → Critic 뒤 → 검증 뒤 상태 변화를 기록한다. Critic 전후 변화만으로 전체 구조의 성능 향상을 추정하지 않는다.
- 승인 무효화·의도적 변조·8회 초과 차단·모델 timeout 같은 불변식 시험은 따로 두고, 40건 처리정확도에 더해 부풀리지 않는다.
- MVP 기준(로드맵 체크리스트 5번): dev20 × 비교군 3개(`checklist`·`agent`·`full`) 점수표가 나온다.

### 9.6 숫자 등급과 자기채점

- 숫자 등급(규범이 정한 숫자 신뢰 등급 A~D `[DESIGN]`)은 "누가 정답을 만들었나"와 "정답이 개선 과정에 노출됐나"로만 판정한다.
  - 대표 지표(`real_sealed` 사실 주장 오류율): A. §9.4의 조건을 채울 때만 대표 숫자로 내세운다.
  - holdout40 근거 충족 처리정확도: C
  - dev20·`real_dev` 결과: D(개선 과정에 노출된 값)
- 합성 자료로 만든 숫자의 등급은 holdout40이 C, dev20이 D이며 그보다 높게 적지 않는다. 대표 숫자는 `real_sealed`에서만 나온다.
- Part A 자기채점: 규범 §2~§4의 하드 게이트·채점 지표·보정 규칙을 TradeSentry 증거 정의로 풀어 쓴 것이 룰북 Part A다. 평가 스킬 ①이 자기채점하고, 회차마다 새 실행 폴더에 쓴 결과 파일 `scorecard-{시각}.md`를 같은 이름의 폴더 `artifacts/scorecard/scorecard-{시각}/`로 복사해 커밋한다(증거 복사). 규범의 가중치·게이트·앵커는 팀 설계 규칙 `[DESIGN]`이고 대회 공식 배점이 아니다.
- 컴포넌트 삭제 시험(NVIDIA 구성요소마다 "지우면 어떤 지표가 나빠지는가")은 룰북 Part A에서 판정한다. 답이 약한 구성요소는 약하다고 정직하게 적는다. 예: NemoClaw는 정확도 지표에 영향이 없다.

### 9.7 실행 규칙과 동결

- 채점 대상 실행은 OpenShell 안에서 하고, 정답 대조 채점은 밖에서 한다.
- 정답표·봉인 사례 목록은 샌드박스와 개발 에이전트에게 들이지 않는다. 예외는 공식 채점 대상 실행에 필요한 봉인 입력을 §9.8 절차 4대로 그 전용 샌드박스에만 읽기 전용으로 넣는 것 하나다. 정답표는 어떤 경우에도 넣지 않는다.
- 동시성은 1로 시작한다. 할당량·실패율을 확인한 뒤에만 올리고, 모든 모드에 같게 적용한다.
- 순서는 교차·무작위로 섞는다.
- 실패·미실행·timeout·invalid는 분모에 남긴다. 결과를 본 뒤 어려운 사례를 지우지 않는다.
- 120회(40건 × 비교군 3개)의 보수적 순차 상한은 약 10시간이다. NIM 간헐 HTTP 500을 고려한 재실행 여유를 일정에 따로 둔다. `real_sealed`의 `freeform`/`full`은 표본 40건 기준 80회, 약 1~2시간이다.
- 룰북 `RB-1`은 **2026-09-26(토) 12:00**(조정값)에 동결한다. 동결 조건은 `policy_v1` 승인, `g1` 동결 또는 `g0` 대체 선언, 봉인 자료 해시 커밋이다.
- 동결 뒤 holdout40과 `real_sealed`를 **한 번만** 채점한다. 동결 뒤 변경은 새 버전과 사유로만 한다. 결과를 본 뒤 유리하게 고치지 않는다.
- 봉인 채점 시작 마감: 목표 2026-09-26(토) 14:00, 늦어도 2026-09-27(일) 06:00이다. 동결이나 실행이 늦어지면 끝난 만큼만 보고하고 미완료 사실을 표시한다(§9.4).

### 9.8 봉인 자료 보관과 권한 분리

- 봉인 대상: holdout40 입력과 정답표, `real_sealed` 사례 목록과 채점 표본
- 보관 위치: **저장소 밖** `~/.tradesentry/sealed/`(환경변수 `TRADESENTRY_SEALED_DIR`로 바꿀 수 있음). 에이전트 작업 폴더에도 두지 않는다.
- 내용 증명용 sha256 해시만 PR로 커밋한다(`eval/sealed_manifest.json`). 원본 파일은 최종 채점이 끝난 뒤 커밋한다.
- 모델 트랙 에이전트와 Codex의 작업 지시에 봉인 폴더를 넣지 않고, 읽지 말라고 지시한다. 봉인 실행 출력(trace 포함, `outputs/sealed/{실행명}/`)에도 봉인 입력 내용이 담기므로, 금지 해제 조건(자료 계약 §10.3 N10) 전에는 `outputs/sealed/` 아래 출력과 봉인 묶음을 채점한 채점기 출력 폴더도 읽지 말라고 지시한다. 봉인 묶음 실행 출력은 샌드박스 작업 폴더에 있는 동안(내려받기 전, 지우기 전)에도 같은 열람·커밋 금지를 받는다. 에이전트는 그 폴더를 `openshell sandbox exec`·`connect`·`download`로 열거나 받지 않는다. 내려받기는 샌드박스 밖 실행기(프로그램)만 `outputs/sealed/{실행명}/`로 한다. 예외는 기존 셋 그대로다: 채점기 실행, 결정적 건수 추출(내용을 열지 않고 상태·원인 코드의 건수만 뽑는 명령), 한 번만 채점하기 위한 존재 확인. 공식 채점 대상 실행 전용 샌드박스를 내려받은 뒤 지우는지 남기는지를 봉인 사건(봉인 폴더에 닿거나 봉인 묶음을 움직인 일. 평가 스킬 ②가 결정 기록에 남긴다)으로 기록한다. 지우는 시점은 정답 대조 채점 뒤다.
- 정직한 한계는 §4.5와 같다. 룰북과 제출서에 이 한계를 적는다.
- `real_sealed`의 정직한 한계: 사례 목록은 기록된 분할 seed·동결 스냅샷·승인된 `policy_v1`로 다시 계산할 수 있으므로 봉인은 기밀 유지가 아니다. 봉인의 목적은 개발·튜닝에 쓰지 않도록 지시와 기록으로 관리하는 것과, 결과를 보기 전에 표본을 고정하고 해시로 증명하는 것(무결성)이다. 표본 추출 seed는 생성 전에 정해 봉인 폴더 안에 두고, 채점 뒤 공개한다.
- 생성 → 봉인 → 해시 등록 → 한 번 채점의 권한 분리 절차
  1. 생성: holdout40 생성 에이전트(격리된 Claude 보조 에이전트)는 시나리오 명세와 생성 규칙만 입력으로 받는다. 결과를 봉인 폴더에 **직접** 기록하고, 저장소에는 쓰지 않는다. 생성 에이전트는 런타임 코드를 작성하지 않고, 그 대화 기록은 모델 트랙에 넘기지 않는다.
  2. 봉인: 생성 직후 파일별 sha256 목록을 만든다.
  3. 해시 등록: 해시 목록만 PR로 커밋한다.
  4. 한 번 채점: `RB-1` 동결 뒤 오케스트레이터(작업을 배분하고 병합하는 주관 에이전트)가 평가 스킬 ②를 실행할 때만 봉인 **입력**을 샌드박스에 읽기 전용으로 넣는다. 파일시스템 정책(정적 계층)은 샌드박스를 만들 때 고정되므로, 봉인 입력은 **공식 채점 대상 실행 전용 샌드박스를 새로 만들어** 넣는다. 개발·시연용 샌드박스에는 넣지 않는다. 넣는 방식은 로드맵 MT5에서 확정한다 `[미확인]`. 공식 실행 전에 그 샌드박스의 라이브 정책 조회 결과와 최소 시험 행(비허용 호스트, 정답표 부재, `outputs/`·채점기 출력 부재 확인, 요건 (c) 키 조회, 봉인 입력 쓰기 거부)을 "공식 채점용"으로 남긴다(§4.4). 정답표는 어떤 샌드박스에도 넣지 않고, 샌드박스 밖 채점기만 읽는다.
  5. 채점 전에 해시를 다시 대조한다. 일치하지 않으면 그 묶음을 무효로 하고 사용자에게 올린다.
  - `real_sealed`의 사례 목록과 표본도 같은 절차를 따른다. 다만 `real_sealed`에서 4단계의 봉인 입력 전달은 룰북 B5와 부록 40번(사용자 확인 대기)을 따른다. 지금 안은 목록·표본 파일을 샌드박스에 넣지 않고, 샌드박스 밖 실행기(프로그램, 로드맵 MT7)가 해시 대조 뒤 사례 식별자를 `run-case`에 한 건씩 넘기는 것이다.
- 세부 규칙은 병렬 개발 규칙(`docs/rules/PARALLEL_DEV_RULES.md`)과 룰북에 있다.

### 9.9 경계 처리

| 상황 | 처리 |
|---|---|
| 평가 스킬 ②를 구현 전에 부른 경우 | 사전 점검 단계에서 멈춘다. 없는 구성요소 목록(명령·파일·해시)을 보고하고 어떤 실행도 하지 않는다 |
| 동결 조건이 하나라도 빠진 경우(평가 스킬 ②) | 봉인 자료 채점을 거부한다. dev20·`real_dev` 실행은 허용한다 |
| 자기채점 스킬 ①에서 증거를 찾지 못한 지표 | 앵커 정의상 낮은 점수를 준다. 추정해서 올리지 않는다. 점수마다 근거 한 줄과 경로를 적고, 근거 한 줄이 비면 그 판정은 무효로 표시한다 |
| `real_sealed` 경보 부족 또는 봉인 실행 미완료 | A등급 대표 주장을 보류하고 참고치로만 보고한다(§9.4) |
| 봉인 해시와 실제 파일이 다른 경우 | 그 묶음의 채점을 무효로 하고 사용자에게 올린다 |
| `g1` 미동결 | `g0`로 채점하고 제출서에 사실대로 적는다(§8.4) |
| NemoClaw 대체 경로 발동 | 대체 경로(Brev → OpenShell만)와 제출서 표기 방식을 함께 적는다(§5.4) |
| 외부 자문이 공용 약속을 바꾸자고 하는 경우 | 사용자 승인 절차를 거친다(§10.4) |

### 10.4 협업 규칙 요약

- **합성 시험자료 먼저 넘기기**: D가 `controlled_fixture_v0`를 먼저 넘기고, M은 실자료를 기다리지 않고 이것으로 개발한다. 구성은 분담 D6을 따른다(3 HS6 × 10국 × 36개월 + HS10 2개월 + `peer_group` + 수집 기록 + A/B/C, 규모는 조정값). 실스냅샷은 코드 변경 없이 교체된다.
- **D → M 인수 조건**(넘겨받는 쪽이 확인하는 완료 기준)
  - 인수물마다 `schema_version=1` 표시가 있어야 한다.
  - 자료 계약 검사 명령이 통과해야 한다.
  - 자료 접근층(`dal/` 패키지)으로 읽혀야 한다.
  - `metrics/` 패키지가 oracle A/B/C를 재현해야 한다.
  - 인수물마다 검증 명령과 종료 코드가 PR에 기록돼 있어야 한다.
  - 인수 조건을 못 채운 인수물은 M이 받지 않고 D에게 돌려보낸다.
- **공용 약속 변경 = 사용자 승인**(공용 약속: 두 트랙이 함께 기대는 형식과 값)
  - 대상: 자료 형식(계약 필드), 상태값, 탐지 임계값, 도구 한도, 품목·국가 확정, 평가 구성, 제출서 주장 문구
  - 절차: 계약 버전 올림 → 합성 시험자료 재생성 → 양 트랙 검토 → 사용자 승인
  - 승인을 기다리는 동안에는 그 약속에 의존하는 작업만 멈춘다. 그 외 세부는 에이전트가 정하고 결정 기록에 남긴다.
- **결정 기록**: 이번 설계 세션의 결정과 이유는 §13과 부록 A에 있다. 이후 결정은 `docs/tracking/decisions/`에 적는다.
- **실행 주체**
  - 구현은 Claude 보조 에이전트가 두 트랙 모두 맡는다.
  - Codex headless(화면 없이 명령으로 실행하는 Codex, `codex exec`)는 두 가지에만 쓴다: 입출력·시험이 정해진 작은 코드 부품의 구현(Claude가 캡처된 종료 코드로 검증), 위험이 큰 산출물(지표 계산, 판정 정책, 검증기, 평가 정답표·채점기, 자료 계약, 룰북)의 교차 검토.
  - Codex에는 `.env`와 봉인 경로를 주지 않는다. 검토는 `-s read-only`, 구현은 `-s workspace-write`로 해당 작업 폴더에만 쓴다. macOS에는 `timeout` 명령이 없으므로 제한 시간은 다른 방법으로 건다. 비대화형 실행은 2026-09-23(수)에 확인했다 `[사실]`.
  - `-s` 모드는 쓰기 범위 설정이다. `.env`·봉인 경로를 주지 않는 것은 지시 수준 통제이며, §4.5의 한계(같은 OS 사용자로 도는 에이전트의 열람을 기술적으로 막지 못함)는 Codex에도 해당한다.
- **도메인 검토 에이전트** 4종(작업 성격에 맞는 검토자만 띄운다): 무역통계·관세 / 평가 방법론 / NVIDIA 스택 / 보안
- **검토 판정과 반복**: 판정은 `PASS` 또는 `CHANGES_REQUIRED`이고, 번호 붙인 지적(파일:행, 이유, 고칠 방법)을 붙인다. 검토는 병합을 막는다. 수정은 최대 2회이고, 그래도 의견이 갈리면 오케스트레이터가 이유를 기록하고 결정한다. 공용 약속에 해당하면 사용자에게 올린다.
- **작업 단위 PR**: 작업마다 브랜치와 PR을 만든다. 검사 통과와 필요한 검토자 전원 `PASS`를 받으면 에이전트가 main에 병합한다(squash 병합: 여러 커밋을 하나로 합쳐 넣는 방식, 조정값). PR 본문에 검사 명령·종료 코드·검토 판정 요약을 남긴다.
- 로드맵의 구현 작업 ID는 데이터 트랙 `DT`, 모델 트랙 `MT`, 승인 `AP` 접두사를 쓴다.
- 세부는 병렬 개발 규칙(`docs/rules/PARALLEL_DEV_RULES.md`)과 에이전트 운용 규칙(`docs/rules/AGENT_OPS.md`)에 있다.

### 10.5 S0 앱 스캐폴딩과 외부 자문

- S0는 구현 단계의 첫 작업 단위다. 대상은 디렉터리·패키지 구조, 가상환경과 lock, 설정 파일 뼈대, CLI 진입점, 시험 배치다. 단위 표(`docs/plan/UNITS.md`)에 따라 단위 파일 뼈대, 단위 등록부와 공통 실행기, 골든 시험(고정 입력과 기대 출력 한 쌍으로 단위 출력을 확인하는 시험) 틀, 경계 시험(허용 밖 import가 없는지 import 문만 읽어 확인하는 시험)도 만든다.
- S0는 **외부 자문 체크포인트**다. 실행자는 뼈대를 만들기 전에 `docs/plan/SCAFFOLD_BRIEF.md`를 사용자에게 제시하고, 사용자가 외부 자문 결과(또는 "반영 없음")를 전해 줄 때까지 스캐폴딩 생성을 **멈춘다**.
- 자문 내용은 반영 여부와 이유를 결정 기록에 남긴다. 공용 약속을 바꾸는 자문은 §10.4의 사용자 승인 절차를 거친다.
- X1(§5.3)은 S0 자문 대기와 병렬로 진행할 수 있다.

### 12.2 정직한 주장 규칙

공식 문서와 대조했을 때 틀린 주장이거나 규범에 어긋나 쓰지 않는 서술과, 대신 쓸 서술:

| 쓰지 않는 서술(요지) | 대신 쓸 서술 |
|---|---|
| OpenShell 정책으로 근거·토큰·요청 본문의 의미를 검사한다는 서술 | OpenShell의 L7 규칙은 method·path·query만 본다. 의미 검사는 앱 코드(검증기)의 일이다 `[사실: R3 문서 §2]` |
| Policy Advisor를 감사 기록 저장소로 쓰는 서술 | 감사 증거는 `openshell logs`의 허용·차단 이벤트와 앱 실행 기록이다. 대회 조사 문서 §8-2는 허용·차단이 모두 기록된다고 적지만, 계층별로 실제 남는지와 허용 이벤트 행의 형식은 X1 실측 전까지 `[미확인]`이다. 허용 이벤트 행이 없으면 "허용 증거 출처: 앱 기록(`openshell logs` 행 없음)"으로 적는다. Policy Advisor의 역할은 정책 예외 제안·승인 흐름이다 `[사실: R3 문서 §3]` |
| 목적지가 허용 목록에 있으니 안전하다는 서술 | 정책은 목적지를 승인할 뿐 오가는 내용의 의미를 승인하지 않는다 `[사실: 03 문서 §4]` |
| 명령 실패만으로 차단이 증명됐다는 서술 | 종료 코드·거부 문구·감사 로그 행·라이브 정책 조회를 함께 둔다. 파일이 없어서 난 실패는 차단 증거가 아니다 `[사실: 03 문서 §6.6]` |
| 합성 자료 숫자에 대표 등급(A 또는 B 등급)을 붙이는 표기 | 합성 숫자는 holdout40이 C, dev20이 D다. 대표 숫자는 `real_sealed`에서만 나온다 |
| 단가 변화를 부정·위법·원산지 조작·개별 거래가격의 증거로 쓰는 서술 | 단가 변화는 경보일 뿐이다. 보고서는 담당자의 다음 업무(검토 유지·모니터링·자료 보류)만 제시한다 |
| 일몰 예정 구성요소(§3.4)를 핵심 기술로 적는 서술 | Tech Stack에는 실제로 쓴 구성요소(NIM·Nemotron, NAT, OpenShell, NemoClaw, Agent Skills)만 적는다 |

그 밖의 규칙:

- `[DESIGN]` 규칙(규범의 가중치·게이트·앵커)을 대회 공식 규칙처럼 쓰지 않는다.
- 대표 숫자는 `real_sealed`에서만 나오며, §9.4 조건을 채울 때만 A등급으로 내세운다. 개발용 결과를 대표로 올리지 않는다.
- NemoClaw는 정확도 지표에 영향이 없다고 밝힌다.
- 정성 서술의 의미 정확성은 대표 지표 범위 밖이라고 밝힌다.
- 저장소 경로 차단(①)이 저장소 밖 봉인 격리(②)를 보장한다고 쓰지 않는다. 봉인 격리의 한계(같은 OS 사용자)를 적는다.
- OpenShell에 관한 주장은 로컬 실측 결과로만 한다. 확인되지 않은 기능은 `[미확인]`으로 적는다.
- 같은 모델을 두 번 쓰는 구조(조사자·Critic)를 정확성 보증으로 표현하지 않는다(구 개발계획 §8.3).
- `checklist`보다 개선도 비용 절감도 없으면 "이 범위에서 LLM 추가 가치 미확인"으로 보고한다(구 개발계획 §8.3).
- A/B/C 합성 사례를 실제 사건이라고 부르지 않는다. 일부러 넣은 실패는 주입 시험이라고 표시하고 자연 발생 실패처럼 말하지 않는다(구 개발계획 §10).
- 합성 자료 데모를 실제 통계 성능으로 표현하지 않는다.
- 자료 교정 뒤 경보가 해소돼도 "정상 확정"이라고 쓰지 않는다.
- 비밀값: 키·토큰·쿠키 값을 쓰지 않고 변수 이름(`NVIDIA_API_KEY`, `DATA_GO_KR_SERVICE_KEY`)만 쓴다. 산출물은 비밀값·로컬 경로 검사(NVIDIA API 키 접두어, 공공데이터포털 서비스키 요청 파라미터, 로컬 절대경로를 찾는 검사. 실제 패턴 문자열은 검사 스크립트에만 두고 문서에는 적지 않는다)를 통과해야 한다.
- 경로는 저장소 루트 기준 상대경로만 쓴다. 예외는 봉인 폴더 기본값 `~/.tradesentry/sealed/`다.

## 13. 결정 기록

이번 설계 세션(설계 2026-09-23(수) 밤, 문서 작업 2026-09-24(목))에서 확정한 의도와 이유다. 문서 작업 중 검토에서 정한 이견·해석과 그 뒤의 결정은 `docs/tracking/decisions/`에 적는다.

1. **문서 먼저, 구현은 다음 단계.** 사용자가 선택했다.
   - 이유: 규범 §6 "개발 순서 경고"(평가 규칙과 기준선 측정을 기능보다 먼저)를 따르고, 두 트랙이 동시에 착수할 수 있도록 공용 약속을 먼저 고정한다.
2. **두 트랙 모두 Claude 보조 에이전트가 수행하고, 작업 성격별 도메인 검토 에이전트를 따로 띄운다.** 사용자가 직접 입력한 결정이다.
   - 분담 문서의 사람 2인 서명 절차는 "사용자 승인 + 검토 에이전트"로 바뀐다.
3. **NVIDIA 결합은 하네스 → 스킬 → 샌드박스.** NemoClaw(OpenClaw)가 우리 스킬을 부르고, 실행은 OpenShell 안에서 한다. 조사 흐름은 NAT로 감싼다.
   - 기각한 대안 ①: OpenShell 중심 축소형. NemoClaw 활용 깊이 점수(규범 1c)가 낮다.
   - 기각한 대안 ②: 조사자를 OpenClaw로 구현. 도구 8회·재조사 1회를 코드로 강제하는 설계와 충돌하고 공수가 크다.
4. **대표 지표는 실자료 사실 주장 오류율(A등급)이고, 합성 40건은 보조(C)다.**
   - 이유: 규범상 합성 자료를 우리가 만들고 우리가 채점하면 D등급이라 규범 3a 상한이 1점이 된다 `[DESIGN]`. 생성과 판정을 분리한 holdout40도 최대 C라 대표 지표에 필요한 A·B가 될 수 없다(§1.2, §9.6).
   - 기각한 대안 ①: 합성 40건을 대표로. 생성 규칙과 판정 정책이 같은 뿌리다.
   - 기각한 대안 ②: BFCL(공개 함수 호출 벤치마크) 추가. TradeSentry 목적과의 연결이 약하다.
5. **대표 지표는 모든 사실 주장을 결정적으로 채점한다.**
   - 이유: AI 채점자가 끼면 D등급 위험이 있다. 숫자 칸만 세면 TradeSentry는 숫자를 검증된 값으로만 채우므로 구조상 0%가 돼 당연한 결과로 보인다.
6. **실자료는 탐지 임계값 조정 전에 시계열 단위로 고정 난수 분할한다.**
   - 이유: 개발 과정에 노출된 사례로 대표 숫자를 만들면 등급 논란이 생긴다. 경보가 많아(771/1,267) 나눠도 손해가 거의 없다.
   - 사용자는 "비교 가능한 조합을 고정 난수로 나눈다"를 승인했다. 같은 품목·국가 시계열이 양쪽에 섞이지 않도록 분할 단위를 품목×국가로 구체화했다.
7. **채점 대상 실행은 OpenShell 안 CLI로 직접 돌리고, NemoClaw는 시연과 스킬 호출 성공률로 따로 증명한다.**
   - 이유: 하네스 에이전트가 한 겹 더 끼면 비교군 차이가 흐려지고 비용·실패가 는다. NemoClaw는 정확도에 영향이 없다고 정직하게 밝힌다.
8. **봉인 자료는 저장소 밖에 두고 해시만 커밋한다.**
   - 이유: PR이 main에 자동 병합되므로 저장소에 두면 모델 트랙 에이전트가 보게 된다.
9. **holdout40은 격리된 Claude 보조 에이전트가 만든다.**
   - 사용자가 Codex에 격리 생성 역할을 맡기지 않기로 했다. Codex는 교차 검토와 명세가 뚜렷한 코드 구현만 맡는다.
10. **비교 대상은 MVP 시험까지 `g0`, 이후 기본은 `g1`이다.**
    - 그룹핑은 2026-09-27(일)로 묶어 두지 않고 2026-09-24(목)부터 바로 병렬로 진행한다(사용자 결정). 분담 문서 §3 초안 방법을 쓴다.
    - `g1`이 동결 시한까지 안 되면 `g0` + 사실 표기로 간다.
11. **승인 기능은 코드 검증만 한다.**
    - 이유: 가장 바쁜 2026-09-26(토)~2026-09-27(일)에 화면 작업을 늘리지 않는다.
12. **품목은 v2 그대로 동결한다.**
    - 추가 수집이 없고, 빈 달이 많은 850432 국가들은 자료 보류 실사례가 된다.
13. **공개 저장소 방식은 2026-09-28(월) 오전에 사용자가 결정한다.**
    - 이유: 되돌릴 수 없는 공개 작업이다. 현재 이력에 과거 문서가 있다.
14. **S0 앱 스캐폴딩은 외부 자문 체크포인트다.** 사용자 요구다.
    - 자문용 명세서(`docs/plan/SCAFFOLD_BRIEF.md`)를 미리 만들어 둔다.
15. **일정이 밀릴 때 줄이는 순서**: 승인 불변식 시험 → 같은 사례 반복 실행 → 화면 3번째 → 화면 2번째.
    - 대표 지표, holdout40 비교군 3개 실행, OpenShell 증거, `g1`은 지킨다(사용자 확인).
16. **A등급 주장 조건**(사용자 결정, Codex 검토 회의에서 제기): `real_sealed`에서 모드별(`freeform`, `full` 각각) 유효 보고서가 최소 20건(조정값)이고 봉인 실행이 끝났을 때만 A등급 대표 숫자로 쓴다.
    - 미달·미완료면 보류하고, 건수·신뢰구간·미완료 사실과 함께 참고치로만 보고한다.
    - 개발 결과를 대표로 올리지 않는다.
    - 이유: 작은 표본이나 부분 결과로 A등급을 주장하면 규범이 요구하는 "외부인이 믿을 수 있는 숫자"가 되지 않는다.
17. **X1은 세로형 최소 통합 시험이다**(Codex 검토 회의 합의). 구현을 시작하는 2026-09-24(목)에 NemoClaw 에이전트 → 스킬 → 샌드박스 안 CLI → NIM → NAT 추적 → 차단 로그를 한 번에 통과시킨다. 키 주입 방식은 실제로 성공한 방식만 채택한다.
    - 이유: macOS + Docker + 알파 단계 NemoClaw 조합은 문서만으로 동작을 확정할 수 없다 `[미확인]`. 구성요소를 따로 확인하면 경계(호스트·컨테이너·키 경로)의 실패를 늦게 발견한다.
18. **대표 지표의 채점 범위**(Codex 검토 회의 합의): typed claim 전 필드와 산문 속 숫자·증감 표현(결정적 패턴)만 채점한다. 정성 서술의 의미 정확성은 범위 밖이라고 밝힌다.
    - 이유: 사용자가 고른 "AI 채점자 없는 기계적 대조"를 지키면서 과장 없이 말할 수 있는 범위이기 때문이다.

- **Codex가 동의한 핵심 설계**
  - 위법 판정이 아닌 다음 업무 제안
  - 실자료 시계열 단위 분할
  - `freeform`/`full` 동일 조건 비교와 실패 분모 유지

- **합의 상태**: 2차에서 Codex가 "2번(사용자 결정)만 남고 나머지 합의"라고 답했다. 사용자가 2번을 "미달이면 A등급 주장 보류"로 결정해 **전 항목 합의로 종료**했다.

## 용어 설명

| 용어 | 설명 |
|---|---|
| 단가(단위가치) U | 금액(USD) ÷ 순중량(kg). kg당 수입 금액 |
| 점유율 s | 해당 상대국 금액 ÷ 전체국가(`ALL`) 금액. 분모는 `ALL`의 HS10 월 행을 (HS10 코드, 월) 기준으로 중복 제거해 합한 값이다(§6.1) |
| 전년동월 | 비교월 t와 12개월 전 t−12를 짝지어 비교하는 방식 |
| pp(퍼센트포인트) | 두 비율의 차이를 나타내는 단위. 10%에서 6%로 바뀌면 −4pp |
| HS 코드 | 국제 통일 상품 분류 코드. HS2 → HS4 → HS6 → HS10으로 세분된다. 6자리까지는 국제 공통이고 7~10자리는 한국 세분(HSK)이다. BACI는 HS6까지만 있다 |
| 부모 HS6 행 | 국가별 API에 HS4로 요청해 받은 HS6 월 행. 단가 U와 점유율 분자의 원천이며, HS10 하위 행은 구성 분해와 부모 대조에만 쓴다 |
| 총계 행 | API가 `hsCd='-'`로 주는 요청 구간 합계 행. 하위 행 합과 대조하는 데 쓴다 |
| 탐지 임계값 | 경보를 발동시키는 기준. 예: 단가 변화율 r_U의 절댓값 30% 이상, 점유율 변화 d_s의 절댓값 10pp 이상. `policy_v1`에 기록한다 |
| 기준월 값 | 전년동월 비교에서 12개월 전 달(t−12)의 값 |
| CIF·FOB | 무역 금액의 가격 기준. CIF는 운임·보험료를 포함한 도착 가격(관세청 수입 금액), FOB는 수출항 본선 인도 가격(BACI 조화 기준) |

| `mix_effect`(구성효과) | 하위품목의 중량 비중 변화 때문에 생긴 평균 단가 변화 부분 |
| 스냅샷 | 한 시점에 수집해 동결한 원자료 묶음(raw 응답, manifest, SQLite). 모든 조회의 유일한 원천 |

| 관측 상태 | 월·국가·품목 단위 자료의 상태 5종(`OBSERVED` 등). 실패·미수집·빈 응답을 구분한다 |
| 사례(case) | 경보가 난 HS6 × 상대국 × 월과 기준월, 신호 2종의 발동 여부 묶음. 코드가 만든다 |
