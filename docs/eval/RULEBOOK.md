# TradeSentry 평가 룰북 (RULEBOOK)

이 문서는 TradeSentry의 평가 규칙을 **구현과 측정 전에** 고정해 두는 룰북이다. Part A는 팀 채점 규범으로 프로젝트를 자기채점하는 규칙이고, Part B는 TradeSentry 성능 평가 규칙이다. 결과를 본 뒤 규칙을 유리하게 바꾸지 않으려고 먼저 쓴다. 규범 §6 "개발 순서 경고"가 평가 규칙과 기준선 측정을 기능보다 먼저 만들라고 한 데 따른 것이다.

TradeSentry(관세청 수입통계에서 kg당 단가와 상대국 점유율이 전년 같은 달보다 급변한 경우를 경보로 잡고, Nemotron 조사자와 검수자가 제한된 조회 도구로 반증을 시도해 담당자의 다음 업무를 제시하는 에이전트 시스템)는 부정·위법·원산지 조작을 판정하지 않는다. 이 룰북의 어떤 지표도 그런 판정의 정확도를 재지 않는다.

## Part A. 프로젝트 자기채점

Part A는 규범의 §2~§4와 §7을 TradeSentry에서 **무엇이 있으면 몇 점인가**로 풀어 쓴다. 이 Part에 나오는 G1~G6, 지표 코드, CAP·TIE 규칙은 모두 규범의 ID다.

**`[DESIGN]` 경고.** 규범의 가중치(35/25/30/10), 하드 게이트(통과하지 못하면 채점하지 않는 필수 조건), 0/1/3/5 앵커(점수마다 붙은 판정 기준 문장)는 팀이 만든 설계 규칙이다. 대회가 공개한 것은 채점 항목 4개와 그 순서뿐이다 `[사실: 규범 §1, 대회 조사 §5]`. 자기채점 점수를 대회 점수처럼 제출서에 쓰지 않는다.

### 자기채점 회차와 결과 위치

- 회차: 2026-09-25(금) MVP 시험 뒤 1회, 2026-09-27(일) 결과 정리 때 1회, 2026-09-28(월) 제출 전 최종 1회 `[DESIGN: 로드맵]`
- 결과 파일: `artifacts/scorecard/<YYYY-MM-DD>-scorecard.md`(양식은 A3 끝)
- 실행: 평가 스킬 ① `skills/tradesentry-scorecard/SKILL.md`

### 적용 원칙

1. 순서는 규범 §6을 따른다. 한 문장 가설 → 하드 게이트(A1) → 채점 지표 20개(A2) → `2e` 표시 → 보정 규칙 → 총점과 판정 밴드(A3) → 가장 낮은 축 2개와 보강 가능성.
2. **증거가 점수를 정한다.** 증거를 찾지 못한 지표는 앵커 정의대로 낮은 점수를 준다. 추정해서 올리지 않는다.
3. **판정마다 근거 한 줄과 증거 경로(또는 명령)를 적는다.** 근거 한 줄이 비면 그 판정은 무효다. 무효 판정은 지표면 0점, 게이트면 FAIL로 계산한다 `[DESIGN]`.
4. 점수는 0/1/3/5만 쓴다. 2와 4는 쓰지 않는다. `4d`는 규범에 1점 앵커가 없어서 0/3/5만 쓴다.
5. 앵커 문언이 두 가지로 읽히면 A2 주석과 부록에 적은 해석을 따른다. 거기에도 없으면 낮은 점수를 주는 해석을 쓰고, 다른 해석은 근거 줄에 함께 적는다 `[DESIGN]`.
6. 증거 경로는 계획 경로·명령 표(`docs/rules/DATA_CONTRACT_V1.md`)의 예정 위치만 쓴다. `artifacts/runs/`는 커밋하지 않는다. 그래서 심사위원이 볼 수 있어야 하는 증거는 요약을 `artifacts/eval/<run_id>/summary.md`에 옮겨 둔다 `[추론]`.

### 적용의 한계 `[DESIGN]`

- 규범 §8이 밝힌 한계를 그대로 안고 간다.
  - 가중치는 공식 발표가 아니다.
  - 게이트의 문턱(3종 이상 등)은 임의로 정한 값이다.
  - 앵커 문언은 채점 재현성을 위해 팀이 쓴 것이라 심사위원이 같은 기준을 쓴다는 보장이 없다.
  - 예선에만 적용한다.
- 같은 팀이 자기 프로젝트를 채점하므로 점수가 후해질 위험이 있다. 원칙 2·3·5로 줄이지만 없애지는 못한다 `[추론]`.
- 규범 §2는 게이트가 하나라도 FAIL이면 아이디어를 폐기하고 채점하지 말라고 한다. 아이디어는 이미 정해졌으므로, 개발 중 자기채점에서는 FAIL을 "제출 전에 반드시 풀어야 할 결함"으로 읽는다 `[추론]`. 채점하지 않는다는 규칙은 그대로 지킨다. FAIL이 하나라도 있는 회차는 게이트 표와 해소 조건만 남기고 총점·밴드를 내지 않는다.

## Part B. TradeSentry 성능 평가

- **증명할 한 문장 가설(대표 지표)**: "Nemotron이 숫자를 직접 쓴 조사 보고서보다, 검증된 값만 틀에 채우고 검증기로 막는 TradeSentry 보고서가 실제 관세청 자료 경보에서 사실 주장 오류율이 낮다."
- **기준선(규범 G1 한 문장)**: 같은 자료·도구·예산으로 Nemotron이 사실 주장의 값을 직접 쓰는 보고서(`freeform` 모드).
- **판정 상태의 채점 범위** `[DESIGN]`: 실자료에는 판정 상태의 정답이 없다(구 개발계획 §8.1). 그래서 실자료 평가는 사실 주장만 채점하고, 판정 상태(`MAINTAIN` 검토 유지 / `MONITOR` 모니터링 / `HOLD` 자료 보류)의 옳고 그름은 채점하지 않는다. 판정 상태의 정확도는 합성 `holdout40`(B4)에서만 잰다.
- 모든 평가는 채점 대상 실행(샌드박스 안)과 정답 대조 채점(샌드박스 밖)을 나눠서 한다(0.4).

### B2. 비교 방식

| 모드 | 동작 | 숫자를 채우는 방식 | 검증기 |
|---|---|---|---|
| `checklist` | 고정 체크리스트. 모델 없음. 비교조건 → 이력 → 필요한 하위·비교국 조회를 고정 순서로 하고 정책으로 결과를 낸다. 비교 불가면 조기 종료 | 검증된 metric에서 틀로 채움 | 막음 |
| `agent` | Critic 없는 Nemotron. 조사자가 도구를 고르고 근거를 보고한다. 코드 검증 오류에 대해 같은 1회 수정 기회를 받는다 | 검증된 metric에서 틀로 채움 | 막음 |
| `full` | 전체 TradeSentry. 조사자 + 별도 문맥 Critic + 코드 검증 + 수정 1회 | 검증된 metric에서 틀로 채움 | 막음 |
| `freeform` | 대표 지표의 기준선. `full`과 **처리만 다르고 나머지는 같다** | typed claim의 값을 모델이 직접 쓴다(틀 채우기 없음) | 기록 전용. 막지 않고 막았을 것만 `validator_findings`에 적는다 |

- **`freeform`과 `full`이 같은 것**: 조사자, Critic, 수정 1회, 스키마 검사, 도구, 예산, 한도, 자료. 그래서 두 모드의 차이에는 "검증된 값만 채우고 검증기로 막는 처리"의 효과만 남는다.
- **모든 모드에 같은 조건** `[DESIGN]`:
  - 자료·스냅샷, 도구 5개(`check_comparability`, `get_history`, `compare_partners`, `decompose_hs`, `verify_evidence`)와 공통 출력 봉투, `policy_v1`, `grouping_version`, 모델 ID와 설정, 샌드박스 정책, 동시성
  - 한도(조정값): 도구 호출 시도 `tool_attempts ≤ 8`(기본 경로 ≤5, 재조회 ≤2, 최종 검증 1), 재조사 1회(그 안의 조회 ≤2), 모델 요청 10회(재전송 포함), 사례당 wall time 300초, 누적 토큰 32,000. 먼저 닿는 한도가 실행을 멈춘다.
  - 재시도: provider 자동 재시도는 끈다. HTTP 5xx 명시 재전송만 요청당 최대 3회, 지수 대기로 하고 모델 요청 횟수에 센다.
  - Critic의 비용·토큰도 같은 예산 안에 든다. 모델이 없는 `checklist`의 토큰은 0으로 표시한다.
- **`checklist`는 약한 상대가 아니다**(구 개발계획 §8.2): 결정적 조기 종료와 같은 캐시 정책을 허용한다. 필수 근거는 "어떤 호출 순서를 썼는가"가 아니라 "검증에 필요한 정보를 얻었는가"로 정의한다.
- 조기 종료·호출 한도·같은 인자 재호출 차단은 프롬프트가 아니라 코드가 강제한다 `[사실: 구 개발계획 G4 관문 시험 관찰, 사실 메모 §5]`.

|---|---|---|
| `controlled_fixture_v0` | 네 모드 모두 가능 | 개발과 시험 |

### B3. 대표 지표

**실자료 사실 주장 오류율.** `real_sealed` 경보 표본의 모든 사례에서 `freeform`과 `full`의 최종 보고서에 담긴 **모든 사실 주장**을 채점한다. 설명 문장 속 주장도 포함한다.

**채점 범위**:

- ① typed claim(정해진 필드를 가진 사실 주장 레코드)의 모든 필드: 숫자·단위·증감 방향·기간·국가·품목·지표·근거 ID. 규칙은 B3-1이다.
- ② 설명 문장 속 숫자·증감 표현. 결정적 패턴 목록으로 잡는다. 이 목록은 `RB-1`과 함께 동결하고, 누락 사례는 `real_dev`에서만 보강한다. 규칙은 B3-2다.
- 숫자·증감이 없는 정성 서술(가설·해석)의 의미 정확성은 대표 지표의 **범위 밖**이다. 제출서에도 그렇게 밝힌다.
- 사람 판정자도 AI 채점자도 두지 않는다. 공식 통계 원본(스냅샷 원본 행)과 결정적으로 대조한다.

**판정 결과 집합**:

| 결과 | 뜻 | 붙는 채점 단위 |
|---|---|---|
| `CORRECT` | typed claim: 대상·단위·방향·값·근거가 모두 맞다. 산문 표현: 같은 보고서의 typed claim으로 뒷받침된다 | claim, prose |
| `WRONG_VALUE` | 값이 허용오차 밖이다. 계산할 수 없는 대상에 값을 적었거나, 계산할 수 있는 대상을 계산 불가로 적은 경우도 포함한다 | claim |
| `WRONG_DIRECTION` | 증감 방향이 다르다 | claim |
| `WRONG_UNIT` | 단위가 틀렸거나 지표와 맞지 않는다 | claim |
| `WRONG_REFERENT` | 기간·국가·품목·지표가 가리키는 대상이 없거나 다르다 | claim |
| `UNSUPPORTED` | 근거 ID가 없거나, 풀리지 않거나, 주장을 뒷받침하지 않는다 | claim |
| `UNBACKED_PROSE` | 설명 문장 속 숫자·증감 표현이 같은 보고서의 typed claim으로 뒷받침되지 않는다 | prose |

- 채점 단위의 출처는 주장 채점 기록의 `source` 값으로 구분한다. `claim`은 typed claim, `prose`는 산문 패턴으로 잡힌 표현이다.
- 뒷받침된 산문 표현의 참·거짓은 그것을 뒷받침한 typed claim의 결과로 판정한다. 같은 사실을 두 번 세지 않는다.

**채점 절차(정답 대조 채점, 샌드박스 밖)**:

0. 사전 조건
   - 채점기 검증: `eval/dev/oracle_ABC.json`의 합성 사례 A/B/C 기대값과 손계산 예제를 재현하는 시험이 `tests/`에서 통과한다.
   - 스냅샷 검증: `python3 src/tradesentry/ingest.py verify --snapshot kcs_202201_202412_v2 --out <파일>`. 기본 출력을 덮어쓰므로 `--out`을 쓴다.
   - 봉인 묶음이면 해시 재대조(B6).
1. 실행 기록을 읽는다. 실행 결과 기록 키와 보고서 객체 키는 `docs/rules/DATA_CONTRACT_V1.md`를 따른다.
2. 보고서마다 채점 단위를 뽑는다. `claims`의 typed claim 각각(`source`=`claim`)과, 자유 문장 필드에서 산문 패턴에 잡힌 표현 각각(`source`=`prose`)이다.
3. 기대값을 스냅샷 원본 행에서 **독립 계산**한다. 도구 출력 봉투나 런타임 metric 값을 정답으로 쓰지 않는다.
4. B3-1과 B3-2로 결과를 하나씩 붙인다.
5. 채점 단위마다 `artifacts/eval/<run_id>/claims.jsonl`에 기록한다. 키는 `run_id, report_id, claim_id, source, outcome, expected_value, reported_value, unit_expected, unit_reported, tolerance, referent_resolved, evidence_ok, note`다. 요약은 `artifacts/eval/<run_id>/summary.md`(B7)에 쓴다.
6. 같은 입력이면 같은 결과가 나온다. 채점기는 모델도 네트워크도 부르지 않는다.

**오류율 정의**:

- **주장 단위 오류율** = `CORRECT`가 아닌 typed claim ÷ 전체 typed claim. `source`=`claim`만 센다. 유효한 최종 보고서의 주장만 분모에 들어간다.
- **보고서 단위 오류율** = 오류 claim이나 `UNBACKED_PROSE`가 1개 이상인 보고서 ÷ 전체 보고서. 분모는 예정된 모든 실행(사례 × 모드)이다. 유효한 최종 보고서가 없는 실행은 보고서 단위 실패로 분모에 남는다.
- **`UNBACKED_PROSE` 건수**: 보고서당 건수를 모드별 평균·중앙값·최대로 따로 보고한다.
- **필수 주장 누락** `[DESIGN]`: 발동한 신호마다 그 신호에 대한 typed claim(값·변화 주장 또는 `data_status` 주장)이 1개 이상 있어야 한다. 없으면 그 보고서는 보고서 단위 오류로 센다. 주장이 0개인 보고서가 "오류 없음"으로 세어지는 것을 막기 위해서다.

**주 지표 사전 지정** `[DESIGN]`: 모드 사이의 차이 주장은 **보고서 단위 오류율로만** 한다. 주장 단위 오류율은 함께 보고하는 설명 지표다. 결과를 보기 전에 정해 둔다. 이유는 둘이다.

1. 주장 단위의 분모에는 유효 보고서의 주장만 들어간다. `full`에서 검증기가 막아 `INVALID`가 된 보고서의 오류 주장은 이 분모에서 빠진다. 보고서 단위에서는 그 실행이 실패로 남는다.
2. 한 보고서 안의 주장끼리는 서로 독립이 아니다. 그래서 주장 단위로 구한 신뢰구간은 실제보다 좁게 나온다.

**실패 처리**:

- `execution_status`가 `COMPLETED`가 아닌 실행(`FAILED`, `TIMEOUT`, `INVALID`, `BUDGET_EXCEEDED`)은 보고서 단위 실패로 분모에 남긴다. 상태별 건수를 모드별로 보고한다. 이런 실행의 `review_status_final`은 `null`이다.
- `freeform`은 검증기가 막지 않으므로 `INVALID`가 스키마 검사 실패에서만 생긴다. `full`은 검증기 차단으로도 `INVALID`가 생긴다. 모드별 실패 수 차이를 결과와 함께 적는다.
- `full`의 검증기가 같은 규칙으로 산문을 막으므로 `full`의 `UNBACKED_PROSE`가 0에 가까운 것은 설계상 예상되는 결과다. 그 대가는 `INVALID`로 분모에 남는다. 그래서 가설의 핵심 증거는 필드 오류(①)와 보고서 단위 오류율이다 `[추론]`.
- 채점기가 claim을 해석하지 못하면 그 claim은 `WRONG_REFERENT`로 기록하고 `note`에 사유를 적는다 `[DESIGN]`.

**독립 채점기 요건**:

- 위치는 `eval/scorer/`, 실행은 `python -m eval.scorer --run <run_dir>`이다.
- 런타임 모듈(`src/tradesentry/`의 `metrics.py` 등)을 import하지 않는 독립 구현이다.
- 봉인 채점 전에 `eval/dev/oracle_ABC.json`과 손계산 예제로 먼저 검증한다.
- 샌드박스 밖에서 돈다. 정답표를 읽는 것은 채점기뿐이다.
- 결정적이다. 모델·네트워크를 부르지 않고, 사람·AI 판정을 섞지 않는다.
- 채점기 코드와 산문 패턴 목록은 `RB-1`과 함께 동결한다(B6).

### B3-1. 필드별 채점 규칙

typed claim의 필드는 `claim_id, claim_type, hs6, partner, period, baseline_period, metric, value, unit, direction, evidence_ids, text`이고, `claim_type`은 `value | change | share | share_change | decomposition | comparison | data_status` 중 하나, `direction`은 `UP | DOWN | FLAT | NA` 중 하나다. 지표 이름, 기간 형식, 단위 이름과 표시 자릿수는 `docs/rules/DATA_CONTRACT_V1.md`의 단위와 정밀도 절을 따른다. 이 절은 그 값을 새로 정하지 않는다.

| 필드 | 검사 | 틀리면 |
|---|---|---|
| `claim_type`, `hs6`, `partner`, `period`, `baseline_period`, `metric` | 스냅샷에 있는 대상인가. 지표 정의와 맞는가. 예: 전년동월 지표(r_U, d_s)는 기준월이 t−12여야 한다 | `WRONG_REFERENT` |
| `unit` | 지표에 맞는 단위인가 | `WRONG_UNIT` |
| `direction` | 기대 변화의 부호와 같은가 | `WRONG_DIRECTION` |
| `value` | 표시 자릿수로 반올림해 기대값과 같은가 | `WRONG_VALUE` |
| `evidence_ids` | 근거 ID(`ev:<snapshot_id>:<table>:<rowid>`)가 있고, 풀리고, 기대값 계산에 필요한 원본 행을 모두 포함하는가 | `UNSUPPORTED` |
| `claim_id` | 식별용. 채점하지 않는다 | — |
| `text` | 자유 문장이므로 B3-2로 검사한다 | `UNBACKED_PROSE` |

- **판정 순서** `[DESIGN]`: 대상 → 단위 → 방향 → 값 → 근거 순서로 보고 처음 걸린 결과를 붙인다. 모두 통과하면 `CORRECT`다. 나머지 오류는 `note`에 적고, 근거 검사 결과는 `evidence_ok`에 따로 남긴다. 순서는 결과 분포만 바꾸고 오류율은 바꾸지 않는다.
- **값 비교** `[DESIGN, 조정값]`: 기대값과 보고값을 자료 계약이 정한 지표별 표시 자릿수로 반올림해 같으면 일치다(명세의 "표시 자릿수 반올림 기준"을 구현한 것). 반올림은 사사오입이며, 딱 절반이면 절댓값이 커지는 쪽으로 올린다. 보고값을 계약보다 거칠게 썼어도 계약 자릿수로 비교한다.
- **방향의 기대값**: 기대 변화가 0보다 크면 `UP`, 작으면 `DOWN`이다. 정확히 0이면 `FLAT`이다. 0은 아니지만 표시 자릿수로 반올림해 0이 되면 `FLAT`과 실제 부호 방향을 모두 맞다고 본다. 변화 주장이 아니면 `NA`다.
- **계산할 수 없는 대상**: 기준값이 0이거나 미상이면 변화율을 계산하지 않고, 중량이 0이면 단가를 계산하지 않는다. HS10 구성효과 분해는 같은 HS10 집합, 양 시점 중량 유효, 부모 합계 일치일 때만 계산한다. 이런 대상의 기대값은 null이다. null 대상에 숫자를 적으면 `WRONG_VALUE`다. 계산 불가 사실은 `data_status` 주장으로 쓴다.
- **`data_status` 주장**: 관측 상태(`OBSERVED | NOT_COLLECTED | REQUEST_FAILED | UNRESOLVED_ZERO | CONFIRMED_NO_TRADE`)를 스냅샷 기록과 대조한다. 다르면 `WRONG_VALUE`다.
- **근거 ID 풀기**: 근거 ID를 원본 행으로 푸는 규칙(metric 기록을 거쳐 원본 행으로 가는 경우 포함)은 자료 계약을 따른다. 채점기는 풀린 원본 행 집합이 기대값 계산에 필요한 행 집합을 포함하는지만 본다. 예를 들어 점유율 주장에는 해당국 행과 전체국가(`ALL`) 행이 모두 필요하다.

**예시**. 금액은 USD 정수, 중량은 kg 정수다. 표시 자릿수는 설명을 위해 가정한 값이다(단가는 소수 둘째 자리, %와 pp는 소수 첫째 자리). 실제 자릿수는 자료 계약을 따른다.

| # | 주장(필드 요약) | 기대값 | 결과 |
|---|---|---|---|
| 1 | 단가 값 주장: CN·850450·2024년 1월, 값 20.34, 단위 USD/kg, 근거 = 그 달의 원본 행 | 21,876,681 USD ÷ 1,075,490 kg = 20.3411… → 20.34 `[사실: 사실 메모 §1]` | `CORRECT` |
| 2 | 1번과 같고 값만 20.43 | 20.34 | `WRONG_VALUE` |
| 3 | 1번과 같고 단위만 USD/톤 | USD/kg | `WRONG_UNIT` |
| 4 | 1번과 같고 근거 ID 없음 | — | `UNSUPPORTED` |
| 5 | 1번과 같고 상대국이 수집하지 않은 국가 | 대상 없음 | `WRONG_REFERENT` |
| 6 | 합성 사례 A의 단가 변화 주장: r_U 값 −40.0, 단위 %, 방향 `DOWN` | U 6.0 → 3.6, r_U −40.0% | `CORRECT` |
| 7 | 6번과 같고 방향만 `UP` | `DOWN` | `WRONG_DIRECTION` |

| 9 | 합성 사례 A의 분해 주장: within_effect 0.0, mix_effect −2.4 | within 0.0, mix −2.4 | `CORRECT`(주장 2건) |

합성 사례 A/B/C의 값은 `eval/dev/oracle_ABC.json`의 설계값이다 `[DESIGN]`. 통계 실행 결과가 아니고 실제 사건도 아니다. 채점기는 이 값을 먼저 재현해야 한다.

**경계 사례**:

### B3-2. 산문 패턴 규칙

**적용 범위** `[DESIGN]`: 보고서의 자유 문장 필드 전부, 즉 `narrative`(설명 문장), `hypotheses`(미확인 가설), 각 typed claim의 `text`다. 가설 필드를 빼면 숫자 주장을 가설로 옮겨 채점을 피할 수 있으므로 넣는다. 런타임 검증기가 같은 범위를 막지 않으면 `full`도 이 규칙으로 감점된다. 검증기 범위를 이 절에 맞추는 것은 구현 과제다.

**잡는 표현**(패턴 분류. 정확한 정규식은 채점기에 둔다):

| 분류 | 잡는 것 | 예 |
|---|---|---|
| PT-1 백분율 | 숫자 + `%`·`퍼센트` | "40%", "−40%", "40퍼센트" |
| PT-2 퍼센트포인트 | 숫자 + `pp`·`%p`·`%포인트`·`퍼센트포인트` | "4pp", "4%p" |
| PT-3 금액·중량·단가 | 숫자(쉼표·소수점, 천·만·억 배수 포함) + `USD`·`달러`·`kg`·`킬로그램`·`톤`, "kg당 N달러" 꼴 | "3.6 USD/kg", "kg당 20달러", "2,188만 달러", "1,075톤" |
| PT-4 배수·비율 말 | 숫자나 두·세·네·다섯 + `배`, `절반` | "2배", "두 배", "절반으로" |
| PT-5 단위 없는 숫자와 개수 | 빼는 표현이 아닌 나머지 숫자 전부. `개국`·`개` 같은 개수 포함 | "5개국 중 4개국", "33에서 20으로" |
| PT-6 증감 어휘 | 오름: `증가`, `상승`, `급증`, `급등`, `늘었`·`늘어`, `올랐`, `확대`, `반등`, `높아졌` / 내림: `감소`, `하락`, `급감`, `급락`, `줄었`·`줄어`, `떨어졌`, `축소`, `낮아졌` / 그대로: `보합`, `변화가 없`, `변동이 없` | "40% 떨어졌다", "점유율이 늘었다" |

**빼는 표현**:

| 분류 | 빼는 것 | 예 |
|---|---|---|
| EX-1 날짜·기간 | 연·월·연월, 기간 표현 | "2024년 3월", "2024-03", "12개월 전", "36개월" |
| EX-2 품목·국가 식별 | `HS`와 함께 쓴 숫자, 4·6·10자리 품목 코드, 국가 코드 | "HS 8504", "850450" |
| EX-3 식별자·버전 | 근거 ID(`ev:`로 시작), `case_id`·`claim_id`·`run_id` 값, 버전 이름과 스냅샷 이름 | `policy_v1`, `RB-1`, `g1`, `kcs_202201_202412_v2` |

**뒷받침 판정** `[DESIGN]`:

- **숫자(PT-1~PT-5)**: 같은 보고서의 typed claim 가운데 하나의 `value`를 그 표현의 단위로 바꾸고 산문의 표시 자릿수로 반올림했을 때 절댓값이 같으면 뒷받침된다. 산문에 부호가 명시돼 있으면("−40%") 부호까지 비교한다.
  - 단위가 붙은 표현은 단위가 호환되는 claim만 본다. `%`와 `pp`는 서로 호환되지 않는다. 톤과 kg, 천·만·억 배수는 환산한다.
  - `달러`·`USD`만 붙은 숫자(kg당 표시 없음)는 금액(USD) claim과 단가(USD/kg) claim 모두와 비교한다. "kg당 6.0달러에서 3.6달러로"처럼 단위를 앞 숫자에만 붙이는 자연스러운 표현을 형식 때문에 오류로 세지 않기 위해서다.
  - 단위 없는 숫자는 단위를 따지지 않고 값만 비교한다.
- **표시 자릿수**: 산문 숫자의 마지막 자리다. `약`·`대략`·`거의`·`가량`·`쯤`이 붙으면 끝자리의 0은 자릿수로 치지 않는다("약 40%"는 십의 자리).
- **부등식**: `이상`·`넘게`·`초과`·`웃도는`이 붙으면 그 값 이상인 claim 값이 있을 때, `미만`·`이하`·`밑도는`이 붙으면 그 값 이하인 claim 값이 있을 때 뒷받침된다.
- **증감 어휘(PT-6)**: 같은 보고서에 같은 `direction`의 typed claim이 1개 이상 있으면 뒷받침된다. 부정형("증가하지 않았다")은 반대 방향이나 `FLAT`인 claim이 있으면 뒷받침된다.
- 뒷받침되면 `CORRECT`, 아니면 `UNBACKED_PROSE`다.
- **한계** `[추론]`: 문장 단위로 주어를 맞추지 않는다. 같은 보고서의 다른 주장과 우연히 맞는 표현은 놓친다. 이 한계는 두 모드에 똑같이 작용하며, 결과 보고에 적는다.

**예시**. 같은 보고서에 합성 사례 A의 typed claim이 있다고 하자: U(기준월) 6.0 USD/kg, U(비교월) 3.6 USD/kg, r_U −40.0% `DOWN`, 점유율(기준월) 10.0%, 점유율(비교월) 6.0%, d_s −4.0pp `DOWN`.

| # | 문장(필드) | 잡힌 표현 | 결과 |
|---|---|---|---|
| 1 | "단가가 kg당 6.0달러에서 3.6달러로 40% 떨어졌다."(`narrative`) | 6.0(PT-3, kg당 달러), 3.6(PT-3, 달러), 40%(PT-1), 떨어졌(PT-6 내림) | 모두 `CORRECT`. 3.6은 달러만 붙은 숫자라 단가 claim과도 비교한다 |

| 3 | "점유율이 4% 줄었다."(`narrative`) | 4%(PT-1), 줄었(PT-6 내림) | 4%는 pp claim과 단위가 호환되지 않고 % claim(10.0, 6.0)과 값이 달라 `UNBACKED_PROSE`. "줄었"은 `CORRECT` |

**동결과 보강**:

- 누락 사례는 `real_dev` 결과만 보고 동결 전에 보강한다. 오탐 수정도 같은 규칙을 따른다 `[DESIGN]`. `real_sealed`나 `holdout40`의 결과를 본 뒤에는 고치지 않는다.
- 런타임 검증기와 채점기는 이 절을 각자 구현한다. 이 절이 정본이고, 둘이 어긋나면 채점기 판정이 기준이다 `[DESIGN]`.

### B3-3. A등급 주장 조건

아래 조건을 **모두** 채울 때만 대표 지표 값을 A등급 대표 숫자로 내세운다(사용자 결정).

| # | 조건 |
|---|---|
| 1 | `RB-1` 동결 완료(B6의 동결 조건 3개 충족) |
| 2 | 채점 전 봉인 해시 재대조 일치 |
| 3 | 채점기 사전 검증 통과(합성 oracle과 손계산 예제 재현) |
| 4 | `real_sealed` 봉인 실행 완료: 예정된 모든 (사례 × 모드) 실행이 최종 `execution_status`를 가진다 |
| 5 | 모드별(`freeform`, `full` 각각) 유효 보고서(`execution_status=COMPLETED`) 최소 20건(조정값) |
| 6 | 두 모드가 같은 사례 집합에서 실행됐다 |
| 7 | 한 번만 채점했다(재채점 없음) |

- **조건을 채우면**: 모드별 보고서 단위 오류율을 Wilson 95% 구간, 표본 수, 실행 실패 수와 함께 등급 A로 표기한다. `full`이 "낮다"고 쓰려면 B4의 차이 주장 규칙도 통과해야 한다. 통과하지 못하면 "이번 표본에서 차이를 확인하지 못했다"고 쓴다.
- **조건을 못 채우면**(표본 부족이나 실행 미완료): A등급 대표 주장을 **보류**한다. 실제 건수, 신뢰구간, 미완료 사실과 함께 참고치로만 보고한다.
  - 개발용 결과(`dev20`, `real_dev`)를 대표로 올리지 않는다.
  - `real_dev` 경보를 빌려 표본을 채우지 않는다.
  - 이때 `3a`는 3점이 상한이다(A5).
- **`holdout40`의 미완료**: 실행이 다 끝나지 않으면 끝난 부분만 실패 집계와 함께 보고한다. 분모는 40 그대로 두고 미실행 건은 실패로 센다. 미완료 부분에 대해서는 어떤 주장도 하지 않는다.

### B4. 보조 지표

대상은 `holdout40`의 비교군 `checklist`·`agent`·`full`이고 등급은 C다. 같은 지표를 `dev20`에서 계산한 값은 등급 D다. 구 개발계획 §8.3의 지표를 유지한다.

| 지표 | 정의 |
|---|---|
| 근거 충족 처리정확도 | (예상 상태 일치 AND 필수근거 AND 수치/단위 AND 출처/버전 AND 정상 실행) 사례 ÷ 40 |
| 불필요 보류율 | 예상 상태가 보류가 아닌 사례 중 최종 `HOLD`인 사례 ÷ 예상 상태가 보류가 아닌 사례 |
| 잘못된 모니터링률 | 예상 상태가 `MAINTAIN`이나 `HOLD`인 사례 중 최종 `MONITOR`인 사례 ÷ 예상 상태가 `MAINTAIN`이나 `HOLD`인 사례 |
| 상태별 혼동행렬 | 행은 정답 사례 상태(`MAINTAIN`, `MONITOR`, `HOLD`), 열은 최종 사례 상태와 실행 실패(`review_status_final`이 `null`) |
| 실행 실패 수 ÷ 40 | 실행 상태별(`FAILED`, `TIMEOUT`, `INVALID`, `BUDGET_EXCEEDED`)과 미실행 |
| 비용 | 도구 시도(`tool_attempts`), 모델 요청(`model_requests`), 토큰(`tokens_in` + `tokens_out`), 시간(`wall_ms`)의 중앙값과 범위. `checklist`의 토큰은 0 |
| 모든 사례를 보류했을 때의 점수 | 무조건 보류하는 방식의 처리정확도. 기준 비교용 |
| 상태 변화 | 모델 원초안 → Critic 뒤 → 검증 뒤 상태의 복구·악화 건수 |
| 개선·악화 목록 | 비교군 사이에 같은 사례가 좋아지거나 나빠진 목록 |

- **예상 상태 일치** `[DESIGN]`: 사례 판정(`review_status_final`), 신호별 판정(`signal_status`), `unresolved_evidence`가 모두 정답표와 같을 때다. 사례 집계 규칙(`MAINTAIN > HOLD > MONITOR`, `MAINTAIN`과 `HOLD`가 섞이면 `MAINTAIN`에 `unresolved_evidence=true`)까지 맞아야 한다.
- **채점 필드의 주체** `[DESIGN]`: 결과 기록의 `required_evidence_ok`, `numeric_ok`, `provenance_ok`는 샌드박스 밖 채점기가 정답표로 채운다. 런타임이 쓴 값이 있으면 채점기 값이 우선한다.
- **정상 실행**: `execution_status=COMPLETED`. 실행 실패로 끝난 보류 화면은 기대 상태가 보류여도 성공이 아니다.
- **모든 사례를 보류했을 때의 점수** `[DESIGN]`: 발동한 신호는 모두 `HOLD`, 발동하지 않은 신호는 `NOT_TRIGGERED`로 둔 가상의 결과를 예상 상태 일치만으로 채점한다(근거 조건은 충족했다고 가정한 상한). 구 개발계획 §8.1 배분대로면 예상 상태가 `HOLD`인 사례가 최소 16건이라 이 점수는 40% 이상이 된다 `[추론]`.
- **상태 변화의 해석**: Critic 전후 변화만으로 전체 구조의 성능 향상을 추정하지 않는다. 같은 모델을 두 번 쓴 것을 정확성 보증으로 표현하지 않는다(구 개발계획 §8.3).
- **LLM의 추가 가치**: `full`과 `agent`가 `checklist`보다 개선도 비용 절감도 없으면 "이 범위에서 LLM 추가 가치 미확인"으로 보고한다(구 개발계획 §8.3).

#### 신뢰구간과 차이 주장

- **방법**(조정값): 비율마다 Wilson 95% 신뢰구간을 쓴다. x건 성공, n건 전체, z = 1.96일 때 다음과 같다.

```text
p = x / n
중심 = (p + z²/(2n)) / (1 + z²/n)
반폭 = z × √( p(1−p)/n + z²/(4n²) ) / (1 + z²/n)
구간 = [중심 − 반폭, 중심 + 반폭]
```

- **표본 크기의 감각**: 40건이면 50% 부근에서 반폭이 약 ±14.8pp다. 20건이면 약 ±20pp다 `[추론: 위 식으로 계산]`.
- **차이 주장 규칙** `[DESIGN, 조정값]`: 두 모드(또는 두 비교군)의 Wilson 95% 구간이 겹치면 차이를 주장하지 않는다. 점추정과 구간만 적고 "차이를 확인하지 못했다"고 쓴다. 작은 차이는 주장하지 않는다. 대표 지표와 보조 지표에 모두 쓴다.
- **짝 설계**: 대표 지표의 두 모드와 `holdout40`의 세 비교군은 같은 사례에서 돈다. 같은 사례의 짝 비교표(둘 다 오류 / 한쪽만 오류 / 둘 다 무오류)를 설명 자료로 함께 싣는다. 검정은 하지 않는다.
- 주장 단위 오류율의 구간은 참고로만 적는다(B3 "주 지표 사전 지정").

  - 금지 표현: 부정·위법·원산지 조작·개별 거래가격을 단정하는 표현, "정상 확정" 같은 문구. 목록은 채점기에 두고 `RB-1`과 함께 동결한다.
  - 필수 항목: 판정 상태의 한국어 표기(검토 유지·모니터링·자료 보류·미발동)와 보고서 계약의 필수 필드
- **검토 에이전트 표본 점검**: 모드별 무작위 5건(조정값)을 검토 에이전트가 읽고 자연스러움, 용어 설명, 단정 표현 여부를 적는다. 사람 검토는 필수가 아니다.
- **보고**: 참고 수치로만 보고한다. 등급을 주장하지 않고 대표·보조 지표와 합치지 않는다.

### B5. 실행 규칙

- **어디서 돌리나**: 채점 대상 실행은 OpenShell 샌드박스 안에서 같은 CLI(`tradesentry run-case`, `tradesentry evaluate`, 공통 옵션 `--snapshot`, `--policy`, `--mode`)로 직접 돌린다. NemoClaw 에이전트를 거치지 않는다. 봉인 묶음은 공식 채점 대상 실행 전용 샌드박스에서만 돌린다(B6).
- **어디서 채점하나**: 정답 대조 채점은 샌드박스 밖에서 `python -m eval.scorer --run <run_dir>`로 한다.
- **들이지 않는 것**: 정답표와 봉인 사례 목록은 샌드박스에도 개발 에이전트에게도 들이지 않는다. 봉인 입력은 공식 채점 대상 실행 때 전용 샌드박스에 읽기 전용으로만 넣는다.
- **동시성**: 1로 시작한다. 할당량과 실패율을 확인한 뒤에만 올리고, 모든 모드에 같게 적용한다. 결과 요약에 적는다.
- **순서**: (사례 × 모드) 실행 목록을 고정 난수로 섞어 교차 배치한다. 한 모드가 특정 시간대에 몰리지 않게 한다. seed는 `RB-1`과 함께 동결하고 기록한다.
- **분모**: 실패·미실행·timeout·invalid는 분모에 남긴다. 결과를 본 뒤 어려운 사례를 지우지 않는다.
- **기록**: 모든 실행은 실행 결과 기록 키 `run_id, case_id, dataset, mode, policy_version, rulebook_version, snapshot_id, grouping_version, code_version, review_status_final, signal_status, unresolved_evidence, execution_status, required_evidence_ok, numeric_ok, provenance_ok, tool_attempts, model_requests, tokens_in, tokens_out, wall_ms, critic_used, revision_used, errors`를 모두 남긴다.
- **재전송과 재실행의 구분**: 재전송은 한 실행 안에서 같은 모델 요청을 다시 보내는 것이다(B2의 5xx 규칙). 재실행은 실행 하나를 처음부터 다시 돌리는 것이다.
- **인프라 실패 재실행** `[DESIGN, 조정값]`:
  - `execution_status`가 `FAILED`이고 `errors`에 적힌 원인이 모델 제공자 쪽 오류(재전송 한도를 다 쓴 HTTP 5xx, 연결 실패)뿐인 실행만, 같은 설정으로 1회 다시 돌릴 수 있다.
  - 판단은 채점 전에 실행 기록만 보고 하고, 모든 모드에 같은 기준을 쓴다.
  - 원래 기록은 지우지 않는다. 재실행 건수를 모드별로 보고한다. 재실행도 실패하면 그 결과가 최종이다.
  - `TIMEOUT`, `INVALID`, `BUDGET_EXCEEDED`와 모델 출력 문제는 재실행하지 않는다.
- **같은 사례 반복 실행**(선택): 여력이 있으면 미리 고정한 공통 사례에서 모델 모드를 반복한다. 반복 결과는 독립 표본으로 세지 않는다. 일정이 밀리면 줄이는 순서의 두 번째 항목으로 줄인다.
- **시간 예산**(조정값):
  - `holdout40` 120회(40 × 3)의 보수적 순차 상한은 약 10시간이다.
  - `real_sealed`의 `freeform`/`full`은 표본 40건 기준 80회, 약 1~2시간이다.
  - 봉인 채점 시작 마감은 목표 2026-09-26(토) 14:00, 늦어도 2026-09-27(일) 06:00이다.
  - NIM의 간헐적 HTTP 500 `[사실: 사실 메모 §5]`에 대비한 재실행 여유 시간을 일정에 따로 둔다.
  - 늦어지면 끝난 만큼만 보고하고 미완료 사실을 적는다(B3-3).

### B6. 동결과 봉인

#### 동결 `RB-1`

- **시각**: 2026-09-26(토) 12:00 KST(조정값)
- **동결 조건**(셋 다 충족해야 한다):
  1. `policy_v1`(`configs/policy_v1.json`) 수치를 사용자가 승인했다.
  2. `g1`을 동결했거나, `g0` 대체를 선언했다. `g1`이 시한까지 동결되지 않으면 `g0`로 채점하고 제출서에 사실대로 적는다.
  3. 봉인 자료의 해시 목록(`eval/sealed_manifest.json`)을 커밋했다.
- **함께 동결하는 것**:
  - 이 룰북 본문
  - 산문 패턴 목록과 한국어 품질 금지 표현 목록(채점기 안)
  - 독립 채점기 코드(`eval/scorer/`)
  - 조정값: 유효 보고서 최소 20건, 표본 상한 40건, 분할 비율과 seed, 표본 추출 seed, 실행 순서 seed, 신뢰구간 방법(Wilson 95%)과 차이 주장 규칙, 재실행 규칙, 한도 수치
- **절차**: 오케스트레이터(작업을 배분·병합하는 주관 에이전트)가 조건 3개를 확인하고, 사용자가 룰북 동결을 확인하면 동결 커밋을 만든다. 이후 모든 결과 요약에 그 커밋을 적는다.
- **한 번만 채점**: 동결 뒤 `holdout40`과 `real_sealed`를 한 번만 채점한다.
- **동결 뒤 변경**: 새 버전(예: `RB-2`)과 사유로만 한다. 결과를 본 뒤 유리하게 고치지 않는다. 결과를 본 뒤 규칙이 바뀌면 `RB-1` 기준 결과를 사전 등록된 결과로 먼저 적고, 새 버전 결과는 그 옆에 사유와 함께 적는다 `[DESIGN]`.
- **동결이 늦어지면**: 늦어진 사실을 적는다. 봉인 채점 시작 마감(늦어도 2026-09-27(일) 06:00)을 넘기면 끝난 만큼만 보고한다.

#### 봉인 보관

- **봉인 대상**: `holdout40`의 입력과 정답표, `real_sealed`의 사례 목록과 채점 표본
- **보관 위치**: 저장소 밖 `~/.tradesentry/sealed/`. 환경변수 `TRADESENTRY_SEALED_DIR`로 바꿀 수 있다. 에이전트 작업 폴더에도 두지 않는다.
- **해시**: 파일별 sha256(파일 내용의 지문. 내용이 한 글자만 바뀌어도 달라진다) 목록만 PR로 커밋한다(`eval/sealed_manifest.json`). 원본 파일은 최종 채점이 끝난 뒤 커밋한다. 원본을 커밋할 위치는 계획 경로·명령 표에 아직 없다 `[미확인]`. 그때 표를 먼저 고친다.
- **지시**: 모델 트랙 에이전트와 Codex의 작업 지시에 봉인 폴더를 넣지 않고, 읽지 말라고 지시한다.

**생성 → 봉인 → 해시 등록 → 한 번 채점의 권한 분리 절차**:

1. **생성**: `holdout40` 생성 에이전트(격리된 Claude 보조 에이전트)는 시나리오 명세와 생성 규칙만 입력으로 받는다. 결과를 봉인 폴더에 **직접** 쓰고 저장소에는 쓰지 않는다. 생성 에이전트는 런타임 코드를 작성하지 않고, 그 대화 기록은 모델 트랙에 넘기지 않는다.
2. **봉인**: 생성 직후 파일별 sha256 목록을 만든다.
3. **해시 등록**: 해시 목록만 PR로 커밋한다.
4. **한 번 채점**: `RB-1` 동결 뒤 오케스트레이터가 평가 스킬 ②를 실행할 때만 봉인 **입력**을 샌드박스에 읽기 전용으로 넣는다.
   - 파일시스템 정책(정적 계층)은 샌드박스를 만들 때 고정된다 `[사실: 03 문서 §2.1-1]`. 그래서 봉인 입력은 **공식 채점 대상 실행 전용 샌드박스를 새로 만들어** 넣는다. 개발·시연용 샌드박스에는 넣지 않는다. 넣는 방식은 X1 뒤에 확정한다 `[미확인]`.
   - 정답표는 어떤 샌드박스에도 넣지 않는다. 샌드박스 밖 채점기만 읽는다.
5. **재대조**: 채점 전에 해시를 다시 대조한다. 일치하지 않으면 그 묶음을 무효로 하고 사용자에게 올린다.

`real_sealed`의 사례 목록과 표본도 같은 절차를 따른다. 목록을 만드는 주체와 방법은 `docs/rules/PARALLEL_DEV_RULES.md`의 실자료 분할 절차를 따른다.

**서로 다른 두 통제**:

- ① 샌드박스 파일시스템 정책이 저장소 안의 평가 정답 경로 읽기를 막는다. 파일시스템 정책은 허용 목록 방식이다. 나열한 경로(와 작업 폴더)만 허용하고 나머지는 거부한다 `[사실: 03 문서 §3.6]`. 그래서 이 통제는 정답 경로를 허용 목록이나 작업 폴더에 **넣지 않을 때만** 성립한다.
- ② 봉인 자료를 저장소 밖에 두어 격리한다. 공식 채점 대상 실행 때만 봉인 입력을 전용 샌드박스에 읽기 전용으로 넣고, 정답표는 넣지 않는다.
- ①이 ②를 보장한다고 쓰지 않는다.

**정직한 한계**(제출서에도 적는다):

- 봉인 폴더 위치는 문서에 적혀 있어 비밀이 아니다.
- 개발 에이전트는 같은 OS 사용자로 돌기 때문에 봉인 폴더 열람을 기술적으로 막지 못한다. 지시와 기록으로 관리한다.
- 기술적 차단은 런타임 샌드박스(OpenShell 정책)에만 해당한다. 해시는 변조를 드러낼 뿐 열람을 막지 않는다.
- `real_sealed`의 원자료 행은 공용 스냅샷 `kcs_202201_202412_v2` 안에 있어 누구나 읽을 수 있다. 봉인되는 것은 사례 목록과 채점 표본뿐이다. 그래서 `real_sealed`의 보호는 "그 시계열로 기준값·패턴을 조정하지 않는다"는 절차에 기댄다 `[추론]`.
- `holdout40`의 시나리오 명세(`eval/scenarios/SCENARIO_SPEC.md`)는 공개다. 시나리오 분류·배분·기대 처리는 누구나 안다. 봉인되는 것은 생성된 사례와 정답표다.

#### 경계 규칙(명세 §5 중 평가 관련)

| 상황 | 처리 |
|---|---|
| 평가 스킬 ②를 구현 전에 불렀다 | 사전 점검 단계에서 멈춘다. 없는 구성요소 목록(명령·파일·해시)을 보고하고 어떤 실행도 하지 않는다 |
| 동결 조건이 하나라도 빠졌다 | 봉인 자료 채점을 거부한다. `dev20`·`real_dev` 실행은 허용한다 |
| 자기채점 스킬 ①이 증거를 찾지 못한 지표 | 앵커 정의상 낮은 점수를 준다. 추정해서 올리지 않는다. 점수마다 근거 한 줄과 경로를 적고, 근거가 비면 무효로 표시한다(Part A 원칙 2·3) |
| NemoClaw 대체 경로가 발동했다 | 대체 경로(Brev → OpenShell만)와 제출서 표기 방식을 함께 적는다. 채점 대상 실행은 원래 NemoClaw를 거치지 않으므로 대표·보조 지표는 영향이 없다. `1a`·`1c`에 반영한다 |
| `g1`이 동결되지 않았다 | `g0`로 채점하고 제출서에 사실대로 적는다 |
| `real_sealed` 경보가 부족하거나 봉인 실행이 끝나지 않았다 | B3-3에 따라 A등급 대표 주장을 보류하고 참고치로만 보고한다 |
| 봉인 해시와 실제 파일이 다르다 | 그 묶음의 채점을 무효로 하고 사용자에게 올린다 |

### B7. 결과 보고 양식

평가 결과는 `artifacts/eval/<run_id>/`에 `results.jsonl`(실행 결과 기록), `claims.jsonl`(주장 채점 기록), `summary.md`(요약)로 남긴다. 여기서 `<run_id>`는 평가 묶음 실행의 식별자로 읽는다. `results.jsonl`의 각 행이 (사례 × 모드) 실행 1건이다 `[추론]`. 두 쓰임의 구분은 자료 계약을 따른다.

**등급 표기 규칙**:

- 숫자마다 "등급 A", "등급 C", "등급 D", "참고" 가운데 하나를 붙인다. A등급 주장을 보류한 대표 값에는 "A등급 주장 보류(참고치)"를 붙인다.
- 등급이 해당되지 않는 비용 측정값에는 측정 조건(자료 묶음·모드·동시성)을 붙인다.
- 아래 양식의 꺾쇠 괄호는 채울 자리다. 결과 숫자를 미리 적지 않는다.

````markdown
# 평가 결과 요약 — <평가 묶음 run_id>

## 0. 실행 조건
- 룰북: RB-1, 동결 커밋 <해시>, 동결 뒤 변경 <없음 또는 새 버전과 사유>
- snapshot_id <값>, policy_version <값>, grouping_version <g1 또는 g0와 사유>
- code_version <값>, 채점기 커밋 <해시>, 산문 패턴 목록 커밋 <해시>
- 실행 기간(KST) <시작> ~ <끝>, 동시성 <값>, 순서 seed <값>
- 봉인 해시 재대조 <일치 또는 불일치(그 묶음 무효)>
- 인프라 실패 재실행 <모드별 건수>

## 1. 대표 지표 — 실자료 사실 주장 오류율 (real_sealed)
- A등급 주장 조건(B3-3): <충족 또는 미충족과 사유>

| 모드 | 예정 실행 | COMPLETED | 실행 실패(상태별) | 보고서 단위 오류율(Wilson 95%) | 주장 단위 오류율(참고) | 보고서당 UNBACKED_PROSE(평균/중앙값/최대) | 등급 |
|---|---|---|---|---|---|---|---|
| freeform | <n> | <n> | <상태별 n> | <값> (<하한>~<상한>) | <값> | <값> | <등급 A 또는 A등급 주장 보류(참고치)> |
| full | <n> | <n> | <상태별 n> | <값> (<하한>~<상한>) | <값> | <값> | <같음> |
````

## 용어 설명

- **채점 규범(규범)**: `SCORING_GOLDEN_RULE.md`. 팀이 정한 아이디어·제출물 평가 기준. 대회 공식 배점이 아니다.
- **하드 게이트**: 하나라도 통과하지 못하면 채점하지 않는 필수 조건(규범 G1~G6).
- **앵커**: 0/1/3/5 점수마다 붙은 판정 기준 문장.
- **CAP / TIE**: 점수 상한 규칙 / 동점 처리 규칙.
- **판정 밴드**: 100점 환산 총점을 강함·경쟁권·약함·폐기로 나누는 구간.
- **냄새 목록**: 좋은 신호와 나쁜 신호를 빠르게 가려내는 규범 §7의 목록.
- **컴포넌트 삭제 시험**: 구성요소를 지웠을 때 어떤 측정값이 나빠지는지 답해 보는 점검.
- **숫자 등급(A~D)**: 숫자의 정답을 누가 만들었고 그 정답이 개선 과정에 노출됐는지로 매기는 신뢰도 등급.
- **자기채점**: 팀이 규범으로 자기 프로젝트를 채점하는 일.
- **채점 대상 실행 / 정답 대조 채점**: 샌드박스 안에서 보고서를 만드는 실행 / 샌드박스 밖에서 그 보고서를 정답과 비교하는 일.
- **기준선(baseline)**: 비교 기준이 되는 방식. 대표 지표에서는 `freeform` 모드.
- **모드(비교군)**: 같은 사례를 처리하는 방식. `checklist`, `agent`, `full`, `freeform`.
- **자료 묶음**: 평가에 쓰는 사례 묶음. `controlled_fixture_v0`, `dev20`, `holdout40`, `real_dev`, `real_sealed`.
- **스냅샷**: 한 시점에 수집해 동결한 원자료 묶음. 작업 기준은 `kcs_202201_202412_v2`.
- **시계열(품목×국가)**: 한 HS6 품목과 한 상대국의 월별 수입 기록.
- **전년동월**: 비교월 t와 그 1년 전 같은 달 t−12.
- **단가(U)**: 금액(USD) ÷ 순중량(kg).
- **점유율(s)**: 해당국 금액 ÷ 전체국가(`ALL`) 금액.
- **퍼센트포인트(pp)**: 두 비율의 차이를 나타내는 단위. 점유율 10%가 6%가 되면 −4pp다.
- **구성효과 분해**: 하위품목(HS10) 비중 변화 때문에 생긴 평균 단가 변화(mix_effect)와 품목 안 단가 변화(within_effect)를 나누는 계산.
- **typed claim**: 필드가 정해진 사실 주장 레코드. 채점의 기본 단위다.
- **산문 패턴**: 설명 문장에서 숫자·증감 표현을 기계적으로 잡는 정규식 목록.
- **결정적(deterministic)**: 같은 입력이면 늘 같은 결과가 나오는 성질.
- **독립 채점기**: 런타임 코드를 재사용하지 않고 따로 구현한 채점 프로그램(`eval/scorer/`).
- **검증기(validator)**: 실행 중에 보고서의 숫자·단위·근거·금지 문구를 검사하는 코드. `full`에서는 막고 `freeform`에서는 기록만 한다.
- **조사자 / Critic(검수자)**: 도구를 골라 근거 포함 초안을 쓰는 모델 역할 / 그 초안의 누락·반대 설명을 지적하는 별도 문맥의 모델 역할.
- **근거 충족 처리정확도**: 예상 상태, 필수 근거, 수치·단위, 출처·버전, 정상 실행을 모두 만족한 사례의 비율.
- **혼동행렬**: 정답 상태와 최종 상태를 행과 열로 놓고 건수를 센 표.
- **Wilson 신뢰구간**: 비율의 불확실성을 나타내는 구간 계산법. 표본이 작거나 비율이 0·1에 가까워도 비교적 안정적이다.
- **짝 설계**: 비교하는 방식들을 같은 사례에서 돌려 사례끼리 짝지어 보는 설계.
- **봉인**: 평가 자료를 저장소 밖에 두고 해시만 커밋해 개발 과정에 노출되지 않게 관리하는 일.
- **sha256 해시**: 파일 내용의 지문. 내용이 바뀌면 값이 달라져 변조를 드러낸다.
- **동결**: 규칙·수치를 고정하고 이후에는 새 버전과 사유로만 바꾸는 일. 룰북 동결 버전은 `RB-1`.
- **조정값**: 근거를 붙여 바꿀 수 있는 수치. 동결 뒤에는 새 버전으로만 바꾼다.
- **개선 과정 노출**: 정답이나 결과를 보면서 규칙·기준값을 고친 적이 있다는 뜻. 노출된 숫자는 대표로 쓰지 않는다.

- **OpenShell**: 에이전트를 격리해 실행하는 NVIDIA 샌드박스 런타임. YAML 정책으로 파일·네트워크·프로세스를 통제하고 허용·차단을 감사 로그로 남긴다.
- **정적 계층 / 동적 계층**: OpenShell 정책에서 샌드박스 생성 때 고정되는 부분(파일시스템·landlock·process) / 실행 중 다시 불러올 수 있는 부분(network).
