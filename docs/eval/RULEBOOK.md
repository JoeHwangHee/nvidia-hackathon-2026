# TradeSentry 평가 룰북 (RULEBOOK)

이 문서는 TradeSentry의 평가 규칙을 **구현과 측정 전에** 고정해 두는 룰북이다. Part A는 팀 채점 규범으로 프로젝트를 자기채점하는 규칙이고, Part B는 TradeSentry 성능 평가 규칙이다. 결과를 본 뒤 규칙을 유리하게 바꾸지 않으려고 먼저 쓴다. 규범 §6 "개발 순서 경고"가 평가 규칙과 기준선 측정을 기능보다 먼저 만들라고 한 데 따른 것이다.

TradeSentry(관세청 수입통계에서 kg당 단가와 상대국 점유율이 전년 같은 달보다 급변한 경우를 경보로 잡고, Nemotron(NVIDIA의 언어 모델 제품군) 조사자와 검수자(Critic, 조사자의 초안을 별도 문맥에서 검토하는 모델 역할)가 제한된 조회 도구로 반증을 시도해 담당자의 다음 업무를 제시하는 에이전트 시스템)는 부정·위법·원산지 조작을 판정하지 않는다. 이 룰북의 어떤 지표도 그런 판정의 정확도를 재지 않는다.

- **seed**: 난수 생성기의 시작값. 같은 seed면 같은 분할·표본·순서가 다시 나온다.
- **Wilson 신뢰구간**: 비율의 불확실성을 나타내는 구간 계산법(B4).
- **McNemar 검정**: 같은 사례에서 두 방식의 결과가 엇갈린 쌍만 세어 차이를 보는 짝 검정(B4의 보조 분석).
- **`g0` / `g1`**: 실자료 사례의 상대국 비교 대상 집합. `g0`는 품목(HS6)마다 대상국을 뺀 나머지 15개국에서 2023년 연간 수입금액 상위 5개국(k=5, 조정값)이다(해석은 2026-09-24(목) 사용자 확인, 자료 계약 §2.3.6·로드맵 §6.1). `g1`은 BACI(국가 간 교역 연간 자료) 2023년 HS85 수출 바구니의 코사인 유사도(두 벡터가 얼마나 닮았는지 나타내는 값)로 16개국 안에서 고른 상위 5개국(대상국 제외)이다. `g1`은 늘 5개국이고, `g0`도 늘 5개국이다.
- **탐지 임계값 / 기준월 값**: 경보가 발동하는 기준(예: 단가 변화율 절댓값 30% 이상, 조정값) / 비교월 t의 1년 전인 기준월 t−12의 값. 이 문서는 두 뜻을 섞어 "기준값"이라고 쓰지 않는다.

## Part A. 프로젝트 자기채점

Part A는 규범의 §2~§4와 §7을 TradeSentry에서 **무엇이 있으면 몇 점인가**로 풀어 쓴다. 이 Part에 나오는 G1~G6, 지표 코드, CAP·TIE 규칙은 모두 규범의 ID다.

**`[DESIGN]` 경고.** 규범의 가중치(35/25/30/10), 하드 게이트(통과하지 못하면 채점하지 않는 필수 조건), 0/1/3/5 앵커(점수마다 붙은 판정 기준 문장)는 팀이 만든 설계 규칙이다. 대회가 공개한 것은 채점 항목 4개와 그 순서뿐이다 `[사실: 규범 §1, 대회 조사 §5]`. 자기채점 점수를 대회 점수처럼 제출서에 쓰지 않는다.

### 자기채점 회차와 결과 위치

- 회차: 2026-09-25(금) MVP 시험 뒤 1회, 2026-09-27(일) 결과 정리 때 1회, 2026-09-28(월) 제출 전 최종 1회 `[DESIGN: 로드맵]`
- 결과 파일: `artifacts/scorecard/scorecard-{시각}/scorecard-{시각}.md`(양식은 A3 끝)
- 실행: 평가 스킬 ① `skills/tradesentry-scorecard/SKILL.md`

### 적용 원칙

1. 순서는 규범 §6을 따른다. 한 문장 가설 → 하드 게이트(A1) → 채점 지표 20개(A2) → `2e` 표시 → 보정 규칙 → 총점과 판정 밴드(A3) → 가장 낮은 축 2개와 보강 가능성.
2. **증거가 점수를 정한다.** 증거를 찾지 못한 지표는 앵커 정의대로 낮은 점수를 준다. 추정해서 올리지 않는다.
3. **판정마다 근거 한 줄과 증거 경로(또는 명령)를 적는다.** 근거 한 줄이 비면 그 판정은 무효다. 무효 판정은 지표면 `0(무효)`, 게이트면 `FAIL(무효)`로 표기하고 그 값으로 계산한다 `[DESIGN]`.
   - "증거 없음"은 무효와 다르다. 증거를 찾지 못했으면 증거 칸에 찾아본 경로·명령을 적고, 근거 줄에 "증거 없음"이라고 쓴 뒤 앵커 정의대로 낮은 점수를 준다. 그래야 채점을 빠뜨린 것(무효)과 찾아봤지만 없었던 것(낮은 점수)이 구분된다.
4. 점수는 0/1/3/5만 쓴다. 2와 4는 쓰지 않는다. `4d`는 규범에 1점 앵커가 없어서 0/3/5만 쓴다.
5. 앵커 문언이 두 가지로 읽히면 A2 주석과 부록에 적은 해석을 따른다. 거기에도 없으면 낮은 점수를 주는 해석을 쓰고, 다른 해석은 근거 줄에 함께 적는다 `[DESIGN]`.
6. 증거 경로는 계획 경로·명령 표(`docs/rules/DATA_CONTRACT_V1.md`)의 예정 위치만 쓴다. `outputs/`는 커밋하지 않는다. 그래서 심사위원이 볼 수 있어야 하는 증거는 요약을 `artifacts/eval/score-{시각}/scorer_summary-{시각}.md`에 옮겨 둔다 `[추론]`. 옮기는 주체는 채점기다. 채점기가 실행 조건 입력 파일(채점기가 모르는 실행 조건을 채점기에 넘기는 파일)에서 옮긴다(B7).

### 적용의 한계 `[DESIGN]`

- 규범 §8이 밝힌 한계를 그대로 안고 간다.
  - 가중치는 공식 발표가 아니다.
  - 게이트의 문턱(3종 이상 등)은 임의로 정한 값이다.
  - 앵커 문언은 채점 재현성을 위해 팀이 쓴 것이라 심사위원이 같은 기준을 쓴다는 보장이 없다.
  - 예선에만 적용한다.
- 같은 팀이 자기 프로젝트를 채점하므로 점수가 후해질 위험이 있다. 원칙 2·3·5로 줄이지만 없애지는 못한다 `[추론]`.
- 규범 §2는 게이트가 하나라도 FAIL이면 아이디어를 폐기하고 채점하지 말라고 한다. 아이디어는 이미 정해졌으므로, 개발 중 자기채점에서는 FAIL을 "제출 전에 반드시 풀어야 할 결함"으로 읽는다 `[추론]`. 채점하지 않는다는 규칙은 그대로 지킨다. FAIL이 하나라도 있는 회차는 게이트 표와 해소 조건만 남기고 총점·밴드를 내지 않는다.

**판정 서식**(규범 §2 서식에 증거 칸을 더했다):

```text
| 게이트  | 판정        | 근거 한 줄 | 증거 경로·명령 |
|---------|-------------|-----------|----------------|
| 규범 G1 | PASS 또는 FAIL | <한 줄>  | <경로 또는 명령> |
```

- 판정 값은 PASS와 FAIL 두 가지뿐이다. 근거 한 줄이 비면 무효이고, `FAIL(무효)`로 표기해 FAIL로 계산한다. 증거를 찾지 못한 FAIL은 증거 칸에 찾아본 경로·명령을 적는다(적용 원칙 3).
- 서식 예시(판정 결과가 아니다): `| 규범 G1 | PASS | 기준선 = freeform 보고서, 지표 = 사실 주장 오류율(real_dev 첫 값, 등급 D) | artifacts/eval/score-{시각}/scorer_summary-{시각}.md |`

### A5. 숫자 등급

규범 §3 숫자 4등급 `[DESIGN]`:

| 등급 | 규범 정의 | `3a` 상한 |
|---|---|---|
| A | 외부 공개 벤치마크 또는 실제 라벨 | 5 |
| B | frozen held-out 또는 oracle optimum(한 번만 평가하고 개선 루프에 다시 쓰지 않음) | 5 |
| C | 팀이 독립적으로 만든 결정적 fixture(생성 규칙과 탐지 규칙이 분리됨) | 3 |
| D | 우리가 생성하고 우리가 채점한 합성 자료(생성 규칙을 탐지기가 되찾는 구조) | 1 |

- 등급은 두 질문으로만 정한다. **누가 정답을 만들었나**, 그리고 **그 정답이 개선 과정에 노출됐나**(규범 §3 `3a` 보강).
- 규범은 대표 숫자에 등급 A 또는 B가 하나 이상 있어야 한다고 한다. TradeSentry의 대표 숫자는 `real_sealed`에서만 나온다.
- 합성 자료(`controlled_fixture_v0`, `dev20`, `holdout40`)에서 나온 숫자의 등급은 C 이하다.
- 합성 시연 사례의 이름 A/B/C(A 구성변화, B 잔존변화, C 자료누락)는 숫자 등급과 다른 것이다.

| 숫자 | 자료 묶음 | 정답을 만든 쪽 | 개선 과정 노출 | 등급 |
|---|---|---|---|---|
| 실자료 사실 주장 오류율(대표 지표) | `real_sealed` | 공식 통계 원본(관세청 API 스냅샷의 원본 행). 팀이 만든 정답이 아니다 | 없음. 봉인하고 `RB-1` 동결 뒤 한 번 채점한다 | A. 단, B3-3 조건을 채울 때만 A등급으로 주장한다 |
| 근거 충족 처리정확도 등 B4 지표(보조 지표) | `holdout40` | 격리된 Claude 보조 에이전트가 시나리오 명세로 생성하고 독립 정답표를 둔다 | 없음. 봉인하고 한 번 채점한다 | C |
| 대표 지표와 같은 지표의 개발 값 | `real_dev` | 공식 통계 원본 | 있음. 탐지 임계값 조정, 산문 패턴 보강, 조사 지침(모델 프롬프트)·조사 흐름 조정에 쓴다(B1) | D |
| 보조 지표와 같은 지표의 개발 값 | `dev20` | 팀(D 트랙) 생성 | 있음 | D |
| 시험 통과 여부 | `controlled_fixture_v0`, 합성 oracle `eval/dev/oracle_ABC.json` | 팀 설계 | 있음 | 성능 숫자로 보고하지 않는다 |
| 스킬 호출 성공률 | 시연 입력(합성 사례 A/B/C와 `real_dev` 몇 건) | 팀 선정 | 있음 | D(참고). 정확도 지표가 아니다 |
| 한국어 품질 | 모든 보고서 | 팀이 쓴 자동 검사 규칙 | 해당 없음 | 참고. 등급을 주장하지 않는다 |
| 비용(도구 시도·토큰·시간) | 각 묶음 | 정답이 없는 측정값 | 해당 없음 | 등급 대신 측정 조건(묶음·모드·동시성)을 함께 적는다 |
| OpenShell 위반 시험 | 팀이 만든 시험 입력 | 해당 없음 | 해당 없음 | 성능 숫자가 아닌 보안 증거다. 시험한 행동에 대한 증거일 뿐이다 `[사실: 03 문서 §6.6]` |

- `holdout40`은 봉인과 한 번 채점이라는 점에서 규범 B의 조건을 갖춘다. 그러나 정답이 팀이 설계한 합성 규칙에서 나오므로 C로 둔다.
- `real_dev`는 합성이 아니어서 규범 D의 문언과 다르다. 그래도 개선 과정에 노출돼 대표로 쓸 수 없다는 점에서 D로 둔다.

## Part B. TradeSentry 성능 평가

- **증명할 한 문장 가설(대표 지표)**: "Nemotron이 숫자를 직접 쓴 조사 보고서보다, 검증된 값만 틀에 채우고 검증기로 막는 TradeSentry 보고서가 실제 관세청 자료 경보에서 사실 주장 오류율이 낮다."
- **기준선(규범 G1 한 문장)**: 같은 자료·도구·예산으로 Nemotron이 사실 주장의 값을 직접 쓰는 보고서(`freeform` 모드).
- **판정 상태의 채점 범위** `[DESIGN]`: 실자료에는 판정 상태의 정답이 없다(구 개발계획 §8.1). 그래서 실자료 평가는 사실 주장만 채점하고, 판정 상태(`MAINTAIN` 검토 유지 / `MONITOR` 모니터링 / `HOLD` 자료 보류)의 옳고 그름은 채점하지 않는다. 판정 상태의 정확도는 합성 `holdout40`(B4)에서만 잰다.
- 모든 평가는 채점 대상 실행(샌드박스 안)과 정답 대조 채점(샌드박스 밖)을 나눠서 한다(0.4).

### B2. 비교 방식

| 모드 | 동작 | 숫자를 채우는 방식 | 검증기 |
|---|---|---|---|
| `checklist` | 고정 체크리스트. 모델 없음. 비교조건 → 이력 → 필요한 하위·비교국 조회를 고정 순서로 하고 정책으로 결과를 낸다. 비교 불가면 조기 종료 | 검증된 metric에서 틀로 채움 | 막음 |
| `agent` | Critic 없는 Nemotron. 조사자가 도구를 고르고 근거를 보고한다. 코드 검증 오류에 대해 같은 1회 수정 기회를 받는다 | 검증된 metric에서 틀로 채움 | 막음 |
| `full` | 전체 TradeSentry. 조사자 + 별도 문맥 Critic + 코드 검증 + 수정 1회 | 검증된 metric에서 틀로 채움 | 막음 |
| `freeform` | 대표 지표의 기준선. `full`과 **처리만 다르고 나머지는 같다** | typed claim의 값을 모델이 직접 쓴다(틀 채우기 없음) | 기록 전용. 막지 않고 막았을 것만 `validator_findings`에 적는다 |

- **`freeform`과 `full`이 같은 것**: 조사자, Critic, 수정 1회, 스키마 검사, 도구, 예산, 한도, 자료. 그래서 두 모드의 차이에는 "검증된 값만 채우고 검증기로 막는 처리"의 효과만 남는다.
- **스키마 검사의 범위**: 두 모드가 함께 쓰는 스키마 검사는 형식과 자료형만 본다. 값의 자릿수는 강제하지 않는다(자료 계약). 자릿수는 정답 대조 채점(B3-1)에서만 다룬다. 발동 신호별 주장 요건(B3)은 스키마 요건이므로 두 모드에 똑같이 적용된다.
- **모든 모드에 같은 조건** `[DESIGN]`:
  - 자료·스냅샷, 도구 5개(`check_comparability`, `get_history`, `compare_partners`, `decompose_hs`, `verify_evidence`)와 공통 출력 봉투, `policy_v1`, `grouping_version`, 모델 ID와 설정, 샌드박스 정책, 동시성
  - 한도(조정값): 도구 호출 시도 `tool_attempts ≤ 8`(기본 경로 ≤5, 재조회 ≤2, 최종 검증 1), 재조사 1회(그 안의 조회 ≤2), 모델 요청 10회(재전송 제외, 2026-09-25(금) 18:05 사용자 결정), 사례당 wall time 300초, 누적 토큰 128,000(2026-09-25(금) 사용자 결정 4). 먼저 닿는 한도가 실행을 멈춘다.
  - 재시도: provider 자동 재시도는 끈다. HTTP 5xx(서버 오류)와 HTTP 429(호출 한도 초과) 명시 재전송만 요청당 최대 3회, 대기 5·10·20초의 지수 대기(조정값)로 한다. 응답에 `Retry-After`(다시 시도할 때까지 기다릴 시간을 알려 주는 응답 헤더)가 있으면 대기는 max(지수 대기, min(`Retry-After`, 60초))이고 횟수는 그대로다. trace `model_error`에 `retry_after_ms`와 허용 목록의 응답 헤더를 남긴다(2026-09-25(금) 22:22 사용자 결정 ④, 결정 기록 `docs/tracking/decisions/20260925-2225-user-decision-code-boundaries.md`. 세부는 `docs/plan/DEV_PLAN.md` §6.6·§6.7). 대기가 사례 deadline을 넘으면 `DEADLINE`이다. 다른 4xx는 재전송하지 않는다(2026-09-25(금) 15:52 사용자 결정, 결정 기록 `docs/tracking/decisions/20260925-1552-user-decision-429-retry.md`). 재전송은 모델 요청 한도 10회와 `model_requests`에 세지 않고, 요청당 3회와 사례당 wall time 300초로만 묶는다. 재전송은 실행 추적(trace)의 `model_error` 사건에 남는다(2026-09-25(금) 18:05 사용자 결정, 결정 기록 `docs/tracking/decisions/20260925-1805-user-decision-retry-budget.md`).
  - Critic의 비용·토큰도 같은 예산 안에 든다. 모델이 없는 `checklist`의 토큰은 0으로 표시한다.

    - 규칙 참고값과 필수 조회: 모델 모드(`agent`·`full`·`freeform`)의 조사자와 Critic은, 코드가 공개 판정 규칙(판정 정책 P3)을 그 초안을 쓸 때까지 받은 근거에 적용한 신호별 판정을 규칙 참고값으로 받는다(수정 단계에서 새 조회 결과를 받으면 다시 계산한다). 지침은 참고값을 따르게 하고, 규칙이 보지 않는 도구 결과 속 사실이 있을 때만 narrative에 반대 근거를 적고 벗어나게 한다. 코드는 모델의 판정을 덮어쓰지 않는다. 필수 도구(발동 신호가 있으면 `compare_partners`, 단가 신호가 발동했으면 `decompose_hs`)의 결과가 없고 그 단계의 도구 몫이 남은 차례에는 `tool_choice: "required"`와 빠진 도구 이름을 적은 알림을 싣는다(부를 도구를 API로 지정하지는 않는다). Critic 뒤(agent는 첫 검증 뒤)에도 필수 결과가 없으면 코드 지적을 붙여 같은 수정 1회로 보낸다. 문구·시점은 세 모델 모드에 글자까지 같다.
  - 조사 흐름 수정 두 가지도 모든 모델 모드에 같은 규칙이다 `[DESIGN: 2026-09-25(금) 사용자 결정, 결정 기록 `docs/tracking/decisions/20260925-1417-user-decision-real-dev-tuning.md` ③]`. (가) 검수자의 재조회 요청 가운데 그 사례에서 발동하지 않은 신호에만 쓰는 도구 요청은 코드가 버리고 trace에 남긴다. (나) 수정 단계를 연 원인이 검수자의 수정 요구뿐이고, 수정 전 초안이 수정 전 검사(스키마 검사, `freeform`이 아니면 검증기까지)를 통과했는데 고친 초안이 최종 검사에서 막히면, 수정 전 초안의 보고서를 최종 보고서로 둔다. 도구·모델 예산은 늘리지 않고, 버린 수정본은 trace에 남긴다. 세부는 `docs/plan/DEV_PLAN.md` §6.7이다.
  - 필수 근거 주장 덧붙이기도 모든 모드(`checklist`·`agent`·`full`·`freeform`)에 같은 규칙이다 `[DESIGN: 2026-09-25(금) 18:09 사용자 결정, 결정 기록 `docs/tracking/decisions/20260925-1809-user-decision-evidence-claims.md`]`. 보고서를 만들 때(초안·검증·최종 모두) 코드가, 신호별 판정에 필요한 필수 근거 코드(B3-4)마다 그 근거를 보여 주는 주장이 없으면 이미 받은 근거의 검증된 지표·자료 상태에서 골라 덧붙인다(기준은 시나리오 명세 `eval/scenarios/SCENARIO_SPEC.md` §5.3 판정 조건표). 모델(또는 `checklist` 규칙)이 쓴 판정·주장·설명·가설은 바꾸지 않고, 도구를 새로 부르지 않으며, 덧붙인 주장은 trace에 남긴다. 세부는 `docs/plan/DEV_PLAN.md` §6.7이다.

(3) 모델 모드의 코드 지적(필수 도구 빠짐)은 초안 판정과 규칙 참고값이 둘 다 `HOLD`인 신호에는 내지 않는다(도구별 규칙과 참고값이 없을 때의 처리는 `docs/plan/DEV_PLAN.md` §6.7). 판정 정책·검증기의 판정 규칙은 바뀌지 않는다.

### B3. 대표 지표

**실자료 사실 주장 오류율.** `real_sealed` 경보 표본의 모든 사례에서 `freeform`과 `full`의 최종 보고서에 담긴 **모든 사실 주장**을 채점한다. 설명 문장 속 주장도 포함한다.

**채점 범위**:

- ① typed claim(정해진 필드를 가진 사실 주장 레코드)의 모든 필드: 숫자·단위·증감 방향·기간·국가·품목·지표·근거 ID. 규칙은 B3-1이다.
- ② 설명 문장 속 숫자·증감 표현. 결정적 패턴 목록으로 잡는다. 이 목록은 `RB-1`과 함께 동결하고, 누락 사례는 `real_dev`에서만 보강한다. 규칙은 B3-2다.
- 숫자·증감이 없는 정성 서술(가설·해석)의 의미 정확성은 대표 지표의 **범위 밖**이다. 숫자·증감이 없는 극값·순위 말(`최고`·`최저` 등)도 여기에 들며, 건수만 참고로 보고한다(B3-2 PT-7). 제출서에도 그렇게 밝힌다.
- 사람 판정자도 AI 채점자도 두지 않는다. 공식 통계 원본(스냅샷 원본 행)과 결정적으로 대조한다.

**판정 결과 집합**:

| 결과 | 뜻 | 붙는 채점 단위 |
|---|---|---|
| `CORRECT` | typed claim: 대상·단위·방향·값·근거가 모두 맞다. 산문 표현: 같은 보고서의 typed claim으로 뒷받침된다 | claim, prose |
| `WRONG_VALUE` | 값이 기대값과 다르다(B3-1 "값 비교"). 계산할 수 없는 대상에 값을 적었거나, 계산할 수 있는 대상을 계산 불가로 적었거나, 자료 상태가 기대 관측 상태와 다른 경우도 포함한다 | claim |
| `WRONG_DIRECTION` | 증감 방향이 다르다 | claim |
| `WRONG_UNIT` | 단위가 틀렸거나 지표와 맞지 않는다 | claim |
| `WRONG_REFERENT` | 기간·국가·품목·지표가 가리키는 대상이 없거나 다르다 | claim |
| `UNSUPPORTED` | 근거 ID가 없거나, 풀리지 않거나, 주장을 뒷받침하지 않는다 | claim |
| `UNBACKED_PROSE` | 설명 문장 속 숫자·증감 표현이 같은 보고서의 typed claim으로 뒷받침되지 않는다 | prose |

- 채점 단위의 출처는 주장 채점 기록의 `source` 값으로 구분한다. `claim`은 typed claim, `prose`는 산문 패턴으로 잡힌 표현이다.
- 뒷받침된 산문 표현의 참·거짓은 그것을 뒷받침한 typed claim의 결과로 판정한다. 같은 사실을 두 번 세지 않는다.

**채점 절차(정답 대조 채점, 샌드박스 밖)**:

0. 사전 조건
   - 채점기 검증: `eval/dev/oracle_ABC.json`의 합성 사례 A/B/C 기대값과 손계산 예제를 재현하는 시험이 `tests/`에서 통과한다.
   - 스냅샷 검증: `tradesentry snapshot-verify --snapshot kcs_202201_202412_v2`
   - 스냅샷 정규화 해시 대조: 자료 계약이 정한 스냅샷 정규화 해시(`normalized_sha256`)가 기록된 값과 같은지 본다. 같아야 rowid로 된 근거 ID(`ev:<snapshot_id>:<table>:<rowid>`)가 결정적으로 풀린다. 다르면 근거 ID를 믿을 수 없으므로 채점을 멈추고 사용자에게 올린다 `[DESIGN]`.
   - 봉인 묶음이면 해시 재대조(B6).
1. 실행 기록을 읽는다. 실행 결과 기록 키와 보고서 객체 키는 `docs/rules/DATA_CONTRACT_V1.md`를 따른다.
2. 보고서마다 채점 단위를 뽑는다. `claims`의 typed claim 각각(`source`=`claim`)과, 자유 문장 필드에서 산문 패턴에 잡힌 표현 각각(`source`=`prose`)이다.
3. 기대값을 스냅샷 원본 행에서 **독립 계산**한다. 도구 출력 봉투나 런타임 metric 값을 정답으로 쓰지 않는다. 어느 원본 행으로 계산하는지는 자료 계약의 원천 규칙을 따른다(B3-1 "기대값의 원본 행").
4. B3-1과 B3-2로 결과를 하나씩 붙인다.
5. 채점 단위마다 `outputs/score-{시각}/scorer_claims-{시각}.jsonl`에 기록한다. 키는 `run_id, report_id, claim_id, source, outcome, expected_value, reported_value, unit_expected, unit_reported, tolerance, referent_resolved, evidence_ok, note`다. 요약은 `outputs/score-{시각}/scorer_summary-{시각}.md`(B7)에 쓴다.
6. 같은 입력이면 같은 결과가 나온다. 채점기는 모델도 네트워크도 부르지 않는다.

**오류율 정의**:

- **주장 단위 오류율** = `CORRECT`가 아닌 typed claim ÷ 전체 typed claim. `source`=`claim`만 센다. 유효한 최종 보고서의 주장만 분모에 들어간다.
- **보고서 단위 오류율** = 오류 claim이나 `UNBACKED_PROSE`가 1개 이상인 보고서 ÷ 전체 보고서(명세 §3.6 산식). 전체 보고서는 예정된 모든 실행(사례 × 모드)이다. `COMPLETED`가 아닌 실행과 미실행 사례는 보고서 단위 실패로 분자에도 들어간다. 유효한 최종 보고서가 없는 실행은 분모에 남는다.
- **`UNBACKED_PROSE` 건수**: 보고서당 건수를 모드별 평균·중앙값·최대로 따로 보고한다.
- **발동 신호별 주장 요건**(자료 계약의 스키마 요건): 발동한 신호마다 그 신호 계열의 claim이 1개 이상 있어야 한다. 수정 1회 뒤에도 없으면 그 실행은 `INVALID`로 끝나고 보고서 단위 실패로 분모에 남는다. 어느 지표가 어느 신호 계열에 속하는지와, 요건에 세는 claim의 대상 규칙은 자료 계약 `docs/rules/DATA_CONTRACT_V1.md` §9.4가 정한다. 그 규칙의 요지는 사례의 `hs6`(HS10 하위 metric은 부모 `hs6`)·대상국·`period`를 가리키는 claim을 세고 비교국 claim은 세지 않는 것이다. 예외로 `ALL` 분모 관측을 말하는 `data_status` 주장은 `partner`가 `ALL`이어도 세고, 값이 `OBSERVED`인 `data_status` 주장은 세지 않는다. 정본은 계약 §9.4다. 이 `INVALID`는 다른 실행 실패와 똑같이 센다. 룰북은 이와 별도로 보고서 단위 오류 항목을 분자에 더하지 않는다. 이 이유로 생긴 `INVALID` 건수는 B7에 따로 보고한다.

**주 지표 사전 지정** `[DESIGN]`: 모드 사이의 차이 주장은 **보고서 단위 오류율로만** 한다. 주장 단위 오류율은 함께 보고하는 설명 지표다. 결과를 보기 전에 정해 둔다. 이유는 둘이다.

1. 주장 단위의 분모에는 유효 보고서의 주장만 들어간다. `full`에서 검증기가 막아 `INVALID`가 된 보고서의 오류 주장은 이 분모에서 빠진다. 보고서 단위에서는 그 실행이 실패로 남는다.
2. 한 보고서 안의 주장끼리는 서로 독립이 아니다. 그래서 주장 단위로 구한 신뢰구간은 실제보다 좁게 나온다.

- **검출력의 한계**: 1차 주장은 B4의 비겹침 규칙으로만 한다. 이 규칙으로 차이를 주장하려면 두 모드의 오류율이 n=40일 때 약 20~33pp, n=20일 때 약 35~45pp 이상 벌어져야 한다 `[추론: Wilson 식으로 계산]`. "차이를 확인하지 못했다"는 "차이가 없다"는 뜻이 아니다.
- **보조 분석**: 같은 사례끼리의 짝 분석(Newcombe 짝 차이 구간, McNemar 검정)을 보조 분석으로 사전 등록한다. 결과는 보고하지만 1차 주장 규칙은 바꾸지 않는다(B4).

**실패 처리**:

- `execution_status`가 `COMPLETED`가 아닌 실행(`FAILED`, `TIMEOUT`, `INVALID`, `BUDGET_EXCEEDED`)은 보고서 단위 실패로 분모에 남긴다. 상태별 건수를 모드별로 보고한다. 이런 실행의 `review_status_final`은 `null`이다.
- `freeform`은 검증기가 막지 않으므로 `INVALID`가 스키마 검사 실패(발동 신호별 주장 요건 포함)에서만 생긴다. `full`은 검증기 차단으로도 `INVALID`가 생긴다. 모드별 실패 수 차이를 결과와 함께 적는다.
- `full`의 검증기가 같은 규칙으로 산문을 막으므로 `full`의 `UNBACKED_PROSE`가 0에 가까운 것은 설계상 예상되는 결과다. 그 대가는 `INVALID`로 분모에 남는다. 그래서 가설의 핵심 증거는 필드 오류(①)와 보고서 단위 오류율이다 `[추론]`.
- 채점기가 claim을 해석하지 못하면 그 claim은 `WRONG_REFERENT`로 기록하고 `note`에 사유를 적는다 `[DESIGN]`.

**독립 채점기 요건**:

- 위치는 `eval/scorer/`, 실행은 `python -m eval.scorer --run <run_dir>`이다.
- 런타임 모듈(`src/tradesentry/`의 `metrics/` 등)을 import하지 않는 독립 구현이다(간접 import와 `eval/datagen/` 포함, 자료 계약 §10.3).
- 봉인 채점 전에 `eval/dev/oracle_ABC.json`과 손계산 예제로 먼저 검증한다.
- 샌드박스 밖에서 돈다. 정답표를 읽는 것은 채점기뿐이다.
- 결정적이다. 모델·네트워크를 부르지 않고, 사람·AI 판정을 섞지 않는다.
- 채점기 코드와 산문 패턴 목록은 `RB-1`과 함께 동결한다(B6).
- 실자료 묶음(`real_dev`·`real_sealed`)은 정답표가 없으므로 채점 결과 `scorer_results-{시각}.jsonl`의 `required_evidence_ok`를 `null`(판정하지 않음)로 둔다. 합성 묶음은 참·거짓 그대로다 `[DESIGN: 2026-09-25(금) 사용자 결정 7, 자료 계약 §8.1]`.

### B3-1. 필드별 채점 규칙

typed claim의 필드는 `claim_id, claim_type, hs6, partner, period, baseline_period, metric, value, unit, direction, evidence_ids, text`이고, `claim_type`은 `value | change | share | share_change | decomposition | comparison | data_status` 중 하나, `direction`은 `UP | DOWN | FLAT | NA` 중 하나다.

- **표시 자릿수의 정본**은 자료 계약 `docs/rules/DATA_CONTRACT_V1.md` §11 "단위와 정밀도"의 표다(`[DESIGN, 조정값]`). 그 표는 `RB-1`과 함께 동결한다(B6).
- 지표 이름, 단위 이름, 기간 형식, 근거 ID 규칙, 기대값의 원천 행 규칙도 자료 계약을 따른다.
- 이 절은 그 값들을 다시 정하지 않는다. 비교 규칙과 판정 규칙만 정한다.

| 필드 | 검사 | 틀리면 |
|---|---|---|
| `claim_type`, `hs6`, `partner`, `period`, `baseline_period`, `metric` | 스냅샷에 있는 대상인가. 지표 정의와 맞는가. 예: 전년동월 지표(r_U, d_s)는 기준월이 t−12여야 한다. `data_status` 주장은 이 검사 전에 수집 계획과 먼저 대조한다(아래) | `WRONG_REFERENT` |
| `unit` | 지표에 맞는 단위인가 | `WRONG_UNIT` |
| `direction` | 기대 변화의 부호와 같은가 | `WRONG_DIRECTION` |
| `value` | 기대값을 보고값이 보인 소수 자리수로 반올림하면 보고값과 같은가(아래 "값 비교") | `WRONG_VALUE` |
| `evidence_ids` | 근거 ID(`ev:<snapshot_id>:<table>:<rowid>`)가 있고, 풀리고, 기대값 계산에 필요한 원본 행 집합을 포함하는가. 동등한 행은 어느 것을 인용해도 된다. 총계 행은 근거가 될 수 없다. `data_status` 주장은 그 키의 상태 행을 인용해야 한다 | `UNSUPPORTED` |
| `claim_id` | 식별용. 채점하지 않는다 | — |
| `text` | 자유 문장이므로 B3-2로 검사한다 | `UNBACKED_PROSE` |

- **판정 순서** `[DESIGN]`: `data_status` 주장은 먼저 수집 계획과 대조한 뒤(아래 "`data_status` 주장") 상태 값과 근거를 검사한다. `data_status` 주장도 근거 검사를 한다. 그 밖의 주장은 대상 → 단위 → 방향 → 값 → 근거 순서로 보고 처음 걸린 결과를 붙인다. 모두 통과하면 `CORRECT`다. 나머지 오류는 `note`에 적고, 근거 검사 결과는 `evidence_ok`에 따로 남긴다. 순서는 결과 분포만 바꾸고 오류율은 바꾸지 않는다.
- **기대값의 원본 행**: 기대값을 어느 원본 행으로 계산하는지(상대국 금액·중량·단가의 기준 행, 점유율 분모, HS10 하위 행의 쓰임과 residual 계산, `ALL`의 중복 행 처리)는 자료 계약의 원천 규칙이 정한다. 채점기는 그 규칙을 런타임과 따로 구현한다. 아래 예시 1과 6이 그 규칙을 적용한 값이다.
- **값 비교** `[DESIGN, 조정값]`:
  - typed claim과 산문(B3-2)에 같은 규칙을 쓴다. 명세 §4.9의 "표시 자릿수 반올림 기준"을 구현한 것이다.
  - 기대값을 보고값이 보인 소수 자리수로 반올림해 보고값과 같으면 일치다.
  - 보인 자리수는 저장된 JSON 숫자 토큰을 십진수(Decimal)로 읽어 센다(끝자리 0 포함). 보고서 저장과 채점 모두 수의 원문 표기를 보존하고, 부동소수로 다시 직렬화하지 않는다. 20.30이 20.3으로 바뀌면 비교 자리가 달라져 판정이 바뀌기 때문이다.
  - 보고값이 계약 §11 자릿수보다 자리가 많으면 계약 자릿수에서 비교한다(두 값을 모두 계약 자릿수로 반올림한다).
  - 반올림 방식(사사오입)과 기대값 계산 방법(정수 USD·kg에서 십진 연산)은 계약 §11을 따른다. 딱 절반인 경우도 정수 V·Q에서 정확히 계산한 값으로 판정한다.
  - 스키마 검사는 자릿수를 강제하지 않는다(B2). 자릿수는 이 비교에서만 다룬다.
  - **민감도 보고(사전 등록)**: 보고값과 반올림 전 기대값의 차가 비교 자리 1단위 미만인 `WRONG_VALUE`를 "자릿수만 다른 `WRONG_VALUE`"로 모드별로 따로 센다(B7). 반올림·자리 처리 차이가 결과를 얼마나 움직이는지 보이기 위한 것이다. 1차 지표 계산은 바꾸지 않는다.
- **방향의 기대값**: 기대 변화가 0보다 크면 `UP`, 작으면 `DOWN`이다. 정확히 0이면 `FLAT`이다. 0은 아니지만 보고값이 보인 자리수로 반올림해 0이 되면 `FLAT`과 실제 부호 방향을 모두 맞다고 본다. 변화 주장이 아니면 `NA`다.
- **계산할 수 없는 대상**: 기준월 값이 0이거나 미상이면 변화율을 계산하지 않고, 중량이 0이면 단가를 계산하지 않는다. 이 문서에서 "변화율"은 단가 변화율 `r_U`만 뜻한다. 점유율 차 `d_s`(pp)는 기준월 점유율이 0이어도 계산된다. 기준월 점유율이 0인 달은 수입 0이 명시된 달(대상 쌍 합계 68개월 `[사실: 사실 메모 §3]`)과 승격된 달이다. HS10 구성효과 분해는 같은 HS10 집합, 양 시점 중량 유효, 부모 합계 일치일 때만 계산한다. 이런 대상의 기대값은 null이다. null 대상에 숫자를 적으면 `WRONG_VALUE`다. 계산 불가 사실은 `data_status` 주장으로 쓴다.
- **승격된 달** `[DESIGN]`: 동결된 `policy_v1`의 승격 규칙으로 `CONFIRMED_NO_TRADE`가 된 달은 금액·중량을 0으로 다룬다. 자료 계약 §3.4에 따라 그 행의 V·Q 칸은 null로 남고, 지표와 채점에서만 0으로 다룬다. 그런 달이 기준월이면 `r_U` 기대값은 null이고, `d_s`는 기준월 점유율 0으로 계산된다.
  - 명세 §3.3의 "빈 응답을 0으로 채우지 않는다"는 승격 전 상태(`UNRESOLVED_ZERO`)에 적용된다. 승격은 사용자가 승인한 `policy_v1` 규칙으로만 일어난다.
- **`data_status` 주장**: 기대 관측 상태를 다음 셋으로 정한다. 주장한 상태가 그것과 다르면 `WRONG_VALUE`다.
  1. 스냅샷 관측 기록. 자료 계약에 따라 `snapshot-build`가 수집 계획이나 비교 대상에 필요한데 수집 기록이 없는 키마다 `NOT_COLLECTED` 행을 만든다.
  2. 수집 계획(manifest, 무엇을 수집하기로 했는지 적은 기록). 계획에 없는 키(예: 수집 대상 16개국 밖의 상대국)는 대상 판정보다 먼저 계획과 대조한다. 그래서 그런 키를 `NOT_COLLECTED`(미수집)라고 적은 주장은 대상 오류(`WRONG_REFERENT`)로 판정하지 않는다.
  3. 동결된 `policy_v1`의 `CONFIRMED_NO_TRADE` 승격 규칙. 채점기가 런타임과 따로 독립 구현해 적용한다.
- **`data_status` 주장의 근거**: 계획 안 키와 비교 대상 키는 자기 상태 행을 인용한다. 곧 `UNRESOLVED_ZERO` 행, `REQUEST_FAILED` 행, `snapshot-build`가 만든 `NOT_COLLECTED` 행, 승격된 행이다. 수집 계획에도 비교 대상에도 없는 키는 인용할 상태 행이 없으므로 상태가 맞아도 근거 검사에서 `UNSUPPORTED`다(명세 §4.9). 대상 오류가 아니다.
- **근거 ID 풀기**: 근거 ID를 원본 행으로 푸는 규칙은 자료 계약을 따른다. 채점기는 풀린 원본 행 집합이 기대값 계산에 필요한 행 집합을 포함하는지만 본다.
  - 같은 키가 두 요청에 중복돼 값이 같은 행은 서로 동등하다. 그중 어느 행을 인용해도 통과한다. 예를 들어 `ALL`의 HS10 월 행은 HS4 요청과 HS6 요청에 모두 들어 있다. v2에는 이런 `ALL` HS10 키가 1,224개(수입·수출 합계) 있고 값은 모두 같다 `[사실: v2 스냅샷 조회 2026-09-24(목)]`.
  - 총계 행(원자료의 `hsCd='-'` 행. 스냅샷에서는 월 칸이 `RAW:총계`이고 요청 기간 전체의 합계다)은 월별 주장의 근거가 될 수 없다. 총계 행만 인용한 주장은 `UNSUPPORTED`다.
  - 예: 점유율 주장에는 해당국의 부모 HS6 행과, 그 달 `ALL`의 HS10 행들이 모두 필요하다.
- **`comparison` 주장**: 기대값은 실행 기록의 `grouping_version`이 가리키는 동결 비교집합(`g1` 또는 `g0`)으로 계산한다 (`g0` 대체 선언, 결정 기록 `20260926-0810-user-decision-rb1-g0-substitute-and-prose-ex2.md`).

**뒷받침 판정** `[DESIGN]`:

- **숫자(PT-1~PT-5)**: 같은 보고서의 typed claim 가운데 하나의 `value`를 그 표현의 단위로 바꾼 뒤 B3-1의 값 비교 규칙으로 비교해 같으면 뒷받침된다. 산문 숫자가 보인 소수 자리수로 claim 값을 반올림하고, 산문 숫자의 자리가 계약 자릿수보다 많으면 계약 자릿수에서 비교한다. 배수(PT-4)는 아래 "배수" 규칙대로 비율 단위로 비교한다.
  - 부호: `△`·`▼`·`-`·`−`는 음수, `▲`·`+`는 양수로 읽는다. 부호가 있으면 부호까지 비교하고, 없으면 절댓값을 비교한다. 지표 이름 속 증감 글자가 있으면 EX-6대로 부호를 정한다.
  - 단위가 붙은 표현은 단위가 호환되는 claim만 본다. `%`와 `pp`는 서로 호환되지 않는다. 톤과 kg, 천·만·백만·억 배수는 환산한다.
  - `달러`·`USD`·`$`만 붙은 숫자(kg당 표시 없음)는 금액(USD) claim과 단가(USD/kg) claim 모두와 비교한다. "kg당 6.0달러에서 3.6달러로"처럼 단위를 앞 숫자에만 붙이는 자연스러운 표현을 형식 때문에 오류로 세지 않기 위해서다.
  - 단위 없는 숫자는 단위를 따지지 않고 값만 비교한다.
- **표시 자릿수**: 산문 숫자의 마지막 자리다. 근사어(`약`·`대략`·`거의`·`가량`·`쯤`·`안팎`·`내외`·`정도`·`남짓`)가 붙으면 끝자리의 0은 자릿수로 치지 않는다("약 40%"는 십의 자리). "N%대"는 N 이상 N+폭 미만의 구간으로 읽는다. 폭은 N의 마지막 0이 아닌 자리의 단위다("40%대"는 40 이상 50 미만).
- **부등식**: 부호 없는 산문의 부등식은 절댓값으로 비교한다. `이상`·`넘게`·`초과`·`웃도는`이 붙으면 절댓값이 그 값 이상인 claim 값이 있을 때, `미만`·`이하`·`밑도는`이 붙으면 절댓값이 그 값 이하인 claim 값이 있을 때 뒷받침된다.
- **배수(PT-4)** `[DESIGN, 조정값]`: 배수 표현은 비율 단위로 비교한다. claim의 변화율 `r_U`를 비율 k = 1 + r_U/100으로 바꾸고, 배수 숫자가 보인 자리에서 반올림해 배수와 같으면 뒷받침된다.
  - 예: "2배" 대 claim +98.7%이면 비율 1.987 → 일의 자리 2이므로 `CORRECT`다.
  - 숫자 없는 말의 비율과 자리: "두 배"·"세 배"·"네 배"·"다섯 배"는 비율 2·3·4·5(일의 자리), "절반"과 "반토막"은 비율 0.5(소수 첫째 자리)다. 예: "절반으로 줄었다" 대 −47.0%이면 0.53 → 0.5이므로 `CORRECT`다.
  - "N배 증가"는 "비율 N"과 "N배만큼 증가(비율 N+1)"로 뜻이 갈리므로 비율 N으로 읽는다.
- **증감 어휘(PT-6)**: 같은 보고서에 같은 `direction`의 typed claim이 1개 이상 있으면 뒷받침된다. 부정형("증가하지 않았다")은 반대 방향이나 `FLAT`인 claim이 있으면 뒷받침된다. 지표 이름 속 증감 글자(EX-6)는 방향으로 치지 않는다.
- **"X에서 Y로"(PT-8)**: Y가 X보다 크면 오름, 작으면 내림, 같으면 그대로로 보고 증감 어휘와 같은 규칙으로 뒷받침을 찾는다.
  - 기간 순서(짝 규칙): X와 Y를 뒷받침하는 claim 가운데 같은 `hs6`·`partner`·`metric`의 수준 claim 짝이 있으면, 그런 짝 가운데 X 쪽 기간이 Y 쪽보다 앞서는 짝이 하나라도 있어야 통과다. 그런 짝이 있는데 모두 순서가 뒤집혀 있으면 `UNBACKED_PROSE`다. 사실 메모 §5의 오류(점유율 10→6 감소를 "6→10 증가"로 씀)가 이 경우다.
  - 그런 짝이 아예 없으면 기간 순서는 보지 않고 방향만 본다.
- **극값·순위 말(PT-7)**: 채점하지 않는다. 비교국 값인 `comparison` claim으로는 "36개월 중 최저" 같은 시계열 극값을 가를 수 없고, "최소 금액 기준" 같은 방법 서술까지 잡히기 때문이다. 건수만 "극값·순위 표현 건수(참고, 채점 제외)"로 보고한다(B7).
- 뒷받침되면 `CORRECT`, 아니면 `UNBACKED_PROSE`다.
- **배수의 한계** `[추론]`: 배수 표현을 뒷받침하는 claim은 `r_U`뿐이다. 그래서 "점유율이 2배", "금액이 절반"처럼 수준 claim 두 개로 계산되는 참인 문장도 `UNBACKED_PROSE`가 되고, 자유 문장을 쓰는 `freeform`에 더 자주 걸린다. 결과 보고(B7)에 이 한계를 적는다.
- **한계** `[추론]`: 문장 단위로 주어를 맞추지 않는다. 같은 보고서의 다른 주장과 우연히 맞는 표현은 놓친다. 이 한계는 두 모드에 똑같이 작용하며, 결과 보고에 적는다. 숫자·증감이 없는 극값·순위 말은 틀려도 잡히지 않는다(대표 지표 범위 밖).

### B3-3. A등급 주장 조건

아래 조건을 **모두** 채울 때만 대표 지표 값을 A등급 대표 숫자로 내세운다(사용자 결정).

| # | 조건 |
|---|---|
| 1 | `RB-1` 동결 완료(B6의 동결 조건 3개 충족) |
| 2 | 채점 전 봉인 해시 재대조 일치 |
| 3 | 채점기 사전 검증 통과(합성 oracle과 손계산 예제 재현) |
| 4 | `real_sealed` 봉인 실행 완료: 예정된 모든 (사례 × 모드) 실행이 최종 `execution_status`를 가진다 |
| 5 | 모드별(`freeform`, `full` 각각) 유효 보고서(`execution_status=COMPLETED`) 최소 20건(조정값) |
| 6 | 두 모드가 같은 사례 집합에서 실행됐다 |
| 7 | 한 번만 채점했다(재채점 없음) |

- **조건을 채우면**: 모드별 보고서 단위 오류율을 Wilson 95% 구간, 표본 수, 실행 실패 수와 함께 등급 A로 표기한다. `full`이 "낮다"고 쓰려면 B4의 차이 주장 규칙도 통과해야 한다. 통과하지 못하면 "이번 표본에서 차이를 확인하지 못했다"고 쓴다. 이 말은 차이가 없다는 뜻이 아니다. 보조 분석 결과(B4)와 `hypotheses`를 뺀 민감도 값(B3-2)을 함께 적는다.
- **조건을 못 채우면**(표본 부족이나 실행 미완료): A등급 대표 주장을 **보류**한다. 실제 건수, 신뢰구간, 미완료 사실과 함께 참고치로만 보고한다.
  - 개발용 결과(`dev20`, `real_dev`)를 대표로 올리지 않는다.
  - `real_dev` 경보를 빌려 표본을 채우지 않는다.
  - 이때 `3a`는 3점이 상한이다(A5).
- **`holdout40`의 미완료**: 실행이 다 끝나지 않으면 끝난 부분만 실패 집계와 함께 보고한다. 분모는 40 그대로 두고 미실행 건은 실패로 센다. 미완료 부분에 대해서는 어떤 주장도 하지 않는다.

#### 신뢰구간과 차이 주장

- **방법**(조정값): 비율마다 Wilson 95% 신뢰구간을 쓴다. x건 성공, n건 전체, z = 1.96일 때 다음과 같다.

```text
p = x / n
중심 = (p + z²/(2n)) / (1 + z²/n)
반폭 = z × √( p(1−p)/n + z²/(4n²) ) / (1 + z²/n)
구간 = [중심 − 반폭, 중심 + 반폭]
```

- **표본 크기의 감각**: 40건이면 50% 부근에서 반폭이 약 ±14.8pp다. 20건이면 약 ±20pp다 `[추론: 위 식으로 계산]`.
- **차이 주장 규칙(1차)** `[DESIGN, 조정값]`: 두 모드(또는 두 비교군)의 Wilson 95% 구간이 겹치면 차이를 주장하지 않는다. 점추정과 구간만 적고 "차이를 확인하지 못했다"고 쓴다. 작은 차이는 주장하지 않는다. 대표 지표와 보조 지표에 모두 쓴다.
  - 최소 검출 차이: 이 규칙으로 차이를 주장하려면 두 비율이 n=40일 때 약 20~33pp, n=20일 때 약 35~45pp 이상 벌어져야 한다. 폭은 기준 비율에 따라 다르다 `[추론: 위 식으로 계산]`.
  - "차이를 확인하지 못했다"는 "차이가 없다"는 뜻이 아니다. 두 모드가 같다고 쓰지 않는다.
- **짝 설계와 보조 분석(사전 등록)** `[DESIGN]`: 대표 지표의 두 모드와 `holdout40`의 세 비교군은 같은 사례에서 돈다. 다음을 보조 분석으로 보고한다. 1차 주장 규칙은 바꾸지 않는다.
  - 같은 사례의 짝 비교표(둘 다 오류 / 한쪽만 오류 / 둘 다 무오류)
  - Newcombe 짝 차이 95% 구간(Wilson 점수에 기반해 같은 사례 짝의 비율 차이를 구하는 구간)
  - McNemar 정확 검정(엇갈린 쌍만 세는 양측 이항 검정)의 p값
  - 보조 분석과 1차 규칙의 결론이 다르면 둘 다 적고, 주장은 1차 규칙을 따른다.
- **독립 가정의 한계** `[추론]`: Wilson 구간은 사례끼리 독립이라고 가정한다. 한 시계열(같은 품목×국가)에서 경보가 여러 건 뽑히면 사례끼리 닮아 구간이 실제보다 좁을 수 있다. 결과에 서로 다른 시계열 수를 함께 적는다(B7).
- 주장 단위 오류율의 구간은 참고로만 적는다(B3 "주 지표 사전 지정").

### B5. 실행 규칙

- **어디서 돌리나**: 채점 대상 실행은 OpenShell 샌드박스 안에서 같은 CLI(`tradesentry run-case`, `tradesentry evaluate`, 공통 옵션 `--snapshot`, `--policy`, `--mode`)로 직접 돌린다. NemoClaw 에이전트를 거치지 않는다. 봉인 묶음은 공식 채점 대상 실행 전용 샌드박스에서만 돌린다(B6).
- **어디서 채점하나**: 정답 대조 채점은 샌드박스 밖에서 `python -m eval.scorer --run <run_dir>`로 한다.
- **들이지 않는 것**: 정답표와 봉인 사례 목록은 샌드박스에도 개발 에이전트에게도 들이지 않는다. 봉인 입력은 공식 채점 대상 실행 때 전용 샌드박스에 읽기 전용으로만 넣는다. `real_sealed`는 사례 목록·표본 파일을 샌드박스에 넣지 않고, 샌드박스 밖 실행기(프로그램)가 해시 대조 뒤 사례 식별자를 `run-case`에 한 건씩 넘긴다(`skills/tradesentry-eval/SKILL.md`, 부록 #40). 그래서 식별자는 목록 파일 없이 스냅샷과 `policy_v1`만으로 사례(`hs6`·대상국·비교월과 신호 발동 여부)를 다시 만들 수 있는 형식이어야 한다. 형식은 S0에서 정한다(`docs/plan/SCAFFOLD_BRIEF.md` Q18).
- **동시성**: 1로 시작한다. 할당량과 실패율을 확인한 뒤에만 올리고, 모든 모드에 같게 적용한다. 결과 요약에 적는다.
- **순서**: (사례 × 모드) 실행 목록을 고정 난수로 섞어 교차 배치한다. 한 모드가 특정 시간대에 몰리지 않게 한다. seed는 `RB-1`과 함께 동결하고 기록한다. 동결한 값(조정값): 개발 묶음(`dev20`·`real_dev`)의 순서 seed는 `dev-order-v1`(단위 F2 `dispatch.DEV_ORDER_SEED`), 봉인 묶음(`holdout40`·`real_sealed`)의 순서 seed는 `rb1-order-v1`(단위 E2 `SEALED_ORDER_SEED`)이다. 섞는 규칙은 두 봉인 묶음에 같고 단위 E1 `plan_order` 하나다: (사례, 모드) 쌍마다 seed와 함께 만든 sha256 열쇠(`order_key`)의 순위로 정렬하고, 동시성 1로 한 건씩 돌린다. 재실행 순서도 이 순서를 따른다(아래 "인프라 실패 재실행"). 값은 실행 조건 입력 파일 `order_seed`와 `prescoring_checks.seed_concurrency`에 적히고 결과 요약 0절에 옮겨진다(결정 기록 `docs/tracking/decisions/20260926-0805-model-decision-mt7-sealed-runner.md` ③·④, 동결 확인 기록 `docs/tracking/decisions/20260926-0850-user-decision-rb1-freeze.md`).
- **분모**: 실패·미실행·timeout·invalid는 분모에 남긴다. 결과를 본 뒤 어려운 사례를 지우지 않는다.
- **기록**: 모든 실행은 실행 결과 기록 키 `run_id, case_id, dataset, mode, policy_version, rulebook_version, snapshot_id, grouping_version, code_version, review_status_final, signal_status, unresolved_evidence, execution_status, required_evidence_ok, numeric_ok, provenance_ok, tool_attempts, model_requests, tokens_in, tokens_out, wall_ms, critic_used, revision_used, errors`를 모두 남긴다.
- **재전송과 재실행의 구분**: 재전송은 한 실행 안에서 같은 모델 요청을 다시 보내는 것이다(B2의 5xx·429 규칙). 재실행은 실행 하나를 처음부터 다시 돌리는 것이다.
- **인프라 실패 재실행** `[DESIGN, 조정값]`: 명세의 "NIM 오류 재실행 여유"를 실행 규칙으로 고정한 것이다. 재량을 두지 않는다.
  - 조건: `execution_status`가 `FAILED`이고, 실행 기록의 `errors`에 적힌 원인 분류 코드가 모델 제공자 쪽 오류(재전송 한도를 다 쓴 HTTP 5xx, 재전송 한도를 다 쓴 HTTP 429, 연결 실패)뿐인 실행. 원인 분류 코드는 자료 계약 §8.1의 11개이고, 이 조건에 드는 것은 `PROVIDER_HTTP_5XX`·`PROVIDER_CONNECTION`과, 오류 항목의 HTTP 상태가 429인 `PROVIDER_HTTP_4XX`다(2026-09-25(금) 사용자 결정 5, 429는 2026-09-25(금) 15:52 사용자 결정, 결정 기록 `docs/tracking/decisions/20260925-1552-user-decision-429-retry.md`). 그 밖의 4xx(400·401·403·404·422 등)가 적힌 `PROVIDER_HTTP_4XX` 항목이 하나라도 있으면 대상이 아니다. 샌드박스 정책이 막은 요청(`CODE_ERROR`, 사유 `policy_denied`)은 재실행하지 않는다. HTTP 429 재실행은 위 15:52 결정으로 정했다. 재실행 규칙의 나머지 빈칸(결정 D12: 요청별 시간 초과·세션 중단을 재실행할지, 재실행 시점의 단위 등)은 아직 정하지 않았다 `[미확인]`.
  - 조건을 채운 실행은 **모두** 같은 설정으로 1회 재실행한다. 일부만 골라 돌리지 않는다.
  - 재실행 순서는 첫 실행의 순서(고정 난수로 섞은 순서)를 그대로 따르고, 첫 실행이 모두 끝난 뒤에 돌린다.
  - (사례 × 모드)마다 분모에 들어가는 행은 1개다. 재실행했으면 재실행 결과가 그 행이 된다. 재실행도 실패하면 그 실패가 최종이다.
  - 원래 기록은 지우지 않는다. 재실행 건수와, 재실행 전 기록으로 계산한 값을 모드별로 함께 보고한다(B7).
  - 판단은 채점 전에 실행 기록만 보고 하고, 모든 모드에 같은 기준을 쓴다.
  - `TIMEOUT`, `INVALID`, `BUDGET_EXCEEDED`와 모델 출력 문제는 재실행하지 않는다.

  - 늦어지면 끝난 만큼만 보고하고 미완료 사실을 적는다(B3-3).

#### 봉인 보관

- **봉인 대상**: `holdout40`의 입력과 정답표, `real_sealed`의 사례 목록과 채점 표본(표본 추출 seed 파일 포함)
- **보관 위치**: 저장소 밖 `~/.tradesentry/sealed/`. 환경변수 `TRADESENTRY_SEALED_DIR`로 바꿀 수 있다. 에이전트 작업 폴더에도 두지 않는다.
- **해시**: 파일별 sha256(파일 내용의 지문. 내용이 한 글자만 바뀌어도 달라진다) 목록만 PR로 커밋한다(`eval/sealed_manifest.json`). 원본 파일은 최종 채점이 끝난 뒤 커밋한다. 원본을 커밋할 위치는 계획 경로·명령 표에 아직 없다 `[미확인]`. 그때 표를 먼저 고친다.
- **지시**: 모델 트랙 에이전트와 Codex의 작업 지시에 봉인 폴더를 넣지 않고, 읽지 말라고 지시한다.

**생성 → 봉인 → 해시 등록 → 한 번 채점의 권한 분리 절차**:

1. **생성**: `holdout40` 생성 에이전트(격리된 Claude 보조 에이전트)는 시나리오 명세와 생성 규칙만 입력으로 받는다. 결과를 봉인 폴더에 **직접** 쓰고 저장소에는 쓰지 않는다. 생성 에이전트는 런타임 코드를 작성하지 않고, 그 대화 기록은 모델 트랙에 넘기지 않는다.
2. **봉인**: 생성 직후 파일별 sha256 목록을 만든다.
3. **해시 등록**: 해시 목록만 PR로 커밋한다.
4. **한 번 채점**: `RB-1` 동결 뒤 오케스트레이터가 평가 스킬 ②를 실행할 때만 봉인 **입력**을 샌드박스에 읽기 전용으로 넣는다.
   - 파일시스템 정책(정적 계층)은 샌드박스를 만들 때 고정된다 `[사실: 03 문서 §2.1-1]`. 그래서 봉인 입력은 **공식 채점 대상 실행 전용 샌드박스를 새로 만들어** 넣는다. 개발·시연용 샌드박스에는 넣지 않는다. 넣는 방식은 로드맵 MT5에서 확정한다 `[미확인]`.
   - 정답표는 어떤 샌드박스에도 넣지 않는다. 샌드박스 밖 채점기만 읽는다.
5. **재대조**: 채점 전에 해시를 다시 대조한다. 일치하지 않으면 그 묶음을 무효로 하고 사용자에게 올린다.

`real_sealed`의 사례 목록과 표본도 같은 절차를 따르되, 4단계의 봉인 입력 전달은 B5와 부록 40번(2026-09-26(토) <<FREEZE_TIME>> `RB-1` 동결 때 사용자 확인)을 따른다. 목록을 만드는 주체와 방법은 `docs/rules/PARALLEL_DEV_RULES.md`의 실자료 분할 절차를 따른다.

**서로 다른 두 통제**:

- ① 샌드박스 파일시스템 정책이 저장소 안의 평가 정답 경로 읽기를 막는다. 파일시스템 정책은 허용 목록 방식이다. 나열한 경로(와 작업 폴더)만 허용하고 나머지는 거부한다 `[사실: 03 문서 §3.6]`. 그래서 이 통제는 정답 경로를 허용 목록이나 작업 폴더에 **넣지 않을 때만** 성립한다.
- ② 봉인 자료를 저장소 밖에 두어 격리한다. 공식 채점 대상 실행 때만 봉인 입력을 전용 샌드박스에 읽기 전용으로 넣고, 정답표는 넣지 않는다.
- ①이 ②를 보장한다고 쓰지 않는다.

**정직한 한계**(제출서에도 적는다):

- 봉인 폴더 위치는 문서에 적혀 있어 비밀이 아니다.
- 개발 에이전트는 같은 OS 사용자로 돌기 때문에 봉인 폴더 열람을 기술적으로 막지 못한다. 지시와 기록으로 관리한다.
- 기술적 차단은 런타임 샌드박스(OpenShell 정책)에만 해당한다. 해시는 변조를 드러낼 뿐 열람을 막지 않는다.
- `real_sealed`의 원자료 행은 공용 스냅샷 `kcs_202201_202412_v2` 안에 있어 누구나 읽을 수 있다. 사례 목록도 기록된 분할 seed, 동결 스냅샷, 승인된 `policy_v1`로 누구나 다시 계산할 수 있다. 그래서 `real_sealed` 사례 목록은 기밀이 아니다. 다만 경보가 40건을 넘으면 어느 표본을 채점하는지는 공식 채점 실행 전까지 알 수 없다. 실행 중에는 사례 식별자가 인자로 드러난다(B5). 봉인의 목적은 두 가지다.
  - ① 개발·튜닝에 쓰지 않도록 지시와 기록으로 관리한다("그 시계열로 탐지 임계값·패턴을 조정하지 않는다"는 절차).
  - ② 결과를 보기 전에 표본을 고정하고 해시로 증명한다(무결성). 표본 추출 seed 파일(nonce 포함)은 생성 전에 정해 봉인 폴더에 두고 채점 뒤 공개한다.
- 스냅샷 전체 집계(전년동월 비교가 되는 조합 약 1,267개, 그중 단가 변화율 절댓값 30% 이상 771개, 금액은 있고 중량이 0인 677행)는 분할 전인 2026-09-23(수)에 이미 봤다 `[사실: 2026-09-23 v2 조회]`. 탐지 임계값 조정 전에 분할한다는 것이 봉인 시계열을 한 번도 보지 않았다는 뜻은 아니다.
- `holdout40`의 시나리오 명세(`eval/scenarios/SCENARIO_SPEC.md`)는 공개다. 시나리오 분류·배분·기대 처리는 누구나 안다. 봉인되는 것은 생성된 사례와 정답표다.

### B7. 결과 보고 양식

평가 결과는 `artifacts/eval/score-{시각}/`에 `scorer_results-{시각}.jsonl`(실행 결과 기록), `scorer_claims-{시각}.jsonl`(주장 채점 기록), `scorer_summary-{시각}.md`(요약)로 남긴다.

- 평가 결과 폴더 이름 `score-{시각}`은 채점 실행의 실행명이다(자료 계약 §10.3 N5·N11). `scorer_results-{시각}.jsonl`의 각 행은 (사례 × 모드) 실행 1건이고, 그 행의 `run_id`는 사례 실행의 실행명(자료 계약 §4.5)이라 폴더 이름과 겹치지 않는다.
- 실행 기록 `outputs/`는 커밋하지 않는다. 재채점용 보고서 원문은 `artifacts/eval/score-{시각}/{run_id}/`(`{run_id}`는 사례 실행의 실행명)에 증거 복사한다. 조건은 다섯이다. 봉인 묶음은 그 묶음의 금지 해제 조건 뒤에만 복사한다. 허용 목록(증거 복사할 보고서 파일 이름의 목록)의 보고서 파일만 복사하고 실행 폴더를 통째로 복사하지 않는다. 원문 무결성은 `report_hash`가 아니라 파일 바이트 sha256으로 본다. 커밋 전에 비밀값·로컬 경로 검사를 거친다. 커밋 사본으로 다시 채점하는 명령을 결과 요약 "재현 명령"에 함께 적는다(자료 계약 §10.3 N11, 결정 기록 `20260924-2315-user-decision-impl-plan-approval.md` D3). 저장소만으로 다시 채점할 수 있는지는 아직 알 수 없다 `[미확인]`. 까닭은 다섯이다. 실자료 스냅샷의 SQLite와 raw 응답은 커밋하지 않는다. holdout40 정답표를 커밋할 위치가 정해지지 않았다. 채점기가 커밋 사본의 사례 폴더를 여는 규칙이 없다. 묶음 기록과 기준 sha256을 둘 자리가 없다. 원문이 빠졌는지는 결과 요약이 굳은 뒤에야 안다. 이 문서에서 새 경로를 짓지 않는다.
- 요약 `scorer_summary-{시각}.md`는 채점기만 쓴다. 에이전트는 채점기 출력 파일을 고쳐 쓰지 않는다(자료 계약 §10.3 N8). 채점기가 모르는 값은 실행 조건 입력 파일(채점기가 모르는 실행 조건을 채점기에 넘기는 파일)로 채점기에 들어가고, 채점기는 그 값을 아래 양식의 0절·4절에 그대로 옮긴다. 채점기는 실행 조건을 이 파일에서만 읽는다. 샌드박스가 쓴 파일은 믿지 않는 입력이다. 채점기 명령(`python -m eval.scorer --run <run_dir>`)은 바꾸지 않는다(자료 계약 §8.2).
  - 담는 값: 사전 점검 결과, 샌드박스 이름, 라이브 정책 sha256, 시험표 폴더 이름, 봉인 해시 재대조 결과, 봉인 출처 점검 결과, 스킬 호출 성공률, 한도 값, 순서 seed, 동시성, 평가 스킬 ② 채점 전 확인 1·2·5번의 결과(참·거짓과 건수). 봉인 묶음이 아니면 NAT 프로파일 요약과 한국어 품질 표본 점검 결과도 이 파일로 요약에 들어간다.
  - 봉인 묶음이면 봉인 실행 출력을 열지 않고 얻는 값만 넣는다. 봉인 출력이 있어야 하는 값(NAT 프로파일 요약, 한국어 품질 표본 점검)은 금지 해제 조건(정답 대조 채점이 끝나고, `real_sealed`이면 표본 추출 seed 공개 기록까지 있는 때. 자료 계약 §10.3 N10) 뒤에 결과표(로드맵 R1)에 적고, 채점기 요약에는 넣지 않는다.
  - 만드는 주체와 방법: 내려받기를 끝낸 호스트 쪽 프로그램이 자기가 확보한 실행 폴더 안에 배타 생성(이미 있으면 실패하는 방식의 파일 만들기)한다. 샌드박스에서 받은 출력에 같은 이름이 있으면 내려받기를 거부한다. 만드는 때는 담을 값이 모두 정해진 뒤, 채점기를 부르기 전이다. 봉인 묶음이면 채점 직전의 봉인 해시 재대조 뒤다.
  - 이름·형식, `<run_dir>` 안의 위치, 누락·잘못된 입력의 처리는 정해졌다 `[사실: 결정 기록 `docs/tracking/decisions/20260926-0155-model-decision-conditions-extra.md`, 자료 계약 §8.2, 채점기 `eval/scorer/__main__.py` 머리 설명]`: 평가 하네스(단위 E1)가 자기 실행 폴더 `outputs/evaluate-{시각}/`에 `run_conditions-{시각}.json`을 배타 생성한다(글롭으로 찾지 않는다). 형식은 JSON 객체이고 키 집합은 채점기 `CONDITION_KEYS`(필수 키 `dataset`·`planned_cases`·`planned_modes`·`policy_detection_thresholds`, 나머지는 요약에 그대로 옮기는 값)다. 파일이 없으면 채점하지 않고, 약속 밖 키·형식이 틀린 값·로컬 절대경로 모양·키 모양 값이 있으면 거부한다. 개발 묶음에서 옮기는 값이 없으면 요약에 "미기재"로 적는다. 하네스가 모르는 운영자 값은 `tradesentry evaluate --conditions-extra <JSON 상대 경로>`로 같은 파일에 합친다(2026-09-26(토) 02:12 사용자 결정, 결정 기록 `docs/tracking/decisions/20260926-0212-user-decision-cli-options.md`). 이 넷(이름·형식·위치·누락 처리)은 MVP 시험 전에 임시로 정해 썼고 위 기록으로 확정했다 `[DESIGN: 2026-09-24(목) 사용자 결정, 결정 기록 20260924-2315 D6]`.
  - 룰북 B7 공개 값(코드가 덧붙인 주장 수, `review_status` 집계로 바뀐 보고서 수, 버린 초안 수, HOLD 합의로 뺀 도구 지적 수, 덧붙이기 전 기준 보고서 단위 오류율, 덧붙인 주장 덕분에 뒷받침된 산문 표현 수)은 실행 조건 입력 파일이 아니라 실행 추적에서 센다. 세는 도구는 독립 채점기(`eval/scorer/`, 단위 C4 `summary.py`의 "실행 추적 집계"와 `__main__.py`의 `read_trace`·`trace_entry`)이고, 입력은 `<run_dir>`와 같은 부모 폴더의 사례 실행 폴더 `{run_id}/`에 있는 `runlog_trace-{시각}.jsonl`(샌드박스가 쓴 믿지 않는 입력. 채점기는 읽기만 한다)이다. 최종 실행(사례마다 고른 행) 가운데 trace가 없거나("trace 없음": 폴더·파일 없음), 읽을 수 없거나("trace를 읽을 수 없음": 심볼릭 링크·크기 상한·권한·입출력 오류·UTF-8·JSON 아님·`run_id` 불일치), 모양이 다른("trace 모양 다름": `state_change` 사건의 `stage`·`data.phase`·`evidence_claims`의 `added[].code`·`claims[].claim_id`·`code_finding`의 `skipped_for_hold`·`after_critic`의 `requery_dropped` 모양이 골든 `tests/units/I12/`와 다름, 또는 완료 보고서의 `claims`가 목록이 아님) 것이 하나라도 있는 모드는 여섯 값을 "집계하지 않음(사유 n/m건)"으로 적고(사유가 여럿이면 "집계하지 않음(trace 없음 a·trace를 읽을 수 없음 b·trace 모양 다름 c, n/m건)") 0건으로 세지 않으며, 채점은 실패하지 않는다(커밋 사본 `artifacts/eval/score-{시각}/{run_id}/`에는 보고서 원문만 있어 재채점 때가 그렇다). 요약에는 모드별 건수·비율만 적고 사례 식별자·trace 값은 내지 않는다. 봉인 묶음도 같은 값을 낸다(건수·비율은 봉인 내용이 아니다). 계산 규칙은 결정 기록 `docs/tracking/decisions/20260926-0730-data-decision-b7-public-values.md`다 `[DESIGN: 2026-09-25(금) 18:56 사용자 결정 ③이 `RB-1` 전에 정하라고 한 도구 위치와 이름. 데이터 트랙 결정]`.

- 숫자마다 "등급 A", "등급 C", "등급 D", "참고" 가운데 하나를 붙인다. A등급 주장을 보류한 대표 값에는 "A등급 주장 보류(참고치)"를 붙인다.

## 용어 설명

- **채점 규범(규범)**: `SCORING_GOLDEN_RULE.md`. 팀이 정한 아이디어·제출물 평가 기준. 대회 공식 배점이 아니다.
- **하드 게이트**: 하나라도 통과하지 못하면 채점하지 않는 필수 조건(규범 G1~G6).
- **앵커**: 0/1/3/5 점수마다 붙은 판정 기준 문장.
- **CAP / TIE**: 점수 상한 규칙 / 동점 처리 규칙.
- **판정 밴드**: 100점 환산 총점을 강함·경쟁권·약함·폐기로 나누는 구간.
- **냄새 목록**: 좋은 신호와 나쁜 신호를 빠르게 가려내는 규범 §7의 목록.
- **컴포넌트 삭제 시험**: 구성요소를 지웠을 때 어떤 측정값이 나빠지는지 답해 보는 점검.
- **숫자 등급(A~D)**: 숫자의 정답을 누가 만들었고 그 정답이 개선 과정에 노출됐는지로 매기는 신뢰도 등급.
- **자기채점**: 팀이 규범으로 자기 프로젝트를 채점하는 일.
- **채점 대상 실행 / 정답 대조 채점**: 샌드박스 안에서 보고서를 만드는 실행 / 샌드박스 밖에서 그 보고서를 정답과 비교하는 일.
- **기준선(baseline)**: 비교 기준이 되는 방식. 대표 지표에서는 `freeform` 모드.
- **모드(비교군)**: 같은 사례를 처리하는 방식. `checklist`, `agent`, `full`, `freeform`.
- **자료 묶음**: 평가에 쓰는 사례 묶음. `controlled_fixture_v0`, `dev20`, `holdout40`, `real_dev`, `real_sealed`.
- **`dev20`**: 모든 에이전트가 쓰는 공개 합성 개발 자료 20건. 결과는 등급 D다.
- **`holdout40`**: 격리된 에이전트가 만들어 봉인한 합성 평가 자료 40건. 보조 지표를 재며 등급 C다.
- **`real_dev`**: 실자료 시계열 가운데 탐지 임계값 조정, 패턴 보강, 조사 지침(모델 프롬프트)·조사 흐름 조정에 쓰는 개발 묶음. 결과는 등급 D다.
- **`real_sealed`**: 실자료 시계열 가운데 봉인해 대표 지표 채점에만 쓰는 묶음. B3-3 조건을 채우면 등급 A다.
- **스냅샷**: 한 시점에 수집해 동결한 원자료 묶음. 작업 기준은 `kcs_202201_202412_v2`.
- **시계열(품목×국가)**: 한 HS6 품목과 한 상대국의 월별 수입 기록.
- **전년동월**: 비교월 t와 그 1년 전 같은 달 t−12.
- **단가(U)**: 금액(USD) ÷ 순중량(kg).
- **점유율(s)**: 해당국 금액 ÷ 전체국가(`ALL`) 금액.
- **퍼센트포인트(pp)**: 두 비율의 차이를 나타내는 단위. 점유율 10%가 6%가 되면 −4pp다.
- **구성효과 분해**: 하위품목(HS10)의 중량 비중(금액 비중이 아니다) 변화 때문에 생긴 평균 단가 변화(mix_effect)와 품목 안 단가 변화(within_effect)를 나누는 계산. 부모 단가 변화에서 둘을 뺀 나머지가 residual이다.
- **탐지 임계값 / 기준월 값**: 경보가 발동하는 기준(조정값) / 비교월 t의 1년 전인 기준월 t−12의 값. 이 문서는 두 뜻을 섞어 "기준값"이라고 쓰지 않는다.
- **부모 행 / HS10 하위 행**: 상대국의 HS6 월 행(HS4 스캔 요청이 준 행) / 그 HS6 아래 HS10 월 행. 하위 행은 구성 분해와 부모 대조에 쓴다(원천 규칙은 자료 계약).
- **총계 행**: 원자료의 `hsCd='-'` 행. 스냅샷에서는 월 칸이 `RAW:총계`이고 요청 기간 전체의 합계라 월별 주장의 근거가 될 수 없다.
- **수집 계획(manifest)**: 무엇을 수집하기로 했는지 적은 기록. 계획에 있는데 기록이 없는 키는 `NOT_COLLECTED`가 된다.
- **승격 규칙**: 빈 응답 달(`UNRESOLVED_ZERO`)을 무거래 확정(`CONFIRMED_NO_TRADE`)으로 바꾸는 `policy_v1`의 규칙. 사용자가 승인한 규칙으로만 일어난다. 승격된 달의 V·Q 칸은 null로 남고 지표·채점에서 0으로 다룬다(자료 계약 §3.4).
- **극값·순위 말**: `최고`·`최저`·`최대`·`최소`처럼 숫자·증감 없이 순위를 말하는 표현. 채점하지 않고 건수만 참고로 센다(B3-2 PT-7).
- **스냅샷 정규화 해시(`normalized_sha256`)**: 자료 계약이 정한 방식으로 스냅샷 내용에서 구한 sha256. 이 값이 같아야 rowid로 된 근거 ID가 같은 행을 가리킨다.
- **typed claim**: 필드가 정해진 사실 주장 레코드. 채점의 기본 단위다.
- **산문 패턴**: 설명 문장에서 숫자·증감 표현을 기계적으로 잡는 정규식 목록.
- **결정적(deterministic)**: 같은 입력이면 늘 같은 결과가 나오는 성질.
- **독립 채점기**: 런타임 코드를 재사용하지 않고 따로 구현한 채점 프로그램(`eval/scorer/`).
- **검증기(validator)**: 실행 중에 보고서의 숫자·단위·근거·금지 문구를 검사하는 코드. `freeform`을 뺀 모든 모드(`checklist`·`agent`·`full`)에서 막고 `freeform`에서는 기록만 한다.
- **조사자 / Critic(검수자)**: 도구를 골라 근거 포함 초안을 쓰는 모델 역할 / 그 초안의 누락·반대 설명을 지적하는 별도 문맥의 모델 역할.
- **근거 충족 처리정확도**: 예상 상태, 필수 근거, 수치·단위, 출처·버전, 정상 실행을 모두 만족한 사례의 비율.
- **혼동행렬**: 정답 상태와 최종 상태를 행과 열로 놓고 건수를 센 표.
- **Wilson 신뢰구간**: 비율의 불확실성을 나타내는 구간 계산법. 표본이 작거나 비율이 0·1에 가까워도 비교적 안정적이다.
- **최소 검출 차이**: 정한 판정 규칙으로 "차이가 있다"고 말할 수 있는 가장 작은 차이. 표본이 작을수록 커진다.
- **짝 설계**: 비교하는 방식들을 같은 사례에서 돌려 사례끼리 짝지어 보는 설계.
- **McNemar 검정**: 같은 사례에서 두 방식의 결과가 엇갈린 쌍만 세어 차이를 보는 짝 검정. 여기서는 정확(이항) 검정을 보조 분석으로 쓴다.
- **Newcombe 짝 차이 구간**: 짝지은 두 비율의 차이에 대한 신뢰구간. Wilson 점수 구간에 기반한다.
- **사전 등록**: 결과를 보기 전에 분석 방법을 정해 적어 두는 일. 결과를 본 뒤 유리한 분석을 고르는 것을 막는다.
- **민감도 보고**: 해석이 갈릴 수 있는 규칙을 바꿨을 때 결과가 얼마나 달라지는지 따로 보여 주는 값.
- **seed**: 난수 생성기의 시작값. 같은 seed면 같은 분할·표본·순서가 다시 나온다.
- **nonce**: 한 번만 쓰는 임의값. 표본 추출 seed 파일에 넣어, 파일을 공개하기 전에는 어느 표본이 뽑힐지 미리 알 수 없게 한다.
- **봉인**: 평가 자료를 저장소 밖에 두고 해시만 커밋해 개발 과정에 노출되지 않게 관리하는 일.
- **sha256 해시**: 파일 내용의 지문. 내용이 바뀌면 값이 달라져 변조를 드러낸다.
- **동결**: 규칙·수치를 고정하고 이후에는 새 버전과 사유로만 바꾸는 일. 룰북 동결 버전은 `RB-1`.
- **조정값**: 근거를 붙여 바꿀 수 있는 수치. 동결 뒤에는 새 버전으로만 바꾼다.
- **개선 과정 노출**: 정답이나 결과를 보면서 규칙·탐지 임계값을 고친 적이 있다는 뜻. 노출된 숫자는 대표로 쓰지 않는다.
- **실제 라벨**: 팀이 만들지 않은 외부의 정답. 여기서는 공식 통계 원본.
- **OpenShell**: 에이전트를 격리해 실행하는 NVIDIA 샌드박스 런타임. YAML 정책으로 파일·네트워크·프로세스를 통제하고 허용·차단을 감사 로그로 남긴다.
- **정적 계층 / 동적 계층**: OpenShell 정책에서 샌드박스 생성 때 고정되는 부분(파일시스템·landlock·process) / 실행 중 다시 불러올 수 있는 부분(network).
- **NemoClaw / OpenClaw**: 모델·에이전트 하네스·보안 런타임을 묶은 NVIDIA 참조 스택 / 그 기본 에이전트 하네스.
- **하네스**: 에이전트를 돌리는 실행 틀.
- **NAT(NVIDIA NeMo Agent Toolkit)**: 에이전트 워크플로를 실행·추적·프로파일·평가하는 라이브러리.
- **NIM**: NVIDIA의 모델 추론 API·서빙. 여기서는 `nvidia/nemotron-3-super-120b-a12b`를 부른다.
- **Nemotron**: NVIDIA의 언어 모델 제품군.
- **Agent Skills / SKILL.md**: 에이전트의 작업 지침을 담은 패키지 / 그 지침 파일 형식.
- **native tool call**: 모델이 API의 도구 호출 형식으로 함수를 부르는 방식.
- **MCP / A2A**: 모델과 도구를 잇는 표준 프로토콜 / 에이전트끼리 통신하는 프로토콜.
- **trace / 프로파일러**: 실행 단계별 기록 / 단계별 시간·토큰을 재는 도구.
- **스모크 시험**: 핵심 경로가 최소한 동작하는지 보는 짧은 시험.
- **Brev Launchable**: NVIDIA Brev에서 하드웨어·소프트웨어·코드를 한 번에 띄우는 원클릭 링크.
- **`g0` / `g1`**: 실자료 사례의 상대국 비교 대상 집합. `g0`는 품목(HS6)마다 대상국을 뺀 나머지 15개국에서 2023년 연간 수입금액 상위 5개국(k=5, 조정값)이다(해석은 2026-09-24(목) 사용자 확인, 자료 계약 §2.3.6·로드맵 §6.1). `g1`은 BACI 2023 HS85 수출 바구니의 코사인 유사도로 16개국 안에서 고른 상위 5개국(대상국 제외)이다. `g1`은 늘 5개국이고, `g0`도 늘 5개국이다.
- **BACI**: 국가 간 교역 연간 자료(천USD/톤). 관세청 월별 USD/kg 지표와 한 지표 안에서 섞지 않는다.
- **오케스트레이터**: 작업을 배분하고 병합하는 주관 에이전트.
