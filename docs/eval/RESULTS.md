# TradeSentry 평가 결과표 (R1)

로드맵 R1의 결과표다. 두 봉인 묶음(개발 중 보지 않도록 저장소 밖 봉인 폴더에 두었던 평가 자료 묶음) `real_sealed`(실자료 표본 40사례)와 `holdout40`(합성 40사례)의 공식 채점 결과를, 룰북 `RB-1`(평가 룰북 `docs/eval/RULEBOOK.md`의 첫 동결 버전) B7 양식의 절 구성을 따라 한 문서에 정리한다. 숫자는 모두 커밋된 채점기 출력(`artifacts/eval/score-260926135136/scorer_summary-260926135136.md`, `artifacts/eval/score-260926115824/scorer_summary-260926115824.md`, 같은 폴더의 `scorer_results-*.jsonl`)에서 옮겼고, 채점기 출력 파일은 고쳐 쓰지 않았다(자료 계약 `docs/rules/DATA_CONTRACT_V1.md` §10.3 N8). 채점 요약에 없는 값은 `scorer_results-*.jsonl`에서 건수를 센 것이며, 그 계산 근거를 표 아래에 적었다.

**이 결과표와 제출 문구는 등급 A를 주장하지 않는다. 대표 지표 값은 참고치로 제시한다.** 까닭은 §1의 A등급 주장 조건 판정 표에 있다.

용어(처음 나오는 것만)

- 보고서 단위 오류율: 오류 claim(정해진 필드로 쓴 사실 주장 레코드 가운데 `CORRECT`가 아닌 것)이나 `UNBACKED_PROSE`(설명 문장 속 숫자·증감 표현이 같은 보고서의 claim으로 뒷받침되지 않은 것)가 1개 이상인 보고서 ÷ 예정된 모든 실행. `COMPLETED`가 아닌 실행과 미실행도 분자·분모에 든다(룰북 B3).
- Wilson 95% 구간: 비율의 불확실성을 나타내는 신뢰구간 계산법(룰북 B4 식). 표의 `x/N = p% (하한%~상한%)`가 그것이다.
- Newcombe 짝 차이 95% 구간·McNemar 정확 검정: 같은 사례에서 돈 두 모드의 비율 차이 구간과, 결과가 엇갈린 쌍만 세는 양측 이항 검정의 p값(룰북 B4 사전 등록 보조 분석).
- 모드: `checklist`(모델 없이 규칙만), `agent`(조사자만), `full`(조사자 + Critic(별도 문맥의 검수자) + 검증기 차단), `freeform`(조사자가 숫자를 직접 쓰고 검증기가 막지 않음).
- 숫자 등급(룰북 A5): A = 실제 라벨(`real_sealed`), C = 팀이 독립적으로 만든 결정적 픽스처(`holdout40`), D = 우리가 만들고 우리가 채점한 개발 자료(`dev20`·`real_dev`).
- `code_version`: 채점 대상 실행이 돈 코드의 git 커밋 해시. 동결 커밋: 룰북 `RB-1`을 "동결"로 바꾼 PR(GitHub 변경 요청)의 병합 커밋.

## 6. 정직한 한계

- **하네스 공백 2건(요약의 "미기재")**: 단위 E2가 실행 조건 입력 파일에 스냅샷 `normalized_sha256`·대조 결과와 채점 전 확인 2번(버전 키 일치)·5번(모드별 사례 집합 일치)을 넣지 않아 채점기 요약 0절에 "미기재(실행 조건 입력 파일에 없음)"로 남았다(5번은 채점기가 스스로 계산해 "참"). 보완 값은 §0 표에 오케스트레이터 확인으로 적었다. `docs/tracking/findings.md`에 항목이 있다.
- **운영자 조건 형식 오류 2건**: `sealed_hash_recheck`에 문장을 넘겨 채점기 호출이 두 번(holdout40 1회·real_sealed 1회) 입력 오류로 끝났고(사용자 승인 뒤 `"일치"`로 정정, 원본 보존), `a_grade.scorer_prevalidation`에 문장을 넣어 채점기가 조건 3을 미충족으로 판정했다. 뒤의 것은 재채점하지 않아 등급 표기가 "A등급 주장 보류(참고치)"로 남았다(§1.1).
- **무효 시작 1건**: 첫 holdout40 공식 실행(`sealed_evaluate-260926092509`)은 하네스 결함으로 모델 호출 0회에 무효 처리됐다(§0). 봉인 내용이 산출되지 않았으므로 "한 번만 채점" 원칙과 어긋나지 않는다는 해석은 사용자 결정으로 확정했다(결정 기록 20260926-0955).
- **채점기 호출 실패 3회**(holdout40 2회, real_sealed 1회): 모두 입력 준비 문제(운영자 값 형식, 호스트 스냅샷 빌드 부재, 정정 전 자동 호출)이고 출력이 없어 채점이 아니다 `[해석: 오케스트레이터 판단]`. 채점기 코드 문제가 아니다.
- **표본 크기와 구간 폭**: 사례 40건이라 Wilson 95% 반폭이 50% 부근에서 약 ±14.8pp다(룰북 B4). `real_sealed` 40건은 서로 다른 시계열 27개에서 나와 독립 가정이 약하다(§1). `full`의 0/40은 상한 8.8%까지 열려 있다.
- **합성 자료 등급 C의 뜻**: `holdout40`은 봉인하고 한 번 채점했지만 정답이 팀이 설계한 합성 규칙에서 나오므로 C다(룰북 A5). 실자료 성능을 말하지 않는다.
- **`real_dev`로 조정한 사실**: 탐지 임계값·산문 패턴·조사 지침·조사 흐름은 `real_dev`에서 본 실패 유형으로 조정했다(§3). `real_dev` 값은 등급 D다.
- **`g1` 미구현**: 비교국 규칙 `g1`은 계획했으나 구현하지 않았고 `g0`를 썼다(2026-09-26(토) 08:10 사용자 결정).
- **범위 밖**: 숫자·증감이 없는 정성 서술과 극값·순위 표현의 의미 정확성은 채점하지 않으므로 틀려도 잡히지 않는다(룰북 B3). 산문 패턴은 문장 단위로 주어를 맞추지 않아 우연히 맞는 표현을 놓치고, 배수 표현은 `r_U` claim만 뒷받침한다(룰북 B3-2).
- **봉인의 한계(룰북 B6)**: 봉인 폴더 위치는 비밀이 아니고, 같은 OS 사용자로 도는 에이전트의 열람을 기술적으로 막지 못하며, 해시는 변조를 드러낼 뿐 열람을 막지 않는다. `real_sealed` 사례 목록은 기밀이 아니며, 봉인은 튜닝 금지와 무결성(결과를 보기 전에 표본을 고정하고 해시로 증명)을 위한 것이다.
- **저장소만으로 다시 채점할 수 있는지** `[미확인]`: 보고서 원문은 `artifacts/eval/score-*/{run_id}/`에, 봉인 원본(holdout40 정답표 포함)은 `eval/sealed/`에 커밋됐지만, 실자료 스냅샷의 SQLite와 raw 응답은 커밋하지 않고, 채점기가 커밋 사본의 사례 폴더를 여는 규칙이 없으며, 묶음 기록과 기준 sha256을 둘 자리가 없다(평가 스킬 ② "보고와 커밋"). §7의 재현 명령은 그 조건을 채운 호스트를 전제한다.
- **단정하지 않는 것**: 단가 변화를 부정·위법·원산지 조작·개별 거래가격의 증거로 쓰지 않는다. 판정 상태는 담당자의 다음 업무를 뜻할 뿐 기관 승인이나 통관 조치가 아니다.

## 7. 재현 명령

두 채점 요약 5절의 명령을 옮겼다. 봉인 묶음의 채점 대상 실행은 공식 채점 대상 실행 전용 샌드박스와 운영자 조건 파일이 있어야 하고, 봉인 묶음은 한 번만 채점하므로 아래 실행 명령을 다시 돌리는 것은 새 묶음 시작이라 사용자 결정 대상이다(룰북 B6).

- `holdout40` 채점 대상 실행: `python -m tradesentry.evaluation.sealed_runner --dataset holdout40 --sandbox ts-official --snapshot holdout40 --policy policy_v1 --conditions-extra outputs/operator_conditions-f2-holdout40.json`
- `holdout40` 정답 대조 채점: `python -m eval.scorer --run outputs/sealed/sealed_evaluate-260926101039`
- `holdout40` 스냅샷 검증: `tradesentry snapshot-verify --snapshot holdout40`
- `real_sealed` 채점 대상 실행: `python -m tradesentry.evaluation.sealed_runner --dataset real_sealed --sandbox ts-official --snapshot kcs_202201_202412_v2 --policy policy_v1 --conditions-extra outputs/operator_conditions-f2-real_sealed.json`
- `real_sealed` 정답 대조 채점: `python -m eval.scorer --run outputs/sealed/sealed_evaluate-260926114518`
- `real_sealed` 스냅샷 검증: `tradesentry snapshot-verify --snapshot kcs_202201_202412_v2`
- 채점기 입력(보고서 원문) 위치: `artifacts/eval/score-260926115824/{run_id}/`, `artifacts/eval/score-260926135136/{run_id}/`. 보고서 파일 바이트 sha256 목록은 각 채점 요약 5절에 있다.
- 커밋 사본으로 다시 채점하려면 호스트에 그 묶음의 스냅샷 빌드(`data/snapshots/holdout40/snapshot_build.sqlite`, `data/snapshots/kcs_202201_202412_v2/snapshot_build.sqlite`)가 있어야 한다(채점기가 주장 대조에 스냅샷을 읽는다. §0 "채점기 입력 준비"). holdout40 빌드는 반입 도구 `python -m scripts.import_sealed_holdout40`로 만들 수 있고(이제 봉인 원본이 `eval/sealed/`에 있다), 실자료 빌드는 `tradesentry snapshot-build`와 커밋하지 않은 원자료가 필요하다 `[미확인: 커밋 사본만으로 채점기가 돌아가는지는 시험하지 않았다]`.
