# 결정 기록 파일 이름 규칙

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-09-24(목) 08:08 |
| 제목 | 결정 기록 파일 이름 규칙 |
| 결정 | `docs/tracking/decisions/`의 결정 기록은 `YYYYMMDD-HHMM-<짧은 설명>.md`로 이름 짓는다. `YYYYMMDD-HHMM`은 기록을 만든 날짜와 시각(KST)이고, 짧은 설명은 영문 소문자·숫자·하이픈만 쓴다. 같은 시각의 기록이 둘 이상이면 설명으로 구분한다. 기록을 만들면 같은 PR(GitHub 변경 요청)에서 `index.md`에 한 줄을 더한다. 결정을 바꾸면 새 기록을 만들어 이전 기록을 가리키고, 이전 기록 파일은 고치지 않으며 색인의 상태 칸만 "대체됨"과 새 파일 이름으로 바꾼다 |
| 이유와 근거 | 모델 트랙과 데이터 트랙이 각자 브랜치에서 동시에 기록을 만든다 `[사실: docs/rules/PARALLEL_DEV_RULES.md §9.1]`. 일련번호를 쓰면 두 PR이 같은 번호를 잡고, 병합 뒤 번호를 바꾸면 PR 본문과 다른 문서의 참조가 끊긴다. 날짜·시각 앞머리는 따로 정해도 거의 겹치지 않고, 이름순이 곧 기록 순서다. 결정 시각이 여러 번에 걸친 기록도 있으므로 파일 이름에는 기록 시각을 쓰고, 결정 시점은 본문에 적는다. 설명의 글자 집합은 브랜치 이름 규칙(같은 문서 §9.2)과 같게 해 셸과 링크에서 따옴표 없이 쓰게 한다 `[DESIGN]` |
| 검토한 대안 | ① `NNNN-<설명>.md` 일련번호: 병렬 브랜치에서 번호가 겹치고, 병합 순서에 따라 번호를 다시 매겨야 한다. ② 한국어 설명: 셸·URL에서 인코딩 문제가 생기고 브랜치 이름 규칙과 다르다 |
| 결정 주체 | 오케스트레이터(작업을 나누고 PR을 병합하는 주관 에이전트. 병렬 개발 규칙 §8.4: 첫 기록을 만들 때 파일 이름 규칙을 정하고 첫 결정으로 남긴다) |
| 공용 약속 여부 | 아니다(병렬 개발 규칙 §4.1 목록 밖) |
| 영향 | `docs/tracking/decisions/`의 모든 기록. 로드맵 DT4 분할 기록, X1 결정 기록, 사용자 확인 답(로드맵 §6)이 이 규칙을 따른다 |
