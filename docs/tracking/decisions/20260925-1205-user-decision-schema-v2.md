# 자료 계약 버전을 v2로 올림(`schema_version`=2)

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-09-25(금) 12:05 무렵. 사용자가 채팅 선택지로 답했다(질문은 09:34 무렵에 올렸다. 처음에 답 시각을 09:36으로 잘못 적었다가 고쳤다) |
| 제목 | 사용자 결정 5(원인 분류 코드 11개)·7(실자료 묶음 `required_evidence_ok`의 `null`)을 자료 계약의 버전 올림으로 반영할지 |
| 배경 | 두 번째 문서 PR(DOCS2, PR #43)은 두 결정을 자료 계약 §8.1에 옮기고 버전은 `schema_version`=1로 둔 채, 올릴지를 §13.2에 `[미확인]`으로 남겼다. Codex 교차 검토가 이것을 막음으로 짚었다("§13.2는 값 집합 변경 시 버전을 올리도록 합니다. 두 결정 모두 계약 버전 변경으로 반영하고, §13.1 절차에 따라 영향 자료를 재생성·재검증하도록 고치세요"). 오케스트레이터가 사용자에게 물었다 |
| 질문(글자 그대로) | "계약 버전(schema_version)을 올려야 할까요? 결정 5·7이 §13.2의 값 범위 변경에 해당하는지" |
| 선택지(글자 그대로) | "v1 유지(권장)" / "v2로 올림" |
| 답 | "v2로 올림" |
| 결정 | 자료 계약의 버전을 `schema_version`=2로 올린다. 결정 5(`errors`의 원인 분류 코드 11개)와 결정 7(실자료 묶음 `required_evidence_ok`의 `null` 허용)을 자료 계약 §13.2의 "값 집합 변경"으로 본다. 계약 파일 이름 `docs/rules/DATA_CONTRACT_V1.md`는 계획 경로·명령 표와 여러 문서가 가리키는 이름이라 바꾸지 않는다(파일 이름의 V1은 처음 버전 표시로 남긴다) `[추론: 오케스트레이터 지시의 범위가 문서 값 맞춤이고, 파일 이름 변경은 지시에 없다]` |
| 설계 명세와의 관계 | 계약 버전 1은 2026-09-23(수) 설계 세션의 설계 명세 4.7절과 팀 분담 결정 D5에서 온 값이다. 자료 계약 §13.2 마지막 규칙은 "명세 4장과 글자 그대로 같아야 하는 값을 바꾸려면 명세도 사용자 승인을 받아 함께 고친다"고 적는다. 이 답이 그 사용자 승인에 해당한다고 본다 `[추론]`. 설계 명세는 저장소에 없는 로컬 계획 폴더에 있어(`docs/README.md` §3) 이 PR에서 고치지 않는다. 명세의 값을 고칠지는 오케스트레이터가 정한다 `[미확인]`. 루트 이력 문서 `TRADESENTRY_TEAM_SPLIT_DECISIONS.md`의 D5 행(`schema_version=1`)은 고치지 않는 이력 문서라 그대로 둔다 |

| 영향 | 문서: 두 번째 문서 PR(DOCS2)이 자료 계약 §1.2·§13.2와 문서에 적힌 계약 버전 값을 2로 맞춘다. 코드·자료(다른 PR `data/schema-v2`): ① 계약 커널 상수(단위 K1 `src/tradesentry/contract/types.py`의 `schema_version`) ② 정책 파일(`configs/policy_v1.json`, `configs/policy_dev.json`)의 버전 표시 ③ 합성 시험자료 `controlled_fixture_v0` 재생성(자료 계약 §13.1 절차 2) ④ dev20 입력·정답표 재생성 ⑤ 실자료 정본 빌드(v2 최종 빌드)의 재설치 ⑥ 봉인 holdout40은 처음 정한 seed 그대로 재생성하고, 봉인 해시 등록(`eval/sealed_manifest.json`)은 재생성본으로 한다. 재생성과 재검증(자료 계약 §13.1의 3 양 트랙 검토)은 그 PR이 한다 |
