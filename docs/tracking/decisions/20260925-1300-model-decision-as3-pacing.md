# AS3 세 번째 PR: 묶음 실행의 속도 조절(요청 한도 429 막기)

조립 작업 AS3의 세 번째 PR에서 정한 것을 적는다. 평가 묶음 실행이 모델 제공자의 요청 한도를 넘지 않게, 모델을 쓰는 사례 실행 사이를 띄우는 규칙이다.

용어

- HTTP 429: 요청 한도를 넘었을 때 제공자가 돌려주는 응답 코드("Too Many Requests"). 원인 분류 코드는 `PROVIDER_HTTP_4XX`이고 재실행 대상이 아니다(사용자 결정 5, `20260925-0847-user-decision-morning-shared-promises.md`).
- 속도 조절(pacing): 묶음 실행(단위 E1)이 다음 사례 실행을 시작하기 전에 쉬는 규칙.
- 분당 토큰 예산: 직전 실행이 쓴 토큰(입력 + 출력)을 이 값으로 나눈 분만큼, 직전 실행 시작부터 띄우는 기준.

## 까닭

- 2026-09-25(금) 오케스트레이터 실측에서 실자료 사례를 연달아 돌렸다. 한 사례는 약 5만 토큰이었고 1분 안에 3건이 돌았다. 그러자 넷째·다섯째 사례가 HTTP 429로 `FAILED`(`PROVIDER_HTTP_4XX`)가 됐다(main 폴더 `outputs/run_case-260925125419`·`-125425`, 커밋하지 않는 출력) `[사실: 오케스트레이터 전달]`.
- 429는 재실행 대상이 아니다(사용자 결정 5). 그래서 연쇄로 나면 그 실행들이 분모에 실패로 남는다. 모델 모드만 실패가 늘어 비교가 기운다. 한도 안에서 도는 쪽을 먼저 맞춘다.
- NVIDIA 쪽 한도 값은 공개된 숫자를 확인하지 못했다 `[미확인]`. 그래서 실측에서 보수적으로 잡았다(아래 ②).

## 결정 내용

① **규칙(단위 E1 `execute_batch(pacing=…)`)** — 확정

- 모델을 쓰는 실행(`checklist` 밖 모드)을 시작하기 전에, 직전 모델 실행의 시작 시각부터 `max(min_gap_ms, 직전 토큰 수 × 60000 ÷ tokens_per_minute)`밀리초가 지날 때까지 쉰다.
- 직전 모델 실행이 HTTP 429로 끝났으면(원인 `PROVIDER_HTTP_4XX`, `detail`이 `HTTP 429`) 그 실행이 끝난 시각부터 `after_rate_limit_ms`도 지나야 한다. 묶음 전체가 연쇄로 실패하지 않게 하는 장치다. 429 실행은 지금처럼 실패로 남고 재실행하지 않는다.
- `checklist`는 모델을 부르지 않으므로 쉬지 않고, 다음 쉼의 기준에도 들지 않는다. 쉼은 시각만 바꾸고 사례 조건(한도·설정·자료)은 모든 모드에 같다(룰북 B2).
- 인프라 실패 재실행(룰북 B5)에도 같은 규칙이 걸린다. 한 사례 안의 요청 재전송 규칙(5xx만 3회, 지수 대기)은 바꾸지 않았다.
- 쉰 시간의 합(`paced_ms`)과 429 뒤 더 쉰 횟수(`rate_limit_waits`)는 묶음 결과에 남는다.

② **값(`configs/model/model.json`의 `pacing`, 모든 모드 같음)** — 잠정(조정값)

| 키 | 값 | 뜻 |
|---|---|---|
| `min_gap_ms` | 60000 | 모델 실행 시작 사이 최소 1분(1분당 한 사례) |
| `tokens_per_minute` | 50000 | 분당 토큰 예산. 5만 토큰 사례 뒤 1분, 10만 토큰 뒤 2분, 15만 토큰 뒤 3분 |
| `after_rate_limit_ms` | 120000 | 429로 끝난 실행 뒤 그 끝에서 2분 |

- 근거: 실측에서 1분에 3건(약 15만 토큰)일 때 429가 났다. 그래서 1분에 한 사례·5만 토큰을 기준으로 잡았다(실측의 약 1/3). 수정 단계까지 가는 사례(누적 약 9.4만 토큰, AS2 실측)는 약 2분 띄운다.
- 값을 바꾸면 이 기록 뒤에 새 기록을 남기고, 실행 조건 입력 파일의 값으로 어느 묶음이 어떤 값으로 돌았는지 가린다.

③ **실행 조건 입력 파일** — 잠정(형식 확정 때)

- `prescoring_checks.seed_concurrency`(평가 스킬 ② 채점 전 확인 5의 "순서 seed·동시성 적용")에 문장 하나를 적는다. 채점기 요약 0절이 이 칸을 옮긴다. 예: "참: 순서 seed dev-order-v1, 동시성 1, 속도 조절(모델 실행 사이 최소 60초, 분당 토큰 50000, HTTP 429 뒤 120초), 쉰 시간 합 N초, 429 뒤 더 쉰 횟수 k".
- `pacing` 키가 없거나 모양이 틀리면 evaluate는 실행 폴더를 만들기 전에 1로 끝난다.

④ **시간 영향(예상)** `[추론]`

- 쉬지 않을 때 모델 실행 한 건은 실측으로 약 20초였다(1분에 3건). 속도 조절 뒤에는 모델 실행 시작 사이가 1~2분이 된다(토큰 5만~10만).
- dev20(20건 × 3모드 = 60실행): 모델 모드 40실행 × 약 1~1.5분 = 약 40~60분, `checklist` 20실행은 샌드박스 exec·내려받기를 합쳐 몇 분이다. 합계 약 45~65분이다. 인프라 실패 재실행이 있으면 건마다 1~2분이 더해진다.
- `real_dev`(20건 × `freeform`·`full` = 40실행, 모두 모델 모드): 실자료 사례는 5만~9만 토큰이라 약 40~75분이다.
- 429가 나면 그 뒤마다 2분이 더해진다.

## 검토한 대안

- 한도 밖이면 429 실행을 재실행 대상에 넣기: 사용자 결정 5(429는 `PROVIDER_HTTP_4XX`, 재실행 대상 아님)를 바꾸는 일이라 하지 않았다.
- 한 사례 안에서 429를 재전송하기: 요청 재전송 규칙(5xx만)을 바꾸는 일이라 하지 않았다.
- 고정 간격만 두기: 토큰이 많은 사례 뒤에 부족하다. 토큰 비례를 더했다.
- 값을 CLI 옵션이나 환경변수로 두기: 계약 밖 이름이라 하지 않고 모델 설정에 두었다.
