# HTTP 429도 5xx처럼 재전송·재실행함(사용자 결정 5 변경)

| 제목 | NIM(NVIDIA 클라우드 추론 API)의 HTTP 429(호출 한도 초과)·5xx(서버 오류)를 V1(MVP 시험) 전에 어떻게 다룰지 |
| 배경 | ① 흐름 수정 병합 뒤(main 9b10265) `real_dev` 사례 5건을 `full` 모드로 호스트에서 돌렸다(15:28~15:36). `COMPLETED` 2건(`850450-MY-202401` HOLD, `850432-CN-202301` MAINTAIN), `FAILED` 3건이었고, 3건 모두 `PROVIDER_HTTP_4XX`(HTTP 429)였다. 429는 대부분 HTTP 500 바로 뒤, 또는 몇 초 안에 요청 네댓 번을 보낸 뒤에 나왔다 ② 다른 호출이 없는 상태에서 작은 요청(최대 1토큰)을 15초 간격으로 보냈더니 5번 가운데 2번이 HTTP 503이었다. 응답 머리글에 호출 한도를 알리는 줄(`x-ratelimit-*`, `retry-after`)이 없었다. 그래서 429는 우리 쪽 호출량보다 제공자 쪽 처리 용량 문제로 보인다 `[추론]` ③ 지금 규칙: 5xx는 한 실행 안에서 요청당 최대 3회 다시 보내고(대기 1·2·4초), 묶음 끝 인프라 실패 재실행 대상이다(룰북 B5). 429는 `PROVIDER_HTTP_4XX`로 다시 보내지도, 재실행하지도 않는다(사용자 결정 5, 결정 기록 `20260925-0847-user-decision-morning-shared-promises.md`). 이대로면 V1과 봉인 평가에서 인프라 실패가 분모에 많이 남아 A등급 조건(모드별 `COMPLETED` 20건 이상)이 흔들린다 |

| 답 | "429도 5xx처럼 (권장)" |
| 결정 | ① 한 실행 안의 재전송: HTTP 429도 5xx와 같은 규칙으로 요청당 최대 3회 다시 보낸다. 대기는 5xx·429 모두 5·10·20초(지수 대기, 조정값)로 늘린다. 재전송은 지금처럼 모델 요청 횟수(한도 10회)에 센다. 대기가 사례 deadline을 넘으면 지금처럼 `DEADLINE`이다 ② 재전송 한도를 다 쓴 429는 원인 분류 코드 `PROVIDER_HTTP_4XX` 그대로다(코드 11개는 바꾸지 않는다). 다만 룰북 B5의 인프라 실패 재실행 대상에 넣는다. 가르는 값은 그 오류 항목의 HTTP 상태 429다. 다른 4xx(400·401·403·404·422 등)는 지금처럼 재전송·재실행하지 않는다 ③ 모든 모드에 같은 규칙이다. 재전송·재실행 뒤에도 실패하면 그 실패가 최종이고 분모에 남는다 |
