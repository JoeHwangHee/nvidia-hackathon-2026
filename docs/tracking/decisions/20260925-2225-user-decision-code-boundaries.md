| 결정 | ① **`review_status` 코드 집계**: 보고서를 만들 때(초안·검증·최종 모두, 모든 모드) 코드가 신호별 판정 `signal_status`에서 자료 계약 §3.1 우선순위(`MAINTAIN` > `HOLD` > `MONITOR`)로 `review_status`를 계산해 채운다. 같은 절의 결정적 규칙인 `unresolved_evidence`(`MAINTAIN`과 `HOLD`가 섞일 때만 true)도 함께 채운다 `[해석: 오케스트레이터. 둘 다 signal_status의 결정적 함수라 함께 다룬다]`. 모델(또는 `checklist` 규칙)이 쓴 `signal_status`·주장·설명·가설은 바꾸지 않는다. 모델이 쓴 값과 달라진 보고서는 trace에 남긴다(모델이 쓴 값과 집계 값) ② **발동 신호 자기 계열 주장 덧붙이기**: 발동한 신호에 그 계열의 주장(자료 계약 §9.4. 검증기 R3 `SCHEMA_SIGNAL_CLAIM`이 보는 것과 같은 판정)이 사례 대상(hs6·상대국·비교월)에 없으면, 필수 근거 덧붙이기(결정 기록 `20260925-1809-user-decision-evidence-claims.md`)의 확장으로 코드가 그 신호의 변화 지표(단가 `r_U`, 점유율 `d_s`. 사례 대상의 비교월 대 기준월) 주장을 받은 근거의 검증된 지표에서 덧붙인다. 받은 근거에 없으면 덧붙이지 않는다(도구를 새로 부르지 않고 값을 지어내지 않는다). 덧붙인 주장은 기존 덧붙임과 같은 `claim_id` 번호열(`e{번호}`)과 trace 항목을 쓴다 ③ **HOLD 합의 신호엔 빠진 도구 지적 없음**: 흐름 조정의 코드 지적(AS2 결정 기록 ⑲, 초안 전에 받아야 하는 필수 도구가 빠졌다는 지적)은 초안의 판정과 규칙 참고값(판정 정책 P3 출력)이 둘 다 `HOLD`인 신호에는 내지 않는다. 도구별로는 `decompose_hs`(단가 전용)는 단가 신호가 HOLD 합의면 빼고, `compare_partners`는 발동한 모든 신호가 HOLD 합의일 때 뺀다. 참고값을 계산할 수 없으면 지금처럼 지적한다. 그 결과 Critic 지적만으로 열린 수정이 최종 검사에서 막히면 흐름 수정 (나)(AS2 결정 기록 ㉔)대로 수정 전 초안의 보고서로 끝난다 ④ **Retry-After 존중과 헤더 기록**: 재전송 고리(HTTP 429·5xx)에서 응답에 `Retry-After`(다시 시도할 때까지 기다릴 시간을 알려 주는 응답 헤더)가 있으면 대기 시간은 지수 대기와 min(`Retry-After`, 60초) 가운데 큰 값이다 `[해석: 429뿐 아니라 같은 고리의 5xx도 헤더가 있으면 같은 규칙]`. 재전송 횟수(3회)와 한도 세기(결정 기록 `20260925-1552-user-decision-429-retry.md`, `20260925-1805-user-decision-retry-budget.md`)는 그대로다. trace `model_error`에 `retry_after_ms`, 허용 목록의 응답 헤더(`retry-after`, `x-ratelimit-*`, `x-request-id`), 본문 요지(앞 200자. 비밀값 형태는 가린다)를 남긴다 ⑤ **고르지 않음**: 요청별 제한 시간 60초→120초, 재전송 4회 ⑥ 병합 뒤 샌드박스를 다시 굽고 오늘 밤 V1 4차(dev20·`real_dev`)를 돌린다. 결과는 아침에 보고한다 ⑦ 결과 요약(룰북 B7) 공개 항목에 "코드가 `review_status`를 집계 값으로 바꾼 보고서 수(모드별)"를 더하고, 덧붙인 주장 수에는 ②의 주장도 든다 `[해석: 결정 기록 20260925-1856-user-decision-attached-claims-backing.md의 공개 원칙을 같은 방식으로 적용]` |
