# 코드가 덧붙인 주장도 산문 숫자의 뒷받침으로 인정하고, 덧붙이기 전 값을 함께 공개함

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-09-25(금) 18:56 무렵. 사용자가 채팅으로 답했다 |
| 제목 | 코드가 덧붙인 필수 근거 주장(결정 기록 `20260925-1809-user-decision-evidence-claims.md`)이 모델이 쓴 설명 문장·가설의 숫자를 뒷받침하는 것을 채점·검증에서 인정할지 |
| 배경 | ① 필수 근거 덧붙이기 코드(PR #60)를 기록된 실행의 최종 보고서에 적용해 보니, `real_dev` `freeform` 1건(`850490-FI-202402`)에서 덧붙인 주장이 모델 산문의 숫자와 같은 값이라 `PROSE_UNBACKED` 2건이 사라지고 채점기 `numeric_ok`가 거짓에서 참으로 바뀌었다 ② 오케스트레이터가 앞서 "대표 지표는 더한 주장이 맞는 한 바뀌지 않는다"고 설명한 것은 정확하지 않았다고 바로잡았다. 대표 지표(보고서 단위 오류율, 룰북 B3)는 오류 주장이나 뒷받침 없는 산문 숫자가 하나라도 있는 보고서를 센다. 그래서 덧붙이기로 산문 숫자가 뒷받침되면 값이 낮아질 수 있고, 산문 숫자가 많은 `freeform`(기준선)에서 더 크게 움직일 수 있다. 뜻이 다른 숫자가 우연히 같은 값이라 통과할 가능성도 조금 늘어난다 ③ 오케스트레이터가 덧붙인 주장의 성격을 설명했다: 모델의 판정·주장·설명을 바꾸지 않고 나중에 붙는 편집에 가깝다. 붙을지는 사례마다 다르다(모델이 넣지 않았고 받은 도구 결과에 값이 있을 때만). AI의 의견이 아니라 공개 판정 조건표에 따라 코드가 고르고 동결 스냅샷의 검증된 지표로 채우는 수치 항목이다 |
| 사용자 발언(글자 그대로) | "즉 ai가 작성하지 않고 코드가 채우는값을 근거로 인정할지에 대한 부분인걸로 이해되는데 사실 ai도 그 근거를 넘겨받고 판단하는거니까 근거로 봐도 되겠네?" |
| 오케스트레이터 답 | 그렇게 봐도 된다(덧붙인 주장의 값은 모델이 판단할 때 받은 도구 결과에 이미 있던 값이다). 남는 위험(우연히 같은 값)은 덧붙이기 전 기준 값을 함께 공개해 드러낸다. "인정 + 덧붙이기 전 값 함께 공개"로 진행한다 |
| 결정 | ① 검증기와 채점기는 지금처럼 최종 보고서의 모든 typed claim(코드가 덧붙인 주장 포함)으로 산문 숫자·증감 표현의 뒷받침을 판정한다. 주장에 출처 표시를 더하지 않는다(자료 계약 그대로) ② 결과 요약(룰북 B7)에 자료 묶음마다 모드별로 둘을 함께 공개한다: 덧붙이기 전 기준의 보고서 단위 오류율(덧붙인 주장을 빼고 같은 채점 규칙으로 다시 계산), 덧붙인 주장 덕분에 뒷받침된 산문 표현 수. 덧붙인 주장은 실행 추적(trace)의 기록으로 가른다 ③ 이 두 값을 계산하는 방법(추적 기록을 읽는 분석 도구의 위치와 이름)은 `RB-1` 동결 전에 정한다 |
| 결정 주체 | 사용자 |
| 공용 약속 여부 | 그렇다(평가 구성: 결과 요약의 공개 항목). 이 기록이 사용자 승인이다 |
| 영향 | 문서: 룰북 B7 결과 요약 양식의 공개 항목 두 줄, 색인·status. 코드: 덧붙이기 코드(PR #60)는 바꾸지 않는다. 공개 값 계산 도구는 `RB-1` 전에 만든다(V1 개발 묶음 값은 오케스트레이터가 따로 계산해 보고) |
