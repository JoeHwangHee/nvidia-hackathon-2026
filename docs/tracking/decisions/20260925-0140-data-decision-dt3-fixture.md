# DT3 합성 시험자료 `controlled_fixture_v0`의 세부 결정과 넘기는 방식

DT3(합성 시험자료, 데이터 트랙) 구현에서 자료 계약과 병렬 개발 규칙이 데이터 트랙(D)에게 맡긴 세부를 적는다. 특히 병렬 개발 규칙 §2.2와 로드맵 DT3 행이 D에게 정하라고 한 "넘기는 방식(키 없는 스모크 시험이 기대는 커밋 형태 포함)"을 제안한다. 코드와 시험은 DT3 PR에 있다. 항목마다 **확정** 또는 **잠정**을 붙였다.

용어

- 합성 시험자료(controlled fixture): 정답을 알고 규칙대로 만든 가짜 자료 묶음. 여기서는 스냅샷 `controlled_fixture_v0`(`source_kind`=`controlled`)이다. 모든 금액·중량·상대국이 합성이고 실제 통계나 실제 사건이 아니다.
- 생성 규칙: 합성 시험자료를 만드는 입력 파일 `data/snapshots/controlled_fixture_v0/fixture_spec.json`. 단위 S4(`src/tradesentry/snapshot/fixture.py`)가 읽는다.
- 수집기 형식 원천: 실스냅샷과 같은 모양의 원천 파일 묶음. manifest(수집 요청 목록 `manifest.json`), raw 응답(API 응답 XML 원본, `raw/*.xml`), 수집기 SQLite(`snapshot.sqlite`, 수신 기록과 스냅샷 메타)다. 수집기(`src/tradesentry/ingest.py`, 단위 S1)의 함수로 만든다.
- 스냅샷 빌드: 단위 S2(`src/tradesentry/snapshot/build.py`)가 원천에서 만드는 파생 SQLite(`snapshot_build.sqlite`)와 빌드 기록(`snapshot_build.json`, `normalized_sha256` 곧 정규화한 스냅샷 내용의 해시를 담는다). 단위 S3(`verify.py`)이 raw와 대조해 검증한다.
- 결정적 재생성: 같은 생성 규칙이면 몇 번을 다시 만들어도 같은 원천·같은 `normalized_sha256`이 나오게 만드는 일(시각·파일 이름에 실행 시점이 들어가지 않게 고정한다).
- 승격: 승인된 규칙으로 빈 응답 달의 `UNRESOLVED_ZERO` 행을 무거래 확정 `CONFIRMED_NO_TRADE`로 바꾸는 일(자료 계약 §3.4). 단위 S2가 파생 SQLite에만 적용한다.
- 비교국 표: 대상국마다 비교할 상대국을 적은 `peer_group` 행의 CSV(자료 계약 §2.3.6). `g0`는 대상국을 뺀 수입금액 상위 5개국 규칙이다.
- 사례 식별자: 단위 P2(판정 정책의 사례 만들기)가 쓰는 `{hs6}-{partner}-{month}` 형식의 `case_id`.

| 제목 | 합성 시험자료의 넘기는 방식(텍스트 원천 커밋과 결정적 재생성), 합성 국가·HS 코드, 규모, 사례 A/B/C 배치, 관측 상태 5종 배치, 승격 규칙 적용, 합성 비교국 표 위치, 메타 값, 정답과 입력의 분리 |

## 결정 내용

① **넘기는 방식: 텍스트 원천을 커밋하고 나머지는 키 없이 결정적으로 다시 만든다** — 잠정(제안. 오케스트레이터 확인 대기)

- 커밋하는 파일(텍스트 원천. `.gitignore`가 빼지 않는다)
  - `data/snapshots/controlled_fixture_v0/fixture_spec.json`: 생성 규칙
  - `data/snapshots/controlled_fixture_v0/manifest.json`: 수집기 `build_manifest`로 만든 수집 요청 목록
  - `data/snapshots/controlled_fixture_v0/snapshot_hash.json`: raw 결합 해시(`raw_combined_sha256`)
  - `data/snapshots/controlled_fixture_v0/snapshot_build.json`: 빌드 기록(`normalized_sha256` 등). 자료 계약 §4.4 규칙 4의 "SQLite 밖의 커밋된 기록"이다
  - `data/reference/peer_group_controlled_fixture_v0.csv`: 합성 비교국 표(⑧)
- 커밋하지 않고 다시 만드는 파일(지금 `.gitignore`가 뺀다 `[사실: git check-ignore]`): `raw/*.xml`(130개), `snapshot.sqlite`, `snapshot_build.sqlite`
- 다시 만드는 명령(저장소 루트, 키·네트워크 없음): `uv run --locked python -c "from tradesentry.snapshot import fixture; fixture.materialize()"`
  - 모든 것을 `outputs/snapshot_fixture-{시각}/`에서 새로 만들고 단위 S3로 검증한 뒤, 정본 자리에 없는 파일만 이미 있으면 실패하는 방식으로 둔다.
  - 이미 있는 파일은 먼저 모두 대조한다(텍스트는 바이트, SQLite는 `normalized_sha256`, 빌드 기록은 시각을 뺀 기록 키). 하나라도 다르면 아무것도 쓰지 않고 멈춘다. 덮어쓰지 않는다(자료 계약 §10.3 N8·N12).
  - 끝에 정본 자리를 단위 S3로 다시 검증한다(raw 대조 켬). 그 뒤 자료 접근층(단위 K3) `open_snapshot("controlled_fixture_v0")`과 단위 S3 기본값이 그 파일을 찾는다.
- 새 작업 폴더(M 쪽 worktree)와 2026-09-27(일) 키 없는 스모크 시험은 이 명령을 한 번 먼저 부른다. 시험(`tests/units/S4/`)은 저장소 폴더를 쓰지 않고 임시 폴더에 같은 함수로 만든다.
- 확인 `[사실: 2026-09-25(금) 01:32 작업 폴더에서 실행]`
  - 처음 부를 때 7건을 새로 썼다(raw 130개는 한 건으로 센다).
  - 다시 부르면 새로 쓴 파일이 0건이었다.
  - 그 뒤 `git status --short`에는 커밋할 텍스트 원천만 보였다. 이진 파일은 모두 무시 대상이었다.
  - 시험은 커밋한 텍스트 원천이 다시 만든 것과 바이트까지 같은지 본다.
- 이유
  - `.gitignore`를 고치지 않아 보안 검토 대상이 늘지 않는다.
  - 커밋 이력에 이진 SQLite(두 파일 합쳐 약 4MB)가 쌓이지 않는다.
  - 원천과 기록은 사람이 읽고 검토할 수 있는 텍스트다.
  - 다시 만든 결과가 커밋한 기록과 다르면 멈추므로, 작업 폴더마다 다른 스냅샷이 생길 수 없다.

② **합성 국가 코드는 `XA`~`XJ`** — 확정

- 상대국 10개를 `XA`, `XB`, …, `XJ`로 둔다. 관세청 2자리 형식(대문자 두 글자)이라 단위 P1·P2의 형식 검사와 비교국 표 행 규칙을 그대로 통과한다.
- ISO 3166-1(국가 코드 국제 표준)의 사용자 지정 범위(`XA`~`XZ`)라 어느 나라에도 배정되지 않는다. 관세청 국가코드 목록(`data/reference/kcs_country_codes.json`)에도 없다. 시험이 이 둘을 확인한다.
- 비교국 표의 `baci_country_code`(BACI 국가 코드)는 null이다.
- 이유: 실제 나라 코드에 합성 수치와 합성 경보가 붙으면 실제 사건처럼 읽힐 수 있다. TradeSentry는 부정·위법 판정이 아니고, 사례 A/B/C는 합성 시연 사례다(병렬 개발 규칙 §2.5).

③ **HS 코드와 품목명** — 확정

- 대상 HS6(6자리 품목분류 코드)는 실스냅샷 범위의 앞 세 개(`850450`, `850431`, `850432`)다. HS4 스캔은 `8504` 하나다.
- HS10은 HS6마다 두 개, `{HS6}1000`·`{HS6}2000`이다. oracle의 `X1`·`X2` 순서에 대응하고, DT2 시험의 대응과 같은 꼴이다.
- 범위 밖 HS6 `850440`(HS10 `8504401000`)을 HS4 조회 응답에만 넣었다. 행 규칙 7(분석 범위 밖 행은 지표·도구가 쓰지 않는다, 자료 계약 §2.3.2)을 시험하려는 것이다.
- 품목명 칸(`statKor`)은 `합성 품목 {코드}`, 국가명 칸은 `합성국가 {코드}`다.
- HS 코드는 품목분류 번호일 뿐 통계 값이 아니어서 실제 코드를 그대로 썼다. 실스냅샷과 같은 요청 구조(HS4 스캔 + HS6 조회 + 품목별 전체국가)가 나온다.

④ **규모와 일관성** — 확정(규모는 조정값)

- 3 HS6 × 10국 × 36개월(2022-01~2024-12)이다. 요청 132건 가운데 수신 기록이 131건, 미수집이 1건이다. raw 응답은 130개, 관측 행은 8,330개, 수입 흐름 `OBSERVED` 행은 4,136개, 비교국 표는 150행이다.
- HS10 하위 행은 분담 D6의 "2개월"보다 넓혀, 부모 HS6 행(HS4 스캔이 준 상대국별 HS6 행)이 있는 모든 달에 둔다(규모 조정).
  - 부모 행이 있는데 그 달 HS6 조회가 비면 실제 API에서는 나올 수 없는 조합이다.
  - 그렇게 두면 수집기 verify의 부모-하위 교차검증도 어긋난다.
- 부모 행은 HS10 행의 합이라 금액과 중량이 정확히 맞는다. 응답마다 총계 행(요청 구간 전체 합)도 정확한 합이다.
- 전체국가(`ALL`) HS10 행은 상대국 HS10 참값의 합에 나머지 나라 몫을 더한 값이다. HS4 조회와 HS6 조회에 같은 값으로 두 번 나온다(행 규칙 6의 중복 제거 대상).
- 수집기 verify를 임시 폴더의 원천에 돌린 결과 `[사실: 2026-09-25(금) 탐침. 저장소에 쓰지 않았다]`
  - 총계 대조 130건 불일치 0
  - 국가별 부모-하위 1,052건 일치(불일치 0). 부모만 있는 24건은 모두 사례 C 계열의 미수집·실패 요청이다(⑥, 설계대로). 그래서 수집기의 G3 게이트는 거짓이다
  - `ALL` 교차검증 216건 일치
  - 무거래 후보 1건(⑥의 승격 자리)

⑤ **사례 A/B/C** — 확정

| 이름표 | 사례 식별자 | HS6 | 상대국 | 기준월 | 비교월 | 비교월 HS10 |
|---|---|---|---|---|---|---|
| A | `850450-XA-202412` | `850450` | `XA` | 202312 | 202412 | 200/20, 160/80 |
| B | `850431-XB-202412` | `850431` | `XB` | 202312 | 202412 | 300/50, 60/50 |
| C | `850432-XC-202412` | `850432` | `XC` | 202312 | 202412 | 요청 실패(`REQUEST_FAILED`) |

- 값은 `eval/dev/oracle_ABC.json`의 입력 그대로다: 부모 V·Q(기준월 600 USD·100 kg, 비교월 360·100), HS10 V·Q, 전체국가 금액 6000(두 달). 시험이 oracle 파일과 대조한다.
- C의 기준월 HS10은 oracle에 없다. 부모와 맞는 두 행(500/50, 100/50)을 둔다. MT3가 C형 주장의 HS10 코드를 스냅샷 행에서 가져오기 때문이다(MT3 2회차 보고와 오케스트레이터 답).
- C의 비교월 HS10은 그 HS6 조회(`XC`, 2024년)가 HTTP 500으로 실패해 `REQUEST_FAILED`다. 전체국가 합을 맞추려고 쓴 참값(300/50, 60/50)은 응답에 나오지 않는다.
- 사례 계열은 비교월을 뺀 모든 달이 기준월 값(600·100)이다. 비교월을 마지막 달 2024-12로 두어 뒤따르는 달의 반동 경보가 없다.
- 개발용 정책 `dev-0.1`의 기준값(단가 변화율 절댓값 30%, 점유율 변화 절댓값 10pp)으로 단위 P1을 돌리면 이 세 달의 단가 신호만 발동한다. 점유율 변화는 −4pp다 `[사실: 시험 DetectionTest]`.
- 배경 계열의 최대 단가 변화율 절댓값은 1.7%, 최대 점유율 변화 절댓값은 4.1pp다 `[사실: 탐침]`.
- 지표 단위 X1~X3이 이 자료에서 oracle 수치 필드를 모두 재현한다 `[사실: 시험]`. C의 `within`·`mix`는 null이다.
- 사례 식별자는 단위 P2 형식이다. oracle의 사례 이름(`A-composition` 등)과의 대응은 시험 파일에만 둔다(⑪).

⑥ **관측 상태 5종의 자리** — 확정

| 관측 상태 | 만드는 법 | 자리 | 수입 행 |
|---|---|---|---|
| `OBSERVED` | 응답 행 | 전부 | 4,136 |
| `NOT_COLLECTED` | 계획 요청에 수신 기록이 없다 → 단위 S2가 상태 행을 만든다 | `XC`·`850432` HS6 조회 2022년(HS10 하위 자료) | 12 |
| `REQUEST_FAILED` | 요청 실패(HTTP 500 세 번, 본문 없음) | `XC`·`850432` HS6 조회 2024년(HS10 하위 자료, 사례 C) | 12 |
| `UNRESOLVED_ZERO` | 요청은 정상인데 그 달 행이 없다. 같은 HS4 아래 OBSERVED 행이 없어 승격되지 않는다 | `XI` 2022-08(HS4 스캔 한 행 + HS6 조회 세 행) | 4 |
| `CONFIRMED_NO_TRADE` | 그 달 그 HS6만 거래가 없다 → HS6 조회가 빈 달 → 승격(⑦) | `XJ`·`850450` 2022-05 | 1 |

- 수입 0이 명시된 달(`OBSERVED`, 값 0)도 하나 둔다: `XH`·`850431` 2022-10. 그 달은 수출만 있다.
- 부모 값이 빠지거나 0이 되는 빈칸(`UNRESOLVED_ZERO`·`CONFIRMED_NO_TRADE`·수입 0)은 2022년, 점유율이 작은 나라(2~4%)에 두었다. 그래서 사례의 두 달, 사례 B의 비교국 값, 탐지 결과(⑤)에 닿지 않는다.
  - 무거래 확정 달과 수입 0 달은 점유율 분자가 0이 된다. 점유율이 큰 나라에 두면 이듬해 같은 달에 점유율 신호가 발동한다.
- HS10 하위 자료만 빠지는 두 빈칸(`NOT_COLLECTED`·`REQUEST_FAILED`)은 사례 C 계열(`XC`·`850432`)에 둔다. 부모 값은 그대로라 탐지에 닿지 않는다. 한 계열 안에서 미수집(2022년)·정상(2023년)·실패(2024년)를 구분해 볼 수 있다.
- 빈칸 때문에 그다음 해 같은 달의 지표가 null이 되는 곳은 데이터 품질 목록에 남는다(단위 P1 `metric_null`).

⑦ **승격 규칙 적용(빌드 기록 `policy_version`=null)** — 잠정(오케스트레이터 확인 대기)

- `CONFIRMED_NO_TRADE`는 승격으로만 생긴다(자료 계약 §3.4).
- 개발용 정책 `dev-0.1`은 승격하지 않는다(`configs/policy_dev.json` 설명, DT1 결정 ⑩).
- 로드맵은 관측 상태 5종을 요구한다. 그래서 합성 스냅샷 빌드에만 단위 S2가 아는 규칙 `ingest_verify_candidates`를 생성 규칙의 일부로 적용한다.
- 빌드 기록의 `policy_version`은 null이다. 승인된 정책도, 개발용 정책도 아니라는 뜻이다. `confirmed_no_trade_rule`에는 규칙 이름을 적는다(단위 S3가 이것으로 승격 집합을 다시 계산한다).
- 실자료 빌드에는 적용하지 않는다. `policy_v1`이 다른 규칙으로 승인되면, 이 자료를 그 규칙으로 다시 만들지는 그때 정한다.

⑧ **합성 비교국 표: `data/reference/peer_group_controlled_fixture_v0.csv`** — 잠정(새 경로. 오케스트레이터 확인 대기)

- 위치: 단위 S3는 빌드 기록에 적힌 비교국 표를 `data/reference/`에서만 찾는다(DT1 결정 ⑨·⑪). 파일이 스냅샷 폴더 안에 있으면 기본 경로 검증(`snapshot-verify --snapshot controlled_fixture_v0`에 해당)이 실패한다. 그래서 `data/reference/`에 두었다. 소유는 D다(병렬 개발 규칙 §1.4).
- 내용
  - 규칙: 원천의 2023년 `OBSERVED` 부모 HS6 행 수입금액 합으로 `g0` 규칙(`import_value_topk`, k=5, 대상국을 뺀 상위 5개국, 합이 같으면 코드 사전순)을 적용한다.
  - `grouping_version`: `g0`다. MVP 실행이 `g0`를 넘기므로, 도구 `compare_partners`가 `--snapshot`만 바꿔 이 행을 찾는다.
  - 출처 칸: `source_version`=`controlled_fixture_v0`, `input_sha256`=이 자료의 raw 결합 해시다.
  - 빈 칸: `baci_country_code`·`similarity`·`community_id`는 null이다.
- 단위 G1(M의 `g0` 구현, `g0.load_input`과 `g0.run`)을 같은 원천에 돌린 결과와 바이트까지 같다 `[사실: 시험 PeerGroupTest]`. 사례 세 건의 비교국 다섯 나라는 모두 두 달의 부모 값이 있다.
- 합성 `g1` 행은 없다(⑫).

⑨ **생성 규칙 파일과 스냅샷 메타 값** — 확정

- 생성 규칙은 `fixture_spec.json`(합성 시험자료 폴더 안, D 소유)이다. 키의 뜻은 단위 S4 머리 설명에 있다.
- 스냅샷 메타(자료 계약 §2.3.1)
  - `collected_at`: 생성 규칙의 고정 시각 `2026-09-25T09:00:00+09:00`이다(합성은 생성 시각).
  - `source_url`: 생성 규칙과 생성 모듈의 저장소 상대경로 목록이다.
  - `precision_rule`: 합성 자료에 맞춘 문구다.
  - `coverage_status`: 수집기 기본값 `IN_PROGRESS` 그대로다. v1이 값 집합을 정하지 않아 새 값을 만들지 않았다.
  - `hs_version`: `HSK`다.
- `generated_at`은 raw 결합 해시에는 들어가지 않는다. 수신 기록 시각, 스냅샷 메타 `collected_at`, 비교국 표 `generated_at`을 거쳐 `normalized_sha256`에는 들어간다. 그래서 이 값을 바꾸면 새 빌드 기록이 필요하다.

⑩ **결정적 재생성의 방법** — 확정

- 수집기 함수를 쓰는 동안만 수집기의 스냅샷 폴더 뿌리(`ingest.SNAP_DIR`)와 시각 함수(`ingest.now_iso`)를 작업 폴더와 고정 시각으로 바꾸고 되돌린다. DT1 시험 도우미와 같은 방법이다. 시험이 되돌려졌는지 본다.
- 실패 응답은 본문 없이 넘긴다. 그러면 수집기가 시각 이름 실패 파일(`raw/failed/`)을 만들지 않는다.
- 수신 기록의 `elapsed_ms`는 0이다.
- 응답 항목 순서는 총계 행이 먼저이고, 그다음 달 순서, 달 안에서는 코드 순서다.
- 기록값 `[사실: snapshot_build.json, snapshot_hash.json]`: `normalized_sha256` `c56a6dbef3c9710c96528529b05919450ac1fb99b1bdae21551e4c621b433dcd`, raw 결합 해시 `2f8b7f899a1d5fb8b315864c72d12e843cb2e981df9d48e3457337f0e6b9501a`.

⑪ **정답과 입력의 분리** — 확정(샌드박스 반입은 권고)

- 스냅샷 SQLite, 생성 규칙, manifest, 비교국 표, 단위 S4 파일에는 기대 판정(`MAINTAIN`·`MONITOR`·`HOLD`와 한국어 표기)이나 oracle 시나리오 이름이 없다. 시험이 이를 찾아 본다.
- 사례는 이름표 A/B/C와 사례 식별자로만 가리킨다. `src/tradesentry/`는 샌드박스 이미지에 들어갈 수 있다.
- 권고: 샌드박스 반입 목록(로드맵 MT5가 정한다)에는 이 폴더의 `snapshot_build.sqlite`·`snapshot_build.json`만 넣는다. 생성 규칙에는 사례 이름표가 있다.

⑫ **교체 확인의 범위와 남은 것** — 잠정

- 이번에 확인한 것은 둘이다.
  - 자료 접근층과 단위 S3가 경로 없이 `snapshot_id`만으로 이 자료를 연다.
  - 스냅샷 메타 키가 계약 `snapshot` 객체 키와 같다.
- CLI(`tradesentry detect --snapshot controlled_fixture_v0` 등)는 아직 조립체와 잇지 않았다. CLI로 교체되는지는 조립 작업 AS1·AS2의 조립 시험과 로드맵 MT5가 확인한다.
- `g1`이 동결되어 채점 대상 실행의 기본값이 되면, 이 자료에도 합성 `g1` 행이 필요할 수 있다. 필요하면 새 파일 이름과 새 빌드로 더한다(빌드에 쓴 `data/reference/` 파일은 바꾸지 않는다, DT1 결정 ⑪).

## 검토한 대안

- `.gitignore`에 예외 줄(`!data/snapshots/controlled_fixture_v0/raw/`, `!data/snapshots/controlled_fixture_v0/*.sqlite`)을 더해 이진 파일을 커밋하는 안
  - 좋은 점: 새 작업 폴더가 곧바로 쓸 수 있다.
  - 버린 이유
    - 보안 검토 대상이 된다. 예외 줄을 잘못 쓰면 실스냅샷 파일이 드러난다.
    - 약 4MB 이진 파일이 이력에 쌓이고, 다시 만들 때마다 파일 배치가 달라질 수 있다.
    - 생성 규칙과 이진 파일을 두 벌로 관리해야 한다.
- 파생 SQLite를 단위 S2 없이 `write_snapshot_db`로 직접 만드는 안: raw·manifest가 없어 단위 S3의 raw 대조가 실패한다(DT1 결정 ⑨). 버렸다.
- 실제 국가 코드(`CN` 등)에 합성 값을 두는 안: ②의 이유로 버렸다.
- 빌드 기록에 `dev-0.1`을 적는 안: 정책 파일(승격 없음)과 어긋난다. 새 정책 버전 이름(예 `dev-0.2`)은 계약에 없는 이름이다. DT1 시험의 가짜 버전(`dev-9.9`)은 인수물에 맞지 않다. 셋 다 버렸다.
- 합성 비교국 표를 스냅샷 폴더에 두고 단위 S3가 그 자리도 찾게 고치는 안: 다른 작업(DT1)의 단위 파일을 고쳐야 한다. 이번 작업에서는 하지 않았다. 오케스트레이터가 원하면 그 단위 소유 작업으로 옮길 수 있다.
- 생성 규칙을 단위 파일 안의 상수로 두는 안: 사례 이름표가 샌드박스 이미지에 들어갈 수 있다. 규칙과 코드를 따로 검토하기도 어렵다. 버렸다.
- HS10 하위 행을 사례 두 달에만 두는 안(분담 D6의 글자 그대로): ④의 이유로 버렸다.
