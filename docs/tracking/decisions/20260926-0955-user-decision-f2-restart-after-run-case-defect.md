# 사용자 결정: F2 첫 공식 실행(holdout40)의 무효 처리와 `run-case --sealed` 수정 뒤 두 봉인 묶음 새 시작

룰북 `RB-1`(평가 룰북의 첫 동결 버전) 동결 커밋 c557540 뒤 시작한 첫 봉인 묶음 공식 실행이 CLI 결함으로 사례마다 실패해 멈춘 일과, 그 처리에 대한 사용자 결정을 적는다. 봉인 사건(봉인 폴더에 닿거나 봉인 묶음을 움직인 일)은 병렬 개발 규칙 §6.3과 평가 스킬 ②(`skills/tradesentry-eval/SKILL.md`) 공식 채점 단계 7에 따라 날짜·주체·파일 수·해시 대조 결과·봉인 폴더 위치 출처만 적는다. 봉인 자료의 내용(사례 식별자·파일 이름·seed)은 적지 않는다.

용어

- 봉인 묶음: 개발 중 보지 않도록 저장소 밖 봉인 폴더에 두는 평가 자료(`holdout40` 합성 40사례, `real_sealed` 실자료 표본 40사례).
- 공식 채점 대상 실행 전용 샌드박스: `RB-1` 동결 뒤 봉인 묶음을 돌리려고 새로 만드는 OpenShell(에이전트를 격리해 돌리는 NVIDIA 샌드박스 런타임) 샌드박스. 이름 `ts-official`.
- 단위 E2(샌드박스 밖 실행기, `src/tradesentry/evaluation/sealed_runner.py`): 봉인 해시를 대조하고 사례 식별자를 샌드박스 안 `run-case`(사례 1건을 조사하는 CLI 명령)에 한 건씩 넘기는 호스트 쪽 프로그램.
- 원인 코드 `CODE_ERROR`: 실행 결과 기록의 원인 분류 코드 가운데 하네스·코드 오류(자료 계약 §8.1).

## 원인 `[사실: 오케스트레이터 진단 2026-09-26(토) 09:32~09:37]`

1. `src/tradesentry/cli/dispatch.py`의 스냅샷→자료 묶음 표 `RUN_CASE_DATASETS`에 `holdout40`이 없어, `run-case`가 실행 폴더를 확보한 뒤 종료 코드 1로 끝났다. 호스트(E2)는 빈 폴더를 내려받아 실행 결과 기록이 없다고 판정했다. 같은 샌드박스에서 봉인 아닌 픽스처 사례는 정상, `--snapshot holdout40`에 픽스처 사례 식별자를 준 진단 실행은 같은 오류 문장으로 종료 1이었다.
2. 실자료 스냅샷에서 `run-case`는 분할 기록의 `real_dev` 계열만 받고 `real_sealed` 계열을 거부하며 자료 묶음을 `real_dev`로 적는다(결정 기록 `20260925-0605-model-decision-as2-run-case.md`·`20260925-1230-model-decision-as3-real-dev.md`, 병렬 개발 규칙 §7.2의 5). 그래서 `real_sealed` 묶음도 같은 코드로는 돌 수 없었다(E1·E2가 기록의 `dataset`이 묶음 이름과 같기를 요구한다).
3. 발견이 늦은 이유: E2는 실제 전용 샌드박스로 봉인 묶음을 예행하지 않았고(예행하면 곧 공식 실행이 되므로), 단위 시험은 `run-case`를 가짜로 대신했다 `[추론]`. 다음부터는 봉인 아닌 자료 묶음(dev20)으로 E2 리허설을 먼저 돈다(E2에는 dev20 리허설 경로가 있다).
