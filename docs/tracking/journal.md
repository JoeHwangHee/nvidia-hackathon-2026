# TradeSentry 기획·개발 일지

이 문서는 TradeSentry의 기획과 개발을 시간순으로 적은 일지다. 대회를 조사하고 주제를 고른 일부터 저장소 공개와 라이선스 결정까지, 무엇을 어떤 순서로 했고 어떤 대안 가운데 무엇을 왜 골랐는지를 담았다. 2026-09-27(일)에 사용자(팀장)의 요청으로 만들었다. 정본은 결정 기록(`docs/tracking/decisions/`)과 계획 문서다. 이 일지는 그것들과 PR(GitHub 변경 요청)·대화 기록을 시간순으로 엮은 요약이므로, 값이나 규칙이 필요하면 각 항목의 출처를 연다. 공개 저장소에 올라가는 문서다.

## 2. 기획 — 대회 이해와 주제 선정 (2026-09-22~09-23)

대회 요건과 NVIDIA 스택을 먼저 조사하고, 팀 채점 규범을 만든 뒤 그 규범으로 아이디어를 걸렀다. 보안 계열 후보에서 현업·생활 밀착 후보로 넓혔고, 현업 브레인스토밍 1위인 HSGate(수입 품목분류 + 통관신고 게이트)를 깊게 조사했다. 그러다 2026-09-23(수) 저녁에 주제가 TradeSentry로 바뀌었다. 바꾼 이유는 기록에 없다. 같은 저녁 설계 준비 세션에서 수집기 결함을 고치고 v2 스냅샷을 모았다.

### 2026-09-22(화) — 팀 채점 규범과 아이디어 후보 A~J
- 한 일: 팀 채점 규범 `SCORING_GOLDEN_RULE.md`를 만들었다. 제1원리는 "숫자로 증명할 수 없는 아이디어는 채택하지 않는다"이고, 하드 게이트 G1~G6(정량 증명, 교육 미션 정합성, NVIDIA 기술 3종 이상, 재현 가능성, 산업 문제성, 6일 완주)과 가중치를 두었다. 가중치와 게이트는 팀 설계 규칙이고 대회 공식 배점이 아니다. 같은 날 아이디어 후보 10개와 6일 안에 쓸 수 있는 자원 재고도 만들었다.
- 대안: A 에이전트 권한 정책 자동생성·레드팀(1위) 등 7개를 남기고, 일정·여행, 문서 생성, 범용 챗봇 RAG(검색 증강 생성)는 게이트에서 탈락시켰다.
- 이유: 에이전트 데모는 누구나 만들 수 있어서 기준선 대비 개선 수치에서만 차이가 난다고 봤다. 그래서 개발 순서도 "평가 스크립트와 기준선을 먼저, 기능은 나중"으로 정했다.
- 결정 주체: 작업 에이전트(초안). 누가 승인했는지는 기록에 없다 `[미확인]`.
- 영향: 이 개발 순서가 2026-09-23 설계 세션의 결정 "문서 먼저, 구현은 다음"의 근거가 됐다(`docs/plan/DEV_PLAN.md` 13절).

### 2026-09-22(화) 23:20~09-23(수) 00:20 — ChatGPT 교차 비평과 규범 v2.1
- 한 일: 후보를 23개로 넓힌 뒤 ChatGPT 임시 채팅에서 "심사위원 겸 냉정한 기술 리뷰어" 역할로 비평을 받았다. ChatGPT의 근거 주장 6건은 공식 문서로 다시 확인해 5건이 맞았고 1건은 용어가 부분만 맞았다.
- 대안: ChatGPT는 MCP(에이전트가 외부 도구를 부르는 공개 프로토콜) 공급망 감사관·Skill CI 계열을 상위로 두고 하이브리드 두 안을 권했다. 권고 "둘 중 하나로 고정, 새 아이디어 추가 금지"는 따르지 않았다.
- 이유: ChatGPT가 짚은 공통 실수 셋을 받아들였다. NVIDIA 기술의 개수를 필연성으로 착각한다("OpenShell을 지우면 여전히 작동하는가?"), 숫자를 만들 수 있다는 것과 그 숫자가 증거라는 것을 혼동한다, 핵심 실험보다 제품 서사를 먼저 키운다. 실거래가 이상거래 후보(I-12)는 "가격 이상치는 이상거래가 아니다", 합성 라벨 순환 평가를 이유로 폐기됐다.
- 결정 주체: 외부 자문(ChatGPT, 의견) + 작업 에이전트(정리).

## 11. 돌아보며

모두 `[추론]`이다. "남은 일"만 `docs/tracking/status.md`의 "남은 일"에 근거한다.

잘된 선택
- 평가 규칙을 기능보다 먼저 쓰고 동결 절차를 둔 것. 결과를 보기 전에 정책 수치·판정 분포·표본 추출 방법을 못 박았기 때문에, 봉인 채점에서 입력 형식 오류가 났을 때도 재채점하지 않고 "A등급 주장 보류(참고치)"로 적는 판단이 흔들리지 않았다.
- 숫자를 검증된 값에서 채우고 검증기로 막는 구조를 첫날 관찰(G4)에서 바로 설계 원칙으로 올린 것. 대표 지표의 두 모드 차이가 이 구조에서 나왔다.
- 결정을 채팅에 두지 않고 결정 기록으로 옮긴 것. 이 일지를 대화 기록 없이도 대부분 저장소 문서만으로 재구성할 수 있었다.
- 지침 문구가 약하다는 것을 실험으로 확인한 뒤, 모델 출력을 고치지 않는 코드 경계로 옮기고 그 효과를 모드별로 공개하게 한 것.

아쉬운 점
- 주제를 HSGate에서 TradeSentry로 바꾼 이유를 남기지 않았다. 설계의 출발점이 기록으로 설명되지 않는다.
- 봉인 묶음 실행기를 봉인 아닌 자료로 리허설하지 않아 첫 공식 실행을 무효로 처리해야 했다. 운영자 입력 값의 형식 오류 두 번은 결과표의 등급 표기에까지 닿았다.
- NVIDIA 쪽 오류(429·5xx)가 개발 회차 숫자를 크게 흔들었고, 원인을 우리 쪽에서 확정할 방법이 없었다.
- 구현 계획 시점 결정처럼 기록이 늦은 결정이 있었고, 결정 기록의 표기 시각이 대화 기록과 어긋나는 곳이 남았다.
- 실자료 판정 분포가 자료 보류에 치우친 원인(두 달 사이 HS10 구성 변화)은 받아들이고 공개했지만, 정책을 더 다듬을 시간은 없었다.

남은 일(`docs/tracking/status.md` "남은 일" 기준)
- 제출 절차의 교육 미션 확인과 팀장·팀원 제출(`docs/submission/SUBMISSION_FORM.md` 제출 절차).
- 제출 뒤 NVIDIA 키 재발급과 사본 정리 안내.
- `real_dev` 6차는 사용자 지시가 없어 돌리지 않았다(개발 묶음이라 동결 뒤에도 돌릴 수 있다).
- README 터미널 갈무리(선택).
- Codex 재검토는 사용량 한도가 풀린 뒤 받는다(결정 기록 `20260926-1828-user-decision-user-pages-and-review-fallback.md`).
