# 미해결 문제

## 평가 실행 중 네트워크 정책이 다시 적용돼도 드러나지 않는다

- 무엇이 깨지나: 평가 묶음 실행 도중 누가 `openshell policy set`(OpenShell, 곧 에이전트를 격리해 돌리는 NVIDIA 샌드박스 런타임의 정책 다시 불러오기 명령)으로 네트워크 정책을 바꿨다가 되돌려도, 실행 조건에 적은 라이브 정책 sha256(파일 내용의 해시)은 시험표 값과 그대로 일치한다. 그 묶음이 시험을 통과한 정책으로 끝까지 돌았다고 잘못 보고할 수 있다.
- 영향 범위: 규범 G2(팀 채점 규범에서 OpenShell을 실질적으로 썼는지 보는 게이트)의 증거와 결과 요약의 실행 조건. 봉인 묶음(개발 중 보지 않도록 봉인한 평가 자료 묶음)이면 한 번만 채점하므로 다시 돌릴 수 없다.
- 지금 풀 수 없는 이유: X1(구현 첫날의 세로형 최소 통합 시험)이 `openshell policy set`으로 다시 불러올 때마다 `CONFIG:LOADED`(정책 적용 이벤트) 행이 `policy_hash`와 함께 남는 것을 확인했다. 같은 내용을 다시 불러오면 revision(정책 판 번호)은 바뀌고 `policy_hash`는 같았다 `[사실: artifacts/openshell/violation_tests.md §3]`. 그래도 탐지 절차와 어긋났을 때의 무효 표시 규칙은 로드맵 MT5에서 정하므로 아직 판정에 걸려 있지 않다. 또 `openshell logs`는 게이트웨이가 샌드박스별로 두는 크기가 정해진 버퍼에서 읽는다. 이 버퍼는 게이트웨이를 재시작하면 사라지고, 샌드박스에서 게이트웨이로 로그를 보내는 통로는 부하가 걸리면 이벤트를 버린다 `[사실: OpenShell v0.0.116 docs/observability/accessing-logs.mdx 38·60행, X1 두 감사 로그 첫 줄의 버퍼 경고]`. 이렇게 행을 버릴 수 있는 출처에서는 "`CONFIG:LOADED`가 없다"는 사실이 재적용이 없었다는 증거가 되지 않는다.
- 가능한 방법: 로드맵 MT5 완료 기준대로 X1 확인 뒤 탐지 방법을 정한다(예: 실행 기간에 `CONFIG:LOADED`가 없음을 확인하고, 어긋나면 그 묶음의 OpenShell 증거를 무효로 표시). 지금은 평가 스킬 ②(Agent Skills 형식의 성능 평가 작업 절차)가 봉인 실행을 다시 잇기 전에 라이브 정책을 재조회해 비교하는 것까지만 한다. MT5 입력: 행을 버리지 않는 대조 출처로 샌드박스 안 로그 파일(`/var/log/openshell.*.log`, 완전한 기록)이나 OCSF(보안 이벤트 형식) JSON 내보내기를 쓰는 안을 검토한다 `[사실: OpenShell v0.0.116 docs/observability/accessing-logs.mdx 40·60행]`.

## 정책 해시에 쓰는 경로 치환 규칙이 아직 하나가 아니다

- 무엇이 깨지나: 라이브 정책 조회 본문을 커밋하기 전에 로컬 절대경로를 바꿔 적는 규칙이 문서마다 조금씩 다르다(평가 스킬 ②는 변수 이름이나 봉인 폴더 기본값, 운용 규칙 §7.6은 저장소 상대경로). 치환 방식에 따라 봉인 입력 하위 경로만 들인 정책과 봉인 폴더 전체를 들인 정책이 치환 뒤 같은 본문·해시가 될 수 있다. 그러면 "공식 채점용" 증거와 룰북 B7의 실행 조건 대조로 범위가 넓은 정책을 가려내지 못한다.
- 영향 범위: 공식 채점 대상 실행 전용 샌드박스의 격리 증거와 규범 G2의 허용 증거.
- 지금 풀 수 없는 이유: 조회 출력의 형식이 X1 실측 전 `[미확인]`이라 바이트 추출 규칙과 치환 규칙을 함께 정해야 한다. 로드맵 MT5 완료 기준이 이 결정을 맡는다.
- 가능한 방법: MT5에서 치환 규칙을 하나로 정할 때 "치환 뒤에도 봉인 입력 하위 경로만 들인 정책과 봉인 폴더 전체를 들인 정책의 해시가 달라야 한다"를 확인 조건으로 둔다. 평가 스킬 ② 공식 채점 단계 4는 라이브 정책 조회 결과로 통과 기준을 보고, 경로 치환은 커밋할 때 한다 `[추론: 평가 스킬 ② 공식 채점 단계 4]`.

## 샌드박스 밖 실행기의 봉인 해시 대조 경로를 시험할 방법이 없다

- 무엇이 깨지나: 로드맵 MT7은 샌드박스 밖 실행기(샌드박스 밖에서 봉인 해시를 대조하고 사례 식별자를 샌드박스 안 CLI에 넘기는 프로그램)와 추출 명령을 `dev20`(개발용 합성 사례 20건)·`real_dev`(개발용 실자료 묶음)로 리허설하고, 리허설과 시험은 실제 봉인 폴더에 닿지 않게 한다. 그러면 실행기의 첫 단계인 봉인 해시 대조 경로는 공식 채점 전까지 한 번도 돌지 않는다. 봉인 폴더 위치 환경변수(`TRADESENTRY_SEALED_DIR`)가 비어 있으면 실제 봉인 폴더가 기본값이 되는 점도 리허설에서 조심할 곳이다.
- 영향 범위: 봉인 묶음 채점의 첫 단계. 공식 채점에서 처음 실패하면 한 번만 채점하는 묶음의 일정이 밀린다.
- 지금 풀 수 없는 이유: 실행기와 해시 대조 코드가 아직 없고, 시험용 해시 목록을 어디에 어떤 이름으로 둘지는 앱 뼈대(S0)에서 정할 파일 배치에 달려 있다.
- 가능한 방법: 합성 파일과 합성 해시 목록을 시험용 임시 폴더에 두고 봉인 폴더 경로를 그 폴더로 준 채 해시 대조(일치·불일치·목록 밖 파일)를 시험한다. MT7 착수 때 정한다.

## `detect`에 탐지 대상 시계열을 `real_dev`로 좁힐 수단이 없다

- 무엇이 깨지나: 지금 설계대로 개발·시연 중에 v2 전체로 `tradesentry detect`를 돌리면 `real_sealed`(봉인한 실자료 평가 묶음) 시계열의 경보가 나온다.
- 영향 범위: `real_sealed`를 개발에 쓰지 않는다는 규칙이 무너지고, 대표 지표의 A등급 근거가 약해진다.
- 지금 풀 수 없는 이유: CLI가 아직 없고, 인자 형식은 앱 뼈대(S0) 자문 명세서의 열린 질문이다(`docs/plan/SCAFFOLD_BRIEF.md` Q18, 위험 25). 외부 자문이 "반영 없음"이라 S0 작업이 제안하고 오케스트레이터가 결정 기록으로 정한다(결정 기록 `20260924-2035-user-decision-s0-no-advisory.md`).
- 가능한 방법: `detect`·`run-case`가 분할 기록과 묶음 이름을 받아 그 묶음의 시계열만 다루고 기본값을 `real_dev`로 두는 안. 그 전까지는 작업 지시와 기록으로 막는다.

## `g1` 동결이 최종 스냅샷 빌드보다 늦다

- 무엇이 깨지나: 로드맵 DT7 ②(`policy_v1` 승인 뒤 승격 규칙을 적용한 최종 스냅샷 빌드를 동결하고 `normalized_sha256`(정규화한 스냅샷 내용의 해시)을 커밋하는 일)의 빌드는 비교국 표 `data/reference/peer_group_g1.csv`를 스냅샷 SQLite에 적재한다(`docs/rules/DATA_CONTRACT_V1.md` §2.2의 저장 문장, `docs/plan/UNITS.md`의 단위 S2 입력). 그런데 `g1`(BACI 유사도로 고른 비교국 목록) 동결(로드맵 MT6, 시한 2026-09-26(토) 12:00 전)은 로드맵의 순서에서 2026-09-25(금)의 DT7 ②보다 뒤에 있다(`docs/plan/ROADMAP.md` §2.6). 동결 뒤 비교국 표를 다시 적재하면 `normalized_sha256`이 바뀐다 `[추론]`.
- 영향 범위: 근거 ID(주장이 가리키는 스냅샷 행의 식별자)의 안정성, 채점 전 `normalized_sha256` 대조(평가 스킬 ② 사전 점검 단계 4의 3번), 봉인 묶음을 만든 스냅샷의 동결.
- 지금 풀 수 없는 이유: PR #18(도메인 재편 A안 반영) 검토에서 드러났지만 그 PR이 만든 문제는 아니다. 로드맵의 선후 관계를 바꾸는 일이라 사용자·오케스트레이터 결정이다.
- 가능한 방법: DT7 ②의 선행 작업에 "`g1` 동결 또는 `g0`(고정 비교국 목록) 대체 선언"을 더한다.
- 기한: 로드맵 DT7 ② 전. 로드맵 §6.1 사용자 확인 항목에 같은 기한으로 올렸다.

## 같은 OS 사용자로 도는 에이전트의 봉인 폴더 열람을 기술적으로 막지 못한다

- 무엇이 깨지나: 봉인 폴더는 저장소 밖에 있지만, 같은 사용자 권한으로 도는 에이전트가 지시를 어기고 읽으면 막을 장치가 없다.
- 영향 범위: holdout40(봉인한 합성 평가 사례 40건)과 `real_sealed`의 등급 근거. 노출이 확인되면 숫자 등급 판정의 입력이 된다.
- 지금 풀 수 없는 이유: 한 사람이 로컬에서 돌리는 구성이라 OS 계정 분리는 범위 밖이다. 기술적 차단은 런타임 샌드박스에만 있다.
- 가능한 방법: 지시와 기록, 해시 대조로 관리하고 한계를 제출서에 밝힌다(`docs/rules/PARALLEL_DEV_RULES.md` §6.4).

## 인프라 실패 재실행 규칙에 빈칸이 있다

- 무엇이 깨지나: 같은 실패를 문서마다 다르게 판정할 수 있다.
  - 세션이 끊겨 중단된 실행을 평가 스킬 ②는 `FAILED`로 남기고 다시 돌리지 않는데, 룰북 B5는 "연결 실패"를 재실행 대상으로 둔다. 원인 분류 코드로 둘을 가르는 규칙이 없다.
  - "첫 실행이 모두 끝난 뒤" 재실행한다는 시점이 묶음마다인지 두 봉인 묶음 전체인지 적혀 있지 않다.
  - NIM(NVIDIA 클라우드 추론 API) 장애가 `BUDGET_EXCEEDED`·`TIMEOUT`으로 끝나면 재실행 대상에서 빠지는데, 로드맵과 개발 플랜은 재실행을 NIM 500 대응으로 적는다.
  - 룰북 B7의 holdout40 결과 양식에 재실행 칸이 없다.
- 영향 범위: 대표 지표와 보조 지표의 분모, 봉인 묶음의 한 번만 채점 원칙.
- 지금 풀 수 없는 이유: 어떤 실패를 다시 돌릴지는 평가 규칙의 선택이다. 룰북 부록 23번(인프라 실패 재실행)이 이미 `RB-1` 동결 때 사용자 확인 항목이므로 그때 함께 정해야 한다. 원인 분류 코드 이름은 S0 자문의 열린 질문이다(`docs/plan/SCAFFOLD_BRIEF.md` Q21).
- 가능한 방법: `RB-1` 동결 전 룰북 개정 PR(GitHub 변경 요청)로 B5·B7과 자료 계약 §3.3을 함께 정한다.

## 봉인 해시 목록의 생성 시각·생성 주체를 얻을 경로가 없다

- 무엇이 깨지나: 자료 계약 §12.2는 해시 목록에 파일별 `created_at`(생성 시각)·`created_by`(생성 주체)를 적게 하는데, 생성 에이전트는 파일 이름과 sha256만 보고하고 목록을 쓰는 데이터 트랙 에이전트는 봉인 폴더를 열지 않는다.
- 영향 범위: 로드맵 DT6·DT7의 `[봉인 해시]` PR.
- 지금 풀 수 없는 이유: 생성 에이전트가 보고해도 되는 항목을 넓히는 일이라 봉인 절차(병렬 개발 규칙 §6.6, 운용 규칙 §1.2)의 변경이다.
- 가능한 방법: 보고 허용 항목에 파일별 생성 시각·생성 주체(내용이 아닌 메타데이터)를 더하는 안. DT6 착수 전에 정한다.

## 공동 작업이 모델 트랙 소유 증거 파일에 쓴다

- 무엇이 깨지나: 계획 경로 표에서 `artifacts/openshell/`은 모델 트랙(보안 검토) 소유인데, 공동 작업 V1·F2가 그 시험표에 "공식 채점용" 행을 쓴다. 모델 트랙 MT7의 산출물에는 채점기(DT8) 몫인 주장 채점 기록 `scorer_claims-{시각}.jsonl`도 들어 있다.
- 영향 범위: 파일 소유 규칙(병렬 개발 규칙 §1)과 PR 검토자 배정.
- 지금 풀 수 없는 이유: 소유 트랙이 아니면 읽기만 하고 소유 트랙에 변경을 요청해야 하므로(병렬 개발 규칙 §1.2·§1.3), 예외를 두려면 소유 트랙이 정하고 결정 기록에 남겨야 한다 `[추론]`.
- 가능한 방법: 시험표의 "공식 채점용" 행은 평가 스킬 ② 실행 주체가 쓰고 모델 트랙이 검토하는 예외로, 주장 채점 기록 `scorer_claims-{시각}.jsonl`은 채점기가 쓰는 것으로 정한다. S0에서 파일 배치를 정할 때 함께 정한다.

## 비밀값·로컬 경로 검사 스크립트를 만드는 작업이 없다

- 무엇이 깨지나: 모든 PR의 완료 기준에 비밀값·로컬 경로 검사가 들어 있는데(로드맵 §2.1, 운용 규칙 §5.2), 그 스크립트를 누가 어디에 만드는지가 없다.
- 영향 범위: 구현 첫 PR부터의 병합 조건.
- 지금 풀 수 없는 이유: 스크립트 위치는 앱 폴더 구조를 정하는 S0에 달려 있다.
- 가능한 방법: S0 산출물에 넣고, 위치를 앱 뼈대 자문의 Q20(표에 없는 파일 위치)에서 정한다. 검사 패턴에는 홈 폴더 경로(`~/`로 시작하는 경로)도 넣는다. 예외는 봉인 폴더 기본값 `~/.tradesentry/sealed/` 하나다. PR #17 검토에서 이 형태가 지금의 검사를 빠져나간 것이 드러났다. 현재 저장소를 공개로 바꾸는 방식을 고르면 검사 대상에 모든 PR 참조(GitHub가 PR마다 두는 원격 참조 `refs/pull/*`)를 넣는다. 병합된 PR의 중간 커밋도 이 참조로 원격에 남기 때문이다.

## 대체 경로의 규범 G2 영향이 룰북과 다르게 적혀 있다

- 무엇이 깨지나: 개발 플랜 §5.3·§5.4와 로드맵 §7.1은 키 주입(샌드박스 안에 API 키를 두지 않고 추론 요청에 키를 붙이는 일) 두 방식이 모두 실패했을 때의 대안 예, 곧 채점용 실행을 OpenShell 없이 돌리는 안을 고르면 "규범 G2가 약해진다"고 적는다. 그런데 룰북 A1은 채점 대상 실행이 샌드박스 밖에서 돌면 규범 G2를 하드 게이트(통과하지 못하면 채점하지 않는 필수 조건) FAIL로 본다. 룰북이 개발 플랜·로드맵보다 우선한다(`docs/README.md` §3). 그 안이 사용자 결정 자료에 오르면 대가가 실제보다 작게 적힐 수 있다.
- 영향 범위: X1에서 키 주입 두 방식이 모두 실패했을 때의 사용자 결정 자료와 자기채점.
- 지금 풀 수 없는 이유: 고칠 곳이 개발 플랜과 로드맵 본문이라, 계획 문서 수정 PR과 그 검토(개발 플랜은 Codex 교차 검토 포함)가 필요하다. 이 항목을 찾은 PR #16은 결정 기록 PR이다.
- 가능한 방법: 그 경우가 생기면 결정 자료에 룰북 A1 기준(FAIL)으로 적는다(`docs/tracking/decisions/20260924-1504-user-approval-x1-exception.md`). 개발 플랜·로드맵 문구는 다음 계획 문서 수정 PR에서 룰북에 맞춘다.

## NemoClaw `agent` 래퍼가 정상 턴(OpenClaw 결과는 성공, NemoClaw 기준으로는 미완료 표식)을 종료 코드 1로 끝낸다(`replayInvalid`)

- 무엇이 깨지나: X1 시연 샌드박스에서 한 줄 경로가 통과한 턴도 `nemoclaw <이름> agent`(NemoClaw가 OpenClaw 에이전트 턴 하나를 대신 실행하는 명령)는 종료 코드 1로 끝났다. OpenClaw 결과는 `status: ok`, `stopReason: stop`, 도구 실패 0이었고 CLI 결과 JSON도 고치지 않은 채 돌아왔다. 그러나 결과 메타데이터에 `replayInvalid: true`가 있어 래퍼가 1을 냈다 `[사실: artifacts/openshell/violation_tests.md §6.3 DA2·DA4, NemoClaw v0.0.124 저장소 docs/reference/commands.mdx의 agent 명령 설명]`. NemoClaw 문서는 결과가 성공이어도 메타데이터에 `replayInvalid: true`가 있으면 래퍼가 1을 내고 미완료 턴으로 알린다고 적는다 `[사실: NemoClaw v0.0.124 docs/reference/commands.mdx 1288행]`. 이 판(OpenClaw 2026.7.1)에서 `replayInvalid`가 붙은 원인은 `[미확인]`이다.
- 영향 범위: MVP 합격 체크리스트 1번의 증거(`docs/plan/ROADMAP.md` §3). 래퍼 종료 코드로 성공을 세면 X1의 성공 턴도 실패로 잡힌다 `[추론]`. 요청 하나에 CLI가 두 번 돈 경우(X1 4판 턴)를 세는 법은 아래 "가능한 방법"의 D5로 정했다.
- 지금 풀 수 없는 이유: `replayInvalid`가 무엇을 검사한 결과인지 문서와 실측으로 가리지 못했다. X1 4판 턴에서는 OpenClaw가 exec(셸 명령 실행 도구)를 두 번 불러 CLI가 두 번 돈 일도 있었다(DA4). 이것과 관련이 있는지도 `[미확인]`이다. OpenClaw 기본 브랜치 소스는 exec 같은, 부작용이 있을 수 있는 도구가 돌면 `replayInvalid`를 켠다 `[추론: OpenClaw main 소스, 2026.7.1 판은 확인 안 함]`. 그렇다면 스킬 턴마다 래퍼가 1을 낼 수 있다.
- 가능한 방법: 스킬 호출 성공률은 로드맵 §3 1번의 정의(시연 요청 가운데 스킬 호출이 CLI 실행까지 이어진 비율)대로 CLI 실행 기록(`outputs/{실행명}/`의 앱 기록·NAT 실행 추적. X1 때의 기록은 옛 위치 `artifacts/runs/`에 있다)으로 센다. 래퍼 종료 코드와 `replayInvalid` 값은 증거에 따로 적는다. 원인 조사는 MT5에서 한다. 래퍼가 안내한 세션 내보내기(`nemoclaw <이름> sessions export <key>`)로 턴 기록을 보는 방법이 있다 `[추론]`. MVP 합격 체크리스트 1번의 증거를 세는 규칙은 2026-09-24(목) 사용자 승인으로 정했다(결정 기록 `20260924-2315-user-decision-impl-plan-approval.md` D5, 로드맵 V1 행). 스킬 호출 성공률은 요청 단위로 센다. 분자는 CLI 실행 기록이 남은 요청이다. NemoClaw `agent` 래퍼가 정상 턴을 종료 코드 1로 끝내는 경우(`replayInvalid`)는 따로 적고 실패로 세지 않는다. 요청 하나에 CLI가 두 번 돌면 1건으로 세고 중복 수를 기록한다. 남은 것은 원인 조사(MT5)다.
