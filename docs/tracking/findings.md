# 미해결 문제

## 평가 실행 중 네트워크 정책이 다시 적용돼도 드러나지 않는다

- 무엇이 깨지나: 평가 묶음 실행 도중 누가 `openshell policy set`(OpenShell, 곧 에이전트를 격리해 돌리는 NVIDIA 샌드박스 런타임의 정책 다시 불러오기 명령)으로 네트워크 정책을 바꿨다가 되돌려도, 실행 조건에 적은 라이브 정책 sha256(파일 내용의 해시)은 시험표 값과 그대로 일치한다. 그 묶음이 시험을 통과한 정책으로 끝까지 돌았다고 잘못 보고할 수 있다.
- 영향 범위: 규범 G2(팀 채점 규범에서 OpenShell을 실질적으로 썼는지 보는 게이트)의 증거와 결과 요약의 실행 조건. 봉인 묶음이면 한 번만 채점하므로 다시 돌릴 수 없다.
- 지금 풀 수 없는 이유: 재적용마다 `openshell logs`에 `CONFIG:LOADED`(정책 적용 이벤트) 행이 남는지와 그 행 형식이 X1(구현 첫날의 세로형 최소 통합 시험) 실측 전 `[미확인]`이다. 확인되지 않은 형식에 판정 절차를 걸 수 없다.
- 가능한 방법: 로드맵 MT5 완료 기준대로 X1 확인 뒤 탐지 방법을 정한다(예: 실행 기간에 `CONFIG:LOADED`가 없음을 확인하고, 어긋나면 그 묶음의 OpenShell 증거를 무효로 표시). 지금은 평가 스킬 ②가 봉인 실행을 다시 잇기 전에 라이브 정책을 재조회해 비교하는 것까지만 한다.

## 정책 해시에 쓰는 경로 치환 규칙이 아직 하나가 아니다

- 무엇이 깨지나: 라이브 정책 조회 본문을 커밋하기 전에 로컬 절대경로를 바꿔 적는 규칙이 문서마다 조금씩 다르다(평가 스킬 ②는 변수 이름이나 봉인 폴더 기본값, 운용 규칙 §7.6은 저장소 상대경로). 치환 방식에 따라 봉인 입력 하위 경로만 들인 정책과 봉인 폴더 전체를 들인 정책이 치환 뒤 같은 본문·해시가 될 수 있다. 그러면 "공식 채점용" 증거와 룰북 B7의 실행 조건 대조로 범위가 넓은 정책을 가려내지 못한다.
- 영향 범위: 공식 채점 대상 실행 전용 샌드박스의 격리 증거와 규범 G2의 허용 증거.
- 지금 풀 수 없는 이유: 조회 출력의 형식이 X1 실측 전 `[미확인]`이라 바이트 추출 규칙과 치환 규칙을 함께 정해야 한다. 로드맵 MT5 완료 기준이 이 결정을 맡는다.
- 가능한 방법: MT5에서 치환 규칙을 하나로 정할 때 "치환 뒤에도 봉인 입력 하위 경로만 들인 정책과 봉인 폴더 전체를 들인 정책의 해시가 달라야 한다"를 확인 조건으로 둔다. 평가 스킬 ② 공식 채점 단계 4는 라이브 정책 조회 결과로 통과 기준을 보고, 경로 치환은 커밋할 때 한다 `[추론: 평가 스킬 ② 공식 채점 단계 4]`.

## 샌드박스 밖 실행기의 봉인 해시 대조 경로를 시험할 방법이 없다

- 무엇이 깨지나: 로드맵 MT7은 샌드박스 밖 실행기와 추출 명령을 `dev20`(개발용 합성 사례 20건)·`real_dev`(개발용 실자료 묶음)로 리허설하고, 리허설과 시험은 실제 봉인 폴더에 닿지 않게 한다. 그러면 실행기의 첫 단계인 봉인 해시 대조 경로는 공식 채점 전까지 한 번도 돌지 않는다. 봉인 폴더 위치 환경변수(`TRADESENTRY_SEALED_DIR`)가 비어 있으면 실제 봉인 폴더가 기본값이 되는 점도 리허설에서 조심할 곳이다.
- 영향 범위: 봉인 묶음 채점의 첫 단계. 공식 채점에서 처음 실패하면 한 번만 채점하는 묶음의 일정이 밀린다.
- 지금 풀 수 없는 이유: 실행기와 해시 대조 코드가 아직 없고, 시험용 해시 목록을 어디에 어떤 이름으로 둘지는 앱 뼈대(S0)에서 정할 파일 배치에 달려 있다.
- 가능한 방법: 합성 파일과 합성 해시 목록을 시험용 임시 폴더에 두고 봉인 폴더 경로를 그 폴더로 준 채 해시 대조(일치·불일치·목록 밖 파일)를 시험한다. MT7 착수 때 정한다.

## `detect`에 탐지 대상 시계열을 `real_dev`로 좁힐 수단이 없다

- 무엇이 깨지나: 지금 설계대로 개발·시연 중에 v2 전체로 `tradesentry detect`를 돌리면 `real_sealed`(봉인한 실자료 평가 묶음) 시계열의 경보가 나온다.
- 영향 범위: `real_sealed`를 개발에 쓰지 않는다는 규칙이 무너지고, 대표 지표의 A등급 근거가 약해진다.
- 지금 풀 수 없는 이유: CLI가 아직 없고, 인자 형식은 앱 뼈대(S0) 외부 자문의 열린 질문이다(`docs/plan/SCAFFOLD_BRIEF.md` Q18, 위험 25).
- 가능한 방법: `detect`·`run-case`가 분할 기록과 묶음 이름을 받아 그 묶음의 시계열만 다루고 기본값을 `real_dev`로 두는 안. 그 전까지는 작업 지시와 기록으로 막는다.

## 보고서 저장 위치가 없어 저장소만으로 다시 채점할 수 없다

- 무엇이 깨지나: 채점기 입력이 되는 보고서 객체는 실행 기록 폴더 `artifacts/runs/<run_id>/`에 남는데, 이 폴더는 커밋하지 않는다. 계획 경로 표대로면 저장소를 받은 사람이 채점을 다시 할 수 없다.
- 영향 범위: 규범 G4(재현 가능성)와 결과 숫자의 외부 검증.
- 지금 풀 수 없는 이유: 저장 위치를 S0 외부 자문에서 정하기로 했다(`docs/rules/DATA_CONTRACT_V1.md` §9.1·§10.1 `[미확인]`).
- 가능한 방법: 보고서 원문을 `artifacts/eval/<run_id>/` 아래에 커밋하는 안. 원문 표기(숫자 끝자리 0 포함)를 보존해야 한다.

## 같은 OS 사용자로 도는 에이전트의 봉인 폴더 열람을 기술적으로 막지 못한다

- 무엇이 깨지나: 봉인 폴더는 저장소 밖에 있지만, 같은 사용자 권한으로 도는 에이전트가 지시를 어기고 읽으면 막을 장치가 없다.
- 영향 범위: holdout40(봉인한 합성 평가 사례 40건)과 `real_sealed`의 등급 근거. 노출이 확인되면 숫자 등급 판정의 입력이 된다.
- 지금 풀 수 없는 이유: 한 사람이 로컬에서 돌리는 구성이라 OS 계정 분리는 범위 밖이다. 기술적 차단은 런타임 샌드박스에만 있다.
- 가능한 방법: 지시와 기록, 해시 대조로 관리하고 한계를 제출서에 밝힌다(`docs/rules/PARALLEL_DEV_RULES.md` §6.4).

## OpenShell 동작 가운데 X1 전까지 확인되지 않은 것

- 무엇이 깨지나: 아래가 예측과 다르면 위반 시험표와 규범 G2 증거의 형태가 바뀐다.
  - macOS Docker 안 리눅스 커널에서 Landlock(리눅스 커널의 파일시스템 접근 제한 기능)이 실제로 집행되는지
  - 파일시스템 거부와 허용 이벤트가 `openshell logs`에 남는지, 그 행 형식
  - 샌드박스 안 새 셸이 하네스(NemoClaw, 곧 OpenShell 위에서 에이전트를 돌리는 NVIDIA 참조 스택의 에이전트 실행 틀)가 넘기는 환경을 보는지
- 지금 풀 수 없는 이유: 설치와 실측은 X1에서 한다.
- 가능한 방법과 대체 규칙: `docs/plan/DEV_PLAN.md` §4.2·§4.4·§5.3, 룰북 부록 37번(허용 행이 없을 때의 앱 기록 대체).

## 인프라 실패 재실행 규칙에 빈칸이 있다

- 무엇이 깨지나: 같은 실패를 문서마다 다르게 판정할 수 있다.
  - 세션이 끊겨 중단된 실행을 평가 스킬 ②는 `FAILED`로 남기고 다시 돌리지 않는데, 룰북 B5는 "연결 실패"를 재실행 대상으로 둔다. 원인 분류 코드로 둘을 가르는 규칙이 없다.
  - "첫 실행이 모두 끝난 뒤" 재실행한다는 시점이 묶음마다인지 두 봉인 묶음 전체인지 적혀 있지 않다.
  - NIM(NVIDIA 클라우드 추론 API) 장애가 `BUDGET_EXCEEDED`·`TIMEOUT`으로 끝나면 재실행 대상에서 빠지는데, 로드맵과 개발 플랜은 재실행을 NIM 500 대응으로 적는다.
  - 룰북 B7의 holdout40 결과 양식에 재실행 칸이 없다.
- 영향 범위: 대표 지표와 보조 지표의 분모, 봉인 묶음의 한 번만 채점 원칙.
- 지금 풀 수 없는 이유: 어떤 실패를 다시 돌릴지는 평가 규칙의 선택이다. 룰북 부록 23번(인프라 실패 재실행)이 이미 `RB-1` 동결 때 사용자 확인 항목이므로 그때 함께 정해야 한다. 원인 분류 코드 이름은 S0 자문의 열린 질문이다(`docs/plan/SCAFFOLD_BRIEF.md` Q21).
- 가능한 방법: `RB-1` 동결 전 룰북 개정 PR(GitHub 변경 요청)로 B5·B7과 자료 계약 §3.3을 함께 정한다.

## 봉인 해시 목록의 생성 시각·생성 주체를 얻을 경로가 없다

- 무엇이 깨지나: 자료 계약 §12.2는 해시 목록에 파일별 `created_at`(생성 시각)·`created_by`(생성 주체)를 적게 하는데, 생성 에이전트는 파일 이름과 sha256만 보고하고 목록을 쓰는 데이터 트랙 에이전트는 봉인 폴더를 열지 않는다.
- 영향 범위: 로드맵 DT6·DT7의 `[봉인 해시]` PR.
- 지금 풀 수 없는 이유: 생성 에이전트가 보고해도 되는 항목을 넓히는 일이라 봉인 절차(병렬 개발 규칙 §6.6, 운용 규칙 §1.2)의 변경이다.
- 가능한 방법: 보고 허용 항목에 파일별 생성 시각·생성 주체(내용이 아닌 메타데이터)를 더하는 안. DT6 착수 전에 정한다.

## `checklist` 모드에서 검증기가 막았을 때의 상태가 정해지지 않았다

- 무엇이 깨지나: 검증기는 `freeform`(모델이 사실 주장의 값을 직접 쓰는 기준선 비교 모드)을 뺀 모든 모드에서 막고, 막히면 예산 안의 수정 단계로 간다. 모델이 없는 `checklist`(고정 체크리스트 비교 모드)에는 수정 단계가 없어, 막힌 뒤의 실행 상태가 어디에도 없다.
- 영향 범위: holdout40 비교군 `checklist`의 분모와 실행 상태 집계.
- 지금 풀 수 없는 이유: 실행 상태의 정의는 공용 약속(자료 계약 §3.3)이라 사용자 승인이 필요하다.
- 가능한 방법: "수정 단계 없이 곧바로 `INVALID`"로 정하는 안. 모델 트랙 MT3 착수 전에 정한다.

## 공동 작업이 모델 트랙 소유 증거 파일에 쓴다

- 무엇이 깨지나: 계획 경로 표에서 `artifacts/openshell/`은 모델 트랙(보안 검토) 소유인데, 공동 작업 V1·F2가 그 시험표에 "공식 채점용" 행을 쓴다. 모델 트랙 MT7의 산출물에는 채점기(DT8) 몫인 `claims.jsonl`도 들어 있다.
- 영향 범위: 파일 소유 규칙(병렬 개발 규칙 §1)과 PR 검토자 배정.
- 지금 풀 수 없는 이유: 소유 트랙이 아니면 읽기만 하고 소유 트랙에 변경을 요청해야 하므로(병렬 개발 규칙 §1.2·§1.3), 예외를 두려면 소유 트랙이 정하고 결정 기록에 남겨야 한다 `[추론]`.
- 가능한 방법: 시험표의 "공식 채점용" 행은 평가 스킬 ② 실행 주체가 쓰고 모델 트랙이 검토하는 예외로, `claims.jsonl`은 채점기가 쓰는 것으로 정한다. S0에서 파일 배치를 정할 때 함께 정한다.

## 비밀값·로컬 경로 검사 스크립트를 만드는 작업이 없다

- 무엇이 깨지나: 모든 PR의 완료 기준에 비밀값·로컬 경로 검사가 들어 있는데(로드맵 §2.1, 운용 규칙 §5.2), 그 스크립트를 누가 어디에 만드는지가 없다.
- 영향 범위: 구현 첫 PR부터의 병합 조건.
- 지금 풀 수 없는 이유: 스크립트 위치는 앱 폴더 구조를 정하는 S0에 달려 있다.
- 가능한 방법: S0 산출물에 넣고, 위치를 앱 뼈대 자문의 Q20(표에 없는 파일 위치)에서 정한다.
