# 병렬 개발 규칙 — 모델 트랙과 데이터 트랙

TradeSentry(관세청 수입통계에서 kg당 단가와 상대국 점유율의 전년동월 급변을 경보로 잡고, 제한된 조회 도구로 반증을 시도해 담당자의 다음 업무를 제시하는 에이전트 시스템)의 구현은 두 트랙이 동시에 진행한다. 하나는 모델 트랙(M: 판정 정책·조사 흐름·NVIDIA 연동·유사도 그룹핑)이고, 다른 하나는 데이터 트랙(D: 수집·지표·합성과 평가 자료·채점기)이다. 이 문서는 두 트랙이 서로 기다리지 않고 움직이되, 나중에 합칠 때 깨지지 않게 하는 규칙을 정한다.

|---|---|

| 작성일 | 2026-09-24(목) |

**근거 태그.** `[사실]`은 직접 확인한 것(저장소 파일이면 파일과 절을 적는다), `[추론]`은 근거가 있는 판단, `[DESIGN]`은 팀 설계 규칙(대회 공식 규칙이 아니다), `[미확인]`은 검증하지 않은 것이다. 이 문서의 규칙은 대부분 2026-09-23(수) 설계 세션에서 사용자가 확인한 결정을 옮긴 팀 설계 규칙이다. 결정 이유는 `docs/plan/DEV_PLAN.md` §13 결정 기록에 있다. 본문의 "명세 §x"는 그 결정을 담은 이번 문서 실행 명세(저장소에 커밋하지 않는 계획 문서)의 절을 가리킨다. 절마다 첫머리에 기본 태그를 적고, 다른 태그는 해당 문장에 붙인다.

## 한눈에 보기

1. 파일마다 소유 트랙이 하나다. 소유 트랙이 아닌 에이전트는 읽기만 한다. 공동 영역은 `docs/`, `tests/`, 패키지 `src/tradesentry/runlog/`·`src/tradesentry/units/`, 도메인 출력 폴더 `outputs/`(커밋 안 함)다. 예외로 봉인 폴더는 소유 트랙(D)을 포함한 두 트랙의 개발 에이전트와 Codex(교차 검토와 작은 코드 구현에 쓰는 코딩 에이전트) 모두 열거나 읽지 않는다.
2. D는 합성 시험자료(정답을 알고 규칙대로 만든 가짜 자료 묶음) `controlled_fixture_v0`를 먼저 넘긴다. M은 실자료를 기다리지 않고 그것으로 개발한다. 실스냅샷으로는 코드 변경 없이 바꿔 끼운다.
3. D가 넘기는 것은 M이 인수 조건(넘겨받는 쪽이 확인하는 완료 기준) 다섯 가지로 확인한다. 못 채우면 받지 않고 돌려보낸다.
4. 공용 약속(두 트랙이 함께 기대는 약속) 일곱 가지는 사용자 승인으로만 바꾼다. 승인을 기다리는 동안에는 그 약속에 의존하는 작업만 멈춘다.
5. holdout40(봉인 평가용 합성 사례 40건)의 입력·정답표와 `real_sealed`(대표 지표 채점용으로 떼어 둔 실자료 묶음)의 사례 목록·채점 표본은 저장소 밖 봉인 폴더(`~/.tradesentry/sealed/`)에 두고 해시(파일 내용으로 계산한 지문 값)만 커밋한다. 대표 지표는 제출서에 대표로 내세우는 숫자로, `real_sealed` 경보에서 `freeform`(모델이 사실 주장의 값을 직접 쓰고 검증기는 기록만 하는 기준선 방식)과 `full`(검증된 값만 틀에 채우고 검증기로 막는 전체 방식) 보고서의 사실 주장 오류율이다. 같은 OS 사용자로 도는 개발 에이전트와 Codex의 열람은 기술적으로 막지 못하므로 지시와 기록으로 관리한다.
6. 실자료는 기준값을 조정하기 전에 시계열 단위로, 고정한 seed(난수 생성의 시작값. 같은 seed면 같은 결과가 다시 나온다)로 `real_dev`(기준값 조정용 실자료 묶음)와 `real_sealed`로 나눈다. 조정은 `real_dev`만으로 한다.
7. 결정은 `docs/tracking/decisions/`에 남긴다. 채팅에만 남은 결정은 결정으로 치지 않는다.

## 1. 트랙과 파일 소유

이 절의 규칙은 따로 적지 않으면 `[DESIGN]`이다. 파일 소유는 분담 문서(`TRADESENTRY_TEAM_SPLIT_DECISIONS.md`) §2를 에이전트 체계로 옮긴 것이다.

### 1.1 트랙과 실행 주체

| 트랙 | 맡는 일 |
|---|---|
| 모델 트랙(M) | 판정 정책, 조사 흐름(조사자 → Critic(조사자의 초안을 별도 문맥에서 검수하는 역할) → 수정 1회), NVIDIA 연동, 유사도 그룹핑 `g1`(국가 간 연간 교역 자료 BACI로 계산한 유사도로 고른 비교 대상 국가 목록) |
| 데이터 트랙(D) | 수집과 스냅샷, 지표 계산, 자료 접근층, 합성 시험자료와 평가 자료 생성, 독립 채점기 |

- NVIDIA 연동에는 NIM(NVIDIA가 호스팅하는 모델 추론 API), NAT(NeMo Agent Toolkit. 에이전트 실행·추적·프로파일링·사후 평가 도구), OpenShell(에이전트를 격리 실행하는 NVIDIA 샌드박스 런타임), NemoClaw(모델·에이전트 하네스·보안 런타임을 묶은 NVIDIA 참조 스택), 런타임 스킬이 들어간다.
- 두 트랙 모두 Claude 보조 에이전트가 구현한다. 오케스트레이터가 작업을 나누고 병합한다.
- 도메인 검토자는 무역통계·관세, 평가 방법론, NVIDIA 스택, 보안 네 종류다. 작업 성격에 맞는 검토자만 띄운다.
- Codex headless(화면 없이 명령으로 실행하는 Codex)는 교차 검토와, 입출력·시험이 정해진 작은 코드 구현을 맡는다.
- 에이전트 하나는 한 번에 한 트랙의 작업 하나만 맡는다.
- 누구를 언제 띄우는지, 검토를 어떻게 반복하는지는 `docs/rules/AGENT_OPS.md`를 따른다.

### 1.3 공동 영역과 "읽기만" 규칙

- 소유 트랙이 아닌 에이전트는 그 파일을 읽기만 한다. 고칠 일이 생기면 직접 고치지 않고, 오케스트레이터를 거쳐 소유 트랙에 변경을 요청한다. 소유 트랙이 자기 작업으로 고친다.
- 예외: 봉인 폴더에는 "읽기만" 규칙이 적용되지 않는다. 소유 트랙(D)을 포함한 두 트랙의 개발 에이전트와 Codex는 봉인 폴더를 열거나 읽지 않는다(§6.3). 봉인 폴더를 다루는 역할은 §6.3의 셋뿐이다.
- 한 PR은 한 트랙의 소유 파일만 고친다. 공동 영역은 함께 고쳐도 된다. 두 트랙에 걸친 일은 작업을 나눈다. 예외는 두 트랙의 뼈대를 함께 만드는 S0 하나다.
- 같은 파일을 고치는 작업 두 개를 동시에 열지 않는다. 오케스트레이터가 작업을 배분할 때 겹침을 확인한다.

### 1.4 표에 없는 경로

### 2.3 인수 전 M의 작업 방식

- 인수 전에는 자료 계약(`docs/rules/DATA_CONTRACT_V1.md`)의 객체·필드와 도구 출력 봉투(도구 5개가 공통으로 돌려주는 결과 틀)를 기준으로 코드를 쓴다.
- 임시 대역(stub. 진짜 자료 대신 정해진 값을 돌려주는 가짜 함수)은 M이 만든 시험 파일 안에만 둔다. 운영 코드에 넣지 않는다.

### 2.4 실스냅샷 교체 원칙

- 모든 자료 조회는 `snapshot_id`를 받아 `dal/`을 거친다. 코드에 스냅샷 이름이나 파일 경로를 박아 두지 않는다.
- 실스냅샷으로 바꿀 때는 CLI 공통 옵션 `--snapshot`의 값만 `controlled_fixture_v0`에서 `kcs_202201_202412_v2`로 바꾼다. 코드는 고치지 않는다.
- 두 스냅샷은 같은 자료 계약(`schema_version=1`)을 따르고 `source_kind`만 다르다(`controlled`와 `real`).
- 바꿀 때 코드를 고쳐야 한다면 그것은 자료 계약이나 자료 접근층의 결함이다. M은 우회 코드를 쓰지 않고 D에게 돌려보낸다. 계약 필드를 바꿔야 하면 §4 절차를 거친다.

### 2.5 합성 숫자의 표기

- 합성 시험자료로 낸 숫자는 개발용이다. 개선 과정에 노출되므로 등급 D(채점 규범의 숫자 신뢰 등급 중 가장 낮은 단계)로 다루고, 대표 숫자로 쓰지 않는다 `[추론: SCORING_GOLDEN_RULE.md §3의 3a 숫자 4등급]`.
- A/B/C는 합성 시연 사례이며 실제 사건이 아니다. 보고서와 실행 결과 기록에 `source_kind`가 남아 합성과 실자료가 구분된다.

정책 수치 `configs/policy_v1.json`은 인수물이 아니라 공용 약속이다. 사용자 승인으로 확정한다(§4). 실자료 분할 결과는 결정 기록으로 두 트랙에 알린다(§7.2).

### 3.2 인수 조건 다섯 가지

| # | 조건 | 확인 방법 |
|---|---|---|
| 1 | 인수물마다 `schema_version=1` 표시가 있다 | 스냅샷 정보나 모듈의 계약 버전 표시에서 값을 읽는다 |
| 2 | 자료 계약 검사 명령이 통과한다 | 종료 코드 0. 검사 명령의 이름은 계획 경로·명령 표에 아직 없다 `[미확인]`. 정해지면 그 표와 이 문서를 함께 고친다 |
| 3 | 자료 접근층(`dal/`)으로 읽힌다 | `dal/`로 인수물을 열어 계약 객체를 읽는 시험이 통과한다 |
| 4 | `metrics/` 패키지가 oracle A/B/C를 재현한다 | `eval/dev/oracle_ABC.json`의 `expected`에서 아래 목록의 수치 필드가 모두 일치한다 |
| 5 | 인수물마다 검증 명령과 종료 코드가 PR에 기록돼 있다 | PR 본문에서 조건 1~4의 명령과 종료 코드를 확인한다 |

- 조건 4에서 대조하는 수치 필드는 다음과 같다 `[사실: eval/dev/oracle_ABC.json]`.
  - `unit_value`: `U0`·`U1`(기준월·비교월 단가), `r_U`(단가 전년동월 변화율), `within`·`mix`(HS10 구성효과 분해에서 품목 안 단가 변화 효과와 구성비 변화 효과), `residual`(분해 잔차)
  - `share`: `V_country_0`·`V_country_1`(해당국 금액), `V_world_0`·`V_world_1`(전체국가 금액), `s0_pp`·`s1_pp`(점유율, 퍼센트포인트), `d_s_pp`(점유율 변화)
  - C처럼 분해할 수 없는 사례의 `within`·`mix`는 null이다. 0으로 채우지 않고 null 그대로 일치해야 한다. C에는 `residual` 키가 없으므로 C의 `residual`은 대조 대상이 아니다.
  - `threshold_pp`(oracle에 적힌 점유율 판정 기준값), `triggered`(점유율 신호 발동 여부), `signals`(신호별 발동 여부)는 `metrics/`가 아니라 MT1(`policy/`) 시험에서 대조한다. 그 시험의 기준값은 policy_v1이 아니라 oracle에 적힌 개발용 정책 `dev-0.1`의 값(단가 변화율 절댓값 30% 이상, 점유율 변화 절댓값 10pp 이상)이다 `[사실: eval/dev/oracle_ABC.json]`.
  - `review_status`(판정 상태)는 조사 흐름과 근거에 달려 있다. 그래서 조건 4가 아니라 MVP 합격 체크리스트 1번이 A/B/C를 처음부터 끝까지 돌려 확인한다.
- 인수할 때마다 다섯 조건을 모두 확인한다.
- 조건 3·4는 인수물이 자료가 아닐 때도(예: `dal/`만 고친 PR) 회귀 확인으로 다시 돌린다.

### 3.3 확인과 돌려보내기

1. D는 인수물 PR 제목에 `[인수물]` 표시를 붙이고(§9.3), 본문에 조건 1~4의 명령과 종료 코드를 적는다.

### 4.2 변경 절차

기본 순서는 계약 버전 올림 → 합성 시험자료 재생성 → 양 트랙 검토 → 사용자 승인이다. 이 순서는 공용 약속 일곱 가지 모두에 같게 적용한다. 단계를 빼지 않고, 앞의 두 단계를 약속 종류에 맞게 대응시킨다. 앞뒤에 제안과 병합 단계를 붙이면 다음과 같다.

1. 제안: 바꿀 이유가 생긴 에이전트가 승인 요청 초안(§4.4)을 쓰고, 오케스트레이터가 이를 작업으로 연다. PR 제목에 `[공용 약속]`을 붙인다(§9.3).
2. 버전 올림: 그 약속에 해당하는 버전을 올린다.
   - 자료 형식·상태값: `schema_version`. 세부는 `docs/rules/DATA_CONTRACT_V1.md` §13 변경 절차를 따른다.
   - 기준값: `policy_version`(정책 수치의 버전 표시)
   - 비교 대상(그룹핑): `grouping_version`
   - 그 밖의 평가 구성: 룰북 버전(실행 결과 기록 키 `rulebook_version`)
   - 품목·국가 확정: 새 `snapshot_id`로 새 스냅샷을 만든다(§10.1).
   - 도구 한도·제출서 주장 문구: 그 값을 담은 설정이나 문서의 버전. 어느 버전을 올리는지 승인 요청에 적는다.
3. 합성 시험자료 재생성: 영향받는 합성 자료와 정답표를 다시 만들거나 다시 검증한다.
   - 자료 형식·상태값이 바뀌면 D가 합성 시험자료를 새 버전 표시로 다시 만들고 §3 인수 조건을 다시 돌린다.
   - 기준값이 바뀌면 oracle A/B/C와 dev20·holdout40 정답표의 발동 여부·기대 상태가 달라질 수 있다. oracle A/B/C는 `r_U` = -0.4(절댓값 40%), 부모 금액 600 → 360, 중량 100으로 설계돼 있다. 단가 기준 30%에서 단가 신호가 발동하고, 점유율 판정 기준 `threshold_pp` 10에서는 점유율 신호가 발동하지 않는다(점유율 변화 -4pp) `[사실: eval/dev/oracle_ABC.json]`. 이 파일은 고치지 않으므로 다시 검증한다. holdout40은 §6.7에 따라 다시 만든다.
   - 영향이 없으면 그 사실과 이유를 승인 요청의 "영향" 칸에 적는다.
4. 양 트랙 검토: M 쪽과 D 쪽 에이전트가 각각 깨지는 코드·시험·자료를 확인하고 결과를 PR에 남긴다.
5. 사용자 승인: 오케스트레이터가 승인 요청을 사용자에게 올린다. 사용자 승인은 약속 종류와 관계없이 모두 필요하다. 승인이나 거절과 그 날짜를 결정 기록에 남긴다.
6. 병합: 승인을 받은 뒤에만 main에 병합한다. 거절되면 PR을 닫고 현행 약속을 유지한다.

- 처음 정하는 값도 같은 승인을 거친다. policy_v1 수치는 D가 `real_dev` 개발 묶음 통계로 제안하고, 사용자가 승인하면 `configs/policy_v1.json`에 기록한다.
- S0 외부 자문이 공용 약속을 바꾸자고 하면 같은 절차를 거친다.
- 검토 이견이 공용 약속에 해당하면 오케스트레이터가 결정하지 않고 사용자에게 올린다.

### 4.3 승인을 기다리는 동안

- 그 약속에 의존하는 작업만 멈춘다. 의존한다는 것은 바뀌는 필드·값·한도를 읽거나 쓰는 코드·시험·자료를 다룬다는 뜻이다.
- 나머지 작업은 현행 약속으로 계속한다. 바뀔 약속을 미리 가정한 코드는 main에 병합하지 않는다.
- 오케스트레이터는 멈춘 작업과 이유를 기록한다. 승인이 늦어져 2026-09-25(금) MVP 시험이나 2026-09-26(토) 12:00 `RB-1` 동결이 위험해지면 그 사실을 승인 요청에 적는다.

### 4.4 승인 요청 양식


### 4.5 공용 약속이 아닌 세부

- 그 밖의 세부(계약 밖 내부 함수·모듈 구조, 시험 배치 등)는 소유 트랙 에이전트가 정하고 결정 기록에 남긴다.
- 공용 약속인지 애매하면 공용 약속으로 보고 §4.2 절차를 밟는다.

## 6. 봉인 자료 규칙

이 절의 규칙은 따로 적지 않으면 `[DESIGN]`이다. 평가 쪽 규칙(`docs/eval/RULEBOOK.md` B6 동결과 봉인)과 평가 스킬 ②(`skills/tradesentry-eval/SKILL.md`)의 봉인 자료 취급은 이 절과 같아야 한다.

### 6.1 대상과 위치

- 봉인 자료(평가 전까지 개발 과정에 노출하지 않도록 저장소 밖에 격리해 두는 평가 자료)는 다음 둘이다.
  - holdout40의 입력과 정답표
  - `real_sealed`의 사례 목록과 채점 표본
- 위치는 저장소 밖 봉인 폴더다. 기본값은 `~/.tradesentry/sealed/`이고, 환경변수 `TRADESENTRY_SEALED_DIR`로 바꿀 수 있다.
- 봉인 폴더는 저장소 안에도, 에이전트 작업 폴더(git worktree: 한 저장소에서 브랜치마다 따로 여는 작업 폴더) 안에도 두지 않는다. 저장소 안에 두고 `.gitignore`로 숨기는 방식도 쓰지 않는다.
- 봉인 묶음 실행 사슬의 출력(샌드박스에서 내려받은 출력과 샌드박스 밖에서 생기는 봉인 관련 출력)은 저장소 안 `outputs/sealed/` 아래 자기 실행 폴더(커밋 안 함)에 둔다. 이것은 봉인 자료가 아니라 실행 출력이라 위 규칙과 부딪치지 않고, 금지 해제 조건 전에는 열지 않는다(자료 계약 §10.3 N10). 거꾸로 실행 출력을 봉인 폴더에 두지 않는다. 봉인 폴더에는 격리된 생성 에이전트만 쓰고(§6.3), 해시 재대조는 목록에 없는 파일도 불일치로 보기 때문이다(§6.2, 자료 계약 §12.2).

### 6.2 해시 목록과 원본 커밋 시점

- 내용 증명용 sha256 해시 목록만 PR로 커밋한다. 해시는 내용이 조금만 바뀌어도 값이 달라지므로 변조를 드러낸다. 위치는 `eval/sealed_manifest.json`이고, 형식은 `docs/rules/DATA_CONTRACT_V1.md` §12 봉인 해시 기록을 따른다.
- 해시 목록 대상은 봉인 폴더의 파일 전부다. 입력과 정답표뿐 아니라 생성 코드, seed, 부모 원본 계열 ID, `real_sealed` 표본 seed를 담은 파일도 들어간다(§6.6, §7.3).
- 해시 목록에 적히는 파일 이름에 사례의 기대 상태나 시나리오 분류처럼 내용을 드러내는 말을 넣지 않는다.
- 범위가 좁거나 내용이 단순한 봉인 파일(seed, 부모 원본 계열 ID, 사례 ID 목록 등)은 커밋된 sha256에 후보 값을 넣어 보면 원래 값을 맞힐 수 있다 `[추론]`. 그래서 이런 파일에는 nonce(내용 추측을 막으려고 넣는 무작위 값)를 반드시 넣는다. 정답표는 사례별 작은 파일로 쪼개지 않거나, 파일마다 nonce를 넣는다.
- 원본 파일(생성 코드와 seed 포함)은 최종 채점이 끝난 뒤에 커밋한다. 최종 채점은 정답 대조 채점(샌드박스 밖에서 실행 결과를 정답과 비교하는 일)까지를 말한다. 커밋할 때 해시 목록과 다시 대조한다. 원본을 커밋할 위치는 계획 경로·명령 표에 아직 없다 `[미확인]`.

### 6.3 작업 지시와 기록

- 두 트랙의 개발 에이전트와 Codex의 작업 지시에는 봉인 폴더를 입력·작업 위치·첨부로 넣지 않는다. 대신 다음 문장을 그대로 넣는다.

  > 환경변수 `TRADESENTRY_SEALED_DIR`가 가리키는 봉인 폴더는 열거나 나열하거나 검색하지 않는다. 작업에 봉인 자료가 필요해 보이면 멈추고 오케스트레이터에게 보고한다.

- Claude 개발 에이전트의 작업 지시에는 이 문장의 "봉인 폴더" 뒤에 "(설정이 없으면 기본값 `~/.tradesentry/sealed/`)"를 덧붙일 수 있다. 금지 지시 안에서 위치를 밝히는 것은 봉인 폴더를 작업 입력으로 주는 것이 아니다. 봉인 폴더 위치는 문서에 적혀 있어 비밀이 아니다(§6.4, 명세 §3.6 정직한 한계).
- Codex의 작업 지시에는 기본 경로를 덧붙이지 않고 위 문장만 넣는다. 명세 §3.10 "Codex에는 `.env`와 봉인 경로를 주지 않는다"의 문언을 따른다 `[DESIGN]`.
- 어느 쪽이든 작업 지시에 봉인 폴더를 입력이나 작업 대상으로 넣지 않는다(명세 §3.6·§3.10).
- 개발 에이전트는 작업 폴더 밖을 넓게 검색하지 않는다(홈 폴더 전체 검색 등).
- Codex에는 `.env`와 봉인 경로를 주지 않는다. holdout40 생성은 Codex에게 맡기지 않는다(사용자 결정).
- 봉인 폴더를 다루는 역할은 셋뿐이다.
  - 격리된 생성 에이전트: 봉인 폴더에 쓴다(§6.6 1단계). 봉인 폴더를 출력 위치로 받는 유일한 작업 지시다.
  - 오케스트레이터: 평가 스킬 ②를 실행할 때 봉인 입력을 전달하고 해시를 대조한다. `real_sealed` 목록은 오케스트레이터가 돌리는 샌드박스 밖 실행기(프로그램, 로드맵 MT7)가 읽는다.
  - 샌드박스 밖 독립 채점기(`eval/scorer/`): 정답 대조 채점 때 정답표를 읽는다.
- 봉인 폴더에 닿는 사건(생성, 해시 등록, 봉인 입력 전달, 채점, 해시 재대조)은 날짜, 주체, 파일 수, 해시 대조 결과를 결정 기록에 남긴다. 봉인 자료의 내용(생성 코드, seed, 부모 원본 계열 ID, `real_sealed` 표본 seed 포함)은 정답 대조 채점이 끝나기 전에는 적지 않는다. 표본 seed는 정답 대조 채점이 끝난 뒤(§6.2의 원본 커밋 시점)에 결정 기록으로 옮긴다.

### 6.4 정직한 한계

- 봉인 폴더 위치는 이 문서에 적혀 있어 비밀이 아니다.
- 개발 에이전트와 Codex가 같은 OS 사용자로 돌기 때문에 봉인 폴더 열람을 기술적으로 막지 못한다. 지시와 기록으로 관리한다.
- Codex의 `-s read-only`(쓰기를 막는 실행 모드)와 `-s workspace-write`(작업 폴더에만 쓰게 하는 실행 모드)는 쓰기 범위를 정하는 옵션이다. 봉인 폴더나 `.env` 읽기를 막는다는 근거는 없다 `[추론]`.
- 기술적 차단은 런타임 샌드박스(OpenShell 정책)에만 해당한다.
- 해시는 변조를 드러낼 뿐 열람을 막지 않는다.
- `real_sealed` 사례 목록은 기록된 분할 seed, 동결 스냅샷, 승인된 policy_v1(과 탐지 코드)만 있으면 다시 계산할 수 있다. 그래서 `real_sealed` 봉인의 목적은 기밀이 아니고 다음 두 가지다.
  - 첫째, 개발·튜닝에 그 사례를 쓰지 않도록 지시와 기록으로 관리한다.
  - 둘째, 결과를 보기 전에 표본을 고정하고 해시로 증명한다(무결성: 자료가 바뀌지 않았음을 보일 수 있는 성질). 표본 seed는 nonce를 넣은 파일로 봉인 폴더에 둔다(§6.2). 이 조건 아래서만, 사례가 40건을 넘을 때의 표본은 봉인 폴더를 열지 않고는 다시 만들 수 없다. nonce가 없으면 seed 후보를 넣어 보며 커밋된 해시와 맞춰 보는 방식으로 표본을 알아낼 수 있다 `[추론]`.
- 분할 전인 2026-09-23(수)에 64개 시계열 전체의 집계를 이미 봤다.
  - 전년동월 비교가 가능한 조합 약 1,267개, 그중 단가 변화율 절댓값 30% 이상 771개(최소 기준 적용 전) `[사실: 2026-09-23 설계 세션의 v2 조회]`
  - 금액이 있는데 중량이 0인 행 677개, 수입 0이 명시된 달 68개월 `[사실: TRADESENTRY_FACTS_MEMO.md §3]`
  - 그래서 기준값 조정이 `real_sealed`와 완전히 떨어져 있다고 주장하지 않는다.
- 이 한계는 `docs/eval/RULEBOOK.md`와 제출서에도 적는다.

### 6.5 두 통제와 공식 채점 대상 실행 전용 샌드박스

"채점 대상 실행"은 샌드박스 안에서 돌리는 평가용 실행이고, "정답 대조 채점"은 샌드박스 밖에서 하는 비교다. 봉인에 관한 통제는 서로 다른 두 가지다.

- ① 샌드박스 파일시스템 정책(`configs/openshell/policy.yaml`)이 저장소 안의 평가 정답 경로(예: `eval/dev/` 아래 정답표) 읽기를 막도록 설정한다. OpenShell 파일시스템 정책은 허용 목록 방식이라 나열한 경로와 작업 폴더만 허용하고 나머지는 거부한다 `[사실: 03-openshell-policy-yaml-구조.md §3.6]`. 그래서 ①은 정답 경로를 허용 목록이나 샌드박스 작업 폴더에 넣지 않을 때만 성립한다.
- ①의 전제: 허용 목록은 경로 앞부분 일치 방식이다(겹치면 더 긴 앞부분이 이긴다) `[사실: 03-openshell-policy-yaml-구조.md §3.6]`. 이 판정은 DLI(NVIDIA 교육 과정) 코스 평가 함수의 모형이다. 겹치는 경로의 실제 집행은 자료 계약 §10.3 "읽기 전용 입력"을 따른다. 그래서 입력은 들이고 정답표는 빼려면 둘이 서로 다른 하위 경로에 있어야 한다. D가 입력과 정답표를 다른 하위 경로로 나누고, 그 배치를 결정 기록에 남긴다. `eval/dev/dev20/`과 봉인 폴더 안이 여기에 해당한다. 하위 경로 이름은 이 문서에서 정하지 않는다. 허용 목록에는 입력 하위 경로만 넣고 상위 폴더는 넣지 않는다. 03 문서 §2.2가 적은 파일시스템 필드(`include_workdir`, `read_only`, `read_write`)에는 거부 항목이 없어서, 상위 폴더를 넣으면 그 아래 정답표 경로를 따로 막을 수 없기 때문이다 `[추론: 03-openshell-policy-yaml-구조.md §2.2, §3.6]`.
- ② 봉인 자료를 저장소 밖에 두어 격리한다. 공식 채점 대상 실행 때에만 봉인 입력을 샌드박스에 읽기 전용으로 넣고, 정답표는 어떤 샌드박스에도 넣지 않는다.
- ①이 ②를 보장한다고 쓰지 않는다.
- ①이 실제로 작동하는지는 의도적 위반 시험(일부러 정책 위반을 시도해 막히는지 보는 시험)의 표(OpenShell 증거 폴더 `artifacts/openshell/openshell_violation_tests-{시각}/`의 시험표 `openshell_violation_tests-{시각}.md`)로 확인한다. 표에는 예측과 실측, 종료 코드와 감사 로그(OpenShell이 허용·차단 결정을 남기는 기록. `openshell logs`로 모은다)의 해당 행을 함께 남긴다.

공식 채점 대상 실행 전용 샌드박스는 다음과 같이 다룬다.

- OpenShell 정책에서 정적 계층(`filesystem_policy`, `landlock`(리눅스 커널 수준의 파일 접근 제한), `process`)은 샌드박스를 만들 때 고정된다. 동적 계층(`network_policies` 등 네트워크 쪽)만 실행 중에 다시 불러올 수 있다 `[사실: 03-openshell-policy-yaml-구조.md §2.1-1]`.
- 그래서 봉인 입력은 공식 채점 대상 실행 전용 샌드박스를 새로 만들어 넣는다. 개발·시연용 샌드박스에는 넣지 않는다.
- 봉인 입력을 읽기 전용으로 넣는 구체 방식은 로드맵 MT5에서 확정한다 `[미확인]`.
- 이 샌드박스에서는 lethal trifecta(민감 자료 읽기, 외부 입력 수용, 외부 전송 경로가 한 경로에 겹치는 위험)가 생긴다. 봉인 입력을 읽고, 도구가 돌려준 품목명 같은 외부 입력을 받고, NIM으로 요청을 보내는 일이 한곳에 겹친다.
- 완화책은 두 가지다.
  - 정답표를 샌드박스에 넣지 않는다.
  - 외부 전송은 NVIDIA 추론 엔드포인트만 허용하고, L7 규칙(HTTP 요청 수준의 규칙)의 method·path를 명시한다(`docs/plan/DEV_PLAN.md` §4).
- 두 완화책은 위험을 줄일 뿐 없애지 않는다. 정책은 목적지, 요청을 보낸 바이너리 신원, 요청의 method·path·query만 맞춰 보고 요청에 실린 내용은 보지 않는다 `[사실: 03-openshell-policy-yaml-구조.md §3.1, §3.3, §3.4, §4, HSGATE_R3_NVIDIA_STACK_CHECK.md §2, 명세 §2-10]`. 그래서 NIM 요청에는 봉인 입력에서 온 값이 실릴 수 있다. 목적지가 허용 목록에 있다는 사실을 안전의 근거로 쓰지 않는다.
- 도구가 돌려준 품목명·설명은 데이터로만 다루고 지시문으로 따르지 않는다는 조사 규칙(`docs/plan/DEV_PLAN.md`)을 이 샌드박스에서도 그대로 지킨다.

### 6.6 생성 → 봉인 → 해시 등록 → 한 번 채점

권한을 나눈 다섯 단계다. 순서를 바꾸지 않는다.

1. **생성**: holdout40 생성(로드맵 DT6)은 모델 트랙과 격리된 Claude 보조 에이전트가 맡는다.
   - 생성은 policy_v1 승인 뒤에 하고, 생성 규칙에 `policy_version`을 적는다.
   - 입력은 시나리오 명세(`eval/scenarios/SCENARIO_SPEC.md`)와 생성 규칙(자료 계약 형식 포함)뿐이다.
   - 결과(입력과 정답표)를 봉인 폴더에 직접 기록하고 저장소에는 쓰지 않는다. 생성 코드, seed, 부모 원본 계열 ID도 봉인 폴더에 두고 저장소에 쓰지 않는다.
   - 런타임 코드를 쓰지 않는다. 정답표는 운영 코드를 복사하지 않은 독립 구현으로 만든다.
   - 이 에이전트의 대화 기록은 모델 트랙뿐 아니라 D 트랙의 다른 에이전트와 Codex에도 넘기지 않는다.
   - 봉인 직전에 자체 검산을 돌린다. 사례별 발동 여부는 정답표의 표시를 믿지 않고 생성된 자료에서 다시 계산한다. 이 계산은 생성 코드와도 런타임 모듈과도 별도로 하고, 생성 규칙에 적은 `policy_version`의 기준값을 쓴다. 그 결과를 정답표의 발동 여부·기대 상태와 대조하고, 합계(시나리오 분류별 사례 수와 전체 40건)를 확인한다(구 개발계획 `Pasted markdown.md` §8.1 "생성 자료를 독립 검사"). 오케스트레이터에게는 통과 여부와 개수만 보고한다.
2. **봉인**: 생성 에이전트가 생성 직후 그 묶음의 파일 전부(§6.2)에 대해 파일별 sha256 목록을 만든다. 오케스트레이터에게는 해시 목록(파일 이름과 sha256)만 보고한다.
3. **해시 등록**: 해시 목록만 PR로 커밋한다(`eval/sealed_manifest.json`, PR 제목 표시 `[봉인 해시]`). 해시 목록은 오케스트레이터를 거쳐 D 쪽 에이전트에게 넘어가고, 그 에이전트는 봉인 폴더를 열지 않는다. 검토는 평가 방법론·보안 검토자가 맡는다.
4. **한 번 채점**: `RB-1` 동결 뒤 오케스트레이터가 평가 스킬 ②를 실행할 때만 봉인 입력을 공식 채점 대상 실행 전용 샌드박스에 읽기 전용으로 넣는다(§6.5). 정답표는 어떤 샌드박스에도 넣지 않는다. 샌드박스 밖 독립 채점기(`python -m eval.scorer --run <run_dir>`)만 정답표를 읽는다.
5. **해시 재대조**: 채점 전에 해시를 다시 대조한다. 일치하지 않으면 그 묶음을 무효로 하고 사용자에게 올린다.

- `real_sealed`의 사례 목록과 채점 표본도 같은 다섯 단계를 따른다. 표본 seed도 봉인 폴더에 두어 해시 목록 대상에 넣고, 결정 기록에는 정답 대조 채점이 끝난 뒤에 옮긴다. 생성 방법은 §7.3에 있다. 다만 `real_sealed`에서 4단계의 봉인 입력 전달은 룰북 B5와 부록 40번(사용자 확인 대기)을 따른다. 지금 안은 목록·표본 파일을 샌드박스에 넣지 않고, 샌드박스 밖 실행기(프로그램, 로드맵 MT7)가 해시 대조 뒤 사례 식별자를 `run-case`에 한 건씩 넘기는 것이다.
- 봉인 입력을 샌드박스에 넣기 전에도 해시를 대조한다.

- `RB-1` 전에 policy_v1이나 탐지 코드가 바뀌면, 영향받는 봉인 묶음(holdout40, `real_sealed` 사례 목록과 표본)을 다시 만들고 해시를 다시 등록한다. 봉인 묶음을 다시 만들 때도 처음 정한 seed를 그대로 쓴다.
- 동결 뒤 holdout40과 `real_sealed`는 한 번만 채점한다. 봉인 채점 시작은 목표 2026-09-26(토) 14:00, 늦어도 2026-09-27(일) 06:00이다.
- 동결 조건이 하나라도 빠지면 평가 스킬 ②는 봉인 자료 채점을 거부한다. dev20·`real_dev` 실행은 허용한다.
- 실패·미실행·timeout·invalid는 분모에 남긴다. 결과를 본 뒤 어려운 사례를 지우거나 규칙을 바꾸지 않는다.
- 인프라 오류로 실패한 실행을 다시 돌릴지와 그 조건은 `docs/eval/RULEBOOK.md` B5(실행 규칙)를 따른다. 이 문서는 재실행 규칙을 따로 정하지 않는다.

### 6.8 holdout40과 dev20의 분리

- 구 개발계획(`Pasted markdown.md`) §8.1의 10개 시나리오 분류와 개발 20건·평가 40건 배분을 따른다.
- 기초 시계열·하위품목 구조·결측 방식·부모 원본 계열 ID 단위로 dev20과 나눈다. 같은 계열의 규모·seed 변형은 한쪽에만 둔다.
- 공개 시나리오 명세에는 분류 수준의 규칙만 적는다. 사례별 기대 상태와 생성 계열은 적지 않는다(구 개발계획 §5.2가 숨길 대상으로 정한 것).
- 생성 규칙에는 dev20이 이미 쓴 부모 원본 계열 ID를 제외 목록으로 넣는다.
- 합성 자료의 등급은 C 또는 D다. holdout40의 근거 충족 처리정확도(예상 상태가 맞고 필수 근거·수치와 단위·출처와 버전을 갖추고 실행이 정상으로 끝난 사례의 비율. 분모 40)는 보조 지표(대표 지표를 보완하는 C등급 지표)다. dev20 결과는 개선 과정에 노출된 값(D)이다(`docs/eval/RULEBOOK.md` A5).

## 7. 실자료 분할 절차

이 절의 규칙은 따로 적지 않으면 `[DESIGN]`이다.

### 7.1 원칙

- 분할 대상은 스냅샷 `kcs_202201_202412_v2`의 품목(HS6)×상대국 시계열 64개(HS6 4개 × 상대국 16개)다.
- 전체국가(`ALL`) 분모 계열은 나누지 않고 두 묶음의 점유율 계산에 함께 쓴다 `[추론: 64개는 상대국 시계열만 센 수이고, 분모는 두 묶음 모두 필요하다]`.
- 시계열 단위로 나눈다. 같은 시계열의 달이 두 묶음에 섞이지 않는다.
- 기준값을 조정하기 전에, 고정 난수로, 한 번만 나눈다.
- 기준값과 최소 기준은 `real_dev`만으로 조정한다. 산문 패턴 목록(설명 문장 속 숫자·증감 표현을 잡는 결정적 패턴 목록. `RB-1`과 함께 동결한다)의 누락 사례도 `real_dev`에서만 보강한다.
- 분할 전에 64개 시계열 전체의 집계를 이미 본 한계는 §6.4에 적었다.
- 이유: 기준값은 개발 자료를 보며 조정될 가능성이 크다. 조정에 쓰는 자료와 대표 지표를 채점하는 자료를 조정 전에 갈라 둬야 정답이 개선 과정에 새지 않는다.

### 7.2 절차

1. 시점: 2026-09-24(목), D가 policy_v1 수치를 제안하기 전(로드맵 DT4).
2. 분할: seed를 정하고 `real_dev` : `real_sealed` = 1:2로 나눈다. 비율과 seed는 조정값이며 기록한다.
3. 기록: seed, 비율, 분할 방법, 입력 스냅샷, 결과(`real_dev` 시계열 목록)를 결정 기록에 남겨 두 트랙에 알린다. 결과를 본 뒤 다시 나누지 않는다.
4. 조정: D가 `real_dev` 개발 묶음 통계로 기준값(`min_amount`, `min_weight`, 변화율·점유율 기준 등)을 제안한다. 사용자가 승인하면 `configs/policy_v1.json`에 기록한다(§4).
5. 개발 실행 범위: 동결 전에 `real_dev`로 좁히는 것은 다음 두 가지뿐이다.
   - 경보·사례 선택: 개발 실행에 쓰는 경보와 사례는 `real_dev` 시계열에서만 고른다. `real_sealed` 시계열로 경보를 뽑아 보거나 조사 흐름을 돌려 보지 않는다.
   - 조정 통계: 기준값과 산문 패턴 목록을 조정하는 통계는 `real_dev`만으로 낸다.

   도구의 조회 범위는 좁히지 않는다. 비교국 조회 도구 `compare_partners`(비교국의 같은 품목·같은 달 값을 조회하는 도구) 같은 도구는 두 묶음 모두 동결 스냅샷 전체를 읽는다. 자료 접근층에서 `real_sealed` 시계열을 막으면 비교 자료가 빠져 개발 실행이 자료 보류(`HOLD`) 쪽으로 치우친다. 경보·사례를 고르는 방법은 D가 정해 결정 기록에 남긴다.

- 이 제한도 같은 OS 사용자 권한으로는 기술적으로 강제되지 않는다 `[추론]`. §6.4와 같은 한계이며, 지시와 기록으로 관리한다.

### 7.3 `real_sealed` 경보와 채점 표본

1. policy_v1이 승인되면, 격리된 생성 에이전트가 승인된 `policy_v1`로 `real_sealed` 시계열에서 경보를 탐지해 사례 목록을 만든다(로드맵 DT7 중 `real_sealed` 부분). 결과는 봉인 폴더에 직접 기록한다. 봉인 자료 생성에서 부르는 명령(`detect` 등)의 출력은 `outputs/`에 쓰지 않는다. 봉인 폴더에 남기는 파일은 모두 해시 목록에 넣는다. 그 밖의 중간 출력은 저장소와 봉인 폴더 밖 임시 위치에 쓰고, 해시를 등록하기 전에 지운다. 출력 위치를 바꾸는 방법(함수 호출이나 CLI 인자)은 S0 결정 항목으로 둔다 `[미확인]`(`docs/rules/DATA_CONTRACT_V1.md` §10.3 N10).
2. 사례가 40건(표본 상한, 조정값)을 넘으면 고정 난수로 표본을 뽑는다.
   - 표본 seed는 사례 목록을 만들기 전에 정한다. 결과를 본 뒤 고르지 않는다.
   - 표본 seed는 봉인 폴더 안 파일로 두어 해시 목록 대상에 넣는다. 결정 기록에는 정답 대조 채점이 끝난 뒤(§6.2의 원본 커밋 시점)에 옮긴다.
   - 다만 그 파일(nonce 포함)의 sha256은 분할 seed와 함께 `policy_v1` 제안 전에 결정 기록으로 커밋한다. 사례 목록을 계산할 수 있게 되기 전에 표본 seed를 골랐다는 증거다(`docs/rules/DATA_CONTRACT_V1.md` §4.2).
     - 만드는 주체: 분할 직후(`policy_v1` 제안 전) 따로 불러 낸 격리된 생성 에이전트가 봉인 폴더에 한 번만 만들고, 오케스트레이터에게 sha256만 보고한다(`docs/plan/ROADMAP.md` DT4). D 쪽 에이전트는 그 해시만 받아 결정 기록에 커밋하고 seed 값은 보지 않는다(§6.6 3단계와 같은 경로). 해시 값은 봉인 내용이 아니므로 §6.3·§8.4의 기록 제한(파일 수와 해시 대조 결과만)의 예외다.
     - §7.3 1번에서 사례 목록을 만드는 생성 에이전트는 이 파일을 읽어 쓰고 새로 만들지 않는다. 봉인 묶음을 다시 만들 때(§6.7)도 이 파일은 nonce까지 바이트 그대로 둔다. 다시 쓰면 먼저 커밋한 해시와 맞지 않게 된다.
     - 먼저 커밋한 이 값은 해시 등록(§6.6 3단계)과 채점 전 해시 재대조(5단계) 때 `eval/sealed_manifest.json`의 같은 파일 값과 대조한다. 다르면 5단계대로 그 묶음을 무효로 하고 사용자에게 올린다.
   - 시계열 분할 seed와 `real_dev` 시계열 목록은 §7.2대로 기록하고 공개한다. 분할 seed는 기록하기로 한 설계 결정이고, `real_dev` 목록은 개발에 필요하기 때문이다.
3. 사례 목록과 표본은 §6.6의 봉인·해시 등록 단계를 거친다. 해시 등록은 `RB-1` 동결 전에 끝낸다.
4. 동결 뒤 `freeform`과 `full`을 같은 사례 집합에서 실행한다. 참고용 `agent`는 평가 스킬 ②가 예정 실행 목록에 넣지 않고, 동결 뒤 따로 돌리지도 않는다(룰북 B2). 정답 대조 채점은 샌드박스 밖 독립 채점기가 스냅샷 원본 행과 결정적으로 대조해서 한다.

### 7.4 모자라거나 끝나지 않을 때

- `real_dev`를 빌려 쓰지 않는다.
- `real_sealed`에서 모드별(`freeform`, `full` 각각) 유효 보고서(`execution_status=COMPLETED`)가 최소 20건(조정값)이고 봉인 실행이 끝났을 때만, 그 값을 대표 숫자(등급 A)로 내세운다.
- 미달이거나 끝나지 않았으면 대표 주장을 보류한다. 실제 건수·신뢰구간·미완료 사실과 함께 참고치로만 보고한다(`docs/eval/RULEBOOK.md` B3-3).
- `real_dev` 결과는 개선 과정에 노출된 값(등급 D)이며 대표 숫자가 아니다.

- 원격은 비공개 `origin`만 쓴다. 공개 전환, 새 저장소 생성, 저장소 설정 변경은 하지 않는다. 공개 방식은 2026-09-28(월) 오전에 사용자가 정한다.

### 10.2 키 취급

이 소절의 규칙은 따로 적지 않으면 `[DESIGN]`이다.

- 이 소절의 "에이전트"는 두 뜻이다. 사본 위치나 `.env`를 열거나 출력하지 않는 에이전트는 개발 에이전트(오케스트레이터·Claude 보조 에이전트·Codex)다. "에이전트와 그 자식 프로세스"의 에이전트는 샌드박스 안 에이전트(시연의 OpenClaw(NemoClaw의 기본 에이전트 하네스), 채점 대상 실행의 CLI)다.

- 문서·PR·커밋·로그·trace·결정 기록에는 변수 이름만 쓰고 값을 쓰지 않는다.
- 에이전트는 `.env` 내용을 열람·출력·복사하지 않는다. 서브에이전트·Codex·검토자에게도 넘기지 않는다.
- 샌드박스 밖에서 키가 필요한 명령은 실행 프로세스가 환경변수로 읽게 한다. 샌드박스 안에는 환경변수로도 키를 넘기지 않는다.
- 에이전트와 그 자식 프로세스(샌드박스 사용자 권한)가 읽을 수 있는 곳에는 키를 두지 않는다(해석 A, 결정 기록 `20260924-2010-user-decision-key-rule-interpretation.md`). 주입 방식은 X1에서 실제로 성공한 credential placeholder rewrite다. 샌드박스 프로그램에는 자리표시 값만 두고, 샌드박스 안 감독 프로세스(샌드박스 컨테이너 안에서 root로 돌며 정책을 집행하는 OpenShell 프로세스)의 정책 프록시가 게이트웨이에서 받은 자격 증명으로 요청 시점에 실제 키로 바꾼다. 이유는 결정 기록 `20260924-1556-x1-key-injection.md`에 있다.
- 의도적 위반 시험의 키 조회 항목은 키 값을 출력하지 않는다. 키가 있는지 없는지만 기록한다.
- 키가 커밋·PR·로그에 나타나면 작업을 멈추고 오케스트레이터가 사용자에게 올린다. 키 교체는 사용자가 한다.

### 10.3 비밀값·로컬 경로 검사

- PR마다, 그리고 2026-09-27(일) 공개 준비 때 비밀값·로컬 경로 검사(NVIDIA API 키 접두어, 공공데이터포털 서비스키 요청 파라미터, 로컬 절대경로를 찾는 검사. 실제 패턴 문자열은 검사 스크립트에만 두고 문서에는 적지 않는다)를 돌린다. 명령과 종료 코드를 PR에 남긴다.

- 도메인 출력 `outputs/`(실행 폴더 `outputs/{실행명}/`와 봉인 묶음 실행의 `outputs/sealed/{실행명}/`)는 커밋하지 않는다 `[사실: .gitignore]`. 실행명은 `{실행 이름}-{yymmddhhmmss}`다.
